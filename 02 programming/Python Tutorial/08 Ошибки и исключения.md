# 8. Ошибки и исключения

← [[07 Ввод и вывод]] · [[00 Оглавление]] · [[09 Классы]] →

До сих пор сообщения об ошибках лишь упоминались, но если вы пробовали примеры, вы, вероятно, их видели. Существует (как минимум) два различимых вида ошибок: *синтаксические ошибки* и *исключения*.

## 8.1. Синтаксические ошибки

Синтаксические ошибки, также известные как ошибки разбора, пожалуй, самый частый вид жалоб, которые вы получаете, пока изучаете Python:

```python
>>> while True print('Hello world')
  File "<stdin>", line 1
    while True print('Hello world')
               ^^^^^
SyntaxError: invalid syntax
```

Парсер повторяет строку с ошибкой и выводит маленькие стрелки, указывающие на место, где ошибка была обнаружена. Обратите внимание, что это не всегда то место, которое нужно исправить. В примере ошибка обнаружена у функции `print()`, так как непосредственно перед ней пропущено двоеточие (`':'`).

Выводятся имя файла (`<stdin>` в нашем примере) и номер строки, чтобы вы знали, где искать, если ввод пришёл из файла.

## 8.2. Исключения

Даже если инструкция или выражение синтаксически верны, при попытке их выполнить может возникнуть ошибка. Ошибки, обнаруженные во время выполнения, называются *исключениями* и не всегда фатальны: вскоре вы узнаете, как обрабатывать их в программах на Python. Однако большинство исключений программами не обрабатываются и приводят к сообщениям об ошибках, как показано здесь:

```python
>>> 10 * (1/0)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    10 * (1/0)
          ~^~
ZeroDivisionError: division by zero
>>> 4 + spam*3
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    4 + spam*3
        ^^^^
NameError: name 'spam' is not defined
>>> '2' + 2
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    '2' + 2
    ~~~~^~~
TypeError: can only concatenate str (not "int") to str
```

Последняя строка сообщения об ошибке указывает, что произошло. Исключения бывают разных типов, и тип выводится как часть сообщения: типы в примере — `ZeroDivisionError`, `NameError` и `TypeError`. Строка, выводимая как тип исключения, — это имя возникшего встроенного исключения. Это верно для всех встроенных исключений, но не обязательно для пользовательских (хотя это полезное соглашение). Имена стандартных исключений — встроенные идентификаторы (а не зарезервированные ключевые слова).

Остальная часть строки содержит подробности, зависящие от типа исключения и его причины.

Предшествующая часть сообщения об ошибке показывает контекст, в котором произошло исключение, в виде трассировки стека. Как правило, она содержит трассировку стека со строками исходного кода; однако строки, прочитанные со стандартного ввода, она не показывает.

В разделе «Встроенные исключения» перечислены встроенные исключения и их значения.

## 8.3. Обработка исключений

Можно писать программы, которые обрабатывают выбранные исключения. Посмотрите на следующий пример: он запрашивает у пользователя ввод, пока не будет введено допустимое целое число, но позволяет пользователю прервать программу (с помощью Control-C или того, что поддерживает операционная система); обратите внимание, что прерывание пользователем сигнализируется возбуждением исключения `KeyboardInterrupt`.

```python
>>> while True:
...     try:
...         x = int(input("Please enter a number: "))
...         break
...     except ValueError:
...         print("Oops!  That was no valid number.  Try again...")
...
```

Инструкция `try` работает следующим образом.

- Сначала выполняется *блок try* (инструкции между ключевыми словами `try` и `except`).
- Если исключение не возникает, *блок except* пропускается, и выполнение инструкции `try` завершается.
- Если исключение возникает во время выполнения блока `try`, остальная часть блока пропускается. Затем, если его тип совпадает с исключением, названным после ключевого слова `except`, выполняется *блок except*, после чего выполнение продолжается после блока try/except.
- Если возникает исключение, не совпадающее с исключением, названным в *блоке except*, оно передаётся во внешние инструкции `try`; если обработчик не найден, это *необработанное исключение*, и выполнение останавливается с сообщением об ошибке.

У инструкции `try` может быть более одного *блока except*, чтобы задавать обработчики для разных исключений. Будет выполнен не более чем один обработчик. Обработчики обрабатывают только исключения, возникшие в соответствующем *блоке try*, а не в других обработчиках той же инструкции `try`. В *блоке except* можно назвать несколько исключений, например:

```python
... except RuntimeError, TypeError, NameError:
...     pass
```

Класс в блоке `except` совпадает с исключениями, которые являются экземплярами самого класса или одного из его производных классов (но не наоборот — *блок except*, в котором указан производный класс, не совпадает с экземплярами его базовых классов). Например, следующий код выведет B, C, D именно в таком порядке:

```python
class B(Exception):
    pass

class C(B):
    pass

class D(C):
    pass

for cls in [B, C, D]:
    try:
        raise cls()
    except D:
        print("D")
    except C:
        print("C")
    except B:
        print("B")
```

Обратите внимание: если бы *блоки except* стояли в обратном порядке (с `except B` первым), он вывел бы B, B, B — срабатывает первый подходящий *блок except*.

Когда возникает исключение, с ним могут быть связаны значения, также известные как *аргументы* исключения. Наличие и типы аргументов зависят от типа исключения.

В *блоке except* после имени исключения можно указать переменную. Переменная привязывается к экземпляру исключения, у которого обычно есть атрибут `args`, хранящий аргументы. Для удобства встроенные типы исключений определяют `__str__()`, чтобы выводить все аргументы без явного обращения к `.args`.

```python
>>> try:
...     raise Exception('spam', 'eggs')
... except Exception as inst:
...     print(type(inst))    # the exception type
...     print(inst.args)     # arguments stored in .args
...     print(inst)          # __str__ allows args to be printed directly,
...                          # but may be overridden in exception subclasses
...     x, y = inst.args     # unpack args
...     print('x =', x)
...     print('y =', y)
...
<class 'Exception'>
('spam', 'eggs')
('spam', 'eggs')
x = spam
y = eggs
```

Вывод `__str__()` исключения печатается как последняя часть («подробности») сообщения для необработанных исключений.

`BaseException` — общий базовый класс всех исключений. Один из его подклассов, `Exception`, — базовый класс всех нефатальных исключений. Исключения, не являющиеся подклассами `Exception`, обычно не обрабатываются, потому что они служат для указания, что программа должна завершиться. К ним относятся `SystemExit`, возбуждаемое `sys.exit()`, и `KeyboardInterrupt`, возбуждаемое, когда пользователь хочет прервать программу.

`Exception` можно использовать как подстановочный знак, перехватывающий (почти) всё. Однако хорошая практика — быть как можно конкретнее в типах исключений, которые мы собираемся обрабатывать, и позволять любым неожиданным исключениям распространяться дальше.

Самый распространённый шаблон обработки `Exception` — вывести или записать в журнал исключение, а затем возбудить его заново (позволяя вызывающему коду тоже обработать исключение):

```python
import sys

try:
    f = open('myfile.txt')
    s = f.readline()
    i = int(s.strip())
except OSError as err:
    print("OS error:", err)
except ValueError:
    print("Could not convert data to an integer.")
except Exception as err:
    print(f"Unexpected {err=}, {type(err)=}")
    raise
```

У инструкции `try` … `except` есть необязательный *блок else*, который, если присутствует, должен следовать за всеми *блоками except*. Он полезен для кода, который должен выполняться, если *блок try* не возбудил исключения. Например:

```python
for arg in sys.argv[1:]:
    try:
        f = open(arg, 'r')
    except OSError:
        print('cannot open', arg)
    else:
        print(arg, 'has', len(f.readlines()), 'lines')
        f.close()
```

Использование блока `else` лучше, чем добавление дополнительного кода в блок `try`, потому что так случайно не перехватывается исключение, которое не было возбуждено кодом, защищаемым инструкцией `try` … `except`.

Обработчики исключений обрабатывают не только исключения, возникшие непосредственно в *блоке try*, но и те, что возникли внутри функций, вызванных (даже косвенно) в *блоке try*. Например:

```python
>>> def this_fails():
...     x = 1/0
...
>>> try:
...     this_fails()
... except ZeroDivisionError as err:
...     print('Handling run-time error:', err)
...
Handling run-time error: division by zero
```

## 8.4. Возбуждение исключений

Инструкция `raise` позволяет программисту принудительно вызвать указанное исключение. Например:

```python
>>> raise NameError('HiThere')
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    raise NameError('HiThere')
NameError: HiThere
```

Единственный аргумент `raise` указывает возбуждаемое исключение. Это должен быть либо экземпляр исключения, либо класс исключения (класс, производный от `BaseException`, например `Exception` или один из его подклассов). Если передан класс исключения, он будет неявно создан вызовом его конструктора без аргументов:

```python
raise ValueError  # shorthand for 'raise ValueError()'
```

Если нужно определить, было ли возбуждено исключение, но обрабатывать его не предполагается, более простая форма инструкции `raise` позволяет возбудить исключение заново:

```python
>>> try:
...     raise NameError('HiThere')
... except NameError:
...     print('An exception flew by!')
...     raise
...
An exception flew by!
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
    raise NameError('HiThere')
NameError: HiThere
```

## 8.5. Цепочки исключений

Если необработанное исключение возникает внутри секции `except`, к нему будет присоединено обрабатываемое исключение, и оно будет включено в сообщение об ошибке:

```python
>>> try:
...     open("database.sqlite")
... except OSError:
...     raise RuntimeError("unable to handle error")
...
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
    open("database.sqlite")
    ~~~~^^^^^^^^^^^^^^^^^^^
FileNotFoundError: [Errno 2] No such file or directory: 'database.sqlite'

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File "<stdin>", line 4, in <module>
    raise RuntimeError("unable to handle error")
RuntimeError: unable to handle error
```

Чтобы указать, что исключение является прямым следствием другого, в инструкции `raise` можно использовать необязательную конструкцию `from`:

```python
# exc must be exception instance or None.
raise RuntimeError from exc
```

Это может быть полезно при преобразовании исключений. Например:

```python
>>> def func():
...     raise ConnectionError
...
>>> try:
...     func()
... except ConnectionError as exc:
...     raise RuntimeError('Failed to open database') from exc
...
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
    func()
    ~~~~^^
  File "<stdin>", line 2, in func
ConnectionError

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "<stdin>", line 4, in <module>
    raise RuntimeError('Failed to open database') from exc
RuntimeError: Failed to open database
```

Она также позволяет отключить автоматическое построение цепочки исключений с помощью идиомы `from None`:

```python
>>> try:
...     open('database.sqlite')
... except OSError:
...     raise RuntimeError from None
...
Traceback (most recent call last):
  File "<stdin>", line 4, in <module>
    raise RuntimeError from None
RuntimeError
```

Подробнее о механике цепочек — в разделе «Встроенные исключения».

## 8.6. Пользовательские исключения

Программы могут вводить собственные исключения, создавая новый класс исключения (подробнее о классах Python — в главе [[09 Классы]]). Исключения обычно должны быть производными от класса `Exception`, прямо или косвенно.

Можно определять классы исключений, делающие всё, что может любой другой класс, но обычно они остаются простыми, часто предлагая лишь несколько атрибутов, позволяющих обработчикам исключения извлечь информацию об ошибке.

Большинство исключений определяют с именами, оканчивающимися на «Error», по аналогии с именованием стандартных исключений.

Многие стандартные модули определяют собственные исключения для сообщения об ошибках, которые могут возникнуть в определённых ими функциях.

## 8.7. Определение завершающих действий

У инструкции `try` есть ещё один необязательный блок, предназначенный для определения завершающих действий (clean-up), которые должны выполняться при любых обстоятельствах. Например:

```python
>>> try:
...     raise KeyboardInterrupt
... finally:
...     print('Goodbye, world!')
...
Goodbye, world!
Traceback (most recent call last):
  File "<stdin>", line 2, in <module>
    raise KeyboardInterrupt
KeyboardInterrupt
```

Если присутствует блок `finally`, он выполняется как последнее действие перед завершением инструкции `try`. Блок `finally` выполняется независимо от того, породила ли инструкция `try` исключение. Следующие пункты рассматривают более сложные случаи, когда возникает исключение:

- Если исключение возникает во время выполнения блока `try`, оно может быть обработано блоком `except`. Если исключение не обработано блоком `except`, оно возбуждается заново после выполнения блока `finally`.
- Исключение может возникнуть во время выполнения блока `except` или `else`. Опять же, оно возбуждается заново после выполнения блока `finally`.
- Если блок `finally` выполняет инструкцию `break`, `continue` или `return`, исключения не возбуждаются заново. Это может сбивать с толку, поэтому не рекомендуется. Начиная с версии 3.14 компилятор выдаёт для этого `SyntaxWarning` (см. [**PEP 765**](https://peps.python.org/pep-0765/)).
- Если инструкция `try` доходит до инструкции `break`, `continue` или `return`, блок `finally` выполнится непосредственно перед выполнением `break`, `continue` или `return`.
- Если блок `finally` содержит инструкцию `return`, возвращаемым значением будет значение из `return` блока `finally`, а не значение из `return` блока `try`. Это может сбивать с толку, поэтому не рекомендуется. Начиная с версии 3.14 компилятор выдаёт для этого `SyntaxWarning` (см. [**PEP 765**](https://peps.python.org/pep-0765/)).

Например:

```python
>>> def bool_return():
...     try:
...         return True
...     finally:
...         return False
...
>>> bool_return()
False
```

Более сложный пример:

```python
>>> def divide(x, y):
...     try:
...         result = x / y
...     except ZeroDivisionError:
...         print("division by zero!")
...     else:
...         print("result is", result)
...     finally:
...         print("executing finally clause")
...
>>> divide(2, 1)
result is 2.0
executing finally clause
>>> divide(2, 0)
division by zero!
executing finally clause
>>> divide("2", "1")
executing finally clause
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    divide("2", "1")
    ~~~~~~^^^^^^^^^^
  File "<stdin>", line 3, in divide
    result = x / y
             ~~^~~
TypeError: unsupported operand type(s) for /: 'str' and 'str'
```

Как видите, блок `finally` выполняется в любом случае. `TypeError`, возбуждённый делением двух строк, не обрабатывается блоком `except` и потому возбуждается заново после выполнения блока `finally`.

В реальных приложениях блок `finally` полезен для освобождения внешних ресурсов (таких как файлы или сетевые соединения) независимо от того, было ли использование ресурса успешным.

## 8.8. Предопределённые завершающие действия

Некоторые объекты определяют стандартные завершающие действия, которые выполняются, когда объект больше не нужен, независимо от того, успешной или неудачной была использующая его операция. Посмотрите на следующий пример, в котором делается попытка открыть файл и вывести его содержимое на экран.

```python
for line in open("myfile.txt"):
    print(line, end="")
```

Проблема этого кода в том, что он оставляет файл открытым на неопределённое время после завершения выполнения этой части кода. В простых скриптах это не проблема, но может быть проблемой в более крупных приложениях. Инструкция `with` позволяет использовать объекты вроде файлов так, чтобы они всегда оперативно и корректно очищались.

```python
with open("myfile.txt") as f:
    for line in f:
        print(line, end="")
```

После выполнения инструкции файл *f* всегда закрывается, даже если при обработке строк возникла проблема. Объекты, которые, как файлы, предоставляют предопределённые завершающие действия, указывают это в своей документации.

## 8.9. Возбуждение и обработка нескольких несвязанных исключений

Бывают ситуации, когда необходимо сообщить о нескольких возникших исключениях. Это часто бывает во фреймворках параллельного выполнения, когда несколько задач могли завершиться ошибкой параллельно, но есть и другие сценарии, где желательно продолжить выполнение и собрать несколько ошибок вместо возбуждения первого исключения.

Встроенный `ExceptionGroup` оборачивает список экземпляров исключений, чтобы их можно было возбудить вместе. Это само по себе исключение, поэтому его можно перехватить как любое другое.

```python
>>> def f():
...     excs = [OSError('error 1'), SystemError('error 2')]
...     raise ExceptionGroup('there were problems', excs)
...
>>> f()
  + Exception Group Traceback (most recent call last):
  |   File "<stdin>", line 1, in <module>
  |     f()
  |     ~^^
  |   File "<stdin>", line 3, in f
  |     raise ExceptionGroup('there were problems', excs)
  | ExceptionGroup: there were problems (2 sub-exceptions)
  +-+---------------- 1 ----------------
    | OSError: error 1
    +---------------- 2 ----------------
    | SystemError: error 2
    +------------------------------------
>>> try:
...     f()
... except Exception as e:
...     print(f'caught {type(e)}: {e}')
...
caught <class 'ExceptionGroup'>: there were problems (2 sub-exceptions)
>>>
```

Используя `except*` вместо `except`, мы можем выборочно обрабатывать только те исключения группы, которые соответствуют определённому типу. В следующем примере, показывающем вложенную группу исключений, каждая конструкция `except*` извлекает из группы исключения определённого типа, а все остальные пропускает дальше — к другим конструкциям и в итоге к повторному возбуждению.

```python
>>> def f():
...     raise ExceptionGroup(
```

## 8.10. Дополнение исключений заметками

Когда исключение создаётся, чтобы быть возбуждённым, его обычно инициализируют информацией, описывающей возникшую ошибку. Бывают случаи, когда полезно добавить информацию уже после того, как исключение было перехвачено. Для этого у исключений есть метод `add_note(note)`, который принимает строку и добавляет её в список заметок исключения. Стандартное отображение трассировки включает все заметки в порядке их добавления после исключения.

```python
>>> try:

... except Exception as e:
...     e.add_note('Add some information')
...     e.add_note('Add some more information')
...     raise
...

Add some more information
>>>
```
