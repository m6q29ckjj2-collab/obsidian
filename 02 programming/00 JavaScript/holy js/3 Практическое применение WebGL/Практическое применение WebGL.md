
# Практическое применение WebGL (Василика Климова, HolyJS 2016)

## 1. О докладе

Доклад Василики Климовой (frontend-разработчик в компании Artec 3D, производящей 3D-сканеры) — практическое введение в WebGL для фронтенд-разработчиков, которые никогда не писали шейдеры. Основной посыл доклада: **WebGL не такой страшный, как кажется**, и применять его можно далеко не только в играх — для интерактивных карт, конфигураторов, визуализации данных и просто «оживления» обычных сайтов.

## 2. Где на практике применяют WebGL

- **3D-конструкторы**: интерактивные модели анатомии человека (с возможностью рассмотреть отдельные органы), конфигураторы автомобилей и их комплектаций — раньше подобное делали на Flash, сейчас переходит на WebGL, потому что WebGL — «родная» для браузера технология, в отличие от мёртвого Flash.
- **Интерактивные карты и панорамы**: используется, в частности, в Яндекс.Картах для панорам через технику **equirectangular map** — сферическая (или кубическая) проекция из плоских изображений, внутри которой «находится» пользователь.
- **Mapbox GL** — полноценная библиотека для собственных интерактивных карт, построенная поверх WebGL/canvas (разработка украинского программиста).
- **Интерактивная статистика** — например, визуализация военных закупок/импорта-экспорта по странам и годам с фильтрацией и возможностью убирать/добавлять ветви данных.
- **Unity3D** (начиная с Unity 5) добавил экспорт в WebGL как одну из целевых веб-платформ — можно портировать игру для работы прямо в браузере без плагинов.
- **Blend4Web** — российская разработка, встраивающаяся в Blender, позволяющая создавать 3D-сцены с анимацией и экспортировать их для веба; в докладе показан пример, где 95% сцены (сложная анимированная схема производства) сделал 3D-художник в Blender, а фронтенд-разработчик добавил лишь один интерактивный tooltip поверх готовой сцены — иллюстрация разделения труда между 3D-художником и веб-разработчиком.
- Библиотеки готовых **фильтров для canvas** (наподобие Instagram-фильтров) поверх WebGL — проще внедрить, чем писать шейдеры с нуля.

## 3. Что такое WebGL технически

WebGL — это API для элемента **`<canvas>`** (стандартный элемент HTML5). Ключевая особенность: содержимое canvas — это просто **пиксели**, а не DOM-дерево — «потрогать» объекты сцены напрямую нельзя, но сама технология WebGL позволяет находить объект под курсором программно (через рейкастинг), просто это не так привычно, как работа с DOM.

WebGL происходит от **OpenGL ES** — урезанной для встраиваемых систем (embedded systems) версии известной библиотеки OpenGL с большим сообществом C++-разработчиков; для веба в неё добавлены дополнительные математические функции, необходимые для работы с 3D-сценами. Ключевое технологическое преимущество WebGL — **шейдеры исполняются на GPU** (видеокарте), а не на CPU, за счёт чего браузерные игры на WebGL могут приближаться по производительности к десктопным (с оговорками). WebGL поддерживает как 2D-, так и 3D-отрисовку.

## 4. Поддержка браузерами

На момент доклада WebGL поддерживают практически все современные браузеры. Исключения и нюансы:
- **Opera Mini** — сознательно не поддерживает (браузер ориентирован на экономию трафика, эффекты ей не нужны);
- **Internet Explorer** (старые версии) — только через плагин, частично реализующий 3D-сцены;
- проверить поддержку можно на тестовом сайте с вращающимся кубиком; если не работает — возможно, нужно вручную включить флаг поддержки WebGL в настройках браузера (актуально было, например, для некоторых сборок на Linux).

## 5. Сцена в three.js: Scene, Camera, Light, Renderer

Доклад показывает базовые примеры на библиотеке **three.js** (используется вместо написания на «чистом» WebGL из-за readily доступных материалов, текстур, большого сообщества). Ключевые объекты сцены:

- **Scene** — контейнер, в который помещаются все объекты, видимые на сцене.
- **Camera** — определяет, какую часть сцены и откуда мы наблюдаем (позиция и направление взгляда); без камеры, направленной на сцену, ничего не будет видно.
- **Light** — источник освещения (рассеянный, точечный, направленный и т.д.); без света объекты не будут видны корректно.
- **Renderer** — объект, отвечающий за фактическую отрисовку сцены с помощью шейдеров; именно в нём происходит вызов шейдерного кода и от него зависит производительность.

```js
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(75, window.innerWidth / window.innerHeight, 0.1, 1000);
const renderer = new THREE.WebGLRenderer();
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

const light = new THREE.DirectionalLight(0xffffff, 1);
scene.add(light);

const geometry = new THREE.BoxGeometry();
const material = new THREE.MeshBasicMaterial({ color: 0x00ff00 });
const cube = new THREE.Mesh(geometry, material);
scene.add(cube);

function animate() {
  requestAnimationFrame(animate); // не setInterval — браузер сам решает, когда перерисовывать
  cube.rotation.y += 0.01;
  renderer.render(scene, camera);
}
animate();
```

## 6. Шейдеры: вершинный и фрагментный

**Шейдер (shader)** — программа, исполняемая на GPU. Синтаксически GLSL (язык шейдеров) похож на **C** — типизированный язык; в JavaScript шейдер обычно хранится и передаётся как обычная строка, которая компилируется движком WebGL **в реальном времени** (можно редактировать код шейдера прямо в браузере, и он тут же перекомпилируется).

WebGL использует только два типа шейдеров (в полной спецификации OpenGL их больше, но WebGL — урезанная версия):

| Шейдер | Когда вызывается | Что делает |
| --- | --- | --- |
| **Vertex shader** (вершинный) | Один раз для каждой вершины объекта | Принимает на вход массив точек (вершин) объекта, вычисляет итоговые координаты — на выходе полноценная векторная геометрия |
| **Fragment shader** (фрагментный / пиксельный) | Для каждого пикселя при растеризации | Закрашивает пиксели в соответствии с вершинами — переход от векторного представления к пиксельному (**растеризация**) |

Оба шейдера работают только вместе — по отдельности не имеют смысла.

**Типы данных GLSL**: `bool` (true/false), целые числа, числа с плавающей запятой, векторы и матрицы, а также `sampler2D` — специальный тип для хранения ссылки на текстуру.

**Классификаторы (qualifiers) переменных**:
- **attribute** — входные данные для вершинного шейдера (координаты вершин и т.п.);
- **varying** — переменная, которую вершинный шейдер вычисляет и передаёт во фрагментный шейдер (например, для последующей интерполяции цвета);
- **uniform** — значение, одинаковое для всех вершин/пикселей за один вызов рендера (например, матрицы трансформации, текстура).

Есть даже практика использовать шейдеры не для отрисовки, а просто для **параллельных вычислений** тяжёлой бизнес-логики на GPU («GPGPU»-подход в браузере): шейдер ничего не рисует, а просто быстро что-то считает, а результат считывается обратно в JS.

## 7. Минимальный пример: рисуем точку

```html
<script id="vertexShader" type="x-shader/x-vertex">
  void main() {
    gl_PointSize = 10.0;                       // размер точки в пикселях
    gl_Position = vec4(0.0, 0.0, 0.0, 1.0);    // итоговая позиция — нельзя переименовать
  }
</script>
<script id="fragmentShader" type="x-shader/x-fragment">
  void main() {
    // gl_PointCoord — координаты внутри квадратного "пикселя" точки
    float distanceFromCenter = distance(gl_PointCoord, vec2(0.5, 0.5));
    if (distanceFromCenter > 0.5) discard;     // обрезаем всё за пределами круга радиуса 0.5
    gl_FragColor = vec4(1.0, 0.0, 0.0, 1.0);   // закрашиваем оставшийся круг красным
  }
</script>
```

Атрибут `type="x-shader/x-vertex"` в теге `<script>` — не настоящий MIME-тип, а приём, чтобы браузер **не пытался исполнить содержимое как обычный JavaScript** (семантическая разметка: «здесь лежит шейдер», а не рабочий скрипт).

`gl_Position` и `gl_PointSize` — зарезервированные встроенные переменные WebGL, их имена менять нельзя: `gl_Position` должна содержать итоговые вычисленные координаты вершины, иначе шейдер не будет работать корректно.

## 8. Текстурирование

Простейший практический шейдер — наложение текстуры (картинки) на объект вместо однотонной заливки:

```glsl
// Vertex shader — просто передаём UV-координаты дальше
varying vec2 vUv;
void main() {
  vUv = uv; // uv — встроенный атрибут геометрии (координаты текстуры для вершины)
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
}
```

```glsl
// Fragment shader — берём цвет из текстуры по UV-координатам
uniform sampler2D myTexture; // сюда передаётся сама текстура-картинка
varying vec2 vUv;
void main() {
  gl_FragColor = texture2D(myTexture, vUv);
}
```

`modelViewMatrix` и `projectionMatrix` — готовые матрицы модели/вида/проекции, которые в three.js **не нужно считать вручную** — библиотека формирует их сама на основе позиции камеры и объекта (расчёт мировых координат вручную — не самая тривиальная задача, и это одно из практических преимуществ использования готовых библиотек вместо «чистого» WebGL).

## 9. Собственный фильтр: чёрно-белое изображение

Нельзя просто «выбрать пиксели» на canvas и перекрасить только часть модели, поэтому черно-белый фильтр реализуется отдельным фрагментным шейдером, который переопределяет обычную логику текстурирования:

```glsl
uniform sampler2D myTexture;
varying vec2 vUv;

void main() {
  vec4 color = texture2D(myTexture, vUv);
  // среднее арифметическое R, G, B — простейший grayscale
  float gray = (color.r + color.g + color.b) / 3.0;
  gl_FragColor = vec4(gray, gray, gray, color.a);
}
```

Если все три канала (R, G, B) равны — пиксель воспринимается как оттенок серого. Автор показывает отладку этого шейдера прямо в браузере (Firefox Shader Editor): если закомментировать строку с усреднением, возвращается обычная цветная текстура; если поделить сумму каналов не на 3, а на другое число — получаются другие (некорректные) оттенки серого.

## 10. «Мультяшный» (toon) шейдер через пороговые значения

Идея упрощения фотографии до «мультяшной» картинки с меньшим количеством цветов: вместо прямого RGB зачастую удобнее посчитать цвет в другом цветовом пространстве (**HSV**), а затем для каждого канала определить **пороговые значения (thresholds)** — и присваивать пикселю ближайший «разрешённый» цвет из ограниченной палитры в зависимости от того, в какой интервал попадает исходное значение. Это только базовый принцип — конкретный алгоритм toon-шейдера в реальности значительно сложнее и не разбирается подробно.

## 11. Пост-обработка (post-processing)

**Пост-обработка** — это добавление эффекта (шума, размытия, свечения и т.п.) **поверх уже отрисованной сцены**, а не встраивание эффекта в основной материал объекта.

В three.js для этого используется `EffectComposer`:

```js
const composer = new THREE.EffectComposer(renderer);
composer.addPass(new THREE.RenderPass(scene, camera));     // обычный рендер сцены
const shaderPass = new THREE.ShaderPass(customToonShader); // применяем свой эффект поверх
composer.addPass(shaderPass);

function animate() {
  requestAnimationFrame(animate);
  composer.render(); // рендерим НЕ сцену напрямую, а composer
}
```

Ключевое отличие: в цикле рендера вызывается `composer.render()`, а не `renderer.render(scene, camera)` — на экране оказывается сцена, пропущенная через цепочку дополнительных шейдерных эффектов. Пример применения — эффект «тряски» или добавление шума при наведении курсора («пасхалка» для пользователей).

## 12. Система частиц (particle system)

Для сцен с большим количеством однородных мелких объектов (травинки, волосы, огонь, дым) отрисовывать каждый объект по отдельности непрактично по производительности. **Система частиц** — набор однородных точек с общими атрибутами, поведение которых задаётся массово.

В three.js это реализуется через связку геометрии частиц и материала:

```js
const particlesGeometry = new THREE.BufferGeometry();
particlesGeometry.setAttribute('position', new THREE.BufferAttribute(positions, 3));

const particlesMaterial = new THREE.PointsMaterial({ size: 0.05, color: 0xffffff });
const particles = new THREE.Points(particlesGeometry, particlesMaterial);
scene.add(particles);
```

Пример из доклада (игра Quake): «дешёвый» огонь на полигонах (треугольниках) выглядит грубо, тогда как огонь, реализованный на системе частиц (множество мелких точек), выглядит заметно живее. Ещё один эффектный пример — частицы, которые периодически собираются в разные объекты (например, в силуэт лица) в зависимости от положения курсора.

## 13. Отладка шейдеров

- **Firefox Shader Editor** — встроенный инструмент разработчика: достаточно включить нужную опцию в панели инструментов, и можно редактировать код вершинного/фрагментного шейдера прямо в браузере и сразу видеть результат (но показывает только сами шейдеры, не более широкий контекст сцены).
- **three.js inspector** — расширение для Chrome, показывающее объекты конкретно сцены three.js.
- **WebGL Inspector** — упоминается как рекомендуемый инструмент (автор доклада сама им не пользовалась).

## 14. Преимущества и недостатки WebGL

**Преимущества:**
1. **Производительность** — шейдеры выполняются на GPU, а не на CPU.
2. **Отсутствие отдельной компиляции** — шейдеры компилируются в рантайме прямо в браузере; управление памятью для обычных JS-переменных берёт на себя сборщик мусора движка JavaScript.
3. **Кроссплатформенность** — нужен только браузер (с оговоркой: очень старые видеокарты могут не поддерживать нужную версию OpenGL ES, лежащую в основе WebGL).
4. **Открытый и бесплатный стандарт**.

**Недостатки:**
1. Возможны **подвисания/лаги**, особенно на встроенных видеокартах (пример — Intel) при сценах с большим числом вершин/полигонов — требуется ручная оптимизация, вплоть до отказа от высокоуровневого фреймворка и работы с «чистым» WebGL для максимальной производительности.
2. WebGL работает с **растровой графикой** (пикселями), а не векторной — это не «минус» как таковой, но особенность, которую нужно учитывать при выборе технологии под задачу.
3. Ограничения конкретной реализации — например, старые версии WebGL официально поддерживают ограниченное число одновременно используемых текстур (порядка 8), что становится узким местом для сложных сцен.
4. Существенно более слабая производительность на мобильных устройствах/планшетах по сравнению с десктопом — сложные сцены могут не прогружаться, зависать на первых кадрах или показывать белый экран, особенно на нетоповых устройствах.

## 15. Заключение и Q&A

**Главный посыл доклада**: WebGL можно применять далеко не только для игр — фильтрация изображений и видео, интерактивная графика и статистика, конфигураторы, карты, а также просто «оживление» обычных (в том числе корпоративных) сайтов небольшими интерактивными элементами для вовлечения пользователей.

**Из ответов на вопросы:**
- На момент доклада **WebGL 2** уже в активной разработке, но пока не поддерживается всеми браузерами — ориентироваться стоит на актуальную спецификацию WebGL 1 (основанную на определённой версии OpenGL ES).
- На вопрос о выборе между **three.js** и альтернативами (Babylon.js и др.): автор выбрала three.js, так как многие альтернативные библиотеки на тот момент прямо позиционировались как игровые движки, тогда как в задачах компании нужен был более детальный контроль над конкретными объектами сцены, а не полноценный игровой движок.
- Атрибут `type="x-shader/x-vertex"` у `<script>`-тега с шейдером — не служебный MIME-тип браузера, а способ пометить содержимое семантически как «это шейдер», чтобы браузер не пытался исполнить его как JavaScript.
- Готовые шейдеры и алгоритмы фильтров можно находить в открытом доступе (в том числе портируя код из шейдеров, написанных для других диалектов GLSL) — важно учитывать, что WebGL использует урезанную версию языка шейдеров, поэтому не любой сторонний шейдер заработает без адаптации.
- Пока не существует способа применить пост-обработку WebGL (в духе `EffectComposer`) к рендерингу обычной HTML/CSS-страницы «как есть» — пост-обработка ограничена содержимым самого WebGL-канваса.
- Синхронизация WebGL-сцены с CSS-анимациями других элементов страницы не автоматическая: если логика на чистом JavaScript, разработчик сам должен в нужный момент (например, по событию из рендер-цикла) добавлять/убирать классы у DOM-элементов вне canvas — единой «экосистемы» между WebGL-сценой и остальной страницей нет.
- Практические советы по производительности: если в сцене сейчас ничего не меняется (не идёт вращение/анимация), можно **не вызывать `requestAnimationFrame` заново**, приостанавливая цикл рендера до следующего пользовательского взаимодействия; большие 3D-модели (в компании — данные с 3D-сканера) для надёжности разбиваются на части вместо загрузки одним большим бинарным файлом целиком.
- Упомянута сторонняя библиотека **html2webgl** (автор — Денис Родин) для рендеринга HTML-контента средствами WebGL, с отдельными докладами автора на других конференциях.
