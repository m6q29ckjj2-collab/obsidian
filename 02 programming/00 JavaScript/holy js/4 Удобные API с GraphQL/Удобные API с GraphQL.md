
# Удобные API с GraphQL (Михаил Новиков, HolyJS 2016)

## 1. О докладе

Доклад Михаила Новикова (компания Reindex, специализирующаяся на GraphQL-инфраструктуре) — введение в GraphQL с точки зрения проблемы «удобного API» между клиентом (веб/мобильным) и сервером. Facebook публично выпустил спецификацию GraphQL и референсную реализацию на JavaScript примерно за год до доклада, но использовал технологию внутри (на Hack/PHP) уже около 4 лет — именно поэтому у GraphQL к моменту доклада уже накоплен реальный продакшен-опыт, а не только хайп вокруг новой спецификации.

## 2. Что такое «удобный API» — три требования

Автор формулирует три ключевых свойства, которым должен отвечать API между клиентом и сервером:

1. **Эффективность** — минимум запросов и минимум лишних данных. Особенно критично для мобильных приложений с нестабильным интернетом: клиент должен получать ровно те данные, которые нужны для отрисовки конкретного экрана, а не «усреднённый» набор полей на все случаи жизни.
2. **Стабильность (не нужно менять API ради каждого изменения на фронтенде)** — это особенно важно для мобильных приложений, версии которых нельзя контролировать: сервер может годами обслуживать одновременно десятки разных версий клиента. Классический REST-эндпоинт, заточенный под одну конкретную вьюшку, при появлении второй похожей вьюшки вынуждает либо компромиссно расширять этот эндпоинт под обе, либо плодить дублирующиеся эндпоинты.
3. **Удобные инструменты** — интерактивная работа с API при разработке (автодополнение, валидация запроса на лету), а не «магическая строка», для которой нет проверяемой формальной схемы. Проблема классического REST в том, что формальные системы описания (Swagger, JSON API и т.п.) существуют, но не являются обязательной практикой — универсального инструмента, работающего с *любым* REST API, в итоге не существует.

## 3. GraphQL: язык запросов + язык описания схемы

GraphQL состоит из двух связанных частей:

**(а) Язык запросов** — клиент явно описывает граф нужных данных, включая вложенные поля и аргументы:

```graphql
{
  picture(id: "123") {
    url(size: LARGE)
    author {
      name
      avatar(size: SMALL)
    }
    comments {
      text
      author { name }
    }
  }
}
```

Запрос точно описывает форму ответа: нужную картинку, её автора с полем `avatar` конкретного размера, вложенные комментарии со своими авторами — всё **одним запросом**, без over-fetching и без нескольких round-trip'ов.

**(б) Язык описания схемы (типизированный граф типов)** — формальное описание того, какие данные и с какими аргументами доступны на сервере. По этой схеме каждый входящий запрос **проверяется** ещё до выполнения: клиент физически не может запросить несуществующее поле. Пример упрощённой схемы для Instagram-подобного приложения:

```graphql
type Picture {
  id: ID!
  url(size: PictureSize): String
  author: User!
  comments: [Comment!]!
}

type User {
  id: ID!
  name: String!
  avatar(size: AvatarSize): String
}

type Comment {
  id: ID!
  text: String!
  author: User!
}
```

Схема сама по себе является **машиночитаемыми метаданными** — любой GraphQL-сервер способен отдать описание своей схемы программно (интроспекция), что и делает возможными универсальные инструменты (в отличие от мира REST, где единого формата метаданных не сложилось).

## 4. Почему GraphQL решает три исходные проблемы

- **Эффективность**: за один запрос можно вложенно получить всё необходимое для отрисовки конкретного экрана — не нужно несколько запросов, не нужно тащить лишние поля.
- **Стабильность / обратная совместимость**:
  - если нужно добавить новую фичу («лайки» к посту) — достаточно добавить поле в схему на сервере и начать запрашивать его на клиенте; старые клиенты, не запрашивающие это поле, не заметят изменения;
  - если нужно **убрать** поле — это безопасно делать только тогда, когда сервер видит (по логам реальных запросов), что ни один клиент больше это поле не запрашивает; пока поле не убрано явно, старые клиенты продолжают работать — GraphQL-сервер по построению обратно совместим до тех пор, пока поля не удаляются вручную.
- **Инструменты**: интерактивная консоль **GraphiQL** — разделённый интерфейс, где слева пишется запрос с автодополнением по реальной схеме сервера, ошибки подсвечиваются прямо в запросе, а справа сразу же виден результат выполнения.

## 5. Резолверы: реализация схемы на сервере

Референсная серверная реализация — библиотека **graphql-js** от Facebook (есть реализации и на других языках — Java, Scala, Python и т.д., так как GraphQL — открытая спецификация, а не привязанная к конкретному стеку технология). Каждому полю схемы можно назначить **resolve-функцию**, которая знает, откуда фактически взять данные:

```js
const PictureType = new GraphQLObjectType({
  name: 'Picture',
  fields: () => ({
    id: { type: GraphQLID },
    url: {
      type: GraphQLString,
      args: { size: { type: PictureSizeEnum } },
      resolve: (picture, { size }) => getImageUrl(picture, size),
    },
    author: {
      type: UserType,
      resolve: (picture) => db.users.findById(picture.authorId), // возвращает Promise
    },
    comments: {
      type: new GraphQLList(CommentType),
      resolve: (picture) => db.comments.findByPictureId(picture.id),
    },
  }),
});
```

Ключевая гибкость: resolve-функция для каждого поля может обращаться к **любому источнику данных** — базе данных, стороннему API, устаревшему legacy REST API — и всё это будет выглядеть для клиента абсолютно одинаково, как единый согласованный граф. Это делает GraphQL удобным инструментом для построения **тонкой прослойки (API Gateway)** поверх уже существующих разнородных бэкендов, включая legacy REST-сервисы или несколько микросервисов сразу, без необходимости переписывать саму бизнес-логику.

## 6. Проблема N+1 и её решение через батчинг и кэш запроса

Естественная реализация резолверов «в лоб» (например: получить список комментариев к картинке, а затем для каждого комментария отдельным запросом получить его автора) порождает классическую **проблему N+1**: 10 комментариев → 10 дополнительных запросов к базе данных вместо одного.

Решение, используемое в Facebook (и аналогичных реализациях): **батчинг** — если в рамках одного GraphQL-запроса возникает много обращений одного типа (например, «получить пользователя по ID»), они объединяются в один batched-запрос к источнику данных и выполняются одновременно, а затем результат раздаётся обратно каждому резолверу. Дополнительно применяется **кэш на время одного GraphQL-запроса**: если один и тот же автор запрашивается несколько раз внутри одного запроса (например, автор картинки и автор одного из комментариев к ней совпадают), данные о нём будут запрошены у источника данных только один раз.

## 7. Relay — клиентская библиотека с автоматическим кэшем

**Relay** — клиентская библиотека для React от Facebook, изначально представленная вместе с GraphQL. Как и Redux, она поддерживает центральное клиентское хранилище данных, но, в отличие от Redux, **не требует вручную писать экшены** для помещения данных в хранилище — потому что Relay заранее знает схему и типы данных из самого GraphQL-запроса и умеет сам сопоставлять пришедшие данные с нужным местом в хранилище (нормализация по типу и `id`).

Ключевая идея Relay — **компонент декларирует свои данные через фрагмент GraphQL-запроса**, привязанный прямо к компоненту:

```js
const Comment = createFragmentContainer(CommentComponent, {
  comment: graphql`
    fragment Comment_comment on Comment {
      text
      author { name avatar(size: SMALL) }
    }
  `,
});
```

Фрагменты дочерних компонентов **вкладываются** в фрагменты родительских:

```js
const PictureView = createFragmentContainer(PictureViewComponent, {
  picture: graphql`
    fragment PictureView_picture on Picture {
      url(size: LARGE)
      comments { ...Comment_comment }
    }
  `,
});
```

На первый взгляд это выглядит как «жёсткая связка» компонента и данных, но на практике это делает компоненты **более переиспользуемыми**: компонент можно перенести в любое другое место дерева React-приложения, не заботясь о том, откуда возьмутся нужные данные — Relay сам «подтягивает» их по дереву запроса. Библиотека также гарантирует, что компонент физически не сможет получить доступ к полю, которое не было явно запрошено в его собственном фрагменте.

**Пагинация в Relay**: используется паттерн курсоров — сервер возвращает первые N элементов вместе с непрозрачным для клиента курсором, который затем передаётся обратно, чтобы получить следующую страницу; Relay умеет работать с этим паттерном напрямую, включая обновление уже загруженных, но невидимых сейчас страниц при последующих изменениях данных.

**Мутации в Relay** — единственный способ изменять данные на клиенте напрямую через стор; они декларативны и по умолчанию **оптимистичны с откатом**: изменение сразу же применяется на клиенте без ожидания ответа сервера, а при отказе сервера откатывается автоматически. На момент доклада написание мутаций в Relay требовало большого количества ручной конфигурации (в частности, объяснения библиотеке, куда именно в список нужно вставить новый элемент); автор упоминает, что команда Relay в этот момент уже работала над упрощённым API для мутаций.

## 8. Альтернативные клиенты и связанные сервисы

- **Apollo Client** (от Meteor) — альтернатива Relay, построенная поверх Redux; проще и менее «навороченная», чем Relay, но реализует многие из тех же идей (нормализованный кэш по GraphQL-схеме).
- **Reindex** (сервис, в котором работает автор доклада) — «Backend as a Service» (по аналогии с Firebase/Parse), но в отличие от них отдаёт не заранее фиксированный формат API, а полноценный GraphQL API, сгенерированный из декларативно описанной пользователем схемы — без необходимости самостоятельно писать backend-код; включает встроенную авторизацию, права доступа, аналитику.
- Технология развивается быстро: на момент доклада на конференции React Europe GraphQL/Relay были темой значительной части докладов и половины вопросов на общей Q&A-сессии.

## 9. Ограничения и открытые проблемы GraphQL

- **SQL-базы данных** — GraphQL плохо подходит для эффективной трансляции произвольного вложенного графа запроса в один оптимальный SQL-запрос: данные могут требовать разной сортировки на разных уровнях вложенности, и единого решения для автогенерации эффективного SQL пока не существует. На практике GraphQL чаще комбинируют с NoSQL-хранилищами (MongoDB) или используют MySQL просто как key-value store (подход Facebook), а не полагаются на реляционные join'ы напрямую через GraphQL-слой.
- **Малое количество проверенных паттернов**: спецификации на тот момент около года, и большая часть практического опыта — это внутренний опыт Facebook, поэтому не все архитектурные вопросы уже имеют устоявшееся «правильное» решение.
- **Полностью реактивные интерфейсы и данные без единого источника правды** — GraphQL плохо подходит, если данные могут находиться в «промежуточном», не до конца синхронизированном состоянии (например, peer-to-peer чат, где неизвестно, реплицировались ли данные на сервер) — GraphQL по своей модели предполагает, что полученные от сервера данные — это единственная «правда».
- **Ограничение сложности запроса** — поскольку клиент сам решает, насколько глубоко «вложить» запрос (пример: пользователь → его друзья → их друзья → ...), сложность запроса может расти экспоненциально и создавать нагрузку на сервер. На момент доклада в базовой спецификации нет встроенного универсального механизма защиты; отдельные реализации (например, на Scala) уже добавляли статический анализ сложности запроса (глубина вложенности) до его выполнения, чтобы можно было отклонять аномально тяжёлые запросы или ограничивать максимальную вложенность через дизайн самой схемы.
- **Обработка ошибок** — на момент доклада ошибки внутри одного запроса возвращаются единым списком `errors` без точной привязки к конкретному полю графа (хотя данные, не затронутые ошибкой, всё равно могут вернуться частично); по словам автора, в разработке была более точная локализация ошибок относительно конкретного места в дереве запроса. Также ограничение: одна reject-причина Promise в резолвере не позволяет вернуть сразу несколько разных ошибок из одного поля.

## 10. Будущее развитие GraphQL (на момент доклада)

Два ключевых готовящихся направления (озвучены на конференции React Europe незадолго до доклада):

1. **Частичные (потоковые) запросы**: возможность пометить часть полей как менее приоритетные (директива вроде `@defer`) — сервер сначала присылает данные, которые точно нужны для немедленной отрисовки интерфейса, а второстепенные (например, список комментариев) присылает позже, отдельными частями потокового ответа (`@stream`), не блокируя начальную отрисовку.
2. **Подписки (subscriptions)** — механизм получения реактивных обновлений данных (например, автообновление лайков/комментариев к посту): клиент подписывается на конкретное событие, и к этому событию привязывается свой GraphQL-запрос, поэтому каждый подписчик получает только те данные, которые ему действительно нужны — в отличие от типичной проблемы подписок, где приходится выбирать между «слишком много данных» и «слишком мало, нужно догружать отдельно».

## 11. Сравнение с альтернативами (из Q&A)

- **Falcor** (Netflix) — в отличие от GraphQL, не имеет формальной типизированной схемы, это скорее просто язык запросов, способный работать с произвольным API (необязательно GraphQL-совместимым); это преимущественно клиентская библиотека, решающая ту же задачу, что и Relay (эффективно собрать нужные данные с сервера), но заметно проще и без валидации запросов по схеме.
- **Om Next** (ClojureScript) — тоже сравнивается скорее с Relay, чем с GraphQL как таковым: клиентская библиотека для управления кэшем данных, а не альтернативная серверная спецификация.

## 12. Прочие практические детали из Q&A

- **Права доступа**: проверка прав делается непосредственно внутри resolve-функции конкретного поля; типичный паттерн при отсутствии прав — вернуть `null` для этого поля (а не HTTP-код ошибки, как в REST), и клиент должен уметь интерпретировать `null` как «либо данных нет, либо нет прав на просмотр».
- **Мутации** реализуются как обычные поля специального корневого типа: клиент вызывает «ресурс-мутацию» и сразу же в том же запросе описывает, какие данные хочет получить в ответ после изменения (например, после мутации редактирования комментария — сразу запросить обновлённый текст этого комментария).
- **Обфускация идентификаторов**: такие компании, как Facebook и Reindex, кодируют глобальные ID объектов (сочетание типа и внутреннего ID) в непрозрачную для клиента строку (например, через base64), чтобы клиент не мог полагаться на внутреннюю структуру ID — это даёт свободу сменить формат хранения (например, базу данных) в будущем, не ломая контракт с клиентом.
- **Устаревание полей**: в схеме поле можно пометить как **deprecated**; практический эффект — Facebook сообщает, что это в первую очередь скрывает поле из автодополнения инструментов, из-за чего разработчики органически перестают его использовать, что облегчает последующее безопасное удаление поля.
- **Возможность встраивания GraphQL прямо в браузер** (клиентский GraphQL-сервер, резолверы которого сами ходят в REST API) — технически возможна и упоминается пример (в основном заброшенного) клиента, пытавшегося реализовать отдельную клиентскую схему для локальных данных, которых нет на сервере (актуально в первую очередь для расширения Relay-кэша собственными клиентскими полями).

## 13. Границы применимости GraphQL (итоговый вывод)

Автор явно очерчивает случаи, где GraphQL **не стоит использовать**:
1. Полностью реактивные интерфейсы (на момент доклада поддержка подписок ещё не была полноценно готова к продакшн-использованию за пределами Facebook).
2. Системы без единого источника достоверных данных (например, наполовину peer-to-peer синхронизируемые чаты) — GraphQL закладывается на то, что ответ сервера и есть «истина», и плохо описывает промежуточные/неопределённые состояния синхронизации.
