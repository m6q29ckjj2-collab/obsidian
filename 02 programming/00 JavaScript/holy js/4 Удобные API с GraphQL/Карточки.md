Какие три ключевых требования к "удобному API" между клиентом и сервером формулирует автор доклада?::Эффективность (минимум запросов и лишних данных), стабильность (не нужно менять API при каждом изменении клиента, чтобы не ломать старые версии приложений) и наличие удобных инструментов (интерактивная работа с API, автодополнение, валидация запроса).

Почему стабильность API особенно критична именно для мобильных приложений, а не для веб-приложений?::Разработчик не может контролировать, когда пользователь обновит мобильное приложение — на сервере может годами одновременно работать множество разных версий клиента (например, до 50 версий), тогда как веб-фронтенд можно обновить централизованно вместе с сервером.

В чём заключается типичная проблема классического REST-эндпоинта, заточенного под одну конкретную вьюшку, при появлении второй похожей вьюшки?::Приходится либо компромиссно расширять существующий эндпоинт так, чтобы он подходил под обе вьюшки (теряя эффективность для каждой из них по отдельности), либо создавать второй дублирующий эндпоинт — оба варианта требуют лишней работы.

Почему, по мнению автора, инструменты вроде Swagger или JSON API не решают проблему единых инструментов для REST API в целом?::Формальное описание метаданных API не является обязательной практикой, и на деле почти никто не пишет полностью формальный REST API с корректными метаданными, из-за чего невозможно создать универсальный инструмент (валидатор, автодополнение), который бы работал сразу с любым REST API.

Из каких двух связанных частей состоит GraphQL?::Из языка запросов, которым клиент описывает граф нужных данных (включая вложенные поля и аргументы), и языка описания схемы — формальной типизированной системы, описывающей, какие данные и с какими аргументами доступны на сервере.

Зачем нужна типизированная схема на сервере GraphQL, помимо документирования доступных данных?::Каждый входящий запрос проверяется по схеме ещё до выполнения, поэтому клиент физически не может запросить несуществующее поле; кроме того, схема может быть отдана программно (интроспекция), что делает возможными универсальные инструменты вроде автодополнения и валидаторов.

Каким образом GraphQL обеспечивает обратную совместимость при добавлении новой фичи (например, поля "лайки")?::Достаточно добавить новое поле в схему на сервере — старые клиенты, которые его не запрашивают, продолжают работать как прежде; клиенту, которому нужна новая фича, достаточно начать запрашивать это поле на своей стороне, не требуя изменений в самом API для всех остальных.

При каком условии в GraphQL безопасно удалять поле из схемы, не ломая существующих клиентов?::Только когда по логам реальных запросов видно, что ни один клиент больше не запрашивает это поле — до этого момента поле остаётся доступным, и API остаётся обратно совместимым автоматически, поскольку его никто явно не убирал.

Что такое resolve-функция (резолвер) в реализации GraphQL-сервера, и в чём её ключевая гибкость?::Функция, назначенная конкретному полю схемы, которая знает, откуда фактически взять данные для этого поля; резолверы разных полей могут обращаться к разным источникам данных (база данных, стороннее API, legacy REST-сервис), и с точки зрения клиента всё это выглядит как единый согласованный граф данных.

Почему GraphQL хорошо подходит для роли "тонкой прослойки" (API Gateway) поверх нескольких legacy REST-сервисов или микросервисов?::Резолверы полей могут просто проксировать вызовы к существующим REST-эндпоинтам или микросервисам, не требуя переписывания самой бизнес-логики — вся она остаётся на бэкенде, а GraphQL-слой лишь объединяет разнородные источники в единый согласованный запрашиваемый граф.

В чём заключается проблема N+1 в контексте GraphQL, и на конкретном примере из доклада поясни, как она возникает.::Если резолвер для получения списка (например, комментариев к картинке) реализован "в лоб", а затем для каждого элемента списка отдельно вызывается резолвер получения связанных данных (автора комментария), то при 10 комментариях возникает 10 дополнительных отдельных запросов к источнику данных вместо одного batched-запроса.

Какие два приёма используются в продакшене (например, в Facebook) для решения проблемы N+1 в GraphQL?::Батчинг — объединение множества запросов одного типа, возникших в рамках одного GraphQL-запроса, в один пакетный запрос к источнику данных; и кэш на время одного GraphQL-запроса — если один и тот же объект (например, автор) запрашивается несколько раз внутри одного запроса, данные о нём запрашиваются у источника только один раз.

Чем принципиально отличается работа Relay с клиентским хранилищем данных от паттерна Redux?::В отличие от Redux, где экшены для помещения данных в хранилище нужно писать вручную, Relay заранее знает схему и типы данных из самого GraphQL-запроса и умеет автоматически нормализовать и разместить пришедшие данные по типу и id без ручного написания экшенов.

Как компонент в Relay декларирует, какие данные ему нужны, и почему это делает компоненты более переиспользуемыми, а не более жёстко связанными?::Компонент привязывает к себе фрагмент GraphQL-запроса, описывающий нужные ему данные; благодаря этому компонент можно перенести в любое другое место дерева React-приложения без ручной настройки источника данных — Relay сам подтягивает нужные данные по дереву вложенных фрагментов, опираясь на схему.

Что произойдёт в Relay, если компонент попытается использовать поле данных, которое не было явно запрошено в его собственном GraphQL-фрагменте?::Relay не даст компоненту получить доступ к этому полю, поскольку гарантирует, что компонент имеет доступ только к тем данным, которые он сам явно запросил в своём фрагменте — это защищает от случайного использования незапрошенных данных.

Опиши, как устроена пагинация через курсоры в Relay.::Сервер возвращает первые N элементов вместе с непрозрачным для клиента курсором, указывающим на позицию последнего элемента; чтобы получить следующую страницу, клиент передаёт этот курсор обратно, и Relay умеет автоматически работать с этим паттерном, включая обновление данных на страницах, которые сейчас не отображаются.

Что означает "оптимистичность с откатом" применительно к мутациям в Relay?::Изменение данных сразу же применяется на клиенте без ожидания ответа сервера (для мгновенного отклика интерфейса), а если сервер впоследствии отклоняет мутацию, изменение автоматически откатывается на клиенте.

Чем отличается клиентская библиотека Apollo Client от Relay по архитектуре и сложности?::Apollo Client полностью основан на Redux и считается более простым и менее "навороченным" клиентом по сравнению с Relay, при этом реализуя многие сходные идеи (кэш, работающий по GraphQL-схеме), что делает его удобным выбором для тех, кто уже использует Redux и предпочитает более лёгкое решение.

Почему GraphQL плохо подходит для эффективной работы с реляционными SQL-базами данных, по словам автора?::Не существует общего решения, которое надёжно транслирует произвольный вложенный граф GraphQL-запроса в один эффективный SQL-запрос, поскольку данные на разных уровнях вложенности могут требовать разной сортировки и не всегда соединяются в единый SQL-запрос; на практике GraphQL чаще комбинируют с NoSQL-хранилищами или используют SQL-базу как key-value store.

В каких двух случаях, по прямому заявлению автора, не стоит использовать GraphQL?::Когда нужен полностью реактивный интерфейс (на момент доклада поддержка подписок ещё не была готова к полноценному продакшену за пределами Facebook), и когда данные не имеют единого источника достоверности — например, наполовину peer-to-peer синхронизируемый чат, где GraphQL плохо описывает промежуточные, не до конца синхронизированные состояния.

Каким образом в GraphQL-запросе можно ограничить потенциально экспоненциально растущую сложность вложенных запросов (например, "друзья друзей")?::Спецификация на момент доклада не имела встроенного универсального механизма; отдельные реализации (например, на Scala) добавляли статический анализ сложности запроса (глубину вложенности) ещё до его выполнения, что позволяет отклонять или ограничивать аномально тяжёлые запросы, либо изначально проектировать схему так, чтобы запредельно сложные запросы были невозможны.

Как в GraphQL-схемах компаний вроде Facebook и Reindex обычно кодируются глобальные идентификаторы объектов, и зачем?::ID кодируются (например, через base64) в непрозрачную для клиента строку, комбинирующую тип объекта и внутренний идентификатор; это гарантирует, что клиент не сможет полагаться на внутреннюю структуру ID, и позволяет в будущем сменить формат хранения данных (например, базу данных), не ломая контракт с клиентом.

В чём разница между Falcor (Netflix) и GraphQL с точки зрения наличия типизированной схемы и области применения?::Falcor не имеет формальной типизированной схемы и является скорее просто языком запросов, способным работать с произвольным API (не обязательно GraphQL-совместимым); Falcor сравнивают не столько с самим GraphQL, сколько с клиентскими библиотеками вроде Relay, поскольку решает похожую задачу эффективного сбора данных с сервера, но без валидации по схеме.

Что означают два готовящихся направления развития GraphQL, упомянутые в докладе — частичные (потоковые) запросы и подписки?::Частичные запросы (директивы вроде @defer/@stream) позволяют пометить часть полей как менее приоритетные, чтобы сервер сначала присылал данные для немедленной отрисовки, а второстепенные данные — позже отдельными частями; подписки дают возможность подписаться на конкретное событие с привязанным к нему GraphQL-запросом, получая реактивные обновления только по нужным данным, а не весь объект целиком.
