
# Производительность JavaScript через подзорную трубу (Вячеслав Егоров, HolyJS 2016)

## 1. О докладе

Доклад Вячеслава Егорова (в прошлом — разработчик виртуальной машины V8) посвящён не столько конкретным приёмам оптимизации, сколько тому, почему **микробенчмарки JavaScript систематически врут**. На серии реальных примеров с Хабра и Stack Overflow автор показывает, как JIT-компилятор (V8, SpiderMonkey и другие) незаметно «съедает» код бенчмарка целиком или частично, из-за чего измеряется не то, что задумывал автор бенчмарка.

## 2. Ловушка №1: «выделение массива — дорогая операция»

Классический пример с Хабра: автор написал функцию `find`, которая в цикле создаёт литерал массива внутри себя, и получил ~5000 вызовов/мс. Вынеся создание массива за пределы функции, он получил прирост и сделал вывод: **выделение массива внутри функции — дорогая операция**.

На самом деле профилирование (`perf` на Linux) показало, что дело не в массиве, а в том, что в старых версиях V8 не было быстрого пути (`FastCloneShallowArray`) для литералов массивов, создаваемых внутри функции — сам литерал создавался медленно. Позже V8 это починили. Вывод из примера: **правильное объяснение результата бенчмарка часто требует профилирования движка, а не рассуждений «на глаз»**.

```js
// Медленный вариант (в старом V8): литерал массива создаётся внутри функции
function find(arr, needle) {
  const indices = []; // литерал создаётся заново на каждый вызов find
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === needle) indices.push(i);
  }
  return indices;
}

// "Быстрый" вариант: литерал вынесен наружу
const indices = [];
function findFast(arr, needle) {
  indices.length = 0;
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === needle) indices.push(i);
  }
  return indices;
}
// Разница была не в "цене выделения массива", а в отсутствии
// быстрого пути клонирования литерала внутри функции в старом V8.
```

## 3. Ловушка №2: инлайнинг руками (ChaCha20) и трюк с `assert`

Пример со Stack Overflow: реализация блочного шифра ChaCha20. Функция «четверть-раунда» вызывалась в цикле — 20 Мб/с. Когда автор вручную заинлайнил тело функции в цикл («заилайнил руками»), производительность **упала в 10 раз**, хотя ожидался обратный эффект («JIT должен же инлайнить лучше»).

Разгадка — банальная: если добавить в код `assert`-подобную директиву (в духе «не удаляйте эту строчку — это подсказка компилятору»), всё «внезапно разгонялось». Это иллюстрирует, что **в бенчмарках после какого-то момента корень проблемы — это то, что JIT посчитал часть кода мёртвым и выкинул**, а не эффективность инлайнинга самого по себе.

```js
// Вызов через функцию — результат каждой итерации используется дальше
function quarterRound(state, a, b, c, d) { /* ... */ }
function encryptViaCall(state) {
  for (let i = 0; i < ROUNDS; i++) quarterRound(state, 0, 4, 8, 12);
}

// Тело вручную заинлайнено прямо в цикл
function encryptInlined(state) {
  for (let i = 0; i < ROUNDS; i++) {
    // ...тело quarterRound скопировано сюда буквально...
  }
  // Если результат работы цикла (state) нигде дальше не используется,
  // JIT вправе счесть весь цикл мёртвым кодом и выкинуть его целиком.
  assert(state[0] !== 0); // "подсказка" компилятору: state используется, не удаляй
}
```

## 4. jsPerf «умер», а Benchmark.js заворачивает код в цикл

Раньше «производительность» в вебе означало jsPerf. Но jsPerf как сервис умер, хотя движок под ним — библиотека **Benchmark.js** — жив и используется много где. Суть её работы: она берёт ваш код и **заворачивает его в дополнительный цикл**, чтобы повторить операцию много-много раз и получить стабильную оценку времени одной операции.

Пример-ловушка: сравнение способов посчитать число вхождений буквы «е» в строке — через `split('')` и подсчёт длины массива против ручного цикла со `slice`. Способ со `slice` в Firefox «летал». Причина: при повторении операции внутри бенчмарка вторая и последующие итерации получают уже **пустую строку** (предыдущая итерация «съела» всю строку через `slice` в никуда), поэтому измеряется стоимость операции над пустой строкой, а не над исходной.

```js
// Ловушка: str "живёт" между итерациями бенчмарка
let str = "съешь ещё этих мягких французских булок";
let count = 0;

// Каждая итерация бенчмарка выполняет ЭТОТ код заново,
// но str не переинициализируется между итерациями!
while (str.length > 0) {
  if (str[0] === 'е') count++;
  str = str.slice(1); // на второй итерации бенчмарка str уже пуст
}
// В результате замеряется цикл "while (''.length > 0)" — то есть 0 итераций.
```

## 5. Математика микробенчмарка: почему деление на N — это ловушка

Базовая идея микробенчмарка: измерить суммарное время `T` выполнения операции `N` раз и посчитать `T/N` как стоимость одной операции `C`. Это работает, только если операция стоит **одну и ту же величину `C` при каждом повторении**.

Проблема в том, что при наличии JIT это почти никогда не так:
- существует минимум **две версии** операции — неоптимизированная (исполняется первые несколько раз) и оптимизированная (после «прогрева»);
- может существовать **множество** оптимизированных версий (деоптимизации, повторные оптимизации);
- к этому добавляются GC-паузы и стоимость самой компиляции «на лету».

Если операция стоит `C` только один раз, а все остальные `N−1` раз стоит примерно `0` (потому что была вырезана как мёртвый код), то `T/N ≈ C/N → 0` при больших `N` — результат выглядит фантастически быстрым, хотя реальная стоимость операции никуда не делась.

## 6. «Умная собака»: constant folding, loop-invariant code motion, dead code elimination

Автор вводит метафору **JIT как умная собака**, которая проделывает над вашим кодом классические компиляторные оптимизации:

| Оптимизация | Что делает | Пример из доклада |
| --- | --- | --- |
| **Constant folding** (constant propagation) | Если переменная фактически никогда не меняется — подставляет её значение прямо в выражение и вычисляет результат заранее | `~~x` для константного `x` вычисляется один раз |
| **Loop-invariant code motion** (вынос инвариантов цикла) | Если значение выражения не меняется от итерации к итерации (даже если оно не константа), вычисление выносится за пределы цикла | Двойная тильда `~~x` вычисляется один раз до цикла, в цикле остаётся только присваивание |
| **Dead code elimination** (удаление мёртвого кода) | Если результат вычисления никуда не используется и не имеет побочных эффектов — код целиком выбрасывается | Неиспользуемая переменная с результатом `~~x` — компилятор выбрасывает и вычисление, и весь цикл |

Итог: бенчмарк «двойная тильда быстрее, чем `parseInt`, в Firefox» на самом деле измерял **пустой цикл**, из которого выпилили абсолютно всё, включая сам цикл (если движок умеет удалять мёртвые циклы — V8, в отличие от Firefox на тот момент, этого не умел).

```js
const x = "42"; // x не меняется на протяжении всего бенчмарка

for (let i = 0; i < 1_000_000; i++) {
  const n = ~~x; // (1) constant folding: ~~"42" вычисляется заранее
                 // (2) loop-invariant code motion: значение можно вынести из цикла
                 // (3) dead code elimination: n нигде не используется — цикл лишний
}
// После всех трёх оптимизаций от цикла эффективно не остаётся ничего:
// движок, умеющий удалять мёртвые циклы, "выполнит" его за 0 итераций.
```

## 7. Как писать более честные микробенчмарки — и почему даже это не панацея

Рекомендации автора («совет вам, вы всё равно не послушаетесь»):
1. **Не использовать константы** — заводить минимум две переменные, значения которых нельзя предсказать статически, и «вращать» их местами между итерациями, чтобы компилятор не смог свести дело к constant folding.
2. **Обязательно использовать (потреблять) результат** каждой итерации — например, суммировать в аккумулятор и проверять/печатать его в конце — чтобы не сработал dead code elimination.

Но даже это не гарантирует честности: существует **loop unrolling** (раскрутка цикла) — компилятор может продублировать тело цикла и сократить число итераций вдвое. Если внутри тела ничего реально не меняется (например, «переменная А» и «переменная Б» после раскрутки на своих местах), компилятор всё равно может обнаружить, что part of the code мёртв, и вырезать. V8 такую агрессивную раскрутку JS-циклов на тот момент не делал, а компиляторы C/C++/JVM HotSpot — делают. Мораль: **абсолютно надёжного микробенчмарка не существует**, всегда нужно проверять результат другими средствами (профайлер, дизассемблер, здравый смысл).

```js
// Более честная попытка: две непредсказуемые переменные + потребление результата
let a = Math.random() > 0.5 ? 1 : 2;
let b = Math.random() > 0.5 ? 3 : 4;
let acc = 0;

for (let i = 0; i < N; i++) {
  acc += ~~a; // компилятор не может заранее знать значение a
  [a, b] = [b, a]; // "вращаем" переменные местами между итерациями
}
console.log(acc); // потребляем результат — не даём выкинуть цикл как мёртвый код

// Даже это не спасает от loop unrolling: агрессивный компилятор может
// развернуть цикл на 2 итерации разом, увидеть, что a/b просто меняются
// местами туда-обратно, и всё равно упростить/вырезать часть работы.
```

## 8. Презумпция производительности и confirmation bias

Автор формулирует принцип **«презумпция производительности»**: по умолчанию считайте, что современный движок разумно оптимизирует разумно написанный код, и не спешите переписывать код под «слухи» о том, что где-то что-то медленное.

Проблема, которая этому мешает — **confirmation bias** («склонность к подтверждению своей точки зрения»): если у вас уже есть гипотеза («цепочки прототипов — это медленно»), вы пишете бенчмарк, который её подтверждает, публикуете блогпост — и цикл повторяется, распространяя неверные практики.

## 9. Кейс: доступ к свойству через прототип

Бенчмарк с Хабра: создание объекта через `Object.create`, чтение свойства с прототипа в цикле (3 захода, «чтобы наверняка») против варианта, где то же свойство вручную вынесено в локальную переменную перед циклом. Результат в старом Node: доступ к свойству прототипа в цикле **в ~8 раз дороже**, чем к вынесенной вручную переменной. Вывод автора бенчмарка: «подтверждено, цепочки прототипов медленные» — и блогпост про это.

Реальная причина: в конкретной старой версии V8 **не было инлайн-кэширования (inline caching) для обычных свойств (properties), объявленных на прототипе**, хотя для аксессоров (accessor properties, т.е. геттеров/сеттеров) на прототипе такое кэширование уже работало. В актуальной на момент доклада версии V8 оба варианта работают одинаково быстро — **не нужно вручную вытаскивать свойства прототипа в локальные переменные**.

```js
const proto = { value: 42 };
const obj = Object.create(proto);

// Вариант A: чтение свойства прототипа прямо в цикле
let sum = 0;
for (let i = 0; i < N; i++) sum += obj.value; // "медленно" в старом V8 (~8x)

// Вариант B: свойство вынесено в локальную переменную вручную
const cached = obj.value;
let sum2 = 0;
for (let i = 0; i < N; i++) sum2 += cached; // "быстро" — но это не про прототипы,
                                             // это просто чтение локальной переменной
```

## 10. Кейс: геттер против обычного свойства — «уличная магия»

Продолжение той же истории: попытка сравнить обычное свойство прототипа с геттером на прототипе, с ожиданием, что геттер будет «ещё раз в 10 дороже». Внезапно оказалось, что геттер **в 8 раз быстрее**.

Объяснение через инструмент для просмотра внутреннего представления кода: значение, возвращаемое геттером, в данном тесте оказалось эффективно константным для цикла, поэтому JIT применил constant folding/вынос инварианта и «съел» саму загрузку значения — измерялась не стоимость доступа к геттеру, а фактически пустая операция. Обычное же свойство (без геттера) в старом V8 при этом загружалось через медленный путь (не так, как надеялся автор), потому что старая V8 (докладчик подчёркивает: «очень старая, три раза подчёркиваю») не умела инлайнить обращение к обычным свойствам на прототипе — только к аксессорам.

```js
const proto = {
  get value() { return 42; } // геттер, а не обычное свойство
};
const obj = Object.create(proto);

let sum = 0;
for (let i = 0; i < N; i++) sum += obj.value;
// Ожидание: геттер — это вызов функции, значит дороже.
// Реальность: значение геттера не менялось между итерациями,
// JIT вынес его вычисление за пределы цикла — измерялась почти пустая операция.
```

## 11. Кейс: переполнение счётчика и «коробочные» числа (boxing)

Цикл со счётчиком (`Counter`), который увеличивается на каждой итерации. Первый запуск функции быстрый, повторный вызов той же функции — **резко медленнее**. Причина — переполнение диапазонов представления чисел:

1. маленький целочисленный диапазон (**Smi** — small integer);
2. диапазон `int32`;
3. дальше число превращается в `double`.

Как только счётчик выходит за пределы диапазона, который можно хранить «на месте» (в регистре/как immediate), V8 переходит к **коробочному представлению чисел (boxed doubles)**: под число выделяется отдельный объект в куче, и на каждом увеличении счётчика нужно аллоцировать новую «коробку». Именно это резко замедляет цикл на повторном запуске (счётчик продолжает расти от предыдущего вызова и быстрее выходит за пределы диапазона). Причина конкретного бага — сложение счётчика со строкой в конце цикла «протекало» наверх и заставляло V8 заранее выбирать коробочное представление для счётчика. Обходной путь — скрыть факт сложения счётчика со строкой от анализа компилятора.

```js
let Counter = 0;

function bench() {
  for (let i = 0; i < 1_000_000; i++) {
    Counter++; // Smi -> int32 -> double, при выходе за диапазон — boxing
  }
  // Провоцирующая строка: анализ типов "видит", что Counter может
  // складываться со строкой, и заранее выбирает медленное представление
  if (false) Counter = Counter + "x";
}

bench(); // первый вызов: быстро
bench(); // второй вызов: Counter стартует с большого значения — резко медленнее
```

## 12. Кейс: быстрые и медленные представления объектов, скрытые классы

Ещё один пример со Stack Overflow: одна и та же функция с геттером в разных версиях V8 (5.3 против 3.31) работает существенно медленнее в новой версии. При повторном запуске (второй вызов той же тестовой функции) объект **переходит в «медленное» представление**.

V8 хранит объекты в одном из двух режимов — **быстрые свойства** (fast properties, свойства как поля с фиксированным смещением, привязанные к «скрытому классу» — hidden class/Map) и **медленные свойства** (dictionary mode, свойства как хеш-таблица). Переход между скрытыми классами (**transition между hidden classes**) при определённых паттернах модификации объекта заставляет V8 «сдаться» и перевести объект в словарный режим. Можно проверить режим объекта через специальные отладочные функции движка (`%HasFastProperties` и подобные, доступны с флагом для «служебных» функций с `%` в начале имени).

Ранее (в версии 3.31) в V8 был код, который **насильно приводил объекты обратно к быстрому представлению**; позже его убрали, потому что такая принудительная конверсия сама по себе стоит производительности. Обходной путь из доклада — `Object.create(null)`-подобный трюк, который «чинит» ситуацию, но лишь до пятого вызова (то есть это тоже не универсальное решение, а иллюстрация хрупкости).

```js
function makeObj() {
  return { get x() { return 1; } };
}

function bench() {
  const obj = makeObj();
  // ... какие-то модификации obj, приводящие к переходу
  // между скрытыми классами (hidden class transitions) ...
  return obj.x;
}

bench(); // объект в "быстром" представлении (fast properties)
bench(); // в V8 5.3 (в отличие от 3.31) может остаться в "медленном" (dictionary mode)

// Проверка режима объекта через служебные функции движка (нужен спец-флаг):
// %HasFastProperties(obj) // true / false
```

## 13. Кейс: вызов функции против вызова метода

Бенчмарк: обычная функция, вручную считающая хэш строки, против метода с той же логикой, сидящего на прототипе объекта. Ожидаемо «ООП-версия» должна быть медленнее из-за диспетчеризации через прототип — но по факту оказалась *быстрее*, что подало как «объектно-ориентированное программирование — это круто».

На самом деле функция-версия в этом бенчмарке **никогда не прогревалась до оптимизированного состояния** (V8 не считала её достаточно «горячей» и не набрала достаточно информации о типах для оптимизации), тогда как метод на прототипе получал нужный прогрев за счёт паттерна вызовов в тесте. Если добавить в начало метода служебную директиву-подсказку компилятору (аналог trigger'а «эта функция горячая»), у функции-версии производительность так же резко улучшается — то есть исходное сравнение мерило не «функция vs метод», а «прогретый код vs непрогретый код».

```js
// Вариант А: обычная функция
function hash(str) {
  let h = 0;
  for (let i = 0; i < str.length; i++) h = (h * 31 + str.charCodeAt(i)) | 0;
  return h;
}

// Вариант Б: тот же код методом на прототипе
function Hasher() {}
Hasher.prototype.hash = function (str) {
  let h = 0;
  for (let i = 0; i < str.length; i++) h = (h * 31 + str.charCodeAt(i)) | 0;
  return h;
};
const hasher = new Hasher();

// hash(str) в тесте вызывался так, что V8 не успевал "прогреть" и
// оптимизировать функцию; hasher.hash(str) получал нужный прогрев
// из-за другого паттерна вызовов в самом бенчмарке — не из-за "ООП".
```

## 14. Кейс: чек в for-in цикле и мнимый баг транслятора Dart→JS

Разработчики транслятора Dart → JavaScript добавили в транслируемый `for-in` цикл дополнительную проверку (защиту от изменения перечисляемого объекта во время итерации). Бенчмарк показал, что без этой проверки код работает **на 18% быстрее** — то есть «защита от ошибок стоит перформанса».

После разбора с автором доклада выяснилось: дело не в самой проверке, а в конкретном V8-баге, связанном с **обрезанием (truncation) значения до `int32`**. Ветка кода, которая формально никогда не исполнялась в тесте (обработка исключения), «протекала» в анализ типов V8 и заставляла компилятор выбирать менее эффективный путь для всего цикла. Достаточно было в одном месте явно привести значение к `int32`, чтобы этот эффект исчез, и «лишняя» проверка перестала стоить чего-либо ощутимого.

```js
// Транслированный for-in с защитной проверкой (медленнее на 18% в бенчмарке)
function transpiledForIn(obj) {
  const keys = Object.keys(obj);
  const initialLength = keys.length;
  for (let i = 0; i < keys.length; i++) {
    if (keys.length !== initialLength) throw new Error("collection modified"); // почти никогда не срабатывает
    use(obj[keys[i]]);
  }
}

// "Чинящий" вариант — явное приведение к int32 в одном месте
function transpiledForInFixed(obj) {
  const keys = Object.keys(obj);
  const initialLength = keys.length | 0; // явный int32-truncation убирал V8-баг
  for (let i = 0; i < keys.length; i++) {
    if ((keys.length | 0) !== initialLength) throw new Error("collection modified");
    use(obj[keys[i]]);
  }
}
// Реальная причина замедления была не в проверке, а в том, что "мёртвая"
// ветка throw сбивала V8 с толку при анализе типов длины массива.
```

Главный вывод автора из этого кейса: **если вы видите необъяснимо странное поведение производительности — это, скорее всего, баг движка, а не что-то, что нужно тихо обходить**. Разработчики виртуальных машин — открытые люди, им можно и нужно писать/показывать такие случаи напрямую.

## 15. Заключение и Q&A

**Итоговые практические рекомендации:**
1. Не доверяйте микробенчмарку, пока не проверили результат независимо (профайлер, дизассемблер внутреннего представления, обсуждение с разработчиками движка).
2. Помните, что деление «общее время / число повторов» предполагает константную стоимость операции — в мире JIT это предположение почти всегда неверно.
3. Остерегайтесь constant folding, loop-invariant code motion и dead code elimination — они могут «съесть» весь смысл бенчмарка, если результат не используется или входные данные предсказуемы.
4. Не переносите выводы из старых версий движков (или из одного браузера) на все движки и все версии — данные о производительности устаревают буквально день ото дня.
5. Придерживайтесь «презумпции производительности»: пишите нормальный, читаемый код, и не тратьте силы на «слухи» об оптимизациях без проверки.
6. Если код ведёт себя необъяснимо — это, вероятнее всего, баг или особенность движка; сообщайте разработчикам VM напрямую, а не городите обходные пути втихую.

**Из ответов на вопросы:**
- Стрелочные функции в V8 (на момент доклада) оптимизируются нормально, наравне с обычными функциями — не имеют скрытого штрафа по производительности.
- Есть сайты, сравнивающие производительность фич ES2015+ (в том числе транспилированных вариантов) в разных браузерах на микробенчмарках — но такие данные нужно перепроверять и не считать вечной истиной: движки меняются постоянно.
- Benchmark.js/jsPerf — достаточно адекватный инструмент для сравнения между разными движками (в отличие от JMH для одной конкретной JVM/HotSpot), но не претендует на строго научную методологию; тем не менее с задачей прогрева и усреднения справляется приемлемо.
- Совет по дальнейшему изучению внутренностей V8: читать блог автора, книги по устройству виртуальных машин (в том числе классику вроде «Крафта интерпретаторов» и литературу по устройству JVM), а в конечном счёте — читать исходный код движка.
