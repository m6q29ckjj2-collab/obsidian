# Глава 26 · Управление памятью — квиз

> Теория → [[Отчёт]] · карточки → [[Карточки]] · [раздел спецификации](https://262.ecma-international.org/#sec-managing-memory)

> [!question] Что делает `WeakRef` в отличие от обычной переменной, хранящей объект?
> a) ускоряет доступ к объекту
> b) не мешает сборщику мусора удалить объект, даже пока сама ссылка существует
> c) автоматически клонирует объект
> d) делает объект неизменяемым
>> [!success]- Answer
>> b) не мешает сборщику мусора удалить объект, даже пока сама ссылка существует
>> Обычная переменная/свойство держит сильную ссылку, предотвращающую сборку; `WeakRef` держит слабую — объект может быть собран, даже если `WeakRef` на него ещё существует

> [!question] Что вернёт `weakRef.deref()`, если целевой объект ещё не собран сборщиком мусора?
>> [!success]- Answer
>> Сам объект (исходное значение)
>> Если объект уже собран — `deref()` вернёт `undefined`. Момент перехода не специфицирован

> [!question] Что произойдёт при вызове `new WeakRef(5)` — числовой примитив как цель?
> a) сработает как обычно
> b) выбросит `TypeError`
> c) число обернётся в объект автоматически
> d) вернёт `undefined`
>> [!success]- Answer
>> b) выбросит `TypeError`
>> Целью `WeakRef` может быть только объект или обычный (не зарегистрированный) символ — примитивы никогда не собираются сборщиком мусора, слабая ссылка на них бессмысленна

> [!question] Может ли обычный символ (`Symbol('x')`, не через `Symbol.for`) быть целью `WeakRef`?
>> [!success]- Answer
>> True
>> Такой символ может быть собран сборщиком мусора, в отличие от зарегистрированного через `Symbol.for`, который живёт в глобальном реестре вечно

> [!question] Специфицирует ли стандарт точный момент, когда `deref()` начинает возвращать `undefined` после того, как объект стал недостижимым?
>> [!success]- Answer
>> False
>> Момент полностью зависит от реализации сборщика мусора конкретного движка и намеренно не гарантирован спецификацией

> [!question] Какие три аргумента принимает `FinalizationRegistry.prototype.register`?
> a) `callback`, `delay`, `priority`
> b) `target`, `heldValue`, `unregisterToken` (опционально)
> c) `object`, `key`, `value`
> d) `weakRef`, `callback`, `timeout`
>> [!success]- Answer
>> b) `target`, `heldValue`, `unregisterToken` (опционально)
>> `target` — что отслеживать, `heldValue` — что передать колбэку при срабатывании, `unregisterToken` — ключ для последующей отмены регистрации

> [!question] Что произойдёт при вызове `registry.register(obj, obj)` — heldValue равен target?
> a) сработает как обычно
> b) выбросит `TypeError`
> c) heldValue автоматически станет `undefined`
> d) колбэк вызовется немедленно
>> [!success]- Answer
>> b) выбросит `TypeError`
>> Это ограничение обязательно, не произвольно: heldValue хранится обычной (не слабой) ссылкой, и если бы он совпадал с target, регистрация сама навсегда сделала бы объект достижимым

> [!question] Почему запрет `heldValue === target` — структурно обязательное правило, а не случайное ограничение API?
> a) чтобы упростить реализацию движка
> b) иначе регистрация сама создавала бы сильную ссылку на объект, и сборка мусора для него стала бы невозможна
> c) чтобы избежать путаницы у разработчиков
> d) это временное ограничение, которое уберут в будущих версиях
>> [!success]- Answer
>> b) иначе регистрация сама создавала бы сильную ссылку на объект, и сборка мусора для него стала бы невозможна
>> heldValue хранится обычным способом, чтобы быть доступным колбэку в момент вызова — если бы это был сам target, объект никогда бы не стал недостижимым

> [!question] Гарантирует ли спецификация, что зарегистрированный в `FinalizationRegistry` колбэк вообще будет вызван?
>> [!success]- Answer
>> False
>> Колбэк может не вызваться никогда — например, если программа завершится раньше, чем движок решит собрать объект. Это явно оговорено спецификацией, а не побочный эффект конкретной реализации

> [!question] Подходит ли `FinalizationRegistry` для гарантированного закрытия файлового дескриптора или сетевого соединения, когда объект больше не нужен?
> a) да, это основное назначение FinalizationRegistry
> b) нет, для этого нужен явный детерминированный код (try/finally, метод close())
> c) да, но только в Node.js
> d) да, если использовать unregisterToken
>> [!success]- Answer
>> b) нет, для этого нужен явный детерминированный код (try/finally, метод close())
>> Раз вызов колбэка не гарантирован и не привязан к конкретному моменту, полагаться на него для критичной для корректности программы логики структурно неправильно

> [!question] Для каких задач `WeakRef`/`FinalizationRegistry` действительно подходят?
> a) обязательная бизнес-логика приложения
> b) необязательные оптимизации кешей и инструменты отладки утечек памяти
> c) синхронизация между потоками
> d) валидация пользовательского ввода
>> [!success]- Answer
>> b) необязательные оптимизации кешей и инструменты отладки утечек памяти
>> Именно там ненадёжность тайминга не критична — если колбэк не вызовется, худшее последствие — не самая оптимальная утилизация памяти, а не поломка программы

> [!question] Что делает `registry.unregister(token)`?
>> [!success]- Answer
>> Отменяет ранее зарегистрированную запись, используя тот же объект-токен, что передавался третьим аргументом в register
>> Полезно, когда объект уже был явно освобождён другим способом — чтобы избежать повторного или устаревшего срабатывания колбэка для уже обработанного объекта
