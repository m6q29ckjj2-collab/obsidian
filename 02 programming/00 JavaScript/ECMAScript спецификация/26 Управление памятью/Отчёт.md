# Глава 26 · Управление памятью (WeakRef, FinalizationRegistry)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [26 Managing Memory](https://262.ecma-international.org/#sec-managing-memory)

Это самая маленькая и самая опасная в смысле неправильного использования глава спецификации. `WeakRef` и `FinalizationRegistry` дают прямой, но намеренно ненадёжный доступ к внутренней работе сборщика мусора. Спецификация формулирует это почти как предупреждение об ответственности: эти инструменты существуют для конкретных нишевых задач (в первую очередь — кеширование и отладочные инструменты), и их прямо не рекомендуется использовать для чего-либо, что должно работать предсказуемо.

---

## 26.1 WeakRef — ссылка, не мешающая сборке мусора

[26.1 WeakRef Objects](https://262.ecma-international.org/#sec-weak-ref-objects) — обёртка вокруг значения, которая **не удерживает** его от сборки мусора, в отличие от обычной переменной или свойства объекта. Получить исходное значение обратно можно через [26.1.3.2 WeakRef.prototype.deref](https://262.ecma-international.org/#sec-weak-ref.prototype.deref) — но только если оно ещё не было собрано:

```js
let obj = { data: 'важные данные' };
const ref = new WeakRef(obj);

console.log(ref.deref() === obj); // true — объект ещё жив, deref() возвращает его

obj = null; // убрали единственную обычную (сильную) ссылку
// где-то позже, когда сборщик мусора доберётся до объекта,
// ref.deref() начнёт возвращать undefined — но точный момент непредсказуем и не специфицирован
```

### Что можно держать в `WeakRef`

Целью слабой ссылки может быть **объект** или **не зарегистрированный символ** — та же граница, что уже разбиралась применительно к ключам `WeakMap`/`WeakSet` в предыдущей главе (объект или символ, созданный обычным `Symbol('...')`, без `Symbol.for`):

```js
try {
  new WeakRef(5); // числовой примитив — не может быть целью слабой ссылки
} catch (e) {
  console.log(e.constructor.name); // TypeError
}

const uniqueSym = Symbol('локальный');
const symRef = new WeakRef(uniqueSym); // допустимо — обычный символ можно собрать сборщиком мусора

const registeredSym = Symbol.for('глобальный-ключ');
try {
  new WeakRef(registeredSym); // символ из глобального реестра
} catch (e) {
  console.log(e.constructor.name); // TypeError — он никогда не собирается, слабая ссылка бессмысленна
}
```

Логика та же, что и у `WeakMap`: числа, строки и другие обычные примитивы никогда не удаляются сборщиком мусора (значение `5` — не «объект в памяти», а просто число, оно ничего не занимает сверх места хранения), поэтому «слабо ссылаться» на них не имеет смысла как концепция. Зарегистрированные символы (`Symbol.for`) специально исключены по симметричной причине — они гарантированно живут в глобальном реестре вечно, пока жив процесс, так что тоже никогда не будут собраны.

### Почему это не инструмент для повседневного кода

Момент, когда `deref()` действительно начинает возвращать `undefined`, зависит от внутренней реализации сборщика мусора конкретного движка — спецификация намеренно **не** фиксирует ни точное время, ни гарантию, что это вообще произойдёт до завершения программы. Использовать `WeakRef` для логики, которая должна сработать «сразу после того, как объект стал не нужен» (например, освобождение внешнего ресурса) — структурно неправильно: между моментом «на объект больше нет ссылок» и моментом «сборщик мусора его реально забрал» может пройти сколько угодно времени, и на это время нельзя полагаться ни в каком смысле.

## 26.2 FinalizationRegistry — уведомление после сборки мусора

[26.2 FinalizationRegistry Objects](https://262.ecma-international.org/#sec-finalization-registry-objects) идёт на шаг дальше `WeakRef`: вместо того чтобы вручную опрашивать `deref()`, можно зарегистрировать колбэк, который движок **может** вызвать после того, как целевой объект был собран сборщиком мусора.

```js
const registry = new FinalizationRegistry((heldValue) => {
  console.log('объект собран, переданное значение:', heldValue);
});

let obj = { id: 42 };
registry.register(obj, 'какое-то удерживаемое значение для колбэка');

obj = null; // убрали единственную сильную ссылку
// когда-нибудь (или никогда) движок может вызвать колбэк с 'какое-то удерживаемое значение для колбэка'
```

### Ограничения на аргументы `register` — не случайные, а структурно обязательные

[26.2.3.2 FinalizationRegistry.prototype.register](https://262.ecma-international.org/#sec-finalization-registry.prototype.register) принимает три аргумента: `target` (что отслеживать), `heldValue` (что передать колбэку) и опциональный `unregisterToken` (ключ для отмены регистрации). У всех трёх аргументов есть проверки, которые выбрасывают `TypeError` при нарушении, и каждая из них имеет конкретную причину, а не произвольна:

```js
const registry = new FinalizationRegistry(() => {});
const obj = {};

// 1. target должен быть объектом или обычным символом — тем же требованием CanBeHeldWeakly, что и у WeakRef
try { registry.register(1, 'значение'); }
catch (e) { console.log(e.constructor.name); } // TypeError

// 2. heldValue не может быть тем же самым значением, что и target
try { registry.register(obj, obj); }
catch (e) { console.log(e.constructor.name); } // TypeError

// 3. unregisterToken, если передан, тоже должен быть объектом или обычным символом
try { registry.register(obj, 'значение', 5); }
catch (e) { console.log(e.constructor.name); } // TypeError
```

Второе правило — `heldValue !== target` — стоит объяснить отдельно, потому что оно легко может показаться произвольным ограничением. Если бы `heldValue` разрешили быть тем же самым объектом, что и `target`, регистрация сама создавала бы **сильную** ссылку на объект внутри записи реестра (ведь `heldValue` хранится обычным, не слабым способом — колбэку нужно передать что-то реально существующее в момент вызова). Это свело бы на нет саму цель регистрации: объект никогда не стал бы недостижимым, потому что реестр сам держал бы его живым — сборка мусора никогда бы не произошла, и колбэк никогда бы не вызвался. Спецификация запрещает эту ошибку на уровне проверки аргументов, а не оставляет её как «тонкость для внимательных».

### Явная позиция спецификации: не полагайтесь на вызов колбэка

Это единственное место во всей спецификации, где формулировка настолько прямо предупреждает не полагаться на описанное поведение: колбэк `FinalizationRegistry` **может не вызваться никогда** — если программа завершится раньше, чем движок решит собрать объект, если сам движок использует более консервативную стратегию сборки мусора, или по любой другой внутренней причине реализации. Даже если колбэк в итоге вызывается, порядок вызовов для разных объектов не гарантирован, и вызов может произойти сколь угодно позже фактической сборки объекта — стандарт умышленно не даёт таймингового обязательства, чтобы не ограничивать свободу реализаций сборщика мусора.

Практический вывод: `FinalizationRegistry` подходит для **необязательной** оптимизации или диагностики — например, дополнительной подчистки записи в кеше, если движок в принципе решит вызвать колбэк, или инструмента отладки утечек памяти в разработке. Он категорически не подходит для чего-либо, что программа обязана сделать для корректности: закрытие файлового дескриптора, освобождение сетевого соединения, разблокировка мьютекса — для таких задач нужен явный, детерминированный код (например, `try/finally` или явный метод `close()`/`dispose()`), а не расчёт на то, что сборщик мусора когда-нибудь доберётся до объекта.

### `unregister` — отмена ранее зарегистрированной записи

Если объект освобождается явным, контролируемым способом (например, у него есть собственный метод `close()`), регистрацию в `FinalizationRegistry` для него стоит отменить — иначе спецификация всё равно может вызвать колбэк позже, когда сборщик мусора доберётся до уже явно освобождённого объекта, что может привести к дублирующей логике очистки. Для этого при регистрации передаётся `unregisterToken`, и позже — тот же самый токен в `registry.unregister(token)`:

```js
const registry2 = new FinalizationRegistry((v) => console.log('finalized:', v));
const resource = {};
const token = {}; // отдельный объект-токен, специально для отмены

registry2.register(resource, 'значение для колбэка', token);

// когда ресурс освобождён явным образом заранее — отменяем регистрацию,
// чтобы колбэк точно не выполнился повторно для уже обработанного объекта
registry2.unregister(token);
```

## Итог

> [!summary] Что взять с собой
> - `WeakRef`/`FinalizationRegistry` — прямой, но намеренно ненадёжный доступ к сборщику мусора; ни одна деталь тайминга не гарантирована спецификацией
> - Целью `WeakRef` (и `target`/`unregisterToken` у `FinalizationRegistry`) может быть объект или обычный, не зарегистрированный через `Symbol.for` символ — та же граница, что и у ключей `WeakMap`
> - `WeakRef.prototype.deref()` возвращает значение, если оно ещё живо, или `undefined` после сборки — но момент перехода не специфицирован
> - `register(target, heldValue, unregisterToken)` запрещает `heldValue === target` — иначе регистрация сама создавала бы сильную ссылку на объект, делая сборку мусора для него невозможной в принципе
> - Колбэк `FinalizationRegistry` **может не вызваться никогда** — использовать его для логики, критичной для корректности программы (закрытие файлов, освобождение соединений), структурно неправильно
> - `unregister(token)` отменяет ранее зарегистрированную запись — полезно, когда объект уже явно освобождён другим способом, чтобы избежать повторной или устаревшей логики очистки
> - Подходящее применение этих инструментов — необязательные оптимизации кешей и инструменты отладки утечек памяти, а не критичная бизнес-логика
