# Глава 8 · Синтаксически управляемые операции

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [8 Syntax-Directed Operations](https://262.ecma-international.org/#sec-syntax-directed-operations)

Эта глава короткая и формальная — она не описывает конкретное поведение языка, а объясняет **общий механизм**, которым спецификация пользуется во всех остальных главах. Мы уже видели эффекты этого механизма на практике — hoisting `var`, временная мёртвая зона `let`, автоматическое имя у анонимной функции при `const f = function(){}` (главы 9, 14, 18) — но не разбирали формально, откуда эти эффекты берутся. Глава 8 — это как раз то самое "откуда".

---

## Что такое синтаксически управляемая операция

**Синтаксически управляемая операция** (syntax-directed operation) — это алгоритм, определение которого прикреплено не к абстрактному имени функции, а прямо к конкретному правилу грамматики языка. Например, операция [8.1 Evaluation](https://262.ecma-international.org/#sec-evaluation) — "как вычислить это выражение или инструкцию" — определена не одним большим алгоритмом на все случаи жизни, а **россыпью** отдельных определений, каждое из которых привязано к своему грамматическому правилу и раскидано по всей спецификации: определение `Evaluation` для `IfStatement` находится в главе про инструкции (14), для `BinaryExpression` — в главе про выражения (13), и так далее. Когда движок встречает конкретный узел разобранного кода, он вызывает именно то определение `Evaluation`, что соответствует грамматическому правилу, по которому этот узел был разобран.

Это архитектурное решение, а не просто способ организации текста: оно позволяет каждому грамматическому правилу иметь своё точное, локальное определение поведения, вместо одного гигантского `switch` по всем возможным конструкциям языка. Мы, по сути, весь этот момент уже наблюдали неявно на протяжении всего проекта — в каждой главе про конкретную синтаксическую конструкцию всегда была своя логика "как это вычисляется", и глава 8 — просто явное название и каталог этого приёма.

## 8.2 Scope Analysis — формальный источник разницы между `var` и `let`

Здесь спецификация даёт формальное объяснение тому, что мы наблюдали в главе 14 как данность: `var` "всплывает" до начала функции, а `let`/`const` остаются в границах своего блока. Механизм — набор синтаксически управляемых операций, которые обходят дерево разбора и **классифицируют** объявления на две непересекающиеся категории:

- [8.2.6 VarDeclaredNames](https://262.ecma-international.org/#sec-static-semantics-vardeclarednames) — собирает имена всех `var`-объявлений и объявлений функций, находящихся в теле функции/скрипта, **включая те, что лежат глубоко внутри вложенных блоков** — операция буквально "прорастает" сквозь границы блоков
- [8.2.4 LexicallyDeclaredNames](https://262.ecma-international.org/#sec-static-semantics-lexicallydeclarednames) — собирает имена `let`/`const`/`class`, но **останавливается на границе блока** — не заглядывает внутрь вложенных `{}`

```js
function f() {
  console.log(typeof x); // 'undefined' — переменная уже существует к этому моменту
  if (true) {
    var x = 1;   // формально: VarDeclaredNames "прорастает" сквозь блок if,
                 // имя x регистрируется на уровне всей функции f
    let y = 2;   // формально: LexicallyDeclaredNames видит y только внутри этого блока
    console.log(y); // 2
  }
  console.log(x); // 1 — x доступен здесь, потому что был зарегистрирован на уровне функции
  try { console.log(y); } catch (e) { console.log(e.constructor.name); } // ReferenceError — y не существует за пределами блока if
}
f();
```

Именно эта пара операций — формальная причина, почему в главе 9 при создании контекста исполнения функции движок заранее знает **все** `var`-имена во всей функции целиком (даже спрятанные в глубоко вложенных `if`/`for`/`while`), чтобы заранее создать для них связывания в объектной среде окружения, тогда как `let`/`const` получают новые связывания отдельно для каждого блока при входе в него.

### Function declarations — особый переходный случай

Объявления функций (`function foo() {}`) занимают формально пограничное положение: на верхнем уровне функции или скрипта они входят в `VarDeclaredNames` (ведут себя как `var` — доступны из любого места функции благодаря hoisting), но если объявление функции находится **внутри блока** (`if { function foo() {} }`), возникает как раз тот самый нюанс легаси-совместимости из Annex B (глава 17) — по историческим причинам разные движки трактовали это по-разному, и спецификация в итоге закрепила компромиссное поведение (доступность имени и как блочно-локальной лексической привязки, и, при определённых условиях, как поднятой на уровень функции переменной).

## 8.3 Labels — почему `break несуществующаяМетка` ошибка на этапе разбора, а не выполнения

[8.3.2 ContainsUndefinedBreakTarget](https://262.ecma-international.org/#sec-static-semantics-containsundefinedbreaktarget) и [8.3.3 ContainsUndefinedContinueTarget](https://262.ecma-international.org/#sec-static-semantics-containsundefinedcontinuetarget) — синтаксически управляемые операции, проверяющие, что каждая метка, на которую ссылается `break`/`continue`, реально существует в охватывающей структуре кода. Это проверка **времени разбора** (early error), а не времени выполнения — и здесь кроется не вполне очевидная деталь: код может так никогда и не выполниться (например, лежать в ветке `if (false)`), но программа всё равно не запустится **вообще**, потому что синтаксическая ошибка обнаруживается ещё до выполнения хоть одной строки:

```js
try {
  eval(`
    function f() {
      if (false) { break этогоНеСуществует; } // этот код никогда не выполнится
    }
  `);
} catch (e) {
  console.log(e.constructor.name, e.message); // SyntaxError: Undefined label 'этогоНеСуществует'
}
// ошибка поймана на этапе разбора eval-строки, хотя сам break никогда бы не выполнился
```

Та же логика применяется к [8.3.1 ContainsDuplicateLabels](https://262.ecma-international.org/#sec-static-semantics-containsduplicatelabels) — повторное использование одной и той же метки в одной области видимости тоже ошибка разбора:

```js
try {
  eval('outer: outer: for(;;) {}');
} catch (e) {
  console.log(e.constructor.name); // SyntaxError
}
```

Это прямая иллюстрация принципа "статическая семантика вместо семантики времени выполнения" — то же разделение, что уже обсуждалось в главе 5: спецификация явно выделяет "статическую семантику" (Static Semantics) как отдельный класс правил, проверяемых во время разбора, независимо от того, будет ли конкретный участок кода когда-либо фактически выполнен.

## 8.4 Function Name Inference — формальная причина, почему у одних анонимных функций есть `.name`, а у других нет

В главе 18 мы обсуждали, что `.name` функции обычно выводится автоматически из контекста. Механизм, отвечающий за это, — [8.4.5 NamedEvaluation](https://262.ecma-international.org/#sec-runtime-semantics-namedevaluation), синтаксически управляемая операция времени выполнения, которая вызывается **только** для определённого набора грамматических позиций — там, где функция определяется как *непосредственное* значение единственного связывания:

```js
const a = function() {};
console.log(a.name); // 'a' — присваивание const-переменной — одна из позиций, вызывающих NamedEvaluation

const obj = { b: function() {} };
console.log(obj.b.name); // 'b' — свойство объектного литерала — тоже такая позиция

let c;
c = function() {};
console.log(c.name); // 'c' — обычное присваивание существующей переменной — тоже считается

const arr = [function() {}];
console.log(arr[0].name); // '' — а вот элемент литерала массива — НЕ такая позиция!
```

Разница между `obj.b` (имя выводится) и `arr[0]` (не выводится) — не случайность и не недоработка, а прямое следствие того, что `NamedEvaluation` формально определена только для конкретного списка грамматических продукций (свойство объектного литерала, инициализатор переменной, присваивание) — литерал массива в этот список не входит, потому что позиция внутри массива не даёт функции какого-либо единственного, однозначного "имени" в том смысле, в каком его даёт свойство объекта или имя переменной.

## 8.6 Прочие операции — беглый обзор

Оставшиеся операции этой главы — техническая инфраструктура, используемая другими главами, но интересная скорее для того, чтобы понимать структуру спецификации, чем сама по себе:

- [8.6.1 InstantiateFunctionObject](https://262.ecma-international.org/#sec-runtime-semantics-instantiatefunctionobject) — как из грамматического узла объявления функции действительно собирается объект-функция (тот процесс, что уже неявно разбирался в главе 15)
- [8.6.2 BindingInitialization](https://262.ecma-international.org/#sec-runtime-semantics-bindinginitialization) и [8.6.3 IteratorBindingInitialization](https://262.ecma-international.org/#sec-runtime-semantics-iteratorbindinginitialization) — как связываются имена при деструктуризации, в том числе через перебор итератора (`const [a, b] = someIterable`) — формальная основа деструктурирующего присваивания
- [8.6.5 PropName](https://262.ecma-international.org/#sec-static-semantics-propname) — извлекает имя свойства из узла объектного литерала на этапе статического анализа; используется, среди прочего, чтобы находить дублирующиеся `__proto__` в одном литерале (что запрещено, в отличие от прочих дублирующихся ключей, которые в современном JS разрешены и просто перезаписывают друг друга)

## Итог

> [!summary] Что взять с собой
> - Синтаксически управляемая операция — алгоритм, определение которого прикреплено к конкретному правилу грамматики, а не к единой универсальной функции — этим приёмом пользуется вся спецификация, начиная с `Evaluation`
> - `VarDeclaredNames` "прорастает" сквозь границы блоков и собирает все `var`/function-объявления на уровне всей функции — формальная причина hoisting `var` за пределы `if`/`for`/`while`
> - `LexicallyDeclaredNames` останавливается на границе каждого блока — формальная причина, почему `let`/`const` не покидают свой блок
> - Ошибки вроде `break несуществующаяМетка` и повторяющихся меток — синтаксические (обнаруживаются при разборе), а не времени выполнения: программа не запустится вообще, даже если проблемный код лежит в никогда не выполняемой ветке
> - `NamedEvaluation` — механизм автоматического вывода `.name` у анонимной функции — работает только в конкретных грамматических позициях (свойство объектного литерала, присваивание переменной), но не во всех местах, где функция может оказаться значением (например, не в литерале массива)
> - Остальные операции главы (`InstantiateFunctionObject`, `BindingInitialization`, `PropName`) — техническая инфраструктура, формально обосновывающая механизмы, уже разобранные на практике в главах про функции, деструктуризацию и объектные литералы
