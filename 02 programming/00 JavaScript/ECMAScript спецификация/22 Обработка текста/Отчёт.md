# Глава 22 · Обработка текста (String, RegExp)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [22 Text Processing](https://262.ecma-international.org/#sec-text-processing)

Эта глава — самая объёмная в спецификации по количеству методов: строки и регулярные выражения. Мы не будем разбирать каждый метод по отдельности — большинство ведут себя ровно так, как ожидает любой, кто писал JS хотя бы неделю. Вместо этого сосредоточимся на том, что спецификация уточняет неочевидным образом: как строки на самом деле хранятся, почему у методов вроде `replaceAll` есть скрытая ловушка, и почему регулярные выражения с флагом `g` — это не чистая функция, а объект с внутренним состоянием, который может незаметно сломать код.

## 22.1 String — строки: объекты в момент вызова метода

[22.1 String Objects](https://262.ecma-international.org/#sec-string-objects) описывает и сам конструктор `String`, и прототип `String.prototype`, чьи методы вызываются на *примитивных* строковых значениях каждый день.

Важная деталь, о которой редко задумываются: строковый примитив (`'abc'`) — это не объект, у него нет методов. Когда вы пишете `'abc'.toUpperCase()`, движок выполняет внутреннюю операцию **ToObject**, которая на мгновение оборачивает примитив в объект-обёртку `String`, у неё уже есть методы через прототип, и после вызова эта временная обёртка выбрасывается. Отсюда следует конкретное, проверяемое поведение: если попробовать присвоить строковому примитиву свойство, присваивание не сохранится — потому что записываете вы во временный объект, который тут же исчезает.

```js
const s = 'abc';
s.foo = 1;           // в нестрогом режиме тихо ничего не делает
console.log(s.foo);  // undefined — свойство «не прижилось»

'use strict';
// в строгом режиме та же попытка выбросит TypeError,
// потому что запись в свойство временного объекта нарушает его неизменяемость
```

Это не баг и не «фича ради красоты» — это прямое следствие того, что примитив не может иметь состояния. Практический вывод: никогда не полагайтесь на присваивание свойств строковым, числовым или булевым примитивам — они не объекты, что бы ни казалось при вызове метода.

### Что здесь есть — коротко

Большинство методов `String.prototype` работают ожидаемо и не нуждаются в отдельном разборе: [`charAt`](https://262.ecma-international.org/#sec-string.prototype.charat), [`concat`](https://262.ecma-international.org/#sec-string.prototype.concat), [`includes`](https://262.ecma-international.org/#sec-string.prototype.includes), [`indexOf`](https://262.ecma-international.org/#sec-string.prototype.charat) (и `lastIndexOf`), [`slice`](https://262.ecma-international.org/#sec-string.prototype.slice), [`substring`](https://262.ecma-international.org/#sec-string.prototype.substring), [`startsWith`](https://262.ecma-international.org/#sec-string.prototype.startswith), [`endsWith`](https://262.ecma-international.org/#sec-string.prototype.endswith), [`repeat`](https://262.ecma-international.org/#sec-string.prototype.repeat), [`toLowerCase`](https://262.ecma-international.org/#sec-string.prototype.tolowercase)/[`toUpperCase`](https://262.ecma-international.org/#sec-string.prototype.touppercase), [`trim`](https://262.ecma-international.org/#sec-string.prototype.trim)/`trimStart`/`trimEnd`, [`at`](https://262.ecma-international.org/#sec-string.prototype.at) (индексация с конца через отрицательный аргумент).

Дальше — то, что действительно стоит разобрать подробно.

### Длина строки считается в единицах UTF-16, а не в «символах»

Свойство `.length` и большинство индексирующих методов (`charAt`, `charCodeAt`, `slice` по индексу) работают не с «символами» в бытовом смысле, а с **16-битными кодовыми единицами UTF-16** — так внутри устроено строковое представление в ECMAScript. Пока речь идёт об английском алфавите и большинстве символов из Basic Multilingual Plane (кириллица, латиница, большинство иероглифов), один символ — одна кодовая единица, и разница незаметна. Но эмодзи и часть редких иероглифов лежат за пределами этой плоскости и кодируются **суррогатной парой** — двумя кодовыми единицами, представляющими один настоящий символ (кодовую точку Unicode).

```js
const emoji = '😀';
console.log(emoji.length);        // 2 — две кодовые единицы UTF-16, а не один символ
console.log([...emoji].length);   // 1 — оператор расширения (spread) итерирует по кодовым точкам, а не по единицам

console.log(emoji.codePointAt(0)); // 128512 — настоящий код символа (кодовая точка)
console.log(emoji.charCodeAt(0));  // 55357 — только код первой половины суррогатной пары
```

Практический вывод: если код должен правильно считать «символы», которые видит пользователь (длина имени, обрезка текста для превью, подсчёт символов в поле ввода), метод `.length` для этого не годится, если в тексте могут быть эмодзи или редкие иероглифы. Правильный способ — `[...string].length` (через spread или `for...of`, которые итерируют по кодовым точкам) либо `Intl.Segmenter` для ещё более точного разбиения на «графемные кластеры» (то, что пользователь интуитивно называет одним символом — например, эмодзи с модификатором цвета кожи, состоящий из нескольких кодовых точек).

### `normalize()` — один и тот же символ можно записать по-разному

Юникод позволяет закодировать один и тот же видимый символ несколькими разными последовательностями кодовых точек. Классический пример — буква «é»: её можно записать одной **составной** кодовой точкой (`U+00E9`) или **разложенной** последовательностью — обычная латинская «e» плюс отдельный комбинирующий диакритический знак «ударение» (`U+0065 U+0301`). Визуально и то, и другое выглядит одинаково, но со строкового сравнения это два *разных* значения:

```js
const composed = 'é';        // 'é' одной кодовой точкой, length === 1
const decomposed = 'é'; // 'e' + отдельный диакритический знак, length === 2

console.log(composed === decomposed); // false — хотя выглядят одинаково при отрисовке!

// normalize() приводит обе формы к общему стандарту сравнения
console.log(composed.normalize('NFC') === decomposed.normalize('NFC')); // true
```

[22.1.3.28 String.prototype.normalize](https://262.ecma-international.org/#sec-string.prototype.normalize) принимает одну из четырёх форм: `'NFC'` (по умолчанию, максимально составная запись — обычно то, что нужно), `'NFD'` (максимально разложенная), `'NFKC'` и `'NFKD'` (дополнительно схлопывают «совместимые» варианты символов, например полноширинные и обычные цифры). Практический вывод: если строки для сравнения или поиска могли прийти из разных источников (пользовательский ввод с разных ОС, скопированный текст, данные из разных API), нормализация перед сравнением — не экзотика, а необходимость, иначе визуально идентичные строки будут считаться разными.

### `isWellFormed` и `toWellFormed` — что если строка содержит «сломанный» символ

Поскольку строка ECMAScript — это произвольная последовательность 16-битных единиц, ничто формально не запрещает создать строку с **одиночным суррогатом** — половиной суррогатной пары без второй половины. Такая строка не соответствует ни одному реальному символу Unicode:

```js
const lone = '\uD800'; // старшая половина суррогатной пары без младшей — "битая" строка

console.log(lone.isWellFormed()); // false — обнаруживает такую поломку

console.log(lone.toWellFormed().codePointAt(0)); // 65533 — символ замены U+FFFD "�"
// toWellFormed() заменяет каждый одиночный суррогат на символ-заменитель
```

[22.1.3.10 String.prototype.isWellFormed](https://262.ecma-international.org/#sec-string.prototype.iswellformed) и [22.1.3.31 String.prototype.toWellFormed](https://262.ecma-international.org/#sec-string.prototype.towellformed) появились сравнительно недавно (ES2024) именно потому, что такие «битые» строки — не теоретическая проблема: они возникают при неаккуратной работе с суррогатными парами (например, обрезке строки посередине эмодзи по `.length`) и ломают дальнейшую обработку — в частности, при конвертации в UTF-8 для сети или файловой системы, где одиночный суррогат не имеет корректного представления.

### `localeCompare` — сравнение строк с учётом языка, а не байтов

Операторы `<` и `>` сравнивают строки поразрядно по числовому значению кодовых единиц UTF-16 — это быстро, но не совпадает с тем, как человек ожидает увидеть отсортированный список слов на своём языке (например, порядок букв с диакритикой). [22.1.3.13 String.prototype.localeCompare](https://262.ecma-international.org/#sec-string.prototype.localecompare) делегирует сравнение в `Intl`-инфраструктуру, которая учитывает языковые правила.

```js
console.log('a' < 'A');           // false — заглавная 'A' (код 65) меньше строчной 'a' (код 97) в UTF-16
console.log('a'.localeCompare('A', 'en', { sensitivity: 'base' })); // 0 — с точки зрения языка это "одна и та же буква"
```

Сама спецификация ECMA-262 **не определяет** конкретный алгоритм сортировки для `localeCompare` — она лишь требует, чтобы результат был «разумным для языка», а точные правила отданы на откуп реализации через связанный стандарт ECMA-402 (Intl). Практический вывод: не полагайтесь на строгую переносимость результатов `localeCompare` между разными движками для тонких случаев — но для базовой задачи «отсортировать список имён по-человечески» это правильный инструмент, а не `<`/`>`.

## 22.2 RegExp — регулярные выражения: скрытое состояние

[22.2 RegExp (Regular Expression) Objects](https://262.ecma-international.org/#sec-regexp-regular-expression-objects) — вторая половина главы, и именно здесь спрятана самая частая практическая ловушка всей главы.

Прежде всего: экземпляр `RegExp` — **не** чистое неизменяемое значение вроде строки или числа. Это полноценный объект с собственным изменяемым состоянием — свойством [22.2.8.1 lastIndex](https://262.ecma-international.org/#sec-lastindex). Когда регулярное выражение создано с флагом `g` (global) или `y` (sticky), каждый вызов [`exec`](https://262.ecma-international.org/#sec-regexp.prototype.exec) или [`test`](https://262.ecma-international.org/#sec-regexp.prototype.test) не просто ищет совпадение — он **запоминает**, где закончилось предыдущее совпадение, и следующий вызов на том же объекте продолжает поиск именно оттуда, а не с начала строки:

```js
const re = /a/g;
const s = 'aaa';

console.log(re.exec(s).index, re.lastIndex); // 0 1 — нашли первую 'a', запомнили позицию
console.log(re.exec(s).index, re.lastIndex); // 1 2 — начали поиск с позиции 1, не с 0
console.log(re.exec(s).index, re.lastIndex); // 2 3

console.log(re.exec(s));       // null — совпадений после позиции 3 больше нет
console.log(re.lastIndex);     // 0 — после неудачи lastIndex сам сбрасывается в 0
```

`test()` ведёт себя точно так же и увеличивает `lastIndex` при флаге `g`. Отсюда — классический источник багов, который выглядит совершенно необъяснимым, если не знать про это состояние:

```js
const re2 = /x/g;
console.log(re2.test('xx')); // true, lastIndex стал 1
console.log(re2.test('xx')); // true, lastIndex стал 2
console.log(re2.test('xx')); // false! хотя строка та же самая — поиск начался с позиции 2, там 'x' уже нет
```

Если один и тот же объект `RegExp` с флагом `g` используется повторно (например, хранится в константе на уровне модуля и переиспользуется в разных вызовах функции), результат каждого следующего вызова зависит от истории предыдущих — это прямое нарушение ожидания, что функция без побочных эффектов на одинаковых входных данных даёт одинаковый результат. Практическое правило: либо не переиспользуйте один и тот же объект `RegExp` с флагом `g`/`y` между независимыми операциями (создавайте новый литералом на каждый вызов — литералы `/re/` внутри функции создают новый объект при каждом входе в функцию), либо явно сбрасывайте `re.lastIndex = 0` перед использованием, если объект действительно нужно переиспользовать.

Флаг `y` (**sticky**) — более строгий родственник `g`: если `g` при неудаче на текущей позиции продолжает искать совпадение дальше по строке, то `y` требует, чтобы совпадение начиналось *ровно* с позиции `lastIndex`, и если там совпадения нет — результат сразу `null`, без попытки поискать дальше:

```js
const sticky = /foo/y;
sticky.lastIndex = 2;
console.log(sticky.test('__foo')); // true — 'foo' начинается ровно с индекса 2

const sticky2 = /foo/y;
sticky2.lastIndex = 3;
console.log(sticky2.test('__foo')); // false — с индекса 3 идёт 'oo', это не начало 'foo', и sticky не ищет дальше
```

### `matchAll` требует глобального флага

[22.1.3.15 String.prototype.matchAll](https://262.ecma-international.org/#sec-string.prototype.matchall) — способ получить **все** совпадения сразу в виде итератора (в отличие от `match` без флага `g`, который возвращает только первое совпадение с подробностями о группах захвата). Но спецификация явно требует, чтобы переданное регулярное выражение имело флаг `g` — без него метод выбрасывает `TypeError`, а не просто "неявно исправляет" отсутствие флага:

```js
try {
  'aaa'.matchAll(/a/); // без флага g
} catch (e) {
  console.log(e.constructor.name); // TypeError
}

const matches = [...'a1b2'.matchAll(/[a-z](\d)/g)];
console.log(matches.map(m => `${m[0]}:${m[1]}`)); // ['a1:1', 'b2:2']
// matchAll не мутирует внешнее состояние: каждый вызов создаёт свой внутренний итератор
// с собственной копией позиции поиска, в отличие от прямого использования re.exec() в цикле
```

Важное отличие `matchAll` от ручного цикла с `exec`: сам метод `matchAll` **не изменяет** `lastIndex` переданного регулярного выражения — он проходит копию логики поиска внутри своего итератора. Это осознанное решение авторов спецификации: именно `matchAll` придумали как безопасную альтернативу ручному циклу с `exec` в `while`, который как раз страдает от описанной выше проблемы разделяемого состояния.

### `replaceAll` — зеркальная ловушка: без глобального флага бросает исключение

[22.1.3.19 String.prototype.replaceAll](https://262.ecma-international.org/#sec-string.prototype.replaceall) специально проверяет: если аргумент — регулярное выражение без флага `g`, метод не пытается «догадаться», что вы хотели заменить только первое совпадение (для этого есть `replace`), а сразу выбрасывает `TypeError`:

```js
try {
  'aaa'.replaceAll(/a/, 'b'); // регулярное выражение без флага g
} catch (e) {
  console.log(e.message); // "String.prototype.replaceAll called with a non-global RegExp argument"
}

console.log('aaa'.replace(/a/, 'b'));     // 'baa'  — replace без g меняет только первое совпадение
console.log('aaa'.replace(/a/g, 'b'));    // 'bbb'  — replace с g меняет все — так же, как replaceAll
console.log('aaa'.replaceAll(/a/g, 'b')); // 'bbb'  — обязателен флаг g
```

Строковый (не regexp) первый аргумент у `replaceAll` такого требования не имеет — `'aaa'.replaceAll('a', 'b')` работает и без всяких флагов, потому что там нет вопроса «глобальный поиск или нет», строка ищется буквально и заменяются все вхождения. Ограничение касается именно передачи `RegExp` без `g`. Практический вывод: это осознанная защита от самой частой ошибки новичков — ожидания, что `replaceAll(/pattern/, x)` заменит всё само собой; спецификация явно требует написать `g` в флагах, чтобы намерение было видно в самом коде.

### Специальные подстановки `$` в строке замены

Второй аргумент `replace`/`replaceAll`, если это строка, распознаёт специальные последовательности с `$`, позволяющие ссылаться на части найденного совпадения — это тоже часть [22.1.3.19](https://262.ecma-international.org/#sec-string.prototype.replaceall) и связанного алгоритма `GetSubstitution`:

```js
// $1, $2, ... — ссылка на n-ю группу захвата
console.log('2024-01-15'.replace(/(\d+)-(\d+)-(\d+)/, '$3/$2/$1')); // '15/01/2024'

// другие подстановки: $& — всё совпадение целиком, $$ — буквальный доллар,
// $`  — часть строки до совпадения, $' — часть строки после совпадения,
// $<name> — именованная группа захвата
console.log('hello'.replace(/l+/, '[$&]')); // 'he[ll]o'
```

Это удобно, но и небезопасно, если строка замены строится из пользовательского ввода: если пользователь введёт `$&` в поле, которое потом попадёт в `replace` как строка замены, оно будет интерпретировано как спецсимвол, а не как буквальный текст. Если нужно вставить произвольный текст без интерпретации `$`, стоит передавать **функцию** вторым аргументом вместо строки — вызов функции получает совпадение как обычный аргумент и то, что она возвращает, вставляется буквально, без повторной обработки `$`-последовательностей.

### `split` с группами захвата — они попадают в результат

[22.1.3.34 String.prototype.split](https://262.ecma-international.org/#sec-string.prototype.split) с регулярным выражением, где есть группы захвата в круглых скобках, включает содержимое этих групп прямо в возвращаемый массив, вперемешку с фрагментами строки — это отличается от интуитивного ожидания «просто разбить по разделителю»:

```js
console.log('a1b2c3'.split(/(\d)/));
// ['a', '1', 'b', '2', 'c', '3', ''] — цифры-разделители попали в результат как отдельные элементы

console.log('a1b2c3'.split(/\d/));
// ['a', 'b', 'c', ''] — без группы захвата разделители просто выбрасываются, как ожидалось бы интуитивно
```

Это специально документированное поведение, а не побочный эффект — оно даёт способ разбить строку и одновременно сохранить, *чем именно* она была разбита, не прибегая к отдельному вызову `match`. Если такое поведение не нужно — используйте некапturирующую группу `(?:...)` вместо обычной, она в разбиении не участвует.

### Symbol-методы: как `String.prototype` делегирует работу в `RegExp.prototype`

Методы `String.prototype.match`, `.matchAll`, `.replace`, `.replaceAll`, `.search`, `.split`, если получают на вход объект с методом по соответствующему хорошо известному символу (well-known symbol), **делегируют** ему всю работу, а не реализуют логику поиска сами. Это то же самое протокольное устройство «поведение определяется наличием метода с символьным ключом», что мы разбирали в главе 18 для `Symbol.iterator` и `Symbol.hasInstance`.

`RegExp.prototype` реализует пять таких методов: [`[Symbol.match]`](https://262.ecma-international.org/#sec-regexp.prototype-%symbol.match%), [`[Symbol.matchAll]`](https://262.ecma-international.org/#sec-regexp-prototype-%symbol.matchall%), [`[Symbol.replace]`](https://262.ecma-international.org/#sec-regexp.prototype-%symbol.replace%), [`[Symbol.search]`](https://262.ecma-international.org/#sec-regexp.prototype-%symbol.search%), [`[Symbol.split]`](https://262.ecma-international.org/#sec-regexp.prototype-%symbol.split%). Именно поэтому `'text'.replace(regexpInstance, x)` работает не потому, что `String.prototype.replace` умеет распознавать регулярные выражения, а потому что она проверяет: «есть ли у второго аргумента метод `[Symbol.replace]`? если есть — вызвать его». Практическое следствие этого протокола: любой пользовательский объект, реализующий нужный символьный метод, может подставляться вместо настоящего `RegExp` везде, где ожидается «нечто похожее на регулярное выражение» — например, библиотеки могут реализовывать собственные облегчённые matcher-объекты, совместимые со стандартными строковыми методами, без создания настоящего `RegExp`.

### `Symbol.species` для регулярных выражений

Как и встроенные коллекции из будущих глав, `RegExp` поддерживает [22.2.5.3 get RegExp \[ %Symbol.species% \]](https://262.ecma-international.org/#sec-get-regexp-%symbol.species%) — при наследовании от `RegExp` методы, которые должны создавать новый объект регулярного выражения внутри себя (например, при разбиении сложного паттерна), по умолчанию используют конструктор подкласса, а не жёстко захардкоженный `RegExp`. Это тонкость, важная в основном для авторов библиотек, расширяющих `RegExp`, а не для повседневного кода.

## Итог

> [!summary] Что взять с собой
> - Строковые методы работают за счёт временного оборачивания примитива в объект (ToObject) — присвоить свойство примитиву нельзя, оно исчезает вместе с временной обёрткой
> - `.length` считает 16-битные единицы UTF-16, а не «символы» — эмодзи и редкие иероглифы занимают по 2 единицы (суррогатная пара); для подсчёта настоящих символов используйте `[...str].length` или `Intl.Segmenter`
> - Один видимый символ можно закодировать разными последовательностями кодовых точек (составная/разложенная форма) — `normalize()` перед сравнением строк из разных источников не опционален
> - `isWellFormed`/`toWellFormed` находят и чинят «битые» строки с одиночными суррогатами без пары
> - `localeCompare` сравнивает по правилам языка, а не побайтово, как `<`/`>`
> - `RegExp` с флагом `g` или `y` — объект с изменяемым состоянием (`lastIndex`): повторные вызовы `exec`/`test` на одном и том же объекте продолжают поиск с прошлой позиции, а не начинают заново — источник неочевидных багов при переиспользовании
> - `matchAll` требует флаг `g` и выбрасывает `TypeError` без него; сам `matchAll` не мутирует `lastIndex` переданного регэкспа
> - `replaceAll` требует флаг `g` у аргумента-регэкспа и тоже выбрасывает `TypeError` без него — осознанная защита от типичной ошибки
> - Строка замены поддерживает спецподстановки `$1`, `$&`, `$$` и другие — если нужно вставить произвольный текст без их интерпретации, передавайте функцию, а не строку
> - `split` с группой захвата включает захваченное в результат; без захватывающих скобок — не включает
> - Методы `String.prototype` делегируют работу в `Symbol.match`/`Symbol.replace`/`Symbol.split`/`Symbol.search`/`Symbol.matchAll` объекта-аргумента — это открытый протокол, а не жёсткая привязка к встроенному `RegExp`
