# Глава 23 · Индексированные коллекции (Array, TypedArray)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [23 Indexed Collections](https://262.ecma-international.org/#sec-indexed-collections)

Обычные массивы (`Array`) — это экзотические объекты со специальным свойством `length`, о механике которого мы уже говорили в главе 10. Типизированные массивы (`TypedArray` — общее название для `Int8Array`, `Uint32Array`, `Float64Array` и их родственников) — совсем другая конструкция: фиксированный по формату вид на кусок сырой бинарной памяти. У них общий набор методов по именам (`map`, `filter`, `slice`...), но поведение местами расходится неожиданным образом. В этой главе — то, что действительно ловит людей на практике: сортировка по умолчанию, дыры в разреженных массивах, `NaN` в поиске и разница между «мутирующими» и «неизменяющими» версиями методов.

---

## 23.1 Array — обычные массивы

### Сортировка по умолчанию — строковая, а не числовая

Самая частая практическая ловушка всей главы: [23.1.3.30 Array.prototype.sort](https://262.ecma-international.org/#sec-array.prototype.sort) без явного компаратора сравнивает элементы **как строки**, а не как числа — даже если весь массив состоит из чисел:

```js
console.log([10, 1, 2].sort());          // [1, 10, 2] — не [1, 2, 10]!
// строки '10', '1', '2' сравниваются посимвольно: '1' < '1' (равны первым символом),
// дальше у '10' есть второй символ '0', у '1' его нет — короткая строка меньше

console.log([10, 1, 2].sort((a, b) => a - b)); // [1, 2, 10] — правильно с компаратором
```

Спецификация здесь ничего не «упрощает по глупости» — просто у `sort` без аргумента нет способа узнать, что элементы предполагается сравнивать числом, а не как текст, поэтому используется универсальное строковое сравнение (через приведение каждого элемента к строке и сравнение результата операцией `<`). Практическое правило: **всегда** передавайте компаратор в `sort`, если массив содержит числа — привычка писать `arr.sort()` для чисел работает только случайно, на маленьких примерах вроде `[1, 2, 3]`, где строковый и числовой порядок совпадают.

Начиная с ES2019 спецификация требует, чтобы `sort` был **стабильным** — то есть элементы, которые компаратор считает равными, сохраняют свой исходный относительный порядок. До этого стабильность была не гарантирована, и разные движки могли переставлять "равные" элементы местами.

### `includes` находит `NaN`, `indexOf` — нет

[23.1.3.20 Array.prototype.includes](https://262.ecma-international.org/#sec-array.prototype.includes) и [Array.prototype.indexOf](https://262.ecma-international.org/#sec-array.prototype.indexof) выглядят как взаимозаменяемые способы проверить наличие элемента, но используют **разные алгоритмы сравнения** — та же тема из главы 20 про `Object.is`/`SameValue`/`SameValueZero`:

```js
console.log([NaN].indexOf(NaN));  // -1  — indexOf использует строгое равенство (===), а NaN === NaN всегда false
console.log([NaN].includes(NaN)); // true — includes использует SameValueZero, где NaN "равен" самому себе
```

Практический вывод прямой: если нужно проверить массив на присутствие `NaN` (например, результат парсинга, где что-то могло не распарситься), `indexOf`/`lastIndexOf` для этого структурно не подходят — нужен `includes`.

### Дыры в разреженном массиве: методы обращаются с ними по-разному

Массив с пропущенным элементом (например, `[1, , 3]` — запятая без значения между ней) создаёт не элемент со значением `undefined`, а настоящую **дыру** — индекс, для которого у массива вообще нет собственного свойства. Методы стандартной библиотеки обращаются с дырами непоследовательно, и это специфицированное, устойчивое поведение, а не случайность реализации:

```js
const sparse = [1, , 3];

console.log(1 in sparse); // false — индекса 1 не существует как свойства, это настоящая дыра

let count = 0;
sparse.forEach(() => count++);
console.log(count); // 2 — forEach просто пропускает дыры, не вызывая колбэк для них

const mapped = sparse.map(x => x * 2);
console.log(mapped);      // [2, <1 empty item>, 6]
console.log(1 in mapped); // false — map тоже пропускает дыру, но сохраняет её в результате как дыру

const collected = [...sparse]; // spread — как и for...of, и Array.from
console.log(collected);   // [1, undefined, 3] — дыра превращается в настоящее значение undefined

console.log(JSON.stringify(sparse)); // '[1,null,3]' — JSON вообще не умеет представлять дыры, заменяет на null
```

Правило простое: методы, унаследованные от старого дизайна массивов (`forEach`, `map`, `filter`, `reduce`, `every`, `some`) молча пропускают дыры и не вызывают колбэк. Механизмы, основанные на итераторах (`for...of`, spread-оператор `[...arr]`, `Array.from`), не различают дыру и `undefined` — они всегда читают значение через обычный доступ по индексу, который для отсутствующего свойства просто даёт `undefined`. На практике разреженные массивы — источник трудноуловимых багов; если код специально не рассчитан на работу с дырами, лучше вообще их избегать (не создавать массивы через `new Array(n)` с последующей поэлементной инициализацией не всех индексов).

### `Array(n)` создаёт дыры, `Array.of` — нет

[23.1.1.1 Array Constructor](https://262.ecma-international.org/#sec-array-constructor) имеет особый случай: если передан **ровно один** аргумент и это число, оно трактуется как длина создаваемого разреженного массива, а не как единственный элемент:

```js
console.log(Array(3).length);   // 3
console.log(0 in Array(3));     // false — это пустой разреженный массив с длиной 3, без элементов

console.log(Array.of(3));       // [3] — Array.of всегда трактует аргументы как элементы, без особого случая
```

[23.1.2.2 Array.of](https://262.ecma-international.org/#sec-array.of) специально появился, чтобы обойти эту особенность конструктора — если код должен единообразно создавать массив из произвольного числа значений (в том числе одного числового), `Array.of` предсказуем, а вызов конструктора напрямую с одним числовым аргументом — нет.

### `Array.from` — не только из массивов

[23.1.2.1 Array.from](https://262.ecma-international.org/#sec-array.from) принимает **любой** итерируемый объект (строку, `Map`, `Set`, генератор) или **массивоподобный объект** (что угодно с числовым `.length`, даже без `Symbol.iterator` — например, `arguments` или объект вида `{0: 'a', 1: 'b', length: 2}`), и опционально применяет функцию-преобразователь к каждому элементу — не нужно делать `Array.from(x).map(fn)` отдельно:

```js
console.log(Array.from('abc'));                        // ['a', 'b', 'c'] — строка итерируема
console.log(Array.from({ length: 3 }, (_, i) => i * 2)); // [0, 2, 4] — массивоподобный объект + функция-маппер
```

### Новые неизменяющие методы: `toSorted`, `toReversed`, `toSpliced`, `with`

Классические методы `sort`, `reverse`, `splice` мутируют исходный массив на месте — это исторически создавало проблему в функциональном/иммутабельном стиле программирования, где приходилось вручную клонировать массив перед вызовом (`[...arr].sort()`). ES2023 добавил зеркальные **неизменяющие** версии: [23.1.3.33 Array.prototype.toSorted](https://262.ecma-international.org/#sec-array.prototype.tosorted), [23.1.3.34 toReversed](https://262.ecma-international.org/#sec-array.prototype.toreversed), [toSpliced](https://262.ecma-international.org/#sec-array.prototype.tospliced) и [23.1.3.39 Array.prototype.with](https://262.ecma-international.org/#sec-array.prototype.with) (замена одного элемента по индексу):

```js
const arr = [3, 1, 2];

const sorted = arr.toSorted();
console.log(sorted, arr); // [1, 2, 3] [3, 1, 2] — исходный массив не тронут

const withReplaced = arr.with(1, 99);
console.log(withReplaced, arr); // [3, 99, 2] [3, 1, 2] — тоже новый массив, исходный не тронут
```

Правило именования легко запомнить: методы, начинающиеся с `to`, всегда возвращают новый массив и не трогают исходный — тот же паттерн, что и `toUpperCase`/`toString` у строк, которые никогда ничего не мутируют, потому что строки вообще неизменяемы.

### `Symbol.unscopables` — скрытые от `with` имена

[23.1.3.41 Array.prototype \[ %Symbol.unscopables% \]](https://262.ecma-international.org/#sec-array.prototype-%symbol.unscopables%) — специальный объект-список, используемый устаревшей конструкцией `with` (Annex B, глава 17), которая позволяет искать имена переменных прямо среди свойств объекта. Когда в `Array.prototype` появились новые методы вроде `keys`, `values`, `entries`, `flat`, они рисковали "затенить" уже существующий пользовательский код, который внутри блока `with (someArray)` использовал `keys` или `values` как обычные переменные. `Symbol.unscopables` — это явный список имён, которые `with` обязан **игнорировать** при поиске в объекте массива, сохраняя обратную совместимость со старым кодом. Сегодня практической ценности эта деталь почти не имеет (`with` в строгом режиме запрещён и в целом не рекомендуется), но она объясняет, зачем в принципе существует символ, о котором иначе трудно догадаться.

## 23.2–23.3 TypedArray — типизированные массивы поверх сырой памяти

Массив `Array` может содержать значения любого типа и растёт/сжимается динамически. Типизированный массив — принципиально другое устройство: это **вид** (view) на область памяти, представленную объектом [`ArrayBuffer`](https://262.ecma-international.org/#sec-arraybuffer-objects) (разбирается в главе 25), где каждый элемент занимает фиксированное число байт одного числового формата — `Int8Array`, `Uint8Array`, `Uint8ClampedArray`, `Int16Array`, `Uint16Array`, `Int32Array`, `Uint32Array`, `Float32Array`, `Float64Array`, `BigInt64Array`, `BigUint64Array`. [23.2 TypedArray Objects](https://262.ecma-international.org/#sec-typedarray-objects) описывает общий абстрактный `%TypedArray%`, от которого фактически наследуют все конкретные конструкторы — в глобальной области видимости самого `%TypedArray%` нет, обратиться к нему напрямую нельзя.

### Запись мимо диапазона не бросает исключение и не меняет длину

Ключевое структурное отличие от `Array`: длина типизированного массива жёстко привязана к размеру буфера в момент создания вида. Попытка записать по индексу за пределами этой длины — не ошибка и не расширение массива, а **молчаливо игнорируемая операция**:

```js
const ta = new Int8Array(3);
ta[10] = 5;
console.log(ta.length);  // 3 — длина не изменилась
console.log(ta[10]);     // undefined — запись не сохранилась, но и исключения не было
```

Это прямое следствие того, что типизированный массив — **экзотический объект с integer-indexed внутренним методом [[Set]]**, определённым так, что запись по индексу вне допустимого диапазона — операция, которая согласно алгоритму просто ничего не делает (не ошибка уровня движка, а специфицированное поведение).

### Числовое переполнение: обычные типы оборачиваются, `Uint8ClampedArray` — обрезается

Запись значения, не помещающегося в разрядность элемента, ведёт себя по-разному в зависимости от конкретного вида массива. Обычные целочисленные виды (`Uint8Array`, `Int16Array` и другие) применяют модульную арифметику — «оборачивают» значение, как переполнение в языках вроде C:

```js
const wrapped = new Uint8Array(1);
wrapped[0] = 300;
console.log(wrapped[0]); // 44 — это 300 % 256, значение "обернулось"
```

[`Uint8ClampedArray`](https://262.ecma-international.org/#sec-touint8clamp) — единственное исключение, специально созданное для работы с пикселями изображений (значения канала цвета 0–255): вместо оборачивания оно **обрезает (clamps)** значение до границ диапазона:

```js
const clamped = new Uint8ClampedArray(1);
clamped[0] = 300;
console.log(clamped[0]); // 255 — обрезано сверху, не обёрнуто
clamped[0] = -10;
console.log(clamped[0]); // 0 — обрезано снизу
```

Этот тип существует в первую очередь ради `CanvasRenderingContext2D` и `ImageData` в браузерном API — там переполнение цветового канала логически должно означать «максимально яркий», а не оборачиваться в случайное маленькое число.

### `%TypedArray%.prototype.sort` по умолчанию — числовая, в отличие от `Array`

Здесь поведение **прямо противоположно** обычным массивам: [`%TypedArray%.prototype.sort`](https://262.ecma-international.org/#sec-%typedarray%.prototype.sort) без компаратора сортирует **числовым** способом по возрастанию, а не превращает элементы в строки:

```js
const numTa = new Int32Array([10, 1, 2]);
numTa.sort();
console.log(Array.from(numTa)); // [1, 2, 10] — числовой порядок, без явного компаратора
```

Причина в самой природе типа: типизированный массив физически не может хранить ничего, кроме чисел одного формата, так что строковое сравнение просто не имеет смысла как поведение по умолчанию — в отличие от обычного `Array`, который в общем случае может содержать что угодно.

### Разные виды могут работать с одной и той же памятью

Поскольку типизированный массив — это лишь способ *интерпретировать* байты буфера, несколько разных представлений можно создать поверх одного и того же `ArrayBuffer`, и запись через одно представление немедленно видна через другое — потому что оба смотрят в одну и ту же память, не копируя данные:

```js
const buf = new ArrayBuffer(4);
const asBytes = new Uint8Array(buf);
const asInt32 = new Uint32Array(buf);

asBytes[0] = 1;
console.log(asInt32[0]); // 1 (на little-endian платформе — младший байт первый)
```

Подробный разбор `ArrayBuffer`, порядка байт (endianness) и `DataView` для явного контроля над этим — в главе 25 (Структурированные данные). Здесь важно только зафиксировать сам принцип: типизированные массивы — это не независимые копии данных, а окна в общую память, и это открывает как мощные возможности (эффективная передача бинарных данных без копирования), так и риск неожиданных побочных эффектов, если забыть, что два разных на вид представления смотрят в одно и то же место.

### `Uint8Array` получил методы работы с hex/base64 (недавнее дополнение)

[23.3 Uint8Array Objects](https://262.ecma-international.org/#sec-uint8array) описывает дополнительные методы, специфичные именно для `Uint8Array` (не для остальных типизированных видов) — [`toHex`](https://262.ecma-international.org/#sec-uint8array.prototype.tohex), [`toBase64`](https://262.ecma-international.org/#sec-uint8array.prototype.tobase64) и обратные статические [`Uint8Array.fromHex`](https://262.ecma-international.org/#sec-uint8array.fromhex)/[`Uint8Array.fromBase64`](https://262.ecma-international.org/#sec-uint8array.frombase64). До их появления конвертация бинарных данных в hex/base64-строку и обратно требовала либо ручного кода, либо сторонних библиотек, либо неуклюжих трюков через `Buffer` (доступный только в Node.js, не часть стандарта). Это один из немногих примеров, где стандартная библиотека ECMAScript выросла напрямую под давлением того, насколько частой была эта потребность на практике.

## Итог

> [!summary] Что взять с собой
> - `Array.prototype.sort()` без компаратора сортирует как строки, даже для чисел — `[10,1,2].sort()` даёт `[1,10,2]`; для чисел всегда нужен явный компаратор `(a,b) => a - b`
> - `sort` начиная с ES2019 гарантированно стабилен
> - `includes` находит `NaN` (через SameValueZero), `indexOf`/`lastIndexOf` — нет (через строгое `===`)
> - Дыры в разреженном массиве (`[1, , 3]`) — не то же самое, что `undefined`: `forEach`/`map`/`filter` пропускают дыры, а `for...of`/spread/`Array.from` читают их как `undefined`; JSON превращает дыры в `null`
> - `Array(n)` с одним числовым аргументом создаёт разреженный массив длины `n`; `Array.of(n)` всегда создаёт массив из одного элемента — используйте `Array.of`, если число элементов заранее неизвестно
> - `Array.from` принимает и итерируемые объекты, и массивоподобные (с `.length`, без итератора), плюс опциональную функцию-маппер вторым аргументом
> - Методы `toSorted`/`toReversed`/`toSpliced`/`with` — неизменяющие аналоги мутирующих `sort`/`reverse`/`splice`/присваивания по индексу; имя с префиксом `to` — сигнал «возвращает новый массив, исходный не трогает»
> - Типизированные массивы — вид на сырую память `ArrayBuffer`, а не независимая структура: несколько представлений могут указывать на одну и ту же память
> - Запись по индексу вне диапазона у типизированного массива молча игнорируется, не бросает исключение и не расширяет длину — в отличие от обычного `Array`
> - Целочисленные типизированные массивы оборачивают переполнение по модулю (`300` в `Uint8Array` → `44`); `Uint8ClampedArray` — единственное исключение, обрезающее значение до границ диапазона (для работы с пикселями)
> - `%TypedArray%.prototype.sort()` по умолчанию сортирует числово — в этом прямо противоположна обычному `Array.prototype.sort()`
