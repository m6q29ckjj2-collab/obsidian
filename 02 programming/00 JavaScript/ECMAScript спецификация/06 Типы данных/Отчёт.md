# Глава 6 · Типы данных и значения — отчёт

> [!info] Раздел спецификации
> [6 ECMAScript Data Types and Values](https://262.ecma-international.org/#sec-ecmascript-data-types-and-values)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Эта глава отвечает на вопрос «над чем вообще работают все те алгоритмы, которые встретятся дальше по документу». Ключевая идея, без которой остальная часть спецификации выглядит запутанной, — жёсткое разделение на два непересекающихся мира: типы, значения которых реально может хранить переменная JavaScript-программы (**языковые типы**), и типы, которые существуют только внутри текста самого стандарта как инструмент описания, но никогда не появляются в виде значения, доступного из кода (**служебные типы**). Спецификация ни разу не путает эти два мира, и умение отличать один от другого — то, что делает возможным правильно понимать любой алгоритм дальше по документу.

---

## 6.1 Типы языка

[Языковых типов](https://262.ecma-international.org/#sec-ecmascript-language-types) ровно восемь. Именно значения этих типов, и только их, может хранить переменная, свойство объекта или элемент массива в реальной работающей программе.

| Тип | Раздел | Особенность |
|---|---|---|
| Undefined | [6.1.1](https://262.ecma-international.org/#sec-ecmascript-language-types-undefined-type) | ровно одно значение |
| Null | [6.1.2](https://262.ecma-international.org/#sec-ecmascript-language-types-null-type) | ровно одно значение |
| Boolean | [6.1.3](https://262.ecma-international.org/#sec-ecmascript-language-types-boolean-type) | два значения |
| String | [6.1.4](https://262.ecma-international.org/#sec-ecmascript-language-types-string-type) | последовательность 16-битных единиц |
| Symbol | [6.1.5](https://262.ecma-international.org/#sec-ecmascript-language-types-symbol-type) | уникальные неперечисляемые ключи |
| Number | [6.1.6.1](https://262.ecma-international.org/#sec-ecmascript-language-types-number-type) | двойная точность по стандарту чисел с плавающей точкой |
| BigInt | [6.1.6.2](https://262.ecma-international.org/#sec-ecmascript-language-types-bigint-type) | целые произвольной точности |
| Object | [6.1.7](https://262.ecma-international.org/#sec-object-type) | набор свойств и внутренних методов |

> [!warning] Восемь типов, но семь возможных результатов оператора `typeof`
> Стоит сразу предупредить о ловушке, в которую попадает почти каждый, кто впервые сопоставляет эту таблицу с оператором `typeof`: результат `typeof` **не является прямым отражением** этой таблицы из восьми строк. Во-первых, для значения `null` оператор по историческим причинам (баг, зафиксированный ещё в самой первой версии языка и навсегда оставленный ради обратной совместимости) возвращает строку `'object'`, хотя формально `Null` — отдельный, самостоятельный тип. Во-вторых, для функций `typeof` возвращает строку `'function'`, которой в таблице из восьми языковых типов вообще нет — потому что "функция" с точки зрения формальной системы типов — это не отдельный тип, а объект типа `Object`, у которого дополнительно определён внутренний метод `[[Call]]` (разбирается в конце этой главы).
> ```js
> console.log(typeof null, typeof function () {});
> // object function
> ```
> Иными словами: `typeof` — практичный инструмент повседневной разработки, но не точное зеркало формальной системы типов спецификации. Опираться на него как на источник истины о том, "сколько типов в языке", не стоит.

### Строка — не то же самое, что "текст"

[6.1.4](https://262.ecma-international.org/#sec-ecmascript-language-types-string-type) определяет строку формально и весьма неожиданно для тех, кто привык думать о строках как о человекочитаемом тексте: это конечная упорядоченная последовательность **16-битных беззнаковых целых чисел**. Не символов в привычном смысле, и что особенно важно — такая последовательность **не обязана** быть корректной последовательностью UTF-16. Спецификация прямо допускает существование строк, которые физически невозможно отобразить как настоящий текст ни на одном человеческом языке:

```js
const lone = '\uD800'; // "осиротевшая" половина суррогатной пары, без парного символа
console.log(lone.length, lone.isWellFormed()); // 1 false
```

Здесь `\uD800` — это старшая половина суррогатной пары (механизм кодирования символов Юникода за пределами базовой плоскости, например большинства эмодзи, подробно разбирается в главе 22), но без своей второй половины она не соответствует ни одному настоящему символу Unicode. Тем не менее с точки зрения самого языка `lone` — совершенно валидная строка длины 1: движок не проверяет корректность UTF-16 при создании строки, эта проверка — отдельная, необязательная операция (`isWellFormed`), которую нужно вызывать явно, если она действительно нужна. Практическое следствие: любая строка, полученная из внешнего источника (пользовательский ввод, разбор бинарных данных, обрезка строки посередине эмодзи по числовому индексу), теоретически может оказаться такой "некорректной" последовательностью, и код, который рассчитывает передать строку дальше в систему, ожидающую настоящий UTF-8/UTF-16 текст (например, при записи в файл или отправке по сети), может неожиданно столкнуться с этой особенностью.

### Числовые типы — Number и BigInt формально не родственники

[6.1.6](https://262.ecma-international.org/#sec-numeric-types) объединяет `Number` и `BigInt` под общим зонтичным понятием "числовые типы" исключительно для удобства изложения — но с точки зрения формальной системы типов это два совершенно независимых типа, и у каждого — свой собственный, отдельно определённый набор арифметических и сравнивающих операций. Сложение для `Number` (алгоритм `Number::add`) и сложение для `BigInt` (`BigInt::add`) — это буквально два разных алгоритма с разными именами в тексте стандарта, а не один алгоритм, работающий с двумя представлениями одного и того же понятия "число".
 
Именно из этого формального факта — что это два разных типа с двумя разными наборами операций, а не два представления одного типа — прямо следует практическое, наблюдаемое в коде ограничение: JavaScript **намеренно** запрещает напрямую смешивать `Number` и `BigInt` в одном арифметическом выражении, вместо того чтобы неявно приводить один к другому:

```js
console.log(1n + 1n, 1n < 2, 1n == 1);
// 2n true true

try { eval('1n + 1'); } catch (e) { console.log(e.constructor.name); }
// TypeError
```

Обратите внимание на асимметрию: операции **сравнения** (`<`, `==`) между `Number` и `BigInt` работают без проблем — сравнение не обязано сохранять точность результата, оно просто отвечает "да/нет". А вот арифметическое **сложение** между ними запрещено на уровне явной проверки типов, потому что для него пришлось бы выбрать: либо округлить `BigInt` до `Number` (потеряв точность произвольной величины, ради которой `BigInt` вообще существует), либо перевести `Number` в `BigInt` (что невозможно для нецелых чисел вроде `1.5`). Спецификация сознательно отказывается выбирать между этими двумя одинаково плохими вариантами и вместо этого требует, чтобы программист сам явно привёл одно значение к типу другого перед сложением — так ошибка обнаруживается сразу, а не прячется в виде тихой потери точности где-то в середине вычислений.

### Объект — определение не через "пары ключ-значение", а через поведение

[6.1.7 Object Type](https://262.ecma-international.org/#sec-object-type) — концептуально самый важный подраздел всей главы, потому что здесь спецификация даёт определение объекта, сильно расходящееся с интуитивным "объект — это набор пар ключ-значение". Формально объект определяется через одиннадцать обязательных **внутренних методов** (внутренние методы подробно разбираются в главе 10, здесь — только их перечисление и сам принцип): получение и смена прототипа, проверка и запрет расширяемости объекта, получение дескриптора свойства, определение нового свойства, проверка наличия свойства (в том числе унаследованного), чтение значения, запись значения, удаление свойства и перечисление собственных ключей. У объектов, которые можно вызвать как функцию, добавляется ещё один метод — вызов; у тех, что можно вызвать с `new` — конструирование.

Из этого прямо следует ключевое различие, которое пронизывает буквально всю оставшуюся часть спецификации: объект называется **обычным** (ordinary), если каждый из этих внутренних методов реализован ровно тем поведением, которое задано "по умолчанию" в спецификации, и **экзотическим** (exotic), если хотя бы один метод переопределён каким-то нестандартным способом. Массив — классический пример экзотического объекта: у него переопределён внутренний метод записи свойства так, что запись в числовой индекс, превышающий текущую длину, автоматически увеличивает свойство `length`, а прямая запись в само свойство `length` может, наоборот, обрезать массив:

```js
const arr = [1, 2, 3];
Object.defineProperty(arr, 'length', { value: 1 });
console.log(arr); // [1] — переопределённое поведение [[DefineOwnProperty]] у массива обрезало содержимое
```

Обычный объект так себя вести не может в принципе — этот эффект целиком специфичен для экзотического поведения массива, зашитого именно в переопределённые внутренние методы, а не в какую-то отдельную "магию" вокруг свойства `length`.

Здесь же, в этом разделе, вводится и второе фундаментальное различие — **два несовместимых вида** собственных свойств объекта: свойство с данными (data property, имеет само значение) и свойство с аксессорами (accessor property, имеет функции-геттер и/или сеттер вместо прямого значения). Совместить оба вида в одном свойстве нельзя — у свойства либо есть `value`, либо есть `get`/`set`, третьего не дано:

```js
const o = { get computed() { return 42; } };
const d = Object.getOwnPropertyDescriptor(o, 'computed');
console.log('value' in d, 'get' in d); // false true
```

## 6.2 Служебные типы — инструментарий самого текста стандарта

[Служебные типы](https://262.ecma-international.org/#sec-ecmascript-specification-types) не существуют во время выполнения программы — это не типы значений языка, а типы, которыми спецификация пользуется **сама для себя**, чтобы формально описывать промежуточные результаты своих собственных алгоритмов. Значение служебного типа невозможно ни положить в переменную, ни получить через `typeof`, ни как-либо иначе увидеть из обычного кода — это чисто текстовый инструмент документа, а не часть исполняемой программы.

| Тип | Раздел | Зачем нужен |
|---|---|---|
| Enum | [6.2.1](https://262.ecma-international.org/#sec-enum-specification-type) | именованные константы вроде видов завершения |
| List и Record | [6.2.2](https://262.ecma-international.org/#sec-list-and-record-specification-type) | упорядоченные наборы и структуры с именованными полями |
| Set и Relation | [6.2.3](https://262.ecma-international.org/#sec-set-and-relation-specification-type) | нужны формальной модели памяти (глава 29) |
| Completion Record | [6.2.4](https://262.ecma-international.org/#sec-completion-record-specification-type) | результат абсолютно любого шага любого алгоритма |
| Reference Record | [6.2.5](https://262.ecma-international.org/#sec-reference-record-specification-type) | ещё не завершённое обращение к свойству или имени переменной |
| Property Descriptor | [6.2.6](https://262.ecma-international.org/#sec-property-descriptor-specification-type) | набор атрибутов конкретного свойства |
| Environment Record | [6.2.7](https://262.ecma-international.org/#sec-lexical-environment-and-environment-record-specification-types) | механизм областей видимости |
| Abstract Closure | [6.2.8](https://262.ecma-international.org/#sec-abstract-closure) | функция, определённая прямо внутри алгоритма |
| Data Block | [6.2.9](https://262.ecma-international.org/#sec-data-blocks) | последовательность сырых байтов для буферов |
| PrivateElement | [6.2.10](https://262.ecma-international.org/#sec-privateelement-specification-type) | приватные поля и методы классов |
| Private Name | [6.2.12](https://262.ecma-international.org/#sec-private-names) | уникальная идентичность конкретного приватного имени |

Полезность этой таблицы не в запоминании всех одиннадцати строк наизусть, а в узнавании: встретив в алгоритме дальше по спецификации незнакомое слово с заглавной буквы вроде "Reference Record" или "Environment Record", полезно сразу понимать, что речь идёт не о каком-то объекте JavaScript, а именно о служебной структуре из этой таблицы — инструменте описания, а не части языка.

Три из этих типов заслуживают отдельного, более подробного разбора, потому что напрямую объясняют конкретное наблюдаемое поведение языка.

### Reference Record — формальное объяснение всех «потерь получателя» в одном месте

[6.2.5 Reference Record](https://262.ecma-international.org/#sec-reference-record-specification-type) — служебная структура с тремя ключевыми полями: "база" (тот объект, у которого читалось свойство), "имя свойства" и "значение для получателя" (то, чем станет `this` при вызове). Ключевой, не вполне очевидный факт: вычисление выражения `obj.method` формально даёт **не саму функцию**, а именно такую Reference Record — своего рода "незавершённое обращение", которое ещё помнит, из какого объекта оно было получено.

Отсюда вырастает единое, компактное объяснение целого класса ситуаций, которые иначе выглядят как разрозненный список частных случаев "куда пропадает `this`": **любая** операция, которая извлекает из ссылки настоящее значение (то есть превращает Reference Record обратно в обычное значение функции), тем самым стирает информацию о базе — а раз базы больше нет, при последующем вызове `this` окажется `undefined` (в строгом режиме) вместо исходного объекта:

```js
const obj = { f() { return this; } };
console.log(obj.f() === obj);            // true  — вызов идёт прямо через ссылку, база сохранена
console.log((obj.f)() === obj);          // true  — скобки вокруг ссылки её саму не разрушают
console.log((0, obj.f)() === obj);       // false — оператор запятая явно извлекает значение
console.log((obj.f || obj.f)() === obj); // false — логическое ИЛИ тоже извлекает значение
```

Приём с оператором запятая `(0, obj.f)()` — не курьёзный пример ради демонстрации, а реальный, намеренный технический приём: именно так минификаторы и транспиляторы кода специально "отвязывают" вызов функции от объекта, когда по смыслу кода нужно вызвать функцию без получателя (например, чтобы гарантировать, что внутри функции `this` окажется `undefined`, а не случайно захваченным объектом).

### Property Descriptor — противоположные умолчания в двух похожих на вид операциях

[6.2.6 Property Descriptor](https://262.ecma-international.org/#sec-property-descriptor-specification-type) описывает набор атрибутов, которые есть у каждого собственного свойства объекта (перечисляемость, настраиваемость, доступность для записи). Источник регулярных, трудно диагностируемых багов — то, что значения этих атрибутов **по умолчанию** зависят от способа, которым свойство было создано, и эти умолчания оказываются прямо противоположными для двух внешне похожих операций:

```js
const a = {}; a.x = 1;                                      // обычное присваивание
const b = {}; Object.defineProperty(b, 'x', { value: 1 });  // определение через defineProperty

console.log(Object.keys(a), Object.keys(b));       // ['x'] []
console.log(JSON.stringify(b), { ...b });           // '{}' {}
```

Оба фрагмента выглядят как "просто присвоить `x` значение `1`" — но обычное присваивание `a.x = 1` создаёт свойство со всеми атрибутами, установленными в `true` (перечисляемое, настраиваемое, доступное для записи), а `Object.defineProperty` без явного указания атрибутов создаёт свойство, у которого **все** они по умолчанию `false`. Свойство `b.x` при этом технически существует и читается (`b.x === 1`), но полностью невидимо для `Object.keys`, циклов `for...in`, spread-оператора и `JSON.stringify` — все эти механизмы опираются именно на флаг перечисляемости, а он здесь по умолчанию выключен. Разработчики, впервые сталкивающиеся с `Object.defineProperty`, регулярно спотыкаются именно об это несовпадение умолчаний, ожидая, что оно ведёт себя как обычное присваивание.

### Environment Record — формальный ответ на вопрос "что такое замыкание"

[6.2.7 Lexical Environment and Environment Record](https://262.ecma-international.org/#sec-lexical-environment-and-environment-record-specification-types) вводит записи окружения — служебную структуру, лежащую в основе механизма областей видимости языка. Подробный практический разбор того, как это работает при исполнении реального кода, — тема отдельной, следующей главы (9); здесь важно зафиксировать один концептуальный момент, который часто ищут и не находят напрямую в стандарте: слова "замыкание" (closure) в тексте спецификации формально нет вовсе, как отдельного определяемого понятия. То, что в обиходе называют замыканием, — это прямое, естественное следствие всего двух простых фактов: у функции при создании сохраняется ссылка на окружение, в котором она была определена, а у самого окружения есть ссылка на "внешнее" (объемлющее) окружение. Никакого специального, отдельного механизма "замыкания" сверх этого не требуется — вся картина складывается автоматически из связного списка окружений, ссылающихся друг на друга по цепочке наружу.

### Abstract Closure — функции, которые существуют, но недостижимы из кода

[6.2.8 Abstract Closure](https://262.ecma-international.org/#sec-abstract-closure) — способ, которым спецификация описывает функцию, определённую прямо внутри текста другого алгоритма, не создавая для неё какого-либо объекта языка JavaScript. Практический пример, знакомый каждому, кто работал с промисами: внутренние обработчики, вызываемые при выполнении/отклонении промиса (разбираются в главе 27), формально описаны именно как Abstract Closure — они реально существуют и реально выполняются движком в нужный момент, но у них нет соответствующего объекта `Function`, до которого можно было бы добраться из пользовательского кода, вызвать `.toString()` или передать куда-то как значение.

## Порядок собственных ключей объекта — гарантия, а не деталь реализации

Формально полное описание этого поведения относится к главе про обычные объекты (10), но сам вопрос — "в каком порядке `for...in`/`Object.keys` перечисляют свойства" — закономерно возникает уже здесь, сразу после того, как мы увидели, что у объекта вообще есть собственные ключи разной природы (строковые и символьные). Порядок **гарантирован** спецификацией, а не оставлен "на усмотрение" реализации, и состоит из трёх последовательных групп:

1. Целочисленные индексы (строки, канонически представляющие неотрицательное целое число) — по возрастанию их числового значения
2. Остальные строковые ключи — в порядке добавления
3. Ключи-символы — в порядке добавления

```js
const sym = Symbol('s');
console.log(Reflect.ownKeys({ b: 1, 2: 2, a: 3, 1: 4, [sym]: 5, '01': 6 }).map(String));
// ['1', '2', 'b', 'a', '01', 'Symbol(s)']
```

Обратите внимание на `'01'` — этот ключ, несмотря на внешнее сходство с числом, **не считается** каноническим целочисленным индексом (каноническая форма числа не содержит незначащих ведущих нулей) и поэтому попадает не в первую группу с `'1'`/`'2'`, а во вторую, вместе с обычными строковыми ключами `'b'` и `'a'`, сохраняя свою позицию по порядку добавления. Эта деталь — источник неожиданного поведения, если код полагается на порядок ключей объекта, а среди них встречаются строки, лишь внешне похожие на числа.

## Итог

> [!summary] Что взять с собой
> - Языковых типов ровно восемь, но `typeof` — не точное зеркало этой таблицы: для `null` возвращает `'object'` по историческим причинам, а для функций — `'function'`, значения, которого в таблице типов вообще нет
> - Строка — последовательность 16-битных единиц, не обязана быть корректной UTF-16-последовательностью; `isWellFormed()` — отдельная, явная проверка этого факта
> - `Number` и `BigInt` — формально независимые типы с разными наборами операций, поэтому их арифметическое смешение (`1n + 1`) запрещено явной проверкой, а не молчаливым приведением
> - Объект определяется не как "набор пар ключ-значение", а через одиннадцать внутренних методов; переопределение хотя бы одного делает объект экзотическим (пример — массив с особым поведением `length`)
> - Свойство объекта — либо с данными (`value`), либо с аксессорами (`get`/`set`), никогда не оба сразу
> - Служебные типы (Reference Record, Environment Record, Completion Record и другие) существуют только в тексте стандарта — их нельзя положить в переменную или увидеть через `typeof`
> - Reference Record объясняет разом все случаи "потери `this`": извлечение значения из ссылки (запятая, `||`, присваивание переменной) стирает базу вызова
> - У свойства, созданного через `Object.defineProperty` без явных атрибутов, все они по умолчанию `false` — прямая противоположность обычному присваиванию, где все атрибуты `true`
> - "Замыкание" — не отдельный механизм спецификации, а естественное следствие того, что у функции есть ссылка на окружение создания, а у окружения — ссылка на внешнее
> - Порядок собственных ключей объекта гарантирован: целочисленные индексы по возрастанию, затем строки по порядку добавления, затем символы по порядку добавления — при этом `'01'` не считается целочисленным индексом
