# Глава 15 · Функции и классы — отчёт

> [!info] Раздел спецификации
> [15 ECMAScript Language: Functions and Classes](https://262.ecma-international.org/#sec-ecmascript-language-functions-and-classes)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

В языке существует около десяти разных синтаксических форм определения функций и классов — обычная функция, стрелочная функция, метод, генератор, асинхронная функция, класс и их всевозможные комбинации. Хорошая новость: почти все различия в поведении между ними сводятся всего к трём независимым параметрам, зафиксированным в момент создания функции (не вызова!): какое связывание получателя (`this`) у неё есть, создаётся ли для неё собственный объект `arguments`, и можно ли вызвать её как конструктор через `new`. Понимание этих трёх осей превращает длинный список "особенностей каждой формы" в понятную комбинаторику.

## 15.1 Списки параметров

[15.1 Parameter Lists](https://262.ecma-international.org/#sec-parameter-lists) описывает грамматику параметров функции, от которой напрямую зависит поведение уже разбиравшейся в главе 10 операции [FunctionDeclarationInstantiation](https://262.ecma-international.org/#sec-functiondeclarationinstantiation).

Ключевое здесь понятие — так называемый "простой" список параметров: список **без** значений по умолчанию, **без** остаточного параметра (`...rest`), **без** деструктуризации. Именно от этого одного условия зависит, будет ли создан **связанный** (mapped) объект `arguments` — специальный вид объекта, в котором изменение значения параметра и изменение соответствующего элемента `arguments` синхронизированы между собой в обе стороны:

```js
function simple(a, b) { a = 99; return arguments[0]; }
console.log(simple(1, 2)); // 99 — связанный объект: изменение параметра отражается в arguments

function withDefault(a = 0, b) { a = 99; return arguments[0]; }
console.log(withDefault(1, 2)); // 1 — несвязанный объект, несмотря на то что режим нестрогий
```

Обе функции написаны в нестрогом режиме, но ведут себя принципиально по-разному: `simple` имеет "простой" список параметров (без единого значения по умолчанию), и для неё создаётся связанный `arguments` — присваивание `a = 99` синхронно отражается на `arguments[0]`. У `withDefault` список параметров уже не простой (есть значение по умолчанию `a = 0`), и для неё, несмотря на нестрогий режим, создаётся **несвязанный** объект `arguments` — изменение `a` больше никак не отражается на `arguments[0]`. Важно явно зафиксировать: любое из двух условий по отдельности — либо строгий режим самой функции, либо наличие сложного (не простого) списка параметров — уже само по себе достаточно, чтобы `arguments` стал несвязанным. Это осознанное решение авторов спецификации: связывание параметров со значениями по умолчанию с элементами `arguments` создавало бы неоднозначную, трудно формализуемую семантику (что должно произойти с `arguments[0]`, если параметр так и не был передан и получил значение по умолчанию?), поэтому для любого списка параметров сложнее простого эта синхронизация просто не создаётся вовсе.

## 15.2–15.4 Функции, стрелки, методы

[15.2 Function Definitions](https://262.ecma-international.org/#sec-function-definitions) описывает обычные функции, объявленные через `function`. Их внутренний слот `[[ThisMode]]` (разбирается подробно в главе 10) принимает значение `strict` или `global` в зависимости от режима строгости кода, в котором функция синтаксически объявлена.

[15.3 Arrow Function Definitions](https://262.ecma-international.org/#sec-arrow-function-definitions) описывает стрелочные функции — единственную синтаксическую форму во всём языке с `[[ThisMode]]`, равным `lexical`. У стрелочной функции формально **нет** ни внутреннего метода `[[Construct]]` (её нельзя вызвать через `new`), ни собственного свойства `prototype`, ни собственного объекта `arguments`, ни даже слота `[[HomeObject]]` — а раз нет `[[HomeObject]]`, стрелка физически не способна использовать конструкцию `super` внутри себя, потому что `super` формально определяется именно через этот слот (подробнее — чуть ниже):

```js
const obj = { arrow: () => typeof this, method() { return typeof this; } };
console.log(obj.arrow(), obj.method()); // 'object' 'object' (в модуле было бы 'undefined' и 'object')
```

`obj.arrow()` возвращает не `this` самого `obj`, а `this` того окружения, где стрелочная функция была **синтаксически написана** — то есть `this` внешнего, объемлющего кода (объектный литерал сам по себе не создаёт новой области видимости для `this`, глава 6). А `obj.method()`, будучи обычным методом с собственным связыванием получателя, честно возвращает `obj`.

[15.4 Method Definitions](https://262.ecma-international.org/#sec-method-definitions) вводит один из важнейших для понимания наследования внутренних слотов языка — `[[HomeObject]]`: ссылку на тот объект (или прототип класса), внутри которого метод был буквально определён в исходном тексте. Именно от значения этого слота, а вовсе не от того, через какой объект метод был в итоге **вызван**, конструкция `super` берёт точку отсчёта для поиска нужного метода вверх по цепочке прототипов:

```js
const base = { greet() { return 'база'; } };
const mid = { __proto__: base, greet() { return super.greet() + '→сред'; } };
const child = { __proto__: mid, greet: mid.greet }; // тот же самый метод, тот же HomeObject

console.log(child.greet()); // 'база→сред' — super ищет от HomeObject (mid), а не от получателя вызова (child)
```

Метод `greet`, вызванный как `child.greet()`, получает получателем `child` — но `super.greet()` внутри него всё равно находит `base.greet`, потому что поиск идёт не от `child`, а от прототипа `mid` (значение `[[HomeObject]]` метода, зафиксированное ещё при его создании на объекте `mid`, а не изменившееся оттого, что тот же самый метод потом присвоили на `child`). Это же наблюдение объясняет менее очевидный факт: `super` синтаксически невозможен внутри **обычного функционального выражения** (`function() { super.x(); }`) — не потому, что это произвольный синтаксический запрет, а потому что для такой функции `[[HomeObject]]` формально просто не определён и определить неоткуда: слот выставляется исключительно для **сокращённой записи метода** (`{ method() {} }` или метод класса), а не для функций, присвоенных свойству обычным образом.

## 15.5–15.6 Генераторы

[15.5 Generator Function Definitions](https://262.ecma-international.org/#sec-generator-function-definitions) вместе с рантайм-частью [15.5.2](https://262.ecma-international.org/#sec-generator-function-definitions-runtime-semantics-evaluatebody) описывает, вероятно, самый концептуально непривычный вид функции в языке — генератор. Ключевая деталь, которую стоит подчеркнуть отдельно: тело генератора **не выполняется** в момент вызова функции-генератора — вызов лишь создаёт специальный объект генератора, приостановленный ровно перед самой первой строкой тела, и реальное выполнение кода начинается только при первом вызове `.next()`:

```js
function* g() { console.log('старт'); yield 1; }
const it = g();
console.log('создан');
it.next(); // 'создан' затем 'старт'
```

Порядок вывода наглядно демонстрирует эту "ленивость": строка `console.log('старт')` внутри тела генератора выполняется только после явного вызова `it.next()`, а не в момент вызова `g()`, хотя визуально `g()` выглядит как обычный вызов функции. Это принципиальное структурное отличие генератора от обычной функции — вызов обычной функции немедленно начинает выполнение её тела, вызов функции-генератора только подготавливает объект-генератор к будущему пошаговому выполнению.

[15.6 Async Generator Function Definitions](https://262.ecma-international.org/#sec-async-generator-function-definitions) объединяет тот же самый механизм приостановки/возобновления генератора с очередью микрозадач, лежащей в основе `await` (подробно разбирается в разделе про асинхронные функции ниже, а также в главе 27). Конструкция `for await...of` при переборе такого асинхронного генератора вызывает не обычный, а асинхронный метод перехода к следующему значению, который возвращает не сам объект `{ value, done }` напрямую, а промис, резолвящийся в такой объект — именно поэтому перебор асинхронного генератора требует `await` на каждом шаге.

## 15.7 Классы

Это, безусловно, самый насыщенный раздел всей главы. [15.7.14 Runtime Semantics: ClassDefinitionEvaluation](https://262.ecma-international.org/#sec-runtime-semantics-classdefinitionevaluation) описывает точный порядок событий при вычислении определения класса — и в этом порядке немало неочевидных на первый взгляд деталей.

### Порядок инициализации класса — пошагово

1. Создаётся отдельное окружение класса (для хранения приватных имён и, если есть, для имени самого класса — доступного внутри тела класса даже до завершения его определения)
2. Вычисляется родительский класс (если есть `extends`), на основе чего определяется прототип нового класса
3. Создаётся сам конструктор — особый экзотический объект-функция, чей слот `[[HomeObject]]` указывает на прототип класса (что и позволяет использовать `super.method()` внутри методов класса)
4. Собственные (нестатические) и статические поля и методы **вычисляются строго в порядке их объявления** в тексте класса — но с важной оговоркой: обычные (нестатические) поля лишь **регистрируются** на этом этапе и реально инициализируются **лениво**, при каждом создании нового экземпляра класса; статические же поля инициализируются немедленно, один раз, прямо здесь
5. Статические блоки (`static { ... }`) выполняются в этом же самом проходе, вперемешку со статическими полями строго в порядке их совместного объявления в тексте класса — то есть тип элемента (поле или блок) не имеет значения, важен только порядок написания в исходном коде

```js
class Demo {
  static log = [];
  static { Demo.log.push('блок 1'); }
  static field2 = (Demo.log.push('поле после блока'), 1);
  static { Demo.log.push('блок 2'); }
}
console.log(Demo.log); // ['блок 1', 'поле после блока', 'блок 2']
```

Три статических элемента — поле, блок, снова поле с побочным эффектом, снова блок — выполняются строго в том порядке, в котором они написаны в тексте класса, безо всякого разделения "сначала все поля, потом все блоки" или наоборот. Это прямое следствие пункта 4 выше: порядок объявления в исходном тексте — единственный определяющий фактор, тип конкретного элемента роли не играет.

### Производный конструктор и `super()`

Механика связывания `this` через `[[ThisBindingStatus]]` (`uninitialized` до `super()`, `initialized` после) уже подробно разбиралась в главе 9. Здесь стоит добавить важную деталь, легко упускаемую при поверхностном знакомстве: `super()` — это не просто "вызов метода-конструктора родителя" в обычном смысле вызова функции. Формально это операция, которая **реально создаёт** новый объект через внутренний метод `[[Construct]]` базового класса, причём передаёт этому вызову значение `new.target`, унаследованное от самого исходного вызова всей цепочки (операция [GetSuperConstructor](https://262.ecma-international.org/#sec-getsuperconstructor), 13.3.7.2):

```js
class Base { constructor() { console.log(new.target.name); } }
class Sub extends Base {}
new Sub(); // 'Sub' — new.target передан по цепочке super(), а не переустановлен в 'Base'
```

Хотя код конструктора `Base` реально выполняется (потому что `Sub` его не переопределяет), `new.target` внутри него равен `Sub`, а не `Base` — потому что `new.target` формально определяется не тем, чей конструктор физически исполняется прямо сейчас, а тем, **что изначально было вызвано через `new`** на самом верху цепочки, и это значение честно прокидывается через всю цепочку `super()`-вызовов без изменений. Именно этот механизм лежит в основе продвинутых паттернов вроде создания разных подтипов объекта в зависимости от того, какой именно подкласс был реально вызван — базовый конструктор в любой момент может заглянуть в `new.target`, чтобы узнать "настоящего" вызывающего.

### Поля класса и их порядок относительно `super()`

Поля класса инициализируются операцией [ClassFieldDefinitionEvaluation](https://262.ecma-international.org/#sec-runtime-semantics-classfielddefinitionevaluation) сразу в тот момент, когда `this` впервые становится по-настоящему доступным для использования — а этот момент, как уже разбиралось в главе 9, зависит от того, базовый класс или производный: для производного класса это сразу **после** вызова `super()` (до этого `this` находится в неинициализированном состоянии и попросту недоступен), а для базового класса — в самом начале выполнения конструктора, поскольку там `this` доступен с первой же строки:

```js
class Base { field = 'база'; constructor() { console.log(this.field); } }
class Derived extends Base {
  extra = 'доп';
  constructor() { super(); console.log(this.extra); }
}
new Derived();
// база
// доп
```

Порядок вывода наглядно показывает всю цепочку: вызов `super()` внутри `Derived` реально запускает конструктор `Base`, внутри которого сразу инициализируется поле `field` (`this.field` уже доступен, потому что для базового класса `this` готов с самого начала) и выполняется `console.log(this.field)`, выводя `'база'`. Только после того, как `super()` полностью завершится и вернёт управление в конструктор `Derived`, инициализируется уже собственное поле `extra` класса `Derived`, и лишь затем выполняется следующая строка `console.log(this.extra)`, выводя `'доп'`.

### Приватные поля — служебный тип, а не соглашение об именах со знаком решётки

Стоит явно развеять распространённое заблуждение: приватное поле класса (`#field`) — это **не** просто обычное свойство объекта с "особым" именем, начинающимся с `#`, как можно было бы подумать по аналогии с соглашением именования вроде `_field` в старом коде. Формально приватное имя — это отдельный **служебный тип** ("Private Name", [6.2.12](https://262.ecma-international.org/#sec-private-names), уже упоминался в главе 6), обладающий собственной строгой идентичностью, отдельной от любой строки. Доступ к приватному полю реализован через специальную операцию [MakePrivateReference](https://262.ecma-international.org/#sec-makeprivatereference) (6.2.5.9), и попытка обратиться к приватному полю на объекте, который **не является** экземпляром объявившего это поле класса, приводит к `TypeError` — а не к тихому `undefined`, как это было бы с обычным, отсутствующим свойством:

```js
class Box {
  #v = 1;
  static has(x) { return #v in x; }
  get() { return this.#v; }
}
const b = new Box();
console.log(Box.has(b), Box.has({})); // true false
try { Box.prototype.get.call({}); } catch (e) { console.log(e.constructor.name); } // TypeError
```

Синтаксис `#v in x` — специальная, отдельная форма оператора `in`, позволяющая безопасно **проверить**, есть ли у объекта конкретное приватное поле, не рискуя выбросить исключение (в отличие от прямого обращения `x.#v`, которое на объекте без этого приватного поля сразу же бросает `TypeError`). А попытка вызвать метод `get`, ожидающий `this.#v`, на объекте `{}`, у которого в принципе нет и не может быть этого приватного поля (потому что он не был создан конструктором `Box`), закономерно бросает `TypeError` — потому что операция `MakePrivateReference` явно проверяет, что переданный объект действительно обладает соответствующим приватным именем, прежде чем к нему обращаться.

### Статические блоки — единственное место снаружи методов с доступом к приватным полям без экземпляра

Блок `static { ... }` выполняется с `this`, равным самому классу (а не какому-либо экземпляру), и что особенно ценно — имеет полный доступ к приватным полям и методам класса. Это единственное место во всём языке, находящееся синтаксически **снаружи** обычных методов класса, откуда можно работать с приватными полями произвольных экземпляров без необходимости создавать хотя бы один такой экземпляр заранее — полезно, например, для сложной инициализации статических данных класса, которым требуется "подготовить" приватное состояние будущих экземпляров ещё до того, как хоть один из них появится.

## 15.8–15.9 Асинхронные функции

[15.8 Async Function Definitions](https://262.ecma-international.org/#sec-async-function-definitions) описывает функции с ключевым словом `async`. Ключевая деталь их поведения: оператор `await` внутри такой функции приостанавливает выполнение и ставит продолжение в очередь микрозадач (тот же механизм Jobs, что разбирается в главе 9 и 27) — но что важно понимать безотносительно наличия `await` вообще: **любая** `async`-функция всегда возвращает промис, даже если её тело вообще не содержит ни единого `await`:

```js
async function f() { return 1; }
console.log(f() instanceof Promise); // true — обёртка в промис происходит безусловно
```

Само ключевое слово `async` перед объявлением функции — это уже само по себе достаточное условие для того, чтобы возвращаемое значение автоматически оборачивалось в выполненный промис; наличие или отсутствие `await` внутри тела на этот факт никак не влияет.

[15.9 Async Arrow Function Definitions](https://262.ecma-international.org/#sec-async-arrow-function-definitions) описывает асинхронные стрелочные функции — они сочетают сразу оба независимых свойства: лексическое связывание получателя обычной стрелочной функции (унаследованное от объемлющего кода) и способность приостанавливаться на `await`, характерную для асинхронных функций. Это прямая иллюстрация уже заявленного в начале главы принципа: разные "формы" функций в языке — это, по сути, независимые комбинации небольшого числа базовых параметров, а не набор из десяти полностью самостоятельных, никак не связанных друг с другом сущностей.

## 15.10 Хвостовые вызовы

[15.10 Tail Position Calls](https://262.ecma-international.org/#sec-tail-position-calls) — раздел, описывающий формальное требование к оптимизации хвостовых вызовов (tail call optimization), которое существует в тексте стандарта, но крайне редко реализовано на практике. Статическая семантика [HasCallInTailPosition](https://262.ecma-international.org/#sec-static-semantics-hascallintailposition) (15.10.2) формально определяет, какие именно вызовы функций синтаксически находятся в "хвостовой позиции" (то есть являются буквально последним действием функции перед `return`, без какой-либо дальнейшей работы после возврата из вызова), а операция [PrepareForTailCall](https://262.ecma-international.org/#sec-preparefortailcall) (15.10.3) формально **обязывает** движок переиспользовать текущий фрейм стека вызовов для такого вызова вместо того, чтобы создавать новый:

```js
'use strict';
const sum = (n, acc = 0) => n === 0 ? acc : sum(n - 1, acc + n); // рекурсивный вызов в хвостовой позиции
```

Если бы это требование действительно соблюдалось всеми движками, подобная рекурсивная функция могла бы безопасно вызываться с произвольно большим `n`, никогда не переполняя стек вызовов — потому что каждый следующий рекурсивный вызов формально не добавлял бы новый кадр поверх старого, а замещал бы его. На практике же стоит явно предупредить: из всех мейнстримных движков это требование реализовал по-настоящему только один — JavaScriptCore (движок Safari); V8 (Chrome, Node.js) и SpiderMonkey (Firefox) эту часть стандарта, несмотря на формальное требование текста спецификации, не реализуют, и глубокая рекурсия даже в идеальной хвостовой позиции в этих движках по-прежнему может привести к переполнению стека. Это один из самых наглядных, показательных примеров расхождения между тем, что формально **требует** текст стандарта, и тем, что реально **делают** движки на практике — редкий, но полезный урок о том, что сама по себе спецификация не гарантирует единообразного поведения там, где реализации решают не следовать ей полностью.

## Итог

> [!summary] Что взять с собой
> - "Простой" список параметров (без дефолтов, остатка, деструктуризации) — единственное условие для связанного объекта `arguments`; строгий режим или любая сложность параметров дают несвязанный объект
> - Стрелочная функция — единственная форма с лексическим `[[ThisMode]]`; у неё нет собственного конструирования, `arguments` и `[[HomeObject]]`, поэтому в ней невозможен `super`
> - `[[HomeObject]]` задаётся только сокращённой записи метода и определяет точку отсчёта поиска для `super` — не получатель вызова, а объект, где метод синтаксически написан
> - Тело генератора не выполняется при вызове функции-генератора — только при первом `.next()`
> - Порядок инициализации полей и статических блоков класса — строго порядок объявления в тексте, тип элемента (поле или блок) роли не играет
> - `super()` реально создаёт новый объект через `[[Construct]]` базового класса, передавая `new.target` без изменений по всей цепочке
> - Поля класса инициализируются, как только `this` становится доступен: сразу после `super()` в производном классе, в самом начале конструктора в базовом
> - Приватное имя — отдельный служебный тип, а не строковое соглашение; обращение к приватному полю на "чужом" объекте даёт `TypeError`, а не `undefined`
> - `static { }` — единственное место снаружи методов, где доступны приватные поля класса без необходимости создавать экземпляр
> - Асинхронная функция всегда возвращает промис, даже если тело не содержит `await` вовсе
> - Требование переиспользовать фрейм стека для хвостового вызова формально есть в стандарте, но реализовано по-настоящему только в JavaScriptCore, не в V8 или SpiderMonkey
