# Глава 18 · Встроенные объекты: общие положения — отчёт

> [!info] Раздел спецификации
> [18 ECMAScript Standard Built-in Objects](https://262.ecma-international.org/#sec-ecmascript-standard-built-in-objects)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Эта глава короткая по объёму, но её роль в структуре всего документа непропорционально велика: здесь задаются общие конвенции, которым **безусловно** подчиняются все встроенные объекты языка — от `Object` и `Array` до `Promise`, `Map`, `Proxy` и любого другого, что встретится в главах 19–28. Не зная содержания этой главы, легко удивляться конкретным деталям поведения встроенных объектов, которые на самом деле не случайны и не специфичны для отдельного объекта, а являются прямым следствием единых, системных правил, действующих сразу для всей стандартной библиотеки.

---

## Атрибуты свойств по умолчанию — почему методы прототипов не засоряют перечисление

Ключевое общее правило, которое стоит запомнить один раз и применять ко всему: у подавляющего большинства встроенных свойств (методов прототипов, статических методов конструкторов) атрибуты по умолчанию — `[[Writable]]: true` (можно переопределить), `[[Enumerable]]: false` (не перечисляется), `[[Configurable]]: true` (можно удалить или переопределить дескриптор). Именно **неперечисляемость** — то самое свойство, которое системно отличает встроенные методы от обычных свойств, которые программист добавляет сам через простое присваивание:

```js
console.log(Object.keys(Array.prototype));                // []
console.log(Array.prototype.propertyIsEnumerable('map'));  // false
for (const k in []) console.log(k);                        // ничего не выведется
```

`Array.prototype` реально содержит десятки методов (`map`, `filter`, `slice` и остальные), но `Object.keys` над ним возвращает пустой массив — потому что все эти методы неперечисляемы, а `Object.keys` (как и `for...in`, как и spread-раскрытие объекта) опирается именно на флаг перечисляемости, чтобы решить, что показывать. Это прямое, системное объяснение практического факта, который многие воспринимают как данность, даже не задумываясь о причине: `for (const key in someArray)` никогда не проходится по встроенным методам массива, хотя формально они лежат прямо в цепочке прототипов этого массива и полностью доступны для вызова.

Отсюда же вытекает и практическое предупреждение для тех, кто пишет собственные полифиллы или расширения встроенных прототипов: добавление метода в `Array.prototype` через `Object.defineProperty` с явным `enumerable: false` не ломает `for...in` по обычным массивам — а вот наивное `Array.prototype.myMethod = function() {}` через обычное присваивание **сломало** бы, потому что обычное присваивание всегда создаёт перечисляемое свойство (глава 6), и такой самодельный метод неожиданно начал бы появляться в каждом цикле `for...in` по любому массиву во всей программе, включая сторонние библиотеки, которые ничего не знают про это добавление.

## Длина и имя функции — оба ведут себя не совсем так, как ожидается интуитивно

Каждая встроенная (да и практически любая пользовательская) функция автоматически получает два информационных свойства — `length` и `name` — и оба содержат не вполне очевидное с первого взгляда поведение.

`length` — это **не** общее количество параметров функции, как можно было бы предположить. Формально это число **обязательных** параметров, идущих до первого параметра со значением по умолчанию или до остаточного параметра (`...rest`) — то есть то место в списке параметров, где заканчивается "то, что вызывающий код обязан передать":

```js
console.log(Math.max.length);                 // 2 — не 0 (сколько бы аргументов ни принимал реально) и не Infinity
console.log(((a, b = 1, ...c) => {}).length);  // 1 — считается только a, до первого параметра со значением по умолчанию
console.log(Array.prototype.slice.length);     // 2
```

`Math.max` реально способна принять сколько угодно числовых аргументов (`Math.max(1, 2, 3, 4, 5)` работает без проблем), но `.length` при этом равно `2` — это техническая условность самой спецификации, отражающая формальное минимальное число параметров в декларации соответствующей встроенной функции, а не реальное практическое ограничение на число аргументов, которые можно передать.

`name`, в свою очередь, заполняется автоматически из синтаксического контекста присваивания — даже для функций, буквально написанных как анонимные, без единого явного имени в самом их определении. За это отвечает уже знакомая по главам 5 и 8 операция [NamedEvaluation](https://262.ecma-international.org/#sec-runtime-semantics-namedevaluation), которая выводит подходящее имя из места объявления функции, но, как уже отмечалось в главе 8, срабатывает только в конкретном, ограниченном списке синтаксических позиций:

```js
const f = () => {};
console.log(f.name); // 'f' — выведено из имени переменной, куда была присвоена анонимная стрелка

const obj = { method: function () {} };
console.log(obj.method.name); // 'method' — выведено из имени свойства объектного литерала

console.log((() => {}).bind(null).name); // 'bound ' — bind добавляет специальный префикс к имени
```

Последний пример — не опечатка: `Function.prototype.bind` формирует новое имя связанной функции, добавляя к оригинальному имени префикс `'bound '` (с пробелом на конце) — здесь исходная анонимная стрелка вообще не имела собственного имени (пустая строка), поэтому результат — буквально `'bound '` с пробелом и без ничего после него.

## Хорошо известные символы — открытый протокол расширения поведения

[6.1.5.1 Well-Known Symbols](https://262.ecma-international.org/#sec-well-known-symbols) описывает фиксированный, заранее заданный набор символьных значений, встроенных прямо в сам язык, каждый из которых при наличии на объекте одноимённого метода **переопределяет** конкретное стандартное поведение этого объекта в определённых операциях. Три таких символа уже подробно разбирались в предыдущих главах на конкретных практических примерах: `Symbol.iterator` (определяет поведение при переборе в `for...of`, глава 27), `Symbol.hasInstance` (переопределяет `instanceof`, глава 13), `Symbol.toStringTag` (влияет на результат `Object.prototype.toString.call`, глава 20):

```js
class Range {
  constructor(a, b) { this.a = a; this.b = b; }
  *[Symbol.iterator]() { for (let i = this.a; i <= this.b; i++) yield i; }
  get [Symbol.toStringTag]() { return 'Range'; }
}
const r = new Range(1, 3);
console.log([...r], Object.prototype.toString.call(r));
// [1, 2, 3] '[object Range]'
```

Но полный набор хорошо известных символов заметно шире тех трёх, что чаще всего вспоминаются: `Symbol.toPrimitive` (уже разбирался в главе 7, управляет преобразованием объекта в примитив), `Symbol.species` (позволяет подклассу указать, какой именно конструктор использовать для производных объектов — например, результата вызова `Array.prototype.map` на экземпляре подкласса массива), `Symbol.isConcatSpreadable` (влияет на то, "расплющивается" ли объект внутри `Array.prototype.concat`), `Symbol.asyncIterator` (асинхронный аналог `Symbol.iterator`, для `for await...of`, глава 27), и, пожалуй, самый неожиданный из всех — `Symbol.unscopables`.

`Symbol.unscopables` заслуживает отдельного объяснения именно потому, что это единственное официальное, документированное практическое применение конструкции `with` (уже разобранной как легаси-функциональность в главе 17 и как механизм Object Environment Record в главе 9) во всём тексте современного стандарта:

```js
console.log(Array.prototype[Symbol.unscopables]);
// { at: true, copyWithin: true, entries: true, fill: true, find: true, ... }
```

Смысл этого объекта — явный список имён методов, которые оператор `with` обязан **игнорировать** при поиске имени в объекте массива внутри `with`-блока. Практическая причина существования этого механизма — обратная совместимость: когда в `Array.prototype` со временем добавляли новые методы (например, `find`, `includes`, `at`), существовал теоретический риск, что где-то в реальном, давно написанном коде внутри блока `with (someArray) { ... }` уже использовалось имя `find` или `includes` как обычная, независимая переменная — и появление одноимённого нового метода массива могло бы неожиданно "затенить" эту переменную, молча сломав старый код. `Symbol.unscopables` — предохранительный клапан именно для такой ситуации: он явно перечисляет все методы, добавленные в `Array.prototype` уже после того, как сам механизм `with` устоялся, и гарантирует, что `with` продолжит их игнорировать, сохраняя обратную совместимость со старым кодом.

## Инварианты внутренних методов — требование ко всем объектам, а не специфика прокси

[6.1.7.3 Invariants of the Essential Internal Methods](https://262.ecma-international.org/#sec-invariants-of-the-essential-internal-methods) описывает набор формальных гарантий, которые не может нарушить ни один объект языка вообще — включая `Proxy`, уже подробно разбиравшийся в этом контексте в главе 10. Важно правильно расставить акценты: сами эти инварианты сформулированы здесь, в главе 18, как **общие** требования, применимые абсолютно ко всем объектам без исключения, а не как специфическая особенность одной лишь экзотической формы `Proxy` — просто именно у `Proxy` их легче всего случайно нарушить, потому что его поведение целиком программируется пользовательскими ловушками, и именно поэтому практический разбор нарушения инвариантов чаще всего заходит именно через примеры с `Proxy`.

```js
const frozen = Object.freeze({ x: 1 });
console.log(Object.getOwnPropertyDescriptor(frozen, 'x').configurable); // false
// повторный вызов [[GetOwnProperty]] для одного и того же неконфигурируемого свойства
// обязан вернуть один и тот же дескриптор при каждом обращении — это инвариант,
// а не случайность конкретной реализации движка
```

Например, инвариант "для неконфигурируемого свойства повторные вызовы `[[GetOwnProperty]]` обязаны возвращать один и тот же дескриптор" применим не только к `Proxy`, оборачивающему замороженный объект, но и к обычному объекту напрямую — просто для обычного объекта это требование выполняется автоматически, "само собой", в силу самой реализации `[[GetOwnProperty]]` по умолчанию (глава 10), и его никогда не приходится проверять отдельно, потому что нарушить его в принципе невозможно без явного, нестандартного переопределения поведения — то есть без превращения объекта в какой-либо экзотический вид, для которого такое нарушение стало бы в принципе физически возможным.

## Well-Known Intrinsic Objects — единая нотация для ссылок на объекты, недоступные напрямую

[6.1.7.4 Well-Known Intrinsic Objects](https://262.ecma-international.org/#sec-well-known-intrinsic-objects) вводит специальную нотацию вида `%Array.prototype%`, `%IteratorPrototype%`, `%TypedArray%` (уже встречалась ранее, в главе 23, применительно к абстрактному конструктору типизированных массивов) — способ, которым спецификация ссылается на конкретный, всегда один и тот же встроенный объект текущего реалма (глава 9), независимо от того, доступен ли этот объект напрямую по какому-либо имени из пользовательского кода. Эта нотация используется буквально всюду в главах 19–28 при описании поведения встроенных объектов, и умение узнавать её — практически полезный навык для чтения оставшейся части документа.

Особого внимания заслуживает `%IteratorPrototype%` — общий, единый прототип **всех без исключения** встроенных итераторов языка (у массива, у `Map`, у `Set`, у строки — у каждого свой конкретный "низший" прототип итератора, но все они в конце концов наследуют от одного и того же общего `%IteratorPrototype%`). Этот объект недоступен напрямую по какому-либо глобальному имени, но легко достижим косвенно, через цепочку прототипов любого реального итератора:

```js
const arrayIterProto = Object.getPrototypeOf([][Symbol.iterator]());
const mapIterProto = Object.getPrototypeOf(new Map()[Symbol.iterator]());
console.log(Object.getPrototypeOf(arrayIterProto) === Object.getPrototypeOf(mapIterProto));
// true — оба ссылаются на один и тот же общий %IteratorPrototype%
```

Именно существование этого общего прототипа делает возможным относительно недавнее добавление Iterator Helpers (подробно разбирается в главе 27) — методы `map`, `filter`, `take` и другие достаточно определить **один раз**, прямо на `%IteratorPrototype%`, чтобы они автоматически стали доступны сразу у итераторов всех встроенных коллекций языка, без необходимости дублировать реализацию для каждого вида итератора по отдельности.

## Итог

> [!summary] Что взять с собой
> - У подавляющего большинства встроенных свойств атрибут `[[Enumerable]]` равен `false` — именно поэтому методы прототипов не засоряют `for...in`, `Object.keys` и spread-раскрытие обычных объектов и массивов
> - Добавление собственного метода в `Array.prototype` через `defineProperty` с явным `enumerable: false` безопасно; через обычное присваивание — ломает `for...in` по всем массивам программы
> - `length` функции считает только обязательные параметры до первого со значением по умолчанию или остаточного — не общее число параметров
> - `name` автоматически выводится через `NamedEvaluation` из синтаксического контекста присваивания, даже для анонимных функций; `bind()` добавляет к имени префикс `'bound '`
> - Хорошо известных символов заметно больше трёх самых очевидных — есть ещё `Symbol.toPrimitive`, `Symbol.species`, `Symbol.isConcatSpreadable`, `Symbol.asyncIterator`, `Symbol.unscopables`
> - `Symbol.unscopables` — единственное официальное практическое применение `with` во всём современном стандарте: список имён методов, которые `with` обязан игнорировать ради обратной совместимости
> - Инварианты внутренних методов — общее требование ко всем объектам языка, а не специфика одного лишь `Proxy`; на обычных объектах они соблюдаются автоматически и незаметно
> - Нотация `%Имя%` (Well-Known Intrinsic Objects) ссылается на конкретный встроенный объект текущего реалма независимо от доступности по прямому имени
> - `%IteratorPrototype%` — единый общий прототип всех встроенных итераторов языка; именно на нём определены Iterator Helpers, поэтому они автоматически доступны у итераторов любых встроенных коллекций
