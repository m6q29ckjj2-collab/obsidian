# Глава 21 · Числа и даты — отчёт

> [!info] Раздел спецификации
> [21 Numbers and Dates](https://262.ecma-international.org/#sec-numbers-and-dates)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Четыре объекта: [Number](https://262.ecma-international.org/#sec-number-objects), [BigInt](https://262.ecma-international.org/#sec-bigint-objects), [Math](https://262.ecma-international.org/#sec-math-object), [Date](https://262.ecma-international.org/#sec-date-objects). Числа кажутся простой темой, пока не столкнёшься с одной из классических ловушек — а `Date` устроен неожиданно сложнее, чем выглядит снаружи.

## 21.1 Number

### Number.isInteger — не то же самое, что «похоже на целое»

[Number.isInteger](https://262.ecma-international.org/#sec-number.isinteger) проверяет, что значение — действительно целое число типа Number, без всякого приведения типов. Это отличается от того, что часто пишут вручную через `x % 1 === 0`.

```js
console.log(Number.isInteger(5));      // true
console.log(Number.isInteger(5.0));    // true — 5.0 и 5 это одно и то же значение
console.log(Number.isInteger(5.5));    // false
console.log(Number.isInteger('5'));    // false — строка, приведения не происходит
console.log(Number.isInteger(NaN));    // false
console.log(Number.isInteger(Infinity)); // false
```

Обратите внимание на третью строку: `Number.isInteger('5')` даёт `false`, хотя строку явно можно было бы превратить в целое число. Это осознанное решение — метод отвечает строго на вопрос «это значение уже целое число», а не «может ли оно стать целым числом».

### Number.isSafeInteger — граница, за которой числа теряют точность

[Number.isSafeInteger](https://262.ecma-international.org/#sec-number.issafeinteger) — более узкая проверка, чем `isInteger`. «Безопасное» целое число — это такое, которое можно представить точно, и при этом соседнее с ним число (на единицу больше или меньше) тоже представляется точно и отличается от него. Дело в том, что числа типа Number хранятся в формате двойной точности (уже разбирался в главе 5 через понятие математических значений), и, начиная с определённой величины, соседние целые числа начинают «сливаться» в одно и то же представление.

```js
console.log(Number.MAX_SAFE_INTEGER);              // 9007199254740991
console.log(Number.isSafeInteger(Number.MAX_SAFE_INTEGER));     // true
console.log(Number.isSafeInteger(Number.MAX_SAFE_INTEGER + 1)); // false — граница пройдена
console.log(Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2); // true! соседние числа слились
```

Последняя строка — не опечатка. За пределами `MAX_SAFE_INTEGER` арифметика с целыми числами становится ненадёжной: два разных математических результата могут дать одно и то же значение типа Number. Если ваш код работает с очень большими целыми числами (например, идентификаторами баз данных, которые превышают 9 квадриллионов), решение — использовать `BigInt`, а не обычные числа.

### Number.EPSILON — правильный способ сравнивать дробные числа

Классическая проблема с плавающей запятой:

```js
console.log(0.1 + 0.2 === 0.3); // false!
console.log(0.1 + 0.2);         // 0.30000000000000004
```

Это не баг JavaScript, а свойство двоичного представления дробных чисел (уже разбирался в главе 5) — та же проблема существует в любом языке, использующем стандарт двойной точности. [Number.EPSILON](https://262.ecma-international.org/#sec-number.epsilon) — наименьшая разница между `1` и следующим представимым числом больше `1`. Стандартный приём — сравнивать числа не на точное равенство, а с допуском:

```js
function almostEqual(a, b) {
  return Math.abs(a - b) < Number.EPSILON;
}
console.log(almostEqual(0.1 + 0.2, 0.3)); // true
```

Практическое правило: **никогда** не сравнивайте результаты арифметики с дробными числами через `===`. Всегда используйте сравнение с допуском.

### toFixed — округление работает не всегда так, как ожидается

[Number.prototype.toFixed](https://262.ecma-international.org/#sec-number.prototype.tofixed) форматирует число с фиксированным числом знаков после запятой. Кажется простым, но из-за той же двоичной природы чисел результат иногда удивляет:

```js
console.log((1.005).toFixed(2)); // '1.00', а не '1.01', как ожидалось!
```

Причина в том, что число `1.005` физически не может быть представлено точно в двоичной системе — реально хранится значение чуть меньше `1.005`, и округление честно работает с этим реальным значением, а не с тем, что вы написали в исходном коде. Если вам критична денежная арифметика с точным округлением, `toFixed` — не лучший инструмент; правильнее работать в целых копейках/центах или использовать `BigInt`.

## 21.2 BigInt

Мы уже разбирали BigInt в главе 6 (как отдельный языковой тип) и в главе 7 (правила смешения с обычными числами). Здесь — две специфичные функции, о которых редко вспоминают.

[BigInt.asIntN](https://262.ecma-international.org/#sec-bigint.asintn) и [BigInt.asUintN](https://262.ecma-international.org/#sec-bigint.asuintn) обрезают значение произвольной точности до заданного числа бит, имитируя переполнение фиксированного целочисленного типа — то, что происходит в языках вроде C при работе с `int32` или `uint64`.

```js
console.log(BigInt.asIntN(8, 200n));   // -56n — переполнение 8-битного знакового числа
console.log(BigInt.asUintN(8, 200n));  // 200n — влезает в 8-битное беззнаковое
console.log(BigInt.asIntN(32, 2n ** 31n)); // -2147483648n — переполнение 32-битного знакового
```

Эти функции нужны редко — в основном при реализации бинарных протоколов или криптографических алгоритмов, где важна точная имитация переполнения фиксированной разрядности.

## 21.3 Math

Math — не конструктор (нельзя написать `new Math()`), а готовый объект-«пространство имён» с математическими функциями и константами. Стоит выделить несколько мест, где интуиция подводит.

### Math.max и Math.min без аргументов

```js
console.log(Math.max()); // -Infinity — не 0, не NaN, не undefined
console.log(Math.min()); //  Infinity
```

Это логично, если задуматься: `-Infinity` — нейтральный элемент для операции максимума (любое число больше него), `Infinity` — для минимума. Но интуитивно первое, чего ожидаешь, — это `0` или ошибку.

### Math.max с одним NaN портит весь результат

```js
console.log(Math.max(1, NaN, 3)); // NaN
```

Один нечисловой аргумент делает весь результат нечисловым, независимо от остальных значений. Если вы находите максимум в массиве, где могут быть пропуски данных (`NaN`), отфильтруйте их заранее через `Number.isFinite`, иначе весь расчёт «заразится».

### Math.random — не криптографически безопасен

[Math.random](https://262.ecma-international.org/#sec-math.random) возвращает псевдослучайное число от 0 (включительно) до 1 (исключительно). Стандарт **явно не гарантирует** качество генератора случайных чисел — реализация вправе использовать любой алгоритм, включая предсказуемые. Для паролей, токенов сессии, криптографических ключей — никогда не используйте `Math.random`, только `crypto.getRandomValues` (это API из отдельного стандарта Web Crypto, не из ECMA-262, но именно оно даёт криптографически стойкую случайность).

### Math.trunc против Math.floor — разница на отрицательных числах

```js
console.log(Math.floor(-4.5)); // -5 — округление вниз (к меньшему числу)
console.log(Math.trunc(-4.5)); // -4 — отбрасывание дробной части (к нулю)
console.log(Math.floor(4.5));  // 4  — на положительных числах разницы нет
console.log(Math.trunc(4.5));  // 4
```

Если вам нужно именно «отбросить дробную часть», а не «округлить вниз к меньшему целому», используйте `Math.trunc`, а не `Math.floor` — на отрицательных числах они дают разный результат.

## 21.4 Date

`Date` — самый сложный из четырёх объектов этой главы, и большая часть путаницы происходит из-за того, что многие методы работают с **локальным** временем машины пользователя, а другие — с **UTC**, и их легко перепутать.

### Как устроено внутреннее хранение

Внутри `Date` хранит **одно число** — количество миллисекунд, прошедших с 1 января 1970 года по UTC (полночь). Это называется значением времени, и оно не зависит от часового пояса — часовой пояс влияет только на то, как это число **отображается** методами `get*` без приставки UTC.

```js
const d = new Date(0);
console.log(d.getTime());        // 0 — миллисекунды с начала эпохи, всегда одинаково
console.log(d.toISOString());    // '1970-01-01T00:00:00.000Z' — UTC-представление, тоже всегда одинаково
console.log(d.getHours());       // зависит от часового пояса машины, где выполняется код!
console.log(d.getUTCHours());    // 0 — всегда одинаково, не зависит от локали
```

Практическое правило: если вы храните дату в базе данных, передаёте её по сети или сравниваете даты между пользователями в разных часовых поясах — используйте `getTime()` (число) или `toISOString()` (строка в UTC). Методы без приставки UTC (`getHours`, `getDate`, `getMonth` и подобные) годятся только для отображения даты **этому конкретному пользователю** в его локальном времени.

### TimeClip — почему у дат есть предел

[TimeClip](https://262.ecma-international.org/#sec-timeclip) — внутренняя операция, которая обрезает значение времени, если оно выходит за допустимый диапазон, и заменяет его на `NaN` (это делает саму дату «недействительной»).

```js
console.log(new Date(8.64e15).getTime());   // 8640000000000000 — граничное значение, ещё работает
console.log(new Date(8.64e15 + 1).getTime()); // NaN — уже за пределами диапазона
console.log(new Date('чепуха').getTime());    // NaN — невозможно разобрать
console.log(isNaN(new Date('чепуха')));       // true — так проверяют «недействительную» дату
```

Диапазон дат ограничен примерно 273 000 годами в обе стороны от 1970 года — этого достаточно для практически любой задачи, но знать о существовании границы полезно, если вы работаете с очень далёкими датами (например, в астрономических расчётах).

### Date.parse — самая ненадёжная часть всей главы

[Date.parse](https://262.ecma-international.org/#sec-date.parse) (и эквивалентный `new Date(строка)`) пытается разобрать строку с датой. Стандарт **гарантирует** только один точный формат — расширенный ISO 8601 (`'2024-01-15T10:30:00.000Z'`). Для любого другого формата поведение **зависит от реализации** — разные движки могут разобрать одну и ту же нестандартную строку по-разному или не разобрать вовсе.

```js
console.log(new Date('2024-01-15T10:30:00.000Z')); // работает везде одинаково — это стандартный формат
console.log(new Date('15 января 2024'));            // может сработать в одном движке и дать NaN в другом
console.log(new Date('01/15/2024'));                // американский формат, тоже не гарантирован стандартом,
                                                      // хотя на практике почти все движки его понимают
```

Практическое правило: если строка с датой приходит откуда-то извне (API, пользовательский ввод, файл), никогда не передавайте её напрямую в `new Date(...)`, если не уверены, что она в формате ISO 8601. Лучше разобрать её вручную по известному формату (`Date.UTC(год, месяц, день, ...)`) или использовать библиотеку, гарантирующую единообразный разбор.

### Date и приведение типов — единственный тип с особым поведением

Мы уже разбирали это в главе 7, но стоит закрепить как практический факт: `Date` — единственный встроенный тип, у которого приведение к примитиву без явного указания (хинт «по умолчанию», уже разбирался при обсуждении `ToPrimitive`) трактуется как строковое, а не числовое.

```js
const d = new Date();
console.log(d + '');       // строка — человекочитаемое представление даты
console.log(d - 0);        // число — миллисекунды с начала эпохи
console.log(+d);           // число — то же самое, унарный плюс запрашивает числовой хинт явно
console.log(d.valueOf());  // число — самый явный и надёжный способ получить миллисекунды
```

Если вам нужно получить число миллисекунд из объекта `Date`, самый явный и понятный способ — `d.getTime()` или `d.valueOf()` (они эквивалентны), а не полагаться на неявное приведение через арифметические операторы.

## Итог

> [!success] Что забирать
> - `Number.isInteger` не приводит тип: строка `'5'` не считается целым числом, хотя выглядит как одно
> - `Number.isSafeInteger` проверяет границу, за которой соседние целые числа начинают представляться одинаково — арифметика теряет точность
> - Никогда не сравнивайте результаты арифметики с дробными числами через `===`; используйте допуск через `Number.EPSILON`
> - `toFixed` округляет реальное двоичное значение числа, а не то, что написано в исходном коде — не подходит для точной денежной арифметики
> - `BigInt.asIntN`/`asUintN` имитируют переполнение фиксированной разрядности, как в языках с целыми типами
> - `Math.max()` без аргументов даёт `-Infinity`, `Math.min()` — `Infinity`; один `NaN` среди аргументов портит весь результат
> - `Math.random` не криптографически безопасен — для паролей и токенов нужен отдельный API
> - `Math.trunc` отбрасывает дробную часть к нулю, `Math.floor` округляет вниз — на отрицательных числах результат разный
> - `Date` хранит одно число — миллисекунды с начала эпохи по UTC; методы без приставки UTC зависят от часового пояса машины
> - Значение времени ограничено диапазоном примерно 273 000 лет; выход за пределы даёт недействительную дату (NaN)
> - `Date.parse` гарантированно разбирает только расширенный формат ISO 8601 — остальные форматы зависят от движка
> - `Date` — единственный тип, где приведение без явного хинта трактуется как строковое; для получения числа используйте `getTime()`
