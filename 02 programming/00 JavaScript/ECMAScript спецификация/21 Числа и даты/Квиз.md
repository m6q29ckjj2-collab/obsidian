> [!question] Что вернёт `Number.isInteger('5')`?
> a) `true`
> b) `false`
> c) выбросит `TypeError`
> d) `5`
>> [!success]- Answer
>> b) `false`
>> `isInteger` не приводит аргумент к числу — строка не подходит под проверку, даже если выглядит как целое число

> [!question] Что выведет код?
> ```js
> console.log(Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2);
> ```
>> [!success]- Answer
>> `true`
>> За пределами безопасной границы (2^53 − 1) соседние математические результаты сливаются в одно и то же значение типа Number — целые числа там уже не представлены с шагом 1

> [!question] Что проверяет `Number.isSafeInteger`, чего не проверяет обычный `Number.isInteger`?
> a) что число положительное
> b) что число находится в границах точного представления соседних целых
> c) что число меньше `Number.MAX_VALUE`
> d) ничего, это одна и та же проверка
>> [!success]- Answer
>> b) что число находится в границах точного представления соседних целых
>> `isInteger` лишь проверяет отсутствие дробной части; `isSafeInteger` дополнительно гарантирует, что рядом с этим числом нет коллизий с соседними целыми

> [!question] Почему `0.1 + 0.2 === 0.3` возвращает `false`?
>> [!success]- Answer
>> Потому что дробные числа хранятся в двоичном формате с ограниченной точностью, и `0.1`, `0.2`, `0.3` не представимы в нём точно
>> Это свойство формата IEEE 754 double, а не ошибка реализации языка — для сравнения дробных результатов арифметики нужен допуск (`Number.EPSILON`), а не строгое равенство

> [!question] Что выведет код?
> ```js
> console.log((1.005).toFixed(2));
> ```
> a) `'1.01'`
> b) `'1.00'`
> c) `'1.005'`
> d) выбросит ошибку
>> [!success]- Answer
>> b) `'1.00'`
>> Число `1.005` физически не представимо точно в двоичном формате — ближайшее хранимое значение чуть меньше `1.005`, поэтому округление честно даёт `1.00`, вопреки интуитивному ожиданию

> [!question] Для чего нужны `BigInt.asIntN` и `BigInt.asUintN`?
> a) для конвертации BigInt в обычное число
> b) для имитации переполнения фиксированной битовой разрядности
> c) для сравнения двух BigInt
> d) для округления BigInt
>> [!success]- Answer
>> b) для имитации переполнения фиксированной битовой разрядности
>> Полезно там, где нужно точно воспроизвести поведение целочисленных типов вроде int8/uint32 — например, в бинарных протоколах и криптографии

> [!question] Что выведет код?
> ```js
> console.log(BigInt.asIntN(8, 200n));
> ```
> a) `200n`
> b) `-56n`
> c) `0n`
> d) выбросит `RangeError`
>> [!success]- Answer
>> b) `-56n`
>> 200 не помещается в знаковые 8 бит (диапазон −128…127); значение переполняется точно так же, как переполнялся бы `int8_t` в языке C

> [!question] Что вернёт `Math.max()`, вызванный без аргументов?
> a) `undefined`
> b) `NaN`
> c) `-Infinity`
> d) `0`
>> [!success]- Answer
>> c) `-Infinity`
>> Это нейтральный элемент операции максимума: любое реальное число больше `-Infinity`, так что добавление первого аргумента сразу его вытесняет. У `Math.min()` симметрично — `Infinity`

> [!question] Что вернёт `Math.max(1, 2, NaN, 3)`?
> a) `3`
> b) `NaN`
> c) `2`
> d) `undefined`
>> [!success]- Answer
>> b) `NaN`
>> Один `NaN` среди аргументов «отравляет» весь результат — сравнение с `NaN` всегда даёт `false`, поэтому итоговое значение тоже становится `NaN`

> [!question] Спецификация гарантирует, что `Math.random()` криптографически надёжен
>> [!success]- Answer
>> False
>> Спецификация не предписывает конкретный алгоритм — реализация вправе использовать даже предсказуемый генератор. Для паролей, токенов и ключей нужен `crypto.getRandomValues` или аналог, а не `Math.random`

> [!question] Что выведет код?
> ```js
> console.log(Math.floor(-4.5), Math.trunc(-4.5));
> ```
> a) `-5 -5`
> b) `-4 -4`
> c) `-5 -4`
> d) `-4 -5`
>> [!success]- Answer
>> c) `-5 -4`
>> `floor` всегда округляет вниз к меньшему числу; `trunc` просто отбрасывает дробную часть, двигаясь к нулю. На отрицательных числах эти две стратегии дают разный результат

> [!question] Что физически хранится внутри объекта `Date`?
> a) три отдельных числа: год, месяц, день
> b) строка в формате ISO 8601
> c) одно число — миллисекунды с начала эпохи в UTC
> d) объект с полями часового пояса
>> [!success]- Answer
>> c) одно число — миллисекунды с начала эпохи в UTC
>> Всё остальное (локальные getter'ы, форматирование, часовой пояс) — это вычисления поверх этого единственного внутреннего числа

> [!question] Методы `Date.prototype` без приставки UTC (например, `getHours`) зависят от часового пояса машины, на которой выполняется код
>> [!success]- Answer
>> True
>> Методы с приставкой UTC (`getUTCHours` и т.д.) всегда возвращают одинаковый результат независимо от локальных настроек — именно их стоит использовать, когда нужна воспроизводимость между машинами

> [!question] Что произойдёт со значением времени, выходящим за допустимый диапазон дат (~273 000 лет от эпохи)?
> a) выбросится `RangeError`
> b) значение будет обрезано до границы диапазона
> c) операция TimeClip заменит его на `NaN`, дата станет недействительной
> d) значение останется как есть
>> [!success]- Answer
>> c) операция TimeClip заменит его на `NaN`, дата станет недействительной
>> Проверка `isNaN(date.getTime())` — стандартный способ узнать, валиден ли объект `Date`

> [!question] `Date.parse` гарантированно одинаково разбирает любую строку с датой во всех движках
>> [!success]- Answer
>> False
>> Гарантирован только расширенный формат ISO 8601 (например, `'2024-01-15T10:30:00.000Z'`). Разбор произвольных «человеческих» форматов дат оставлен на усмотрение реализации и может отличаться между движками

> [!question] Что выведет код?
> ```js
> const d = new Date();
> console.log(typeof (d + ''), typeof (d - 0), typeof +d);
> ```
> a) `string string string`
> b) `string number number`
> c) `number number number`
> d) `string string number`
>> [!success]- Answer
>> b) `string number number`
>> `Date` — единственный встроенный тип, у которого приведение без явного хинта (`d + ''`, оператор `+` с не-числом) трактуется как строковое по умолчанию. Но арифметические операторы (`-`, унарный `+`) всё равно вызывают числовое приведение

> [!question] Какой способ считается самым надёжным для явного получения числа миллисекунд из объекта `Date`, не полагаясь на неявное приведение типов?
> a) `String(date)`
> b) `date + 0`
> c) `date.getTime()` или `date.valueOf()`
> d) `JSON.stringify(date)`
>> [!success]- Answer
>> c) `date.getTime()` или `date.valueOf()`
>> Явный вызов метода не зависит от контекстных правил ToPrimitive и однозначно возвращает число — рекомендуемая практика вместо неявных приведений вроде `date - 0`
