> [!question] Можно ли напрямую прочитать байт из `ArrayBuffer`, не создавая поверх него `TypedArray` или `DataView`?
>> [!success]- Answer
>> False
>> `ArrayBuffer` — непрозрачный блок памяти без собственного представления о том, какие числа в нём хранятся. Доступ возможен только через вид (`TypedArray`/`DataView`) поверх него

> [!question] Когда нужно указать опцию `maxByteLength` для растяжимого `ArrayBuffer`?
> a) при каждом вызове `resize()`
> b) при создании буфера
> c) это опционально и не влияет на поведение
> d) нельзя указать вообще, растяжимость определяется автоматически
>> [!success]- Answer
>> b) при создании буфера
>> Это позволяет движку сразу зарезервировать нужный диапазон памяти; попытка `resize()` за пределы заранее объявленного максимума — ошибка

> [!question] Что происходит с исходным буфером после вызова `buf.transfer()`?
> a) ничего, буфер продолжает работать как прежде
> b) буфер отсоединяется (detached становится true), его byteLength становится 0
> c) буфер удаляется из памяти немедленно, обращение к нему выбрасывает исключение
> d) буфер становится доступным только для чтения
>> [!success]- Answer
>> b) буфер отсоединяется (detached становится true), его byteLength становится 0
>> Содержимое переносится в новый объект `ArrayBuffer`, а исходный остаётся существовать как пустое, непригодное для использования значение

> [!question] Зачем нужен механизм `transfer()` с отсоединением исходного буфера, а не просто копирование?
> a) чтобы сэкономить место на диске
> b) чтобы безопасно передавать большие бинарные данные между потоками без копирования, гарантируя единственного владельца памяти
> c) это требование браузерной безопасности, не связанное с производительностью
> d) чтобы данные автоматически шифровались
>> [!success]- Answer
>> b) чтобы безопасно передавать большие бинарные данные между потоками без копирования, гарантируя единственного владельца памяти
>> Раз исходный буфер гарантированно становится недоступен, можно безопасно передать саму память другому потоку без риска гонки данных

> [!question] Чем `SharedArrayBuffer` принципиально отличается от обычного `ArrayBuffer` в контексте многопоточности?
> a) ничем, они полностью взаимозаменяемы
> b) он реально виден и доступен нескольким потокам одновременно, а не копируется/передаётся с отсоединением
> c) он работает быстрее для однопоточного кода
> d) он не поддерживает типизированные массивы поверх себя
>> [!success]- Answer
>> b) он реально виден и доступен нескольким потокам одновременно, а не копируется/передаётся с отсоединением
>> Это открывает возможность гонки данных, если запись не координируется через `Atomics`

> [!question] Работают ли методы вроде `Atomics.add` и `Atomics.load` с обычным (не Shared) `ArrayBuffer`?
>> [!success]- Answer
>> True
>> Спецификация ослабила это требование — атомарность операции полезна сама по себе даже без реального параллелизма. Но `Atomics.wait`/`notify` требуют именно `SharedArrayBuffer`

> [!question] Почему `Atomics.wait` требует именно `SharedArrayBuffer`, а не работает с обычным `ArrayBuffer`, как `Atomics.add`?
> a) это ограничение производительности
> b) `wait` блокирует текущий поток в ожидании, пока другой поток изменит значение — блокировка бессмысленна без настоящего другого потока
> c) обычный ArrayBuffer не поддерживает Int32Array
> d) это устаревшее ограничение, которое скоро уберут
>> [!success]- Answer
>> b) `wait` блокирует текущий поток в ожидании, пока другой поток изменит значение — блокировка бессмысленна без настоящего другого потока
>> `Atomics.notify` — парный метод, «будящий» ожидающий поток после изменения значения

> [!question] Какой порядок байт (endianness) использует `DataView` по умолчанию, без явного указания третьего аргумента?
> a) little-endian
> b) big-endian
> c) зависит от платформы (native order)
> d) DataView не работает с порядком байт
>> [!success]- Answer
>> b) big-endian
>> Это отличается от типизированных массивов, которые всегда читают/пишут в native order платформы (обычно little-endian) — смешивать оба подхода над одним буфером без явного учёта порядка опасно

> [!question] Что выведет код?
> ```js
> console.log(JSON.stringify(undefined), typeof JSON.stringify(undefined));
> ```
> a) `'undefined' 'string'`
> b) `undefined 'undefined'`
> c) `null 'object'`
> d) выбросит `TypeError`
>> [!success]- Answer
>> b) `undefined 'undefined'`
>> `JSON.stringify(undefined)` возвращает само значение `undefined`, а не строку — исключение из общего правила «stringify всегда даёт строку»

> [!question] Что выведет код?
> ```js
> console.log(JSON.stringify({ a: 1, b: function() {} }));
> console.log(JSON.stringify([1, function() {}, 2]));
> ```
> a) `'{"a":1,"b":null}'` и `'[1,null,2]'`
> b) `'{"a":1}'` и `'[1,null,2]'`
> c) `'{"a":1}'` и `'[1,2]'`
> d) выбросит `TypeError` в обоих случаях
>> [!success]- Answer
>> b) `'{"a":1}'` и `'[1,null,2]'`
>> В объекте свойство с функцией как значением пропускается целиком; в массиве место функции занимает `null`, потому что длина массива должна сохраниться

> [!question] Что произойдёт при вызове `JSON.stringify` на объекте с циклической ссылкой на самого себя?
> a) программа зависнет в бесконечной рекурсии
> b) выбросится `TypeError`
> c) циклическая ссылка будет проигнорирована и заменена на `null`
> d) вернётся `undefined`
>> [!success]- Answer
>> b) выбросится `TypeError`
>> Алгоритм отслеживает уже посещённые структуры и явно прерывается с ошибкой, а не уходит в бесконечную рекурсию

> [!question] Что делает `JSON.stringify`, если у сериализуемого объекта есть метод `toJSON`?
> a) игнорирует его и сериализует объект как обычно
> b) вызывает `toJSON()` и сериализует то, что он вернул, вместо самого объекта
> c) выбрасывает ошибку, потому что toJSON — зарезервированное имя
> d) добавляет результат toJSON как дополнительное свойство
>> [!success]- Answer
>> b) вызывает `toJSON()` и сериализует то, что он вернул, вместо самого объекта
>> Именно так `Date` превращается в ISO-строку при сериализации — у `Date.prototype` есть собственный `toJSON`, вызывающий `toISOString()`

> [!question] Что выведет код?
> ```js
> console.log(JSON.stringify({ a: 1, b: 2 }, (key, value) => key === 'b' ? undefined : value));
> ```
> a) `'{"a":1,"b":2}'`
> b) `'{"a":1}'`
> c) `'{}'`
> d) выбросит ошибку
>> [!success]- Answer
>> b) `'{"a":1}'`
>> Функция-replacer вызывается для каждого свойства; возврат `undefined` исключает это свойство из результата

> [!question] Что делает второй аргумент-функция, переданный в `JSON.parse` (reviver)?
> a) фильтрует, какие ключи попадут в результат
> b) трансформирует каждое разобранное значение снизу вверх сразу при разборе
> c) определяет порядок ключей в результате
> d) ничего не делает без явного вызова
>> [!success]- Answer
>> b) трансформирует каждое разобранное значение снизу вверх сразу при разборе
>> Позволяет изменить значения на лету — например, привести числовые строки к датам — не проходя дерево заново после парсинга

> [!question] Зачем нужны `JSON.rawJSON`/`JSON.isRawJSON`?
> a) чтобы ускорить сериализацию больших объектов
> b) чтобы вставить число в вывод буквальным текстом, минуя потерю точности при прохождении через тип Number
> c) чтобы проверить, является ли строка валидным JSON
> d) чтобы сериализовать BigInt напрямую без ошибок
>> [!success]- Answer
>> b) чтобы вставить число в вывод буквальным текстом, минуя потерю точности при прохождении через тип Number
>> Актуально для очень больших чисел (например, ID из базы данных), которые не помещаются в безопасный диапазон целых чисел JavaScript без потери точности

> [!question] Какой из двух объектов реально является объектом-неймспейсом со статическими методами, а не конструктором: `JSON` и `Atomics`?
>> [!success]- Answer
>> Оба
>> Ни `JSON`, ни `Atomics` нельзя вызвать через `new` — это объекты-контейнеры для набора связанных статических функций, а не фабрики экземпляров
