# Глава 25 · Структурированные данные (ArrayBuffer, DataView, Atomics, JSON)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [25 Structured Data](https://262.ecma-international.org/#sec-structured-data)

Эта глава объединяет две на первый взгляд не связанные темы: низкоуровневую работу с сырой бинарной памятью (`ArrayBuffer`, `SharedArrayBuffer`, `DataView`, `Atomics`) и текстовую сериализацию структур в `JSON`. Общий знаменатель — обе темы про то, как представить структурированные данные в форме, пригодной для передачи: либо как поток байт, либо как строку.

---

## 25.1 ArrayBuffer — сырая память фиксированного (или растяжимого) размера

Типизированные массивы из главы 23 — это лишь *интерпретация* байт. Сама память, которую они интерпретируют, — это [25.1 ArrayBuffer Objects](https://262.ecma-international.org/#sec-arraybuffer-objects): непрозрачный блок байт без какого-либо встроенного представления о том, что это за числа. `new ArrayBuffer(16)` выделяет 16 байт, заполненных нулями, и всё — без вида `Int8Array`/`Float64Array` поверх него прочитать или записать в этот блок в принципе нельзя.

### Растяжимые буферы — относительно недавнее дополнение

Долгое время `ArrayBuffer` был жёстко фиксированного размера, заданного один раз при создании. [25.1.2 Fixed-length and Resizable ArrayBuffer Objects](https://262.ecma-international.org/#sec-fixed-length-and-resizable-arraybuffer-objects) добавил возможность создать буфер, который можно **растягивать** после создания — до заранее объявленного максимума:

```js
const buf = new ArrayBuffer(4, { maxByteLength: 16 }); // резервируем до 16 байт заранее
console.log(buf.resizable, buf.maxByteLength); // true 16

buf.resize(8);
console.log(buf.byteLength); // 8 — реальный размер увеличен, но не превышает maxByteLength
```

Ключевая деталь: `maxByteLength` нужно указать **при создании**, а не в момент `resize` — это позволяет движку сразу зарезервировать нужный адресный диапазон памяти и потом просто менять «видимую» границу, не перевыделяя и не копируя память при каждом изменении размера. Попытка `resize` за пределы заранее объявленного максимума — ошибка. Обычный (нерастяжимый) `ArrayBuffer` остаётся доступным как раньше — если второй аргумент с `maxByteLength` не передан, поведение не меняется.

### `transfer()` — передача владения памятью с отсоединением исходного буфера

[25.1.6 ArrayBuffer.prototype.transfer](https://262.ecma-international.org/#sec-arraybuffer.prototype.transfer) — операция, которая **переносит** содержимое буфера в новый объект `ArrayBuffer`, одновременно **отсоединяя (detaching)** исходный — старый объект остаётся существовать как значение, но становится совершенно пустым и непригодным для использования:

```js
const src = new ArrayBuffer(4);
const dst = src.transfer();

console.log(src.detached, src.byteLength); // true 0 — исходный буфер отсоединён и опустошён
console.log(dst.byteLength);               // 4 — новый буфер владеет памятью
```

Это осознанная имитация модели владения памятью в духе Rust/C++ (move semantics) внутри языка со сборкой мусора — механизм придуман в первую очередь для передачи больших бинарных данных между потоками выполнения (Web Workers) **без копирования**: раз исходный буфер гарантированно становится недоступен, можно безопасно передать саму память другому потоку, не рискуя гонкой данных из двух потоков, пишущих в одну и ту же область одновременно.

## 25.2 SharedArrayBuffer — память, реально разделяемая между потоками

`ArrayBuffer`, переданный в другой поток (например, через `postMessage` воркеру), либо копируется, либо передаётся через описанный выше `transfer` (с отсоединением у отправителя — в любой момент времени владеет памятью только один поток). [25.2 SharedArrayBuffer Objects](https://262.ecma-international.org/#sec-sharedarraybuffer-objects) — принципиально другая модель: буфер, который **одновременно** доступен нескольким потокам, и запись в него из одного потока видна другому без какой-либо передачи или копирования.

Это открывает дверь к классической проблеме параллельного программирования — гонке данных (data race), если два потока одновременно читают/пишут одну и ту же ячейку памяти без синхронизации. Для этого существует раздел [25.4 Atomics](https://262.ecma-international.org/#sec-atomics-object).

## 25.4 Atomics — атомарные операции без гонок

`Atomics` — не конструктор, а объект-неймспейс со статическими методами (`Atomics.add`, `Atomics.load`, `Atomics.store`, `Atomics.compareExchange`, `Atomics.wait`, `Atomics.notify` и другие), гарантирующими, что операция чтения-модификации-записи над одной ячейкой типизированного массива выполнится **как единое неделимое действие**, даже если несколько потоков пытаются сделать это одновременно.

```js
const regular = new Int32Array(new ArrayBuffer(4));
regular[0] = 5;
const old = Atomics.add(regular, 0, 3);
console.log(old, regular[0]); // 5 8 — атомарно прочитали старое значение и прибавили 3
```

Интересная деталь, которую легко упустить: большинство методов `Atomics` (`add`, `load`, `store`, `compareExchange`...) **работают и с обычным `ArrayBuffer`**, не только с `SharedArrayBuffer` — спецификация ослабила это требование, потому что атомарность операции полезна сама по себе даже без реального параллелизма (например, гарантия того, что операция не будет прервана посередине асинхронным обработчиком). Но два конкретных метода — [`Atomics.wait`](https://262.ecma-international.org/#sec-atomics.wait) и `Atomics.notify` — требуют именно `SharedArrayBuffer`, потому что их смысл — **заблокировать** текущий поток до тех пор, пока другой поток не изменит значение и не «разбудит» ожидающий поток; блокировка потока имеет смысл только тогда, когда есть настоящий другой поток, способный её снять:

```js
try {
  Atomics.wait(regular, 0, 5); // regular — обычный ArrayBuffer, не Shared
} catch (e) {
  console.log(e.constructor.name); // TypeError — wait требует именно SharedArrayBuffer
}
```

Для повседневного прикладного кода (не связанного с Web Workers или Node.js `worker_threads`) `SharedArrayBuffer`/`Atomics` практически никогда не понадобятся напрямую — это низкоуровневый инструментарий, на котором построены более высокоуровневые абстракции многопоточности.

## 25.3 DataView — явный контроль над порядком байт

Типизированные массивы читают и пишут числа в **порядке байт платформы** (native byte order, почти всегда little-endian на современном оборудовании) — этот порядок не настраивается через `Int32Array`. [25.3 DataView Objects](https://262.ecma-international.org/#sec-dataview-objects) даёт альтернативный, более медленный, но полностью явный доступ к той же памяти — с обязательным указанием порядка байт при каждой операции:

```js
const buf = new ArrayBuffer(4);
const dv = new DataView(buf);

dv.setInt32(0, 1); // без третьего аргумента — по умолчанию big-endian (сначала старший байт)
console.log(new Uint8Array(buf)); // Uint8Array(4) [ 0, 0, 0, 1 ]

dv.setInt32(0, 1, true); // третий аргумент true — little-endian
console.log(new Uint8Array(buf)); // Uint8Array(4) [ 1, 0, 0, 0 ]
```

Важная асимметрия, о которой стоит явно предупредить: у `DataView` порядок байт по умолчанию **big-endian**, тогда как у типизированных массивов чтение/запись всегда происходит в **native order** платформы (little-endian почти везде сегодня) — если смешать `DataView` и обычный `Int32Array` над одним и тем же буфером без явного указания порядка, значения будут прочитаны по-разному. `DataView` — правильный инструмент именно тогда, когда порядок байт важен явно: разбор бинарных сетевых протоколов, файловых форматов, данных, пришедших с другой архитектуры процессора.

## 25.5 JSON — сериализация в текст

[25.5 The JSON Object](https://262.ecma-international.org/#sec-json-object) — тоже объект-неймспейс, не конструктор, с методами [`JSON.stringify`](https://262.ecma-international.org/#sec-json.stringify) и [`JSON.parse`](https://262.ecma-international.org/#sec-json.parse). Большая часть поведения интуитивна, но есть ряд деталей, которые стоит проговорить явно.

### `JSON.stringify(undefined)` возвращает не строку, а `undefined`

Это исключение из общего правила «stringify всегда возвращает строку»:

```js
console.log(JSON.stringify(undefined));         // undefined (само значение, не строка "undefined")
console.log(typeof JSON.stringify(undefined));  // 'undefined'
```

То же самое происходит при попытке сериализовать функцию или символ напрямую как корневое значение. Внутри объекта поведение другое — свойство со значением `undefined`, функцией или символом **пропускается целиком**, как будто его не было, а внутри массива на его месте появляется `null` (массив не может «сжаться», пропустив индекс — длина должна сохраниться):

```js
console.log(JSON.stringify({ a: 1, b: function() {} }));   // '{"a":1}' — свойство b пропущено
console.log(JSON.stringify([1, function() {}, 2]));        // '[1,null,2]' — на месте функции null
```

### Циклическая ссылка — гарантированная ошибка, а не зависание

Если объект содержит ссылку сам на себя (прямо или через цепочку вложенных объектов), `JSON.stringify` не уходит в бесконечную рекурсию — алгоритм отслеживает уже посещённые структуры и явно выбрасывает `TypeError`:

```js
const o = {};
o.self = o;
try {
  JSON.stringify(o);
} catch (e) {
  console.log(e.constructor.name); // TypeError: Converting circular structure to JSON
}
```

### `toJSON` — объект может сам решить, как его сериализовать

Если у объекта есть метод `toJSON`, `JSON.stringify` **не** пытается сериализовать сам объект — вместо этого вызывает `toJSON()` и сериализует то, что она вернула. Это тот же встроенный крючок расширения, что уже разбирался в главе 20 применительно к `Symbol.toPrimitive` — язык явно допускает, чтобы пользовательский тип сам определял, как он выглядит в другом контексте:

```js
class Money {
  constructor(amount) { this.amount = amount; }
  toJSON() { return `${this.amount} RUB`; }
}
console.log(JSON.stringify(new Money(100))); // '"100 RUB"'
```

Именно так `Date` (глава 21) превращается в строку ISO 8601 при `JSON.stringify` — у `Date.prototype` есть собственный `toJSON`, который вызывает `toISOString()`.

### `replacer` и `reviver` — фильтрация и трансформация на лету

Второй аргумент `stringify` — функция или массив строк-белый-список — управляет тем, какие свойства попадут в результат:

```js
console.log(JSON.stringify({ a: 1, b: 2 }, (key, value) => key === 'b' ? undefined : value));
// '{"a":1}' — функция-replacer вызывается для каждого свойства, undefined исключает его

console.log(JSON.stringify({ a: 1, b: 2, c: 3 }, ['a', 'c']));
// '{"a":1,"c":3}' — массив работает как белый список разрешённых ключей
```

Второй аргумент `JSON.parse` — функция-`reviver`, вызываемая для каждого разобранного значения снизу вверх (сначала листья, потом объемлющие объекты), позволяющая трансформировать значения сразу при разборе, не проходя дерево заново после:

```js
const parsed = JSON.parse('{"a":1,"b":2}', (key, value) =>
  typeof value === 'number' ? value * 10 : value
);
console.log(parsed); // { a: 10, b: 20 }
```

### `JSON.rawJSON` — точная передача чисел без потери точности (недавнее дополнение)

Классическая проблема JSON и JavaScript: числа в JSON текстуально могут быть сколь угодно точными (например, огромный ID из базы данных), но `JSON.parse` неизбежно превращает их в тип `Number`, у которого, как разбиралось в главе 21, есть предел безопасной целочисленной точности (`MAX_SAFE_INTEGER`) — за этим пределом происходит потеря точности. [25.5.2 JSON.rawJSON](https://262.ecma-international.org/#sec-json.rawjson) и [`JSON.isRawJSON`](https://262.ecma-international.org/#sec-json.israwjson) дают способ обойти эту проблему при **сериализации**: обернуть строку с текстовым представлением числа так, чтобы `JSON.stringify` вставил её в вывод буквально, как есть, не пропуская через числовой тип JavaScript:

```js
const raw = JSON.rawJSON('123456789012345678901234567890'); // огромное число, не помещается в Number точно
console.log(JSON.isRawJSON(raw)); // true

console.log(JSON.stringify({ big: raw }));
// '{"big":123456789012345678901234567890}' — число вставлено буквально, без округления
```

Это особенно ценно на границе с системами вроде BigInt-ориентированных баз данных или других языков с произвольной точностью целых чисел — сериализовать такое число как `Number` означало бы тихую потерю точности, а как строку — сломало бы совместимость со схемой JSON, ожидающей число, а не строку.

## Итог

> [!summary] Что взять с собой
> - `ArrayBuffer` — непрозрачный блок байт; читать/писать в него напрямую нельзя, только через `TypedArray` или `DataView` поверх него
> - Растяжимый `ArrayBuffer` требует `maxByteLength` уже при создании — реальный размер меняется через `resize()`, но не может превысить заранее объявленный максимум
> - `transfer()` переносит владение памятью в новый буфер и **отсоединяет (detach)** исходный — механизм для безопасной передачи больших бинарных данных между потоками без копирования
> - `SharedArrayBuffer` — единственный вид буфера, реально видимый нескольким потокам одновременно; для координации нужны атомарные операции `Atomics`
> - Большинство методов `Atomics` (`add`, `load`, `store`, `compareExchange`) работают и с обычным `ArrayBuffer`; `Atomics.wait`/`notify` требуют именно `SharedArrayBuffer`, потому что блокируют поток в ожидании другого потока
> - `DataView` по умолчанию читает/пишет в **big-endian**, типизированные массивы всегда используют **native order** платформы (обычно little-endian) — смешивать их над одним буфером без явного учёта порядка байт опасно
> - `JSON.stringify(undefined)` возвращает `undefined` (не строку) — исключение из общего правила
> - Свойства со значением `undefined`/функцией/символом пропускаются в объектах, но становятся `null` в массивах
> - Циклическая ссылка при `stringify` — гарантированный `TypeError`, а не зависание
> - Метод `toJSON`, если он есть у объекта, полностью определяет, что попадёт в вывод вместо самого объекта (так работает сериализация `Date`)
> - `replacer` (функция или массив-белый-список) и `reviver` дают точечный контроль над сериализацией и разбором без постобработки результата
> - `JSON.rawJSON`/`JSON.isRawJSON` позволяют вставить в вывод число буквальным текстом, минуя потерю точности при прохождении через тип `Number`
