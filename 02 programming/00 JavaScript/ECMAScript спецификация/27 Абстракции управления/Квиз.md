> [!question] Из каких двух формальных элементов состоит протокол итерации?
> a) `hasNext()` и `getNext()`
> b) метод `[Symbol.iterator]()` у итерируемого объекта и метод `next()` у самого итератора
> c) `start()` и `end()`
> d) свойство `length` и метод `at()`
>> [!success]- Answer
>> b) метод `[Symbol.iterator]()` у итерируемого объекта и метод `next()` у самого итератора
>> `next()` возвращает объект вида `{ value, done }`. Это открытый контракт — им пользуются и встроенные типы, и любой пользовательский объект

> [!question] Что выведет код?
> ```js
> let returnCalled = false;
> const iterable = {
>   [Symbol.iterator]() {
>     return {
>       next: () => ({ value: 1, done: false }),
>       return: () => { returnCalled = true; return { done: true }; }
>     };
>   }
> };
> for (const x of iterable) { break; }
> console.log(returnCalled);
> ```
> a) `true`
> b) `false`
> c) выбросит ошибку
> d) `undefined`
>> [!success]- Answer
>> a) `true`
>> Досрочный выход из `for...of` (через `break`) автоматически вызывает опциональный метод `return()` итератора — шанс освободить удерживаемые ресурсы

> [!question] Чем Iterator Helpers (`map`, `filter`, `take` на `Iterator.prototype`) принципиально отличаются от одноимённых методов `Array.prototype`?
> a) ничем, это одно и то же под разными именами
> b) работают лениво поэлементно и годятся для бесконечных последовательностей, не строя промежуточный массив
> c) Iterator Helpers работают только с числами
> d) Array.prototype методы работают быстрее в любом случае
>> [!success]- Answer
>> b) работают лениво поэлементно и годятся для бесконечных последовательностей, не строя промежуточный массив
>> `arr.map().filter()` строит полный промежуточный массив после `map`; цепочка Iterator Helpers продвигает каждое значение через всю цепочку сразу, без материализации

> [!question] Что выведет код?
> ```js
> function* naturals() { let n = 1; while (true) yield n++; }
> console.log(naturals().map(x => x * 2).filter(x => x % 3 === 0).take(3).toArray());
> ```
> a) программа зависнет в бесконечном цикле
> b) `[6, 12, 18]`
> c) `[2, 4, 6]`
> d) выбросит `RangeError`
>> [!success]- Answer
>> b) `[6, 12, 18]`
>> Несмотря на бесконечный источник, ленивая цепочка Iterator Helpers обрабатывает значения по одному и останавливается сразу после `take(3)`, ни разу не пытаясь материализовать всю последовательность

> [!question] Что делает `Iterator.from(plainIteratorObject)`?
>> [!success]- Answer
>> Оборачивает произвольный самописный итератор так, чтобы у него появились все helper-методы (map, filter, toArray и другие)
>> Полезно для итераторов, которые не наследуют напрямую от `Iterator.prototype`

> [!question] Сколько раз промис может перейти из состояния pending в конечное состояние (fulfilled или rejected)?
> a) неограниченное число раз
> b) не более одного раза, повторные resolve/reject после первого игнорируются
> c) ровно два раза — один на успех, один на отказ
> d) зависит от количества подписчиков .then
>> [!success]- Answer
>> b) не более одного раза, повторные resolve/reject после первого игнорируются
>> После первого settled-перехода промис становится неизменяемым

> [!question] Что выведет код (порядок строк)?
> ```js
> console.log('1');
> setTimeout(() => console.log('4'), 0);
> Promise.resolve().then(() => console.log('3'));
> console.log('2');
> ```
> a) `1 2 3 4`
> b) `1 2 4 3`
> c) `1 3 2 4`
> d) `1 4 2 3`
>> [!success]- Answer
>> a) `1 2 3 4`
>> Весь синхронный код (1, 2) выполняется первым; затем очередь микрозадач (промисы, `3`) опустошается целиком; и только потом наступает очередь макрозадач (`setTimeout`, `4`)

> [!question] Выполняются ли колбэки `.then` синхронно, если промис к моменту вызова `.then` уже выполнен?
>> [!success]- Answer
>> False
>> Колбэки промиса всегда планируются как микрозадача (job) и никогда не вызываются синхронно в момент подписки, даже если промис уже settled

> [!question] Что вернёт `Promise.resolve(existingPromise)`, если `existingPromise` уже промис того же конструктора?
> a) новый промис, оборачивающий исходный
> b) тот же самый объект, без обёртывания
> c) выбросит `TypeError`
> d) `undefined`
>> [!success]- Answer
>> b) тот же самый объект, без обёртывания
>> Спецификация явно избегает лишней обёртки вокруг уже готового промиса того же вида

> [!question] Что происходит, когда в `Promise.resolve()` передаётся thenable — обычный объект с методом `then`, не настоящий `Promise`?
> a) выбрасывается `TypeError`, потому что это не настоящий промис
> b) объект ассимилируется — спецификация следит за его состоянием через собственный then
> c) объект просто оборачивается как обычное значение без вызова его then
> d) это работает только для промисов из той же реализации
>> [!success]- Answer
>> b) объект ассимилируется — спецификация следит за его состоянием через собственный then
>> Это позволяет сторонним, доспецификационным реализациям промисов взаимодействовать со встроенным `Promise` без явной адаптации

> [!question] Что даёт `Promise.withResolvers()`?
> a) массив всех промисов, ожидающих выполнения
> b) объект `{ promise, resolve, reject }`, позволяющий вызвать resolve/reject снаружи исполнителя
> c) промис, который никогда не может быть отклонён
> d) обёртку над Promise.all
>> [!success]- Answer
>> b) объект `{ promise, resolve, reject }`, позволяющий вызвать resolve/reject снаружи исполнителя
>> Убирает необходимость в обходном пути с объявлением внешних переменных и присваиванием их внутри исполнителя `new Promise`

> [!question] При каком условии отклоняется `Promise.allSettled`?
> a) когда хотя бы один из промисов отклонён
> b) никогда — он всегда выполняется успешно после того, как все промисы завершились
> c) когда все промисы отклонены
> d) когда первый промис завершается с ошибкой
>> [!success]- Answer
>> b) никогда — он всегда выполняется успешно после того, как все промисы завершились
>> Результат — массив объектов со статусом `fulfilled`/`rejected` для каждого промиса, независимо от исхода

> [!question] Что выведет код?
> ```js
> Promise.any([Promise.reject('a'), Promise.reject('b')]).catch(e => {
>   console.log(e.constructor.name, e.errors);
> });
> ```
> a) `Error 'a'`
> b) `AggregateError ['a', 'b']`
> c) `TypeError undefined`
> d) промис зависнет и колбэк не вызовется
>> [!success]- Answer
>> b) `AggregateError ['a', 'b']`
>> Когда все переданные промисы отклонены, `Promise.any` отклоняется с `AggregateError`, собирающим все причины отказа сразу, а не только первую или последнюю

> [!question] Можно ли обратиться к конструктору `GeneratorFunction` как к глобальной переменной (`GeneratorFunction(...)`)?
>> [!success]- Answer
>> False
>> `GeneratorFunction`, как и `AsyncFunction`/`AsyncGeneratorFunction`, не является глобально доступной переменной — до него можно добраться только через `.constructor` уже существующей функции такого вида, например `(function*(){}).constructor`

> [!question] Что выведет код?
> ```js
> function* gen() {
>   try { yield 1; yield 2; } finally { console.log('cleanup'); }
> }
> const g = gen();
> g.next();
> g.return('early');
> ```
> a) ничего не выведется, finally не сработает
> b) выведется `'cleanup'`
> c) выбросится исключение
> d) `finally` сработает только при обычном завершении генератора, не при return()
>> [!success]- Answer
>> b) выведется `'cleanup'`
>> `generator.return()` проходит через блоки `finally` в теле генератора перед тем, как генератор действительно завершится — гарантия корректного освобождения ресурсов даже при досрочном прерывании

> [!question] Что возвращает вызов `next()` у асинхронного генератора?
> a) объект `{ value, done }` напрямую, как у обычного генератора
> b) промис, резолвящийся в объект `{ value, done }`
> c) сразу значение value, без обёртки
> d) массив значений
>> [!success]- Answer
>> b) промис, резолвящийся в объект `{ value, done }`
>> Именно поэтому для перебора асинхронных генераторов нужна отдельная конструкция `for await...of`, а не обычный `for...of`

> [!question] Работает ли `for await...of` с обычными (синхронными) итерируемыми объектами, не только с асинхронными?
>> [!success]- Answer
>> True
>> Каждое значение обычного итерируемого объекта автоматически оборачивается в уже выполненный промис на лету — один и тот же синтаксис единообразно работает и с синхронными, и с асинхронными последовательностями

> [!question] Что общего у сигнатуры массива-итератора (`[1,2,3][Symbol.iterator]()`) и Iterator Helpers?
> a) ничего, массив-итератор не поддерживает helper-методы
> b) итератор массива уже наследует от Iterator.prototype и имеет методы вроде map/filter без обёртывания
> c) их нужно явно оборачивать через Iterator.from
> d) helper-методы доступны только у генераторов, не у массивов
>> [!success]- Answer
>> b) итератор массива уже наследует от Iterator.prototype и имеет методы вроде map/filter без обёртывания
>> `%ArrayIteratorPrototype%` (и аналогичные прототипы у Map/Set) наследуют от `Iterator.prototype`, поэтому helper-методы доступны сразу, без Iterator.from
