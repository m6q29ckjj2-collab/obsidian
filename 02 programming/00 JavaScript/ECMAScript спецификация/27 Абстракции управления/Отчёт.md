# Глава 27 · Абстракции управления (Iterator, Promise, генераторы, async)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [27 Control Abstraction Objects](https://262.ecma-international.org/#sec-control-abstraction-objects)

Эта глава — про механизмы, которые управляют *порядком выполнения* кода, а не про данные: протокол итерации, обещания (`Promise`), генераторы и асинхронные функции. Все они опираются друг на друга — асинхронная функция внутри устроена как генератор, генератор реализует протокол итерации, а `for await...of` объединяет итерацию с ожиданием промисов. Разберём и формальный протокол, и относительно недавнее крупное дополнение — Iterator Helpers, — и то, что реально нужно понимать про порядок выполнения промисов.

---

## 27.1 Iteration — формальный протокол итерации

Мы уже пользовались `for...of` и spread-оператором во всех предыдущих главах, но не разбирали формально, что стоит за словом «итерируемый». [27.1.1 Common Iteration Interfaces](https://262.ecma-international.org/#sec-common-iteration-interfaces) фиксирует два разных, но связанных протокола:

- **Iterable** — объект с методом `[Symbol.iterator]()`, который возвращает итератор
- **Iterator** — объект с методом `next()`, возвращающим объект вида `{ value, done }` ([27.1.1.5 The IteratorResult Interface](https://262.ecma-international.org/#sec-iteratorresult-interface))

```js
const customIterable = {
  [Symbol.iterator]() {
    let n = 0;
    return {
      next() {
        n++;
        return n <= 3 ? { value: n, done: false } : { value: undefined, done: true };
      }
    };
  }
};

console.log([...customIterable]); // [1, 2, 3] — любой встроенный механизм итерации работает с этим объектом
```

Ничего специального для встроенных типов здесь нет — `Array`, `Map`, `Set`, `String` реализуют ровно этот же протокол через собственные методы `[Symbol.iterator]`. Именно поэтому `for...of`, spread, `Array.from` и деструктуризация работают одинаково с массивом, с `Map` и с любым пользовательским объектом, реализующим протокол — это открытый контракт, а не список специальных случаев для встроенных типов.

### Опциональные методы `return` и `throw` — корректное завершение итерации досрочно

Итератор может (но не обязан) реализовать методы `return()` и `throw()`. `return()` вызывается автоматически, если итерация прерывается **раньше**, чем `done` стало `true` — например, `break` внутри `for...of`, исключение в теле цикла, или деструктуризация, забирающая не все элементы:

```js
let returnCalled = false;
const iterable = {
  [Symbol.iterator]() {
    return {
      next: () => ({ value: 1, done: false }),
      return: () => { returnCalled = true; return { done: true }; }
    };
  }
};

for (const x of iterable) { break; } // прерываем цикл на первой итерации
console.log(returnCalled); // true — движок сам вызвал return(), чтобы итератор мог освободить ресурсы
```

Это существует не просто для порядка: если итератор держит открытым файл, сетевое соединение или блокировку (типичный сценарий для кастомных итераторов, оборачивающих внешние ресурсы), `return()` — единственный шанс корректно её закрыть при досрочном выходе. Именно поэтому генераторы (ниже) автоматически реализуют `return()` через выполнение блока `finally` в своём теле — язык гарантирует, что ресурс, освобождаемый в `finally` внутри генератора, освободится и при обычном завершении, и при досрочном прерывании цикла.

### Итератор — не то же самое, что итерируемый объект

Частая путаница: сам итератор (объект с `next()`) по соглашению **тоже** реализует `[Symbol.iterator]()`, просто возвращающий сам себя — это позволяет использовать `for...of` как для контейнера (`Array`), так и напрямую для уже полученного итератора (`arr[Symbol.iterator]()`), без разницы в синтаксисе.

## 27.1.2–27.1.3 Iterator Helpers — цепочки операций прямо на итераторе (недавнее дополнение)

До относительно недавнего времени для операций вроде `map`/`filter` над последовательностью нужно было либо материализовать весь массив (`Array.from(iterable).map(...)`, что требует, чтобы последовательность была конечной и помещалась в память), либо вручную писать генератор-обёртку. [27.1.2 Iterator Helper Objects](https://262.ecma-international.org/#sec-iterator-helper-objects) добавил прямо в `Iterator.prototype` методы `map`, `filter`, `take`, `drop`, `flatMap`, `reduce`, `toArray`, `forEach`, `some`, `every`, `find` — **ленивые**, не требующие материализации, и работающие в том числе с **бесконечными** последовательностями:

```js
function* naturals() {
  let n = 1;
  while (true) yield n++; // бесконечная последовательность натуральных чисел
}

const result = naturals()
  .map(x => x * 2)
  .filter(x => x % 3 === 0)
  .take(3)
  .toArray();

console.log(result); // [6, 12, 18]
// ни на каком шаге не была материализована вся бесконечная последовательность —
// каждое значение проходит цепочку целиком, прежде чем запрашивается следующее
```

Это принципиально другая модель вычисления по сравнению с методами `Array.prototype`: `arr.map(fn).filter(fn2)` сначала полностью строит промежуточный массив после `map`, и только потом фильтрует его — два полных прохода и лишняя память на промежуточный результат. Цепочка Iterator Helpers обрабатывает значения по одному, продвигая каждое через всю цепочку прежде, чем запросить следующее у источника — как конвейер, а не как последовательность отдельных полных проходов.

### `[Symbol.iterator]()` от массива и других коллекций уже возвращает объект с этими методами

Поскольку методы определены на `Iterator.prototype`, а стандартный `%ArrayIteratorPrototype%` (и `%MapIteratorPrototype%`, `%SetIteratorPrototype%`) наследует от него, у итератора обычного массива эти методы уже есть без всякой обёртки:

```js
const arrIterator = [1, 2, 3][Symbol.iterator]();
console.log(typeof arrIterator.map); // 'function' — уже наследуется от Iterator.prototype
console.log(arrIterator.map(x => x * 10).toArray()); // [10, 20, 30]
```

### `Iterator.from` — превратить произвольный итератор/итерируемый объект в такой же

Если под рукой не встроенный, а самописный итератор (без наследования от `Iterator.prototype`), [27.1.3.2.2 Iterator.from](https://262.ecma-international.org/#sec-iterator.from) оборачивает его так, чтобы стали доступны все helper-методы:

```js
const plain = { next: (() => { let i = 0; return () => ({ value: i++, done: i > 3 }); })() };
const wrapped = Iterator.from(plain);
console.log(wrapped.map(x => x + 100).toArray()); // [100, 101, 102]
```

## 27.2 Promise — модель асинхронного результата

`Promise` — объект, представляющий значение, которое станет доступно (или окончательно провалится) в будущем. Три состояния — pending (ожидание), fulfilled (выполнено успешно), rejected (отклонено с ошибкой) — и ключевое структурное свойство: переход из pending в одно из двух конечных состояний **происходит не более одного раза**. Повторные вызовы `resolve`/`reject` после первого молча игнорируются:

```js
new Promise((resolve, reject) => {
  resolve('первое значение');
  resolve('второе значение'); // игнорируется — промис уже settled
  reject('ошибка');           // тоже игнорируется
}).then(v => console.log(v)); // 'первое значение'
```

### Микрозадачи — промисы выполняются раньше `setTimeout`, но не синхронно

[27.2.2 Promise Jobs](https://262.ecma-international.org/#sec-promise-jobs) — колбэки, переданные в `.then`/`.catch`/`.finally`, никогда не выполняются синхронно в момент вызова, даже если промис уже был выполнен к этому моменту — они всегда планируются как **job** (микрозадача) и выполняются после текущего синхронного кода, но раньше макрозадач вроде `setTimeout`:

```js
console.log('1: синхронный код начало');
setTimeout(() => console.log('4: setTimeout (макрозадача)'), 0);
Promise.resolve().then(() => console.log('3: промис (микрозадача)'));
console.log('2: синхронный код конец');

// вывод: 1, 2, 3, 4 — весь синхронный код гарантированно выполнится раньше
// любой микрозадачи, а все накопленные микрозадачи — раньше следующей макрозадачи
```

Это не деталь реализации конкретного движка, а прямое следствие устройства очереди задач в спецификации: после каждого синхронного «куска» кода очередь микрозадач (промисы, а также колбэки `queueMicrotask`) полностью опустошается, прежде чем управление перейдёт к следующей задаче из очереди макрозадач (таймеры, события ввода-вывода).

### `Promise.resolve` — либо оборачивает значение, либо ничего не делает

[27.2.4.7 Promise.resolve](https://262.ecma-international.org/#sec-promise.resolve) ведёт себя по-разному в зависимости от типа аргумента: обычное значение оборачивается в новый выполненный промис, а если аргумент — уже промис того же конструктора, метод возвращает **тот же самый** объект без обёртывания:

```js
const p1 = Promise.resolve(42);
const p2 = Promise.resolve(p1);
console.log(p1 === p2); // true — не создаётся лишняя обёртка вокруг уже готового промиса
```

Если аргумент — **thenable** (любой объект с методом `then`, не обязательно настоящий `Promise`), происходит **ассимиляция** — спецификация подключается к чужому объекту через его собственный `then` и следит за его состоянием, как за своим:

```js
const thenable = { then(resolve) { resolve('значение из чужого thenable'); } };
Promise.resolve(thenable).then(v => console.log(v)); // 'значение из чужого thenable'
```

Именно этот механизм ассимиляции thenable-объектов позволяет библиотекам с собственной, доспецификационной реализацией промисов (например, старым версиям jQuery Deferred) взаимодействовать со встроенными `Promise` без явной адаптации — достаточно, чтобы у объекта был метод `then` с ожидаемой сигнатурой.

### `Promise.withResolvers` — вынести `resolve`/`reject` наружу исполнителя (недавнее дополнение)

Классический паттерн `new Promise((resolve, reject) => { ... })` неудобен, когда `resolve`/`reject` нужно вызвать не изнутри исполнителя, а откуда-то снаружи (например, при подписке на внешнее событие) — раньше приходилось объявлять переменные снаружи и присваивать их внутри исполнителя как побочный эффект. [27.2.4.9 Promise.withResolvers](https://262.ecma-international.org/#sec-promise.withresolvers) даёт то же самое напрямую, без этого обходного пути:

```js
const { promise, resolve, reject } = Promise.withResolvers();

someExternalEventEmitter.on('done', (data) => resolve(data));
someExternalEventEmitter.on('error', (err) => reject(err));

// promise можно вернуть из функции сразу, а resolve/reject вызвать существенно позже
```

### Четыре способа скомбинировать несколько промисов — и их различия

[`Promise.all`](https://262.ecma-international.org/#sec-promise.all), [`Promise.allSettled`](https://262.ecma-international.org/#sec-promise.allsettled), [`Promise.race`](https://262.ecma-international.org/#sec-promise.race) и [`Promise.any`](https://262.ecma-international.org/#sec-promise.any) принимают массив (точнее, любой итерируемый объект) промисов и различаются тем, при каком условии сам комбинированный промис считается завершённым:

| Метод | Успех, когда | Провал, когда |
|---|---|---|
| `all` | все выполнились успешно | хотя бы один отклонён (сразу же) |
| `allSettled` | всегда — после того, как все завершились (не важно, как) | никогда не отклоняется сам |
| `race` | первый из всех завершился (успешно) | первый из всех завершился (с ошибкой) |
| `any` | хотя бы один выполнился успешно | все до единого отклонены |

Самая нетривиальная деталь — что происходит, когда `Promise.any` отклоняется: если отклонены **все** переданные промисы, результирующая ошибка — не первая и не последняя из них, а специальный **`AggregateError`**, собирающий все причины отказа сразу:

```js
Promise.any([Promise.reject('a'), Promise.reject('b')]).catch(e => {
  console.log(e.constructor.name); // 'AggregateError'
  console.log(e.errors);           // ['a', 'b'] — обе причины отказа, а не только одна
});
```

`AggregateError` разбирался в главе 20 именно как тип ошибки, специально созданный ради этого сценария — до его появления `Promise.any` попросту не мог бы честно сообщить сразу обо всех причинах отказа, теряя часть информации.

## 27.3–27.7 Генераторы и асинхронные функции — конструкторы, которые почти никогда не вызывают напрямую

`function*`, `async function`, `async function*` — три синтаксические формы, каждая создаёт функцию, чей `[[Prototype]]` указывает не на обычный `Function.prototype`, а на специальный промежуточный прототип (`GeneratorFunction.prototype`, `AsyncFunction.prototype`, `AsyncGeneratorFunction.prototype` соответственно). Сами конструкторы [`GeneratorFunction`](https://262.ecma-international.org/#sec-generatorfunction-objects), [`AsyncFunction`](https://262.ecma-international.org/#sec-async-function-objects) и [`AsyncGeneratorFunction`](https://262.ecma-international.org/#sec-asyncgeneratorfunction-objects) не являются глобальными переменными — как и `%TypedArray%` в главе 23, до них можно добраться только косвенно, через `constructor` уже существующей функции такого вида:

```js
function* g() {}
const GeneratorFunction = g.constructor;
console.log(GeneratorFunction === (function*(){}).constructor); // true

const g2 = new GeneratorFunction('x', 'yield x * 2');
console.log([...g2(5)]); // [10] — динамически собранный генератор, аналог new Function из главы 20
```

На практике этот путь нужен крайне редко — почти всегда генераторы и асинхронные функции создаются обычным синтаксисом (`function*`, `async function`), а не динамической сборкой через конструктор. Но знание, что за `function*`/`async function` стоят настоящие, пусть и скрытые от прямого доступа, конструкторы — та же логика единообразия языка, что уже встречалась применительно к `Function`/встроенным прототипам в главе 20.

### `generator.return()` запускает `finally`, как и досрочный выход из `for...of`

Генератор — конкретная реализация протокола Iterator, поэтому у него есть метод `return()`, который принудительно завершает генератор досрочно — и, что важно, **проходит через блоки `finally`** в теле генератора, прежде чем действительно завершиться:

```js
function* gen() {
  try {
    yield 1;
    yield 2;
  } finally {
    console.log('ресурс освобождён');
  }
}

const g = gen();
console.log(g.next());       // { value: 1, done: false }
console.log(g.return('досрочно')); // выводит "ресурс освобождён", затем { value: 'досрочно', done: true }
```

Это прямое следствие того же принципа, что уже обсуждался выше применительно к `return()` в общем протоколе итератора — генератор, используемый в `for...of` с досрочным `break`, автоматически получает вызов своего `return()`, и поэтому код очистки ресурсов в `finally` внутри генератора срабатывает корректно, даже когда потребитель никогда не доводит итерацию до конца.

### `for await...of` — итерация с ожиданием на каждом шаге

Асинхронные генераторы (`async function*`) реализуют не `Symbol.iterator`, а [`Symbol.asyncIterator`](https://262.ecma-international.org/#sec-asynciterable-interface) — их метод `next()` возвращает не `{ value, done }` напрямую, а **промис**, который резолвится в `{ value, done }`. Конструкция `for await...of` — единственный способ синтаксически удобно перебрать такую последовательность, автоматически дожидаясь каждого промиса перед тем, как перейти к следующей итерации:

```js
async function* asyncNumbers() {
  for (let i = 1; i <= 3; i++) {
    await new Promise(r => setTimeout(r, 10)); // имитация асинхронной задержки
    yield i;
  }
}

async function consume() {
  for await (const n of asyncNumbers()) {
    console.log(n); // 1, 2, 3 — с задержкой перед каждым значением
  }
}
consume();
```

Раздел [27.1.5 Async-from-Sync Iterator Objects](https://262.ecma-international.org/#sec-async-from-sync-iterator-objects) описывает дополнительную деталь: `for await...of` работает и с обычными (синхронными) итерируемыми объектами — каждое значение просто автоматически оборачивается в уже выполненный промис на лету, так что один и тот же синтаксис единообразно работает и с асинхронными, и с обычными последовательностями.

## Итог

> [!summary] Что взять с собой
> - Протокол итерации — открытый контракт (`Symbol.iterator` → объект с `next()`, возвращающим `{value, done}`), а не список специальных случаев для встроенных типов
> - Опциональный метод `return()` итератора вызывается автоматически при досрочном прерывании (`break`, исключение) — шанс корректно освободить ресурсы
> - Iterator Helpers (`map`, `filter`, `take`, `drop`, `reduce`, `toArray`...) на `Iterator.prototype` — ленивая, поэлементная обработка, работающая даже с бесконечными последовательностями, в отличие от `Array.prototype`-методов, строящих промежуточные массивы целиком
> - `Iterator.from` оборачивает произвольный самописный итератор, добавляя ему все helper-методы
> - Промис settled не более одного раза — повторные `resolve`/`reject` после первого молча игнорируются
> - Колбэки `.then`/`.catch` всегда выполняются как микрозадача, никогда синхронно — весь текущий синхронный код и все накопленные микрозадачи выполняются раньше следующего `setTimeout`
> - `Promise.resolve(existingPromise)` возвращает тот же объект без лишней обёртки; `Promise.resolve(thenable)` ассимилирует чужой объект с методом `then`
> - `Promise.withResolvers()` даёт `resolve`/`reject` напрямую, без обходного пути с внешними переменными
> - `Promise.any`, когда отклонены все переданные промисы, даёт `AggregateError` со всеми причинами сразу, а не одну из них
> - `GeneratorFunction`/`AsyncFunction`/`AsyncGeneratorFunction` — реальные, но не глобально доступные конструкторы, до них можно добраться только через `.constructor` существующей функции такого вида
> - `generator.return()` проходит через `finally`-блоки тела генератора — та же гарантия корректной очистки ресурсов, что и у обычного протокола итератора
> - `for await...of` дожидается каждого промиса асинхронного итератора и одинаково работает как с асинхронными, так и с обычными синхронными итерируемыми объектами
