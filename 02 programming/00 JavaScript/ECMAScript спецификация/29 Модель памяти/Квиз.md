# Глава 29 · Модель памяти — квиз

> [!info] Как проходить
> 11 вопросов по формальной модели памяти для разделяемой памяти и Atomics.
> Теория → [[Отчёт]] · карточки → [[Карточки]] · [раздел спецификации](https://262.ecma-international.org/#sec-memory-model)

---

> [!question] Ради какой возможности языка потребовалась формальная модель памяти?
> a) для обычных однопоточных вычислений
> b) для разделяемой памяти между несколькими потоками (SharedArrayBuffer)
> c) для сборки мусора
> d) для оптимизации JIT-компиляции
>> [!success]- Answer
>> b) для разделяемой памяти между несколькими потоками (SharedArrayBuffer)
>> До появления `SharedArrayBuffer` у JavaScript был один поток исполнения на агент, и порядок операций всегда совпадал с порядком строк кода — вопрос о видимости записей между потоками просто не имел смысла

> [!question] Что называется «агентом» в терминологии главы про модель памяти?
>> [!success]- Answer
>> Единица параллельного исполнения — например, Web Worker или поток worker_threads в Node.js
>> Каждый агент выполняет свой код последовательно; вопросы модели памяти касаются взаимодействия между разными агентами

> [!question] Через что возникает happens-before-связь между операциями в разных потоках?
> a) через любое обращение к разделяемой памяти
> b) только через синхронизирующие атомарные операции (Atomics)
> c) через порядок объявления переменных
> d) она возникает автоматически при запуске Worker
>> [!success]- Answer
>> b) только через синхронизирующие атомарные операции (Atomics)
>> Обычное неатомарное чтение/запись не создаёт гарантированной связи порядка между потоками — для этого нужны операции вроде `Atomics.store`/`Atomics.wait`/`Atomics.notify`

> [!question] Создаёт ли обычное (не через Atomics) чтение/запись разделяемой памяти гарантию порядка видимости между разными потоками?
>> [!success]- Answer
>> False
>> Такая гарантия возникает только через синхронизирующие атомарные операции — обычный доступ к разделяемой памяти этой связи не даёт

> [!question] Какую гарантию по умолчанию дают операции `Atomics` относительно всех потоков?
> a) слабую, оптимизированную под производительность модель, которую можно настраивать
> b) sequential consistency — единый, согласованный порядок, видимый одинаково всем потокам
> c) никакой гарантии, порядок полностью не определён
> d) гарантию только в пределах одного потока
>> [!success]- Answer
>> b) sequential consistency — единый, согласованный порядок, видимый одинаково всем потокам
>> Это самая строгая и предсказуемая из возможных гарантий; в отличие от C++, в JS она действует по умолчанию для всех Atomics-операций, без более слабых опциональных режимов

> [!question] Нужно ли в JavaScript явно запрашивать более строгий режим согласованности для атомарных операций, как в C++?
>> [!success]- Answer
>> False
>> В JavaScript всегда действует самая строгая модель (sequential consistency) по умолчанию — более слабых режимов для Atomics не существует, выбора нет

> [!question] Что формально называется data race (гонкой данных)?
> a) любое использование SharedArrayBuffer
> b) конкурентный неатомарный доступ к одной ячейке разделяемой памяти из разных потоков без happens-before-связи, где хотя бы один доступ — запись
> c) вызов Atomics.wait без SharedArrayBuffer
> d) одновременное чтение одной переменной несколькими потоками
>> [!success]- Answer
>> b) конкурентный неатомарный доступ к одной ячейке разделяемой памяти из разных потоков без happens-before-связи, где хотя бы один доступ — запись
>> Если оба конкурирующих доступа — чтение, гонки нет: чтение не изменяет состояние

> [!question] Приводит ли гонка данных в JavaScript к неопределённому поведению (undefined behavior), как это было бы в C++ или Rust?
>> [!success]- Answer
>> False
>> В модели памяти ECMAScript неопределённого поведения не существует в принципе — это сознательный принцип, связанный с общей философией безопасности языка

> [!question] Какой худший практический исход гонки данных над неатомарными операциями в JavaScript?
> a) крах процесса (segmentation fault)
> b) чтение произвольной чужой памяти
> c) tearing — прочитанное значение может оказаться смесью битов от двух одновременных записей, но остаётся валидным значением того же типа
> d) полная остановка сборщика мусора
>> [!success]- Answer
>> c) tearing — прочитанное значение может оказаться смесью битов от двух одновременных записей, но остаётся валидным значением того же типа
>> Это плохо для корректности программы, но принципиально безопаснее, чем UB в языках без встроенной защиты памяти

> [!question] Какую главную практическую рекомендацию даёт раздел Shared Memory Guidelines программистам?
> a) избегать SharedArrayBuffer полностью, использовать только copy-on-write
> b) держать программу свободной от гонок данных
> c) всегда использовать 64-битные ячейки для любых данных
> d) вызывать Atomics.wait перед каждой операцией
>> [!success]- Answer
>> b) держать программу свободной от гонок данных
>> Если это соблюдено, детали формальной модели памяти можно вообще не изучать — они не помогают писать код лучше, а нужны лишь для доказательства корректности спецификации

> [!question] Как избежать tearing, если полностью исключить гонки данных не получается?
> a) использовать одинаковый размер доступа для конкурирующих обращений к одной и той же ячейке
> b) использовать разные ArrayBuffer для чтения и записи
> c) это невозможно предотвратить никаким способом
> d) вызывать Atomics.notify после каждой неатомарной записи
>> [!success]- Answer
>> a) использовать одинаковый размер доступа для конкурирующих обращений к одной и той же ячейке
>> Проще говоря, относиться к разделяемой памяти как к строго типизированной — не смешивать доступы разного размера или атомарные с неатомарными к одной и той же ячейке одновременно
