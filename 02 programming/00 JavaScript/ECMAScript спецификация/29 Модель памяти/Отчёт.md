# Глава 29 · Модель памяти

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [29 Memory Model](https://262.ecma-international.org/#sec-memory-model)

Последняя глава спецификации — самая формальная и самая далёкая от повседневного кода. Она существует ради одной узкой, но структурно необходимой темы: `SharedArrayBuffer` и `Atomics` из главы 25 сделали возможным, чтобы несколько потоков одновременно читали и писали одну и ту же память — а значит, спецификации пришлось формально определить, **в каком порядке** запись одного потока становится видна чтению другого. До появления разделяемой памяти такой вопрос не имел смысла: у JavaScript был ровно один поток исполнения на агент, и "порядок операций" всегда совпадал с порядком строк кода. С несколькими потоками это перестаёт быть очевидным даже теоретически.

Эта глава не про то, что можно "попробовать в консоли" — она даёт формальный язык, на котором строго определяется корректность программ, использующих общую память. Мы разберём идеи на уровне понимания, а не на уровне формальных отношений — как в главе 9 мы разбирали контексты исполнения не построчным разбором алгоритмов, а через объяснение того, зачем нужен каждый механизм.

---

## Зачем вообще нужна формальная модель памяти

Представим упрощённый сценарий: один поток (агент — так спецификация называет единицу параллельного исполнения, будь то Web Worker или `worker_threads` в Node.js) пишет данные в разделяемую память, а затем устанавливает "флаг готовности". Другой поток ждёт, пока флаг станет `true`, и только потом читает данные. Интуитивно кажется очевидным, что если второй поток увидел флаг, он обязан увидеть и записанные перед флагом данные. Но без формальной гарантии это **не** очевидно на уровне возможных оптимизаций компилятора и переупорядочивания на уровне процессора: инструкции могут быть переставлены местами, если ничто явно не запрещает такую перестановку — эта проблема существует не только в JavaScript, а во всех языках, поддерживающих разделяемую память (тот же класс задач решают модели памяти C++, Java, Rust).

```js
// main.mjs — упрощённая демонстрация: два потока, синхронизация через Atomics
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

if (isMainThread) {
  const sab = new SharedArrayBuffer(8);
  const view = new Int32Array(sab);
  Atomics.store(view, 0, 0); // флаг готовности
  Atomics.store(view, 1, 0); // сами данные

  const worker = new Worker(new URL(import.meta.url), { workerData: { sab } });
  worker.on('message', (msg) => console.log('главный поток получил:', msg));

  setTimeout(() => {
    Atomics.store(view, 1, 42);  // сначала пишем данные
    Atomics.store(view, 0, 1);   // потом поднимаем флаг
    Atomics.notify(view, 0, 1);  // будим ожидающий поток
  }, 50);
} else {
  const view = new Int32Array(workerData.sab);
  Atomics.wait(view, 0, 0); // блокируемся, пока флаг не станет ненулевым
  const data = Atomics.load(view, 1);
  parentPort.postMessage(`флаг увиден, данные = ${data}`); // всегда 42, никогда не 0 или мусор
}
```

Реальный запуск этого кода стабильно выводит `данные = 42` — и это не совпадение, а прямая гарантия, которую даёт [29.6.6 happens-before](https://262.ecma-international.org/#sec-happens-before): порядок атомарных операций `Atomics.store`/`Atomics.notify`/`Atomics.wait` формально устанавливает связь "произошло раньше" между записью данных в одном потоке и их чтением в другом, и спецификация запрещает любое переупорядочивание, которое могло бы эту связь нарушить.

## Ключевые понятия — на уровне идеи, не формального определения

Формальный аппарат этой главы (agent events, candidate execution, choice values, relations вроде `reads-from`, `synchronizes-with`) существует, чтобы можно было математически строго доказать: "для любой допустимой перестановки операций разных потоков результат программы остаётся согласованным с тем, что реально написал программист через `Atomics`". Не углубляясь в формальный аппарат, стоит понимать три идеи:

**Happens-before** ([29.6.6](https://262.ecma-international.org/#sec-happens-before)) — отношение порядка между операциями, возможно, в разных потоках, которое спецификация гарантирует сохранённым. Операции внутри одного потока happens-before друг друга просто по порядку кода. Между потоками эта связь возникает **только** через синхронизирующие атомарные операции (в первую очередь пары вида `store`+`notify` / `wait`+`load`, как в примере выше) — обычное, неатомарное чтение/запись такой связи не создаёт.

**Sequential Consistency у атомарных операций** ([29.7.4](https://262.ecma-international.org/#sec-memory-order)) — по умолчанию все операции `Atomics` образуют единый, согласованный между всеми потоками общий порядок: если поток А видит эффект операции из потока Б, то он гарантированно видит и все операции, которые в потоке Б предшествовали ей. Это самая сильная и самая простая для понимания гарантия из всех, что предлагает модель памяти — по этой причине спецификация делает её гарантией **по умолчанию** для всех `Atomics`-операций, а не опциональной надстройкой, которую нужно специально запрашивать (как в C++, где более слабые модели памяти для атомиков нужно явно выбирать через флаги — в JS такого выбора нет, всегда действует самая строгая и предсказуемая модель).

**Data race** ([29.9 Data Races](https://262.ecma-international.org/#sec-data-races)) — формально определённая ситуация: два **неатомарных** обращения к одной и той же ячейке разделяемой памяти из разных потоков, хотя бы одно из которых — запись, без happens-before-связи между ними. Такая ситуация формально называется гонкой данных.

## Гонка данных в JavaScript — не такая катастрофа, как в C++

Здесь у ECMAScript есть важное отличие от C++/Rust: **неопределённое поведение (undefined behavior) в модели памяти JavaScript не существует в принципе** — это фундаментальный, сознательно принятый принцип, который прямо связан с общей философией безопасности языка (глава 6, 10 — никакое действие в ECMAScript не может привести к произвольному повреждению памяти или непредсказуемому крашу интерпретатора). Даже гонка данных над неатомарными операциями в худшем случае может привести к [**tearing**](https://262.ecma-international.org/#sec-tear-free-aligned-reads) — прочитанное значение может оказаться смесью битов от двух разных одновременных записей (например, если два потока пишут разные 32-битные числа в одну ячейку одновременно, прочитанный результат в худшем случае может оказаться "ни тем, ни другим" значением, собранным из кусков обоих). Это плохо для корректности программы — но это всё ещё валидное значение того же типа, а не крах процесса и не чтение чужой памяти, как было бы в языке без встроенной защиты памяти.

## Практические рекомендации спецификации — единственное, что реально нужно помнить

[29.11 Shared Memory Guidelines](https://262.ecma-international.org/#sec-shared-memory-guidelines) — единственный раздел главы, адресованный напрямую программисту (а не автору движка), и единственная часть, которую стоит унести с собой как практическое правило:

> [!summary] Прямая рекомендация спецификации
> **Держите программу свободной от гонок данных.** Не допускайте одновременных неатомарных операций над одной и той же ячейкой разделяемой памяти из разных потоков. Если это соблюдено, детали формальной модели памяти можно вообще не изучать — они не помогут писать код лучше, они существуют только для доказательства корректности самой спецификации.
>
> Если полностью избежать гонок не получается, спецификация даёт более слабую, но всё ещё практичную гарантию: пока конкурирующие обращения имеют **одинаковый размер доступа** (например, всегда 32-битные операции, а не смесь 8-битных и 32-битных над одной ячейкой), tearing не произойдёт — значения не "смешаются" на уровне битов, даже если порядок гонки непредсказуем. Проще говоря: относитесь к разделяемой памяти как к строго типизированной — не смешивайте атомарный и неатомарный доступ к одной и той же ячейке и не смешивайте доступы разного размера к одной и той же ячейке одновременно.

На практике для подавляющего большинства JS-разработчиков, никогда не пишущих код с `SharedArrayBuffer` напрямую (эта глава актуальна в первую очередь для авторов рантаймов, движков и низкоуровневых параллельных библиотек), единственный практический вывод такой: если вы всё же работаете с разделяемой памятью между Web Workers/`worker_threads`, используйте `Atomics` для **всех** обращений к разделяемым ячейкам, на которые может одновременно претендовать другой поток — не только там, где это кажется важным.

## Итог

> [!summary] Что взять с собой
> - Модель памяти существует ради одной задачи: формально определить порядок видимости записей между потоками при разделяемой памяти (`SharedArrayBuffer`) — до появления многопоточности в JS этот вопрос не имел смысла
> - **Happens-before** — гарантированное спецификацией отношение порядка между операциями; между разными потоками оно возникает только через синхронизирующие атомарные операции, не через обычное чтение/запись
> - Атомарные операции `Atomics` по умолчанию **последовательно согласованы** (sequential consistency) между всеми потоками — самая строгая и предсказуемая из возможных гарантий, и в JS она не опциональна, в отличие от C++
> - **Гонка данных** — конкурентный неатомарный доступ к одной ячейке разделяемой памяти из разных потоков без happens-before-связи между ними, хотя бы один доступ — запись
> - В отличие от C++/Rust, гонка данных в JavaScript **не** приводит к неопределённому поведению или краху — худший исход — tearing (смешение битов двух разных записей), но не выход за пределы модели безопасности языка
> - Официальная рекомендация: держите программы свободными от гонок данных; если это невозможно — используйте одинаковый размер доступа для конкурирующих обращений, чтобы избежать tearing
> - Для подавляющего большинства разработчиков, не пишущих код с разделяемой памятью напрямую, вся эта глава не нужна на практике — но она объясняет, почему `Atomics` вообще существует и почему обычные операции для этой задачи не годятся
