# Глава 9 · Исполняемый код и контексты исполнения — отчёт

> [!info] Раздел спецификации
> [9 Executable Code and Execution Contexts](https://262.ecma-international.org/#sec-executable-code-and-execution-contexts)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Эта глава — механика, на которой в буквальном смысле стоит всё остальное поведение языка: области видимости, вычисление `this`, замыкания, стек вызовов функций. Если предыдущие главы объясняли "словарь" (типы значений, базовые операции), то здесь описывается "устройство исполнения" — что именно происходит внутри движка, пока код выполняется, шаг за шагом. Самая насыщенная и самая важная для понимания часть главы — пять видов **записей окружения** из [9.1](https://262.ecma-international.org/#sec-environment-records), формальный механизм, лежащий в основе областей видимости.

---

## 9.1 Записи окружения — формальный механизм области видимости

[9.1.1 The Environment Record Type Hierarchy](https://262.ecma-international.org/#sec-the-environment-record-type-hierarchy) задаёт пять разных видов записей окружения, и важно сразу понять принцип их устройства: все пять — это реализации одного и того же общего интерфейса операций из [9.1.2](https://262.ecma-international.org/#sec-environment-record-operations): проверить наличие связывания по имени, создать новое связывание, инициализировать его значением, записать в него значение, прочитать значение, удалить связывание. Разные виды записи реализуют эти операции по-разному внутри себя, но с точки зрения остального механизма языка все пять взаимозаменяемы — код, который разрешает имя переменной, не обязан знать, с каким конкретно видом записи окружения он имеет дело.

| Вид | Раздел | Хранит |
|---|---|---|
| Declarative | [9.1.1.1](https://262.ecma-international.org/#sec-declarative-environment-records) | `let`, `const`, `class`, параметры функций, привязку переменной в `catch` |
| Object | [9.1.1.2](https://262.ecma-international.org/#sec-object-environment-records) | связывания как свойства настоящего объекта — `var` в глобальном коде, устаревшая конструкция `with` |
| Function | [9.1.1.3](https://262.ecma-international.org/#sec-function-environment-records) | всё то же, что Declarative, плюс `this`, `new.target`, ссылку на саму функцию |
| Global | [9.1.1.4](https://262.ecma-international.org/#sec-global-environment-records) | гибрид Declarative и Object в одном |
| Module | [9.1.1.5](https://262.ecma-international.org/#sec-module-environment-records) | всё то же, что Declarative, плюс особые "индирект-связывания" на импортированные извне значения |

Ключевая деталь устройства: у каждой записи окружения есть указатель на **внешнюю** запись — ту, что "снаружи" по отношению к текущей области видимости. Разрешение имени переменной — это буквально проход по цепочке этих указателей наружу, шаг за шагом, до первого совпадения. Именно эта простая, механическая цепочка указателей — а не что-то более экзотическое — и есть формальная основа того, что на бытовом уровне называют "лексической областью видимости" (глава 6 уже упоминала: слова "замыкание" в тексте стандарта как отдельного понятия нет вовсе — оно целиком выводится из того же самого механизма связанных друг с другом окружений).

### Function Environment Record — формальный источник всего поведения `this`

[9.1.1.3 Function Environment Records](https://262.ecma-international.org/#sec-function-environment-records) — самый практически важный из пяти видов, потому что именно здесь формально описан механизм, определяющий значение `this` внутри функции. К обычной декларативной записи здесь добавляются четыре дополнительных внутренних слота: `[[ThisValue]]` (само значение получателя), `[[ThisBindingStatus]]`, `[[FunctionObject]]` (ссылка на саму функцию), `[[NewTarget]]`.

Из этих четырёх дополнительных полей особенно важен статус связывания получателя — `[[ThisBindingStatus]]`. Он принимает одно из трёх значений, и именно проверка этого статуса — единственный формальный механизм, объясняющий буквально всё разнообразие поведения `this` в языке:

- **`lexical`** — у стрелочных функций. Стрелочная функция вообще не имеет собственного связывания получателя: обращение к `this` внутри неё формально не создаёт нового поиска, а сразу делегируется во внешнее (объемлющее) окружение. Именно поэтому явное указание получателя через `.call()`/`.bind()` для стрелочной функции физически не может сработать — менять там попросту нечего, своего слота `[[ThisValue]]` у неё нет:

```js
const arrow = () => this;
const result = arrow.call({ x: 1 });
console.log(result && result.x === 1); // false — явное указание получателя проигнорировано
```

- **`uninitialized`** — у производного конструктора класса (`extends`) до момента вызова `super()` внутри него. Пока связывание не инициализировано, любое обращение к `this` формально невозможно — попытка обратиться приводит к ошибке, той же самой природы, что временная мёртвая зона у `let`/`const` (глава 6, 14): связывание существует, но ещё не готово к использованию.
- **`initialized`** — обычное, "готовое к использованию" состояние, в котором находится `this` в любой не-стрелочной, не-производной функции с самого начала её выполнения.

```js
class Base {}
class Derived extends Base {
  constructor() {
    try { this; } catch (e) { console.log(e.constructor.name); } // ReferenceError
    super(); // переводит статус из uninitialized в initialized
    console.log(typeof this); // object
  }
}
new Derived();
```

Эта механика — прямое формальное объяснение известного правила "в производном конструкторе `super()` нужно вызвать раньше, чем использовать `this`": дело не в произвольном синтаксическом запрете, а в том, что до `super()` слот `[[ThisValue]]` попросту не существует в готовом виде, и попытка к нему обратиться формально ничем не отличается от обращения к переменной в temporal dead zone.

Операция, которая совершает этот переход состояния, называется [BindThisValue](https://262.ecma-international.org/#sec-bindthisvalue) — она срабатывает изнутри `super()` и переводит статус из `uninitialized` в `initialized`, попутно записывая в `[[ThisValue]]` объект, реально созданный вызовом конструктора базового класса. Смежная операция, [GetSuperBase](https://262.ecma-international.org/#sec-getsuperbase), объясняет механику `super.method()` — она находит не прототип текущего объекта, а прототип того класса, где буквально *написан* текущий метод (через слот `[[HomeObject]]`, подробно разбирается в главе 15), что и позволяет корректно вызывать переопределённый родительский метод независимо от того, через какой конкретно объект был вызван текущий.

### Global Environment Record — гибрид, объясняющий особенности переменных верхнего уровня

[9.1.1.4 Global Environment Records](https://262.ecma-international.org/#sec-global-environment-records) — устройство, которое многих удивляет при первом внимательном изучении: это не единая простая структура, а формальное **объединение** декларативной части (для `let`/`const`/`class` верхнего уровня) с объектной частью, надстроенной прямо поверх настоящего глобального объекта (`globalThis`):

```js
var viaVar = 1;
let viaLet = 2;
function viaFn() {}

console.log(globalThis.viaVar, globalThis.viaLet, typeof globalThis.viaFn);
// 1 undefined function

console.log(delete globalThis.viaVar); // false — свойство неконфигурируемое
```

`var`-объявления и объявления функций на верхнем уровне скрипта попадают в **объектную** часть Global Environment Record и в результате реально становятся собственными свойствами `globalThis` — именно поэтому `globalThis.viaVar` и `globalThis.viaFn` работают. При этом созданные таким образом свойства получают атрибут `[[Configurable]]: false`, поэтому `delete globalThis.viaVar` возвращает `false`, а не удаляет переменную (в нестрогом режиме `delete` для неконфигурируемого свойства просто молча не срабатывает; в строгом бросил бы `TypeError`). А вот `let viaLet = 2` живёт в декларативной части этой гибридной структуры — она формально существует в глобальной области видимости и полностью доступна по имени `viaLet`, но **не** становится свойством `globalThis` — отсюда `globalThis.viaLet === undefined`, при том что сама переменная `viaLet` прекрасно работает.

### Object Environment Record — формальная причина, почему `with` запрещён в строгом режиме

[9.1.1.2 Object Environment Records](https://262.ecma-international.org/#sec-object-environment-records) — механизм, на котором держится устаревшая конструкция `with` (подробно разбирается как часть легаси-функциональности в главе 17): внутри блока `with (obj) { ... }` поиск любого имени переменной формально превращается в проверку, есть ли такое свойство у объекта `obj` (включая унаследованные через прототипную цепочку свойства), и если есть — имя разрешается в это свойство вместо обычной переменной:

```js
'use strict';
// with(obj) {}
// SyntaxError — запрещена в строгом режиме
```

Причина запрета — прямое следствие того, как устроена Object Environment Record: поскольку она проверяет **произвольный** объект во время выполнения, движок в принципе не может заранее, на этапе статического анализа кода, определить, к какой именно переменной обратится имя внутри блока `with` — это зависит от фактического содержимого объекта `obj` в момент выполнения, которое может быть каким угодно. Это делает разрешение имён внутри `with` фундаментально **динамическим**, а не статическим, что ломает целый ряд оптимизаций движка и затрудняет статический анализ кода. Именно поэтому строгий режим, введённый во многом ради предсказуемости и производительности, полностью запрещает эту конструкцию на уровне синтаксической ошибки.

## 9.3 Реалмы — изолированные "вселенные" встроенных объектов

[9.3 Realms](https://262.ecma-international.org/#sec-code-realms) описывает ещё одну структуру, без которой необъяснимо частое практическое разочарование при работе с несколькими фреймами, окнами или изолированными контекстами выполнения: **реалм** — это полностью изолированный, отдельный набор всех встроенных объектов и функций — свой собственный `Array`, свой `Object.prototype`, свой `Error`, свой глобальный объект. У каждого окна браузера, каждого iframe, каждого воркера и каждого изолированного контекста выполнения (например, `vm.runInNewContext` в Node.js) — свой собственный реалм со своим полным набором интринсиков, не разделяемым с остальными.

```js
import { runInNewContext } from 'node:vm';
const arr = runInNewContext('[1,2,3]');
console.log(arr instanceof Array, Array.isArray(arr));
// false true
```

Массив `arr` реально создан и реально является массивом — но он создан конструктором `Array` **другого** реалма, у которого другой, отдельный объект `Array.prototype`. Оператор `instanceof` проверяет цепочку прототипов на предмет конкретного, ссылочно определённого объекта-прототипа (`Array.prototype` из *текущего* реалма) — а прототип у `arr` ссылается на `Array.prototype` из *другого* реалма, поэтому `instanceof` формально честно отвечает `false`, хотя по сути `arr` — самый обычный массив. `Array.isArray`, в отличие от `instanceof`, специально спроектирован так, чтобы проверять внутреннюю природу объекта (по факту — является ли он экзотическим объектом-массивом, глава 10), а не сравнивать конкретные ссылки на прототип, поэтому корректно отвечает `true` независимо от реалма-источника.

Практический вывод для реальной разработки: если код должен работать с объектами, которые потенциально могли прийти из другого реалма (данные из iframe, значения, переданные через `postMessage`, объекты из изолированного `vm`-контекста в Node.js), полагаться на `instanceof` для проверки типа ненадёжно — нужно использовать проверки, опирающиеся на внутреннюю природу значения, а не на конкретную ссылку на прототип (например, `Object.prototype.toString.call`, разбирается в главе 20, или именно `Array.isArray` для массивов).

## 9.4 Контексты исполнения — состояние "где мы сейчас находимся"

[9.4 Execution Contexts](https://262.ecma-international.org/#sec-execution-contexts) описывает структуру, хранящую всё состояние, необходимое движку в конкретный момент выполнения — своего рода "снимок" того, что сейчас исполняется и в каком окружении. Она состоит из семи компонентов: точка возобновления выполнения (куда вернуться после вызова функции), сама функция (или её отсутствие для кода верхнего уровня), реалм, исходный скрипт или модуль, лексическое окружение, окружение переменных, приватное окружение (для приватных полей классов, глава 15).

Контексты исполнения складываются в стек: при каждом вызове функции наверх стека кладётся новый контекст, при возврате из функции — снимается. Контекст на самой вершине стека называется **текущим исполняемым контекстом** — именно относительно него разрешаются все имена переменных и вычисляется `this` в данный конкретный момент.

Разделение состояния контекста на два формально разных компонента — `LexicalEnvironment` (окружение для лексических объявлений) и `VariableEnvironment` (окружение для `var`) — это не техническая деталь ради деталей, а прямой механизм, который разводит поведение `let` и `var` по разным правилам области видимости, уже разобранное практически в главе 8 и главе 14: обычно оба этих указателя ссылаются на одну и ту же запись окружения, но в некоторых конструкциях (например, тело блока `{ }`) для `LexicalEnvironment` создаётся новая, вложенная запись, а `VariableEnvironment` остаётся указывать на прежнюю, более внешнюю — отсюда и разное поведение при выходе из блока.

### Готовые операции над текущим контекстом — словарь для чтения дальнейших глав

Раздел вводит несколько именованных операций, часто встречающихся дальше по тексту спецификации:

- [GetActiveScriptOrModule](https://262.ecma-international.org/#sec-getactivescriptormodule) (9.4.1) — определяет, какому именно скрипту или модулю принадлежит выполняемый прямо сейчас код
- [GetThisEnvironment](https://262.ecma-international.org/#sec-getthisenvironment) (9.4.3) — поднимается вверх по цепочке окружений, пока не найдёт первое, у которого статус связывания получателя даёт содержательный ответ (то есть первую Function/Global/Module запись, минуя чисто декларативные записи без собственного `this`)
- [ResolveThisBinding](https://262.ecma-international.org/#sec-resolvethisbinding) (9.4.4) — операция, которая **фактически и есть** ключевое слово `this` в исполняемом коде: именно она вызывается движком в момент, когда в коде встречается `this`
- [GetNewTarget](https://262.ecma-international.org/#sec-getnewtarget) (9.4.5) — аналогичная операция для `new.target`
- [GetGlobalObject](https://262.ecma-international.org/#sec-getglobalobject) (9.4.6) — возвращает глобальный объект текущего реалма

```js
function f() { return this; }
console.log(typeof f.call('текст')); // 'object' — примитив оборачивается в объект (сloppy mode)
```

```js
'use strict';
function f() { return this; }
console.log(typeof f.call('текст')); // 'string' — в строгом режиме примитив передаётся как есть
```

Разница между этими двумя запусками — прямое следствие того, что `ResolveThisBinding` (и связанные с ней операции подготовки `this` при вызове функции) явно проверяет режим строгости кода: в нестрогом режиме примитивное значение получателя оборачивается во временный объект-обёртку, в строгом — передаётся как есть, без оборачивания.

### Предел глубины стека — намеренное умолчание стандарта

Здесь стоит явно зафиксировать факт, который часто вызывает удивление: конкретное ограничение на глубину стека контекстов исполнения (то есть на глубину рекурсии) **нигде не определено** самим стандартом ECMA-262. Стандарт лишь предполагает, что ресурсы конечны и что реализация вправе как-то ограничивать глубину — но точное число, поведение при превышении и даже конкретный тип возникающей ошибки полностью отданы на усмотрение конкретного движка:

```js
function probe(n = 0) { try { return probe(n + 1); } catch { return n; } }
console.log(probe() > 0); // предел, безусловно, есть, но какой — стандартом не определено
```

Знакомая всем ошибка `RangeError: Maximum call stack size exceeded` — это не требование стандарта, а конкретное, добровольное решение разработчиков V8 (и большинства других движков) о том, как сигнализировать о превышении внутреннего лимита. В тексте самой спецификации словосочетание "maximum call stack" не встречается вовсе — эта ошибка целиком принадлежит миру конкретных реализаций, а не формальному стандарту языка.

## 9.5 Задания и хостовые операции — формальная основа очереди микрозадач

[9.5 Jobs and Host Operations to Enqueue Jobs](https://262.ecma-international.org/#sec-jobs) описывает формальный механизм, стоящий за микрозадачами. Ключевая архитектурная деталь: продолжения промисов (колбэки `.then`) **не** выполняются как часть обычного, синхронного стека контекстов исполнения — они оформляются в виде отдельных "заданий" (jobs), которые ставятся в специальную очередь и извлекаются оттуда только тогда, когда стек контекстов полностью опустошился, то есть когда весь текущий синхронный код уже завершил работу:

```js
console.log('1');
setTimeout(() => console.log('4'), 0);
Promise.resolve().then(() => console.log('2')).then(() => console.log('3'));
// 1 2 3 4
```

Задания из очереди микрозадач (в неё попадают и колбэки промисов, и вызовы `queueMicrotask`) гарантированно обрабатываются **раньше**, чем движок вообще возьмётся за следующую задачу из очереди макрозадач (куда, среди прочего, попадают колбэки `setTimeout`) — подробный практический разбор порядка выполнения с несколькими примерами дан в главе 27, здесь же важно зафиксировать формальный источник этой гарантии: сама очередь заданий (Jobs) описана непосредственно текстом стандарта языка ECMAScript, а значит, это гарантия самого языка, а не случайность конкретной среды выполнения.

При этом важно четко провести границу: то, **когда именно** и **как** появляется в очереди задача таймера (`setTimeout`) или событие ввода-вывода — это **не** описано стандартом ECMA-262 вообще. Это зона ответственности "хоста" — окружения, в котором выполняется движок (браузер, Node.js, любая другая встраивающая среда), формально определяемая через отдельный набор [Host Hooks](https://262.ecma-international.org/#sec-host-hooks-summary) — точек расширения, которые сам стандарт языка оставляет незаполненными и предлагает заполнить конкретному хосту. Именно поэтому детали работы таймеров и очереди событий могут заметно различаться между браузером и Node.js, тогда как порядок обработки микрозадач гарантированно одинаков везде, где вообще реализован стандарт ECMAScript.

## 9.6–9.10 Агенты и основы модели памяти

[9.6 Agents](https://262.ecma-international.org/#sec-agents) вводит формальную единицу параллелизма — **агент**: независимый поток выполнения со своим собственным стеком контекстов исполнения (на практике — например, Web Worker или поток `worker_threads` в Node.js). [9.7 Agent Clusters](https://262.ecma-international.org/#sec-agent-clusters) описывает, какие именно агенты могут в принципе делить память между собой через `SharedArrayBuffer` (подробный практический разбор — в главах 25 и 29). [9.8 Forward Progress](https://262.ecma-international.org/#sec-forward-progress) формулирует требование, что агент не имеет права бесконечно, без ограничения по времени блокировать выполнение других агентов.

Разделы [9.9](https://262.ecma-international.org/#sec-weakref-processing-model) и [9.10](https://262.ecma-international.org/#sec-clear-kept-objects) касаются формальной модели работы `WeakRef` (подробно разбирается на практике в главе 26) и дают одну конкретную, практически полезную гарантию: движок обязан устроить работу так, чтобы объект, на который ссылается `WeakRef`, **не мог** быть собран сборщиком мусора *в середине* выполнения одного синхронного участка кода — даже если формально на объект больше не осталось ни одной сильной ссылки:

```js
function demo() {
  let obj = {};
  const ref = new WeakRef(obj);
  obj = null; // единственная сильная ссылка снята прямо здесь
  // в пределах этого же синхронного участка ref.deref() гарантированно вернёт объект
  console.log(ref.deref() !== undefined); // true
}
demo();
```

Формальный механизм, обеспечивающий эту гарантию, называется "список удерживаемых объектов текущего задания" ([9.10 Clear Kept Objects](https://262.ecma-international.org/#sec-clear-kept-objects)) — каждый объект, на который была получена слабая ссылка в рамках текущего синхронного задания, временно удерживается от сборки до конца этого задания, и очищается только когда задание полностью завершается. Без этой гарантии `WeakRef.prototype.deref()` теоретически мог бы неожиданно вернуть `undefined` даже сразу после создания самой слабой ссылки, если бы сборщик мусора успел сработать в произвольный момент прямо посреди синхронного кода — что сделало бы `WeakRef` практически непредсказуемым и непригодным для использования.

## Итог

> [!summary] Что взять с собой
> - Пять видов записи окружения (Declarative, Object, Function, Global, Module) реализуют общий интерфейс операций; разрешение имени переменной — проход по цепочке указателей на внешнее окружение
> - Function Environment Record хранит статус связывания `this`: `lexical` (стрелочные функции — своего `this` нет вообще), `uninitialized` (производный конструктор до `super()`), `initialized` (обычный случай) — это единственный формальный механизм, объясняющий всё поведение `this`
> - `super()` переводит статус связывания получателя из `uninitialized` в `initialized` через операцию `BindThisValue`
> - Global Environment Record — гибрид: `var`/функции верхнего уровня попадают в объектную часть и становятся неконфигурируемыми свойствами `globalThis`; `let`/`const`/`class` — в декларативную часть и свойствами `globalThis` не становятся
> - `with` работает через Object Environment Record и запрещён в строгом режиме именно потому, что делает разрешение имён принципиально динамическим, зависящим от содержимого произвольного объекта в рантайме
> - Реалм — полностью изолированный набор встроенных объектов (свой `Array`, `Object.prototype` и так далее); `instanceof` через границу реалма ненадёжен, `Array.isArray` и подобные проверки внутренней природы — надёжны
> - Контекст исполнения хранит семь компонентов состояния; разделение `LexicalEnvironment`/`VariableEnvironment` — формальный механизм, разводящий поведение `let` и `var`
> - Предел глубины стека нигде не определён спецификацией — `RangeError: Maximum call stack size exceeded` целиком принадлежит миру конкретных реализаций, а не тексту стандарта
> - Очередь микрозадач (Jobs) описана самим языком, поэтому её порядок гарантирован везде; таймеры и события ввода-вывода — зона ответственности хоста (Host Hooks), отсюда различия между средами выполнения
> - Агент — единица параллелизма со своим стеком контекстов; `WeakRef` гарантированно не теряет объект в пределах одного синхронного участка кода благодаря механизму удерживаемых объектов текущего задания
