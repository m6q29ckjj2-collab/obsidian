> [!question] Чему соответствует каждая функция объекта `Reflect`?
> a) одному методу `Array.prototype`
> b) одному внутреннему методу объекта ([[Get]], [[Set]], [[Delete]] и другим)
> c) одному хорошо известному символу
> d) одному типу ошибки
>> [!success]- Answer
>> b) одному внутреннему методу объекта ([[Get]], [[Set]], [[Delete]] и другим)
>> `Reflect` — прямой, вызываемый как обычная функция доступ к тем же внутренним операциям, которые движок неявно вызывает при обычном коде

> [!question] Чем `Reflect.deleteProperty(obj, key)` практически удобнее оператора `delete obj[key]`?
> a) работает быстрее
> b) это обычная функция, которую можно передать как значение в map/forEach или сохранить в переменную
> c) может удалять неконфигурируемые свойства, в отличие от delete
> d) ничем, это полные синонимы без разницы
>> [!success]- Answer
>> b) это обычная функция, которую можно передать как значение в map/forEach или сохранить в переменную
>> Синтаксическую конструкцию `delete` нельзя передать как значение — `Reflect.deleteProperty` можно

> [!question] Что выведет код?
> ```js
> 'use strict';
> const frozen = Object.freeze({ x: 1 });
> console.log(Reflect.set(frozen, 'x', 2));
> ```
> a) выбросит `TypeError`, как обычное присваивание в строгом режиме
> b) `false`
> c) `true`
> d) `undefined`
>> [!success]- Answer
>> b) `false`
>> `Reflect.set` сообщает о неудаче через возвращаемое булево значение, а не через исключение — в отличие от обычного присваивания `frozen.x = 2` в строгом режиме, которое бросает `TypeError`

> [!question] Что выведет код?
> ```js
> class A {} class B {}
> const obj = Reflect.construct(A, [], B);
> console.log(obj instanceof A, obj instanceof B);
> ```
> a) `true false`
> b) `false true`
> c) `true true`
> d) `false false`
>> [!success]- Answer
>> b) `false true`
>> Третий аргумент `Reflect.construct` задаёт `new.target` — именно он определяет, чей `.prototype` станет прототипом созданного объекта. Такого результата нельзя добиться через обычный `new A()`

> [!question] Что происходит, если ловушка не определена в объекте `handler`, переданном в `new Proxy(target, handler)`?
> a) выбрасывается TypeError при первом же обращении
> b) операция автоматически делегируется реальному внутреннему методу цели
> c) операция молча ничего не делает
> d) прокси становится нерасширяемым
>> [!success]- Answer
>> b) операция автоматически делегируется реальному внутреннему методу цели
>> Только явно определённые ловушки перехватывают поведение — остальные операции проходят к target как обычно

> [!question] Чем обычно заканчивается реализация типичной ловушки Proxy, чтобы сохранить стандартное поведение везде, кроме нужного изменения?
>> [!success]- Answer
>> Вызовом соответствующей функции Reflect для цели (например, `return Reflect.get(target, prop, receiver);`)
>> Это прямая связь между Reflect и Proxy — Reflect даёт способ «передать управление дальше» настоящему поведению внутри ловушки

> [!question] Что выведет код?
> ```js
> const target = {};
> Object.defineProperty(target, 'locked', { value: 42, writable: false, configurable: false });
> const proxy = new Proxy(target, { get() { return 999; } });
> console.log(proxy.locked);
> ```
> a) `999`
> b) `42`
> c) выбросит `TypeError`
> d) `undefined`
>> [!success]- Answer
>> c) выбросит `TypeError`
>> Ловушка `get` не может солгать о значении неконфигурируемого, доступного только для чтения свойства цели — движок сам проверяет этот инвариант независимо от того, что вернула ловушка

> [!question] Может ли ловушка `has` скрыть неконфигурируемое свойство цели, вернув `false` для `'x' in proxy`?
>> [!success]- Answer
>> False
>> Это тоже нарушение инварианта Proxy — попытка скрыть неконфигурируемое свойство цели приводит к `TypeError`

> [!question] Зачем спецификация принудительно проверяет инварианты Proxy для неконфигурируемых свойств?
> a) чтобы упростить реализацию движков
> b) чтобы гарантия неконфигурируемости, данная через Object.defineProperty, не теряла смысл в присутствии Proxy
> c) исторически так сложилось, практической причины нет
> d) чтобы ускорить доступ к таким свойствам
>> [!success]- Answer
>> b) чтобы гарантия неконфигурируемости, данная через Object.defineProperty, не теряла смысл в присутствии Proxy
>> Если бы Proxy мог полностью скрыть или подменить такое свойство без контроля, сама концепция неконфигурируемости стала бы бессмысленной

> [!question] Что делает функция `revoke`, полученная из `Proxy.revocable(target, handler)`?
> a) возвращает прокси в исходное состояние handler
> b) навсегда деактивирует прокси — любая операция с ним выбрасывает TypeError
> c) удаляет целевой объект из памяти
> d) отключает только ловушку get, остальные продолжают работать
>> [!success]- Answer
>> b) навсегда деактивирует прокси — любая операция с ним выбрасывает TypeError
>> После вызова `revoke()` доступ к прокси заблокирован навсегда, независимо от того, что делают сами ловушки

> [!question] Для какой типичной задачи полезен именно `Proxy.revocable`, а не обычный `new Proxy`?
> a) для повышения производительности
> b) для передачи объекта недоверенному стороннему коду с возможностью полностью отрезать доступ позже
> c) для работы с типизированными массивами
> d) для сериализации в JSON
>> [!success]- Answer
>> b) для передачи объекта недоверенному стороннему коду с возможностью полностью отрезать доступ позже
>> Одним вызовом `revoke()` можно заблокировать доступ, не отслеживая все места, куда объект был передан ранее

> [!question] Ловушка `set` объекта Proxy может использоваться для валидации значений перед записью, бросая исключение при недопустимом значении
>> [!success]- Answer
>> True
>> Это один из типичных практических сценариев использования Proxy, наряду с логированием, виртуальными свойствами и реализацией значений по умолчанию

> [!question] Является ли `Reflect` конструктором, который можно вызвать через `new Reflect()`?
>> [!success]- Answer
>> False
>> `Reflect`, как `Math` и `JSON`, — объект-неймспейс со статическими функциями, а не конструктор

> [!question] Module Namespace Object (`import * as ns`), разбиравшийся в главе 16, упоминается в главе про рефлексию, потому что...
> a) он реализован через настоящий Proxy изнутри
> b) это тоже экзотический объект с переопределёнными внутренними методами — тот же общий механизм, что делает возможным Proxy
> c) он не имеет отношения к внутренним методам вообще
> d) это устаревшая функциональность
>> [!success]- Answer
>> b) это тоже экзотический объект с переопределёнными внутренними методами — тот же общий механизм, что делает возможным Proxy
>> Разница в том, что для модулей этот механизм зашит в язык напрямую для одной конкретной цели, а не выставлен программисту как настраиваемый инструмент
