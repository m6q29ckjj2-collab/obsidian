# Глава 28 · Рефлексия (Reflect, Proxy)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [28 Reflection](https://262.ecma-international.org/#sec-reflection)

В главе 10 мы разбирали **внутренние методы** объекта — `[[Get]]`, `[[Set]]`, `[[DefineOwnProperty]]`, `[[OwnPropertyKeys]]` и остальные — абстрактные операции, которые движок вызывает сам, когда выполняет обычный код (`obj.x`, `obj.x = 1`, `for...in`). Обычному коду напрямую вызвать эти внутренние методы нельзя — они не выставлены как что-то, что можно позвать по имени. `Reflect` — это ровно такой публичный, «плоский» доступ к ним. `Proxy` — обратная сторона того же механизма: возможность **перехватить** и переопределить эти внутренние методы для конкретного объекта. Вместе они превращают в явную, программируемую операцию то, что обычно происходит неявно при каждом обращении к свойству.

---

## 28.1 Reflect — прямой вызов внутренних методов

[28.1 The Reflect Object](https://262.ecma-international.org/#sec-reflect-object) — объект-неймспейс (как `Math` и `JSON`, не конструктор) с набором статических функций, каждая из которых практически один в один соответствует одному внутреннему методу из главы 10: `Reflect.get`/`Reflect.set` ↔ `[[Get]]`/`[[Set]]`, `Reflect.has` ↔ `[[HasProperty]]`, `Reflect.deleteProperty` ↔ `[[Delete]]`, `Reflect.ownKeys` ↔ `[[OwnPropertyKeys]]`, `Reflect.defineProperty` ↔ `[[DefineOwnProperty]]`, `Reflect.getPrototypeOf`/`setPrototypeOf` ↔ `[[GetPrototypeOf]]`/`[[SetPrototypeOf]]`, `Reflect.apply`/`Reflect.construct` ↔ `[[Call]]`/`[[Construct]]`.

### Зачем нужен `Reflect`, если для большинства операций уже есть привычный синтаксис

Многие операции `Reflect` дублируют то, что и так можно сделать обычным синтаксисом (`obj.x`, `delete obj.x`, `'x' in obj`) — так что на первый взгляд `Reflect` выглядит избыточным. Но есть конкретные практические причины, почему это отдельный, самостоятельно ценный набор функций:

**Функции, а не операторы — их можно передавать и комбинировать.** `delete obj[key]` — синтаксическая конструкция, её нельзя передать как значение в `.map()` или сохранить в переменную. `Reflect.deleteProperty` — обычная функция:

```js
const keysToRemove = ['a', 'b', 'c'];
const obj = { a: 1, b: 2, c: 3, d: 4 };
keysToRemove.forEach(key => Reflect.deleteProperty(obj, key));
console.log(obj); // { d: 4 }
```

**Сообщают об ошибке через возвращаемое булево значение, а не исключение.** Это — самое практически важное отличие. Обычная запись `obj.x = 1` в нестрогом режиме молча проглатывает неудачу (например, если свойство нерасширяемо), а в строгом режиме бросает исключение. `Reflect.set` в обоих случаях просто возвращает `true`/`false`, оставляя решение о том, что делать с неудачей, вызывающему коду:

```js
'use strict';
const frozen = Object.freeze({ x: 1 });

try {
  frozen.x = 2; // обычное присваивание в строгом режиме — TypeError
} catch (e) {
  console.log(e.constructor.name); // TypeError
}

console.log(Reflect.set(frozen, 'x', 2)); // false — сообщает о неудаче без исключения
```

Это особенно важно при написании ловушек `Proxy` (ниже) — реализация ловушки `set` часто должна вернуть булево значение успеха/неудачи, а не бросить исключение, и `Reflect.set` даёт для этого прямой, естественный способ передать управление настоящему внутреннему методу цели.

**`Reflect.construct` позволяет вызвать конструктор с произвольным `new.target`.** Третий, необязательный аргумент задаёт значение `new.target`, которое конструктор увидит внутри себя — а `new.target` определяет, чей `.prototype` станет прототипом создаваемого объекта (разбирали в главе 15 применительно к производным конструкторам):

```js
class A { constructor() { this.tag = 'A'; } }
class B { constructor() { this.tag = 'B'; } }

const obj = Reflect.construct(A, [], B); // выполняем конструктор A, но с newTarget = B
console.log(obj instanceof B); // true — прототип взят от B, не от A
console.log(obj instanceof A); // false
console.log(obj.tag);          // 'A' — сам код конструктора A выполнился как обычно
```

Такого результата нельзя добиться через `new A()` — обычный синтаксис `new` всегда устанавливает `new.target` равным самому вызываемому конструктору. `Reflect.construct` — единственный способ явно подставить другое значение, что используется в продвинутых паттернах наследования и при реализации кастомных фабрик объектов.

## 28.2 Proxy — перехват внутренних методов

[28.2 Proxy Objects](https://262.ecma-international.org/#sec-proxy-objects) — механизм, позволяющий создать объект-обёртку (`target` — то, что оборачивается, `handler` — набор функций-ловушек), где каждая ловушка перехватывает соответствующий внутренний метод. Если ловушка не определена в `handler`, операция автоматически делегируется настоящему внутреннему методу `target` — отсюда прямая связь с `Reflect`: типичная реализация ловушки почти всегда заканчивается вызовом соответствующей `Reflect`-функции для цели, чтобы сохранить стандартное поведение везде, кроме того единственного места, которое действительно нужно изменить:

```js
const log = [];
const target = { value: 42 };

const proxy = new Proxy(target, {
  get(target, prop, receiver) {
    log.push(`чтение: ${String(prop)}`);
    return Reflect.get(target, prop, receiver); // делегируем настоящему поведению
  },
  set(target, prop, value, receiver) {
    log.push(`запись: ${String(prop)} = ${value}`);
    return Reflect.set(target, prop, value, receiver);
  }
});

proxy.value;      // читаем
proxy.value = 99;  // пишем
console.log(log);  // ['чтение: value', 'запись: value = 99']
console.log(target.value); // 99 — изменения проходят к настоящему объекту
```

### Инварианты — Proxy не может лгать о нерасширяемых/неконфигурируемых свойствах цели

Ключевое ограничение, зафиксированное прямо в спецификации: ловушки не дают Proxy **абсолютной** свободы врать о состоянии — для ряда случаев (в первую очередь связанных с неконфигурируемыми и нерасширяемыми свойствами) спецификация требует **инвариант**: результат работы ловушки обязан быть согласован с реальным состоянием цели, и если он нарушен — движок сам бросает `TypeError`, независимо от того, что вернула ловушка:

```js
const target2 = {};
Object.defineProperty(target2, 'locked', { value: 42, writable: false, configurable: false });

const lyingProxy = new Proxy(target2, {
  get() { return 999; } // пытаемся соврать о значении неконфигурируемого свойства
});

try {
  console.log(lyingProxy.locked);
} catch (e) {
  console.log(e.constructor.name); // TypeError — движок сам обнаружил нарушение инварианта
}
```

Та же защита действует для ловушки `has` (нельзя скрыть неконфигурируемое свойство цели через `'x' in proxy` → `false`) и для `ownKeys` (результат обязан включать все неконфигурируемые собственные ключи цели):

```js
const proxyHidingKey = new Proxy(target2, { has() { return false; } });
try {
  console.log('locked' in proxyHidingKey);
} catch (e) {
  console.log(e.constructor.name); // TypeError
}
```

Смысл этого ограничения — сохранить полезность самого понятия «неконфигурируемое свойство» как гарантии, данной когда-то через `Object.defineProperty`. Если бы `Proxy` мог полностью скрыть или подменить такое свойство без всякого контроля, гарантия неконфигурируемости переставала бы что-либо значить в присутствии прокси — а инварианты явно закрывают эту лазейку.

### `Proxy.revocable` — прокси, который можно «выключить»

Обычный `new Proxy(target, handler)` создаёт постоянно действующую обёртку. [28.2.2.1 Proxy.revocable](https://262.ecma-international.org/#sec-proxy.revocable) даёт вариант с функцией `revoke`, вызов которой навсегда деактивирует прокси — любая последующая операция с ним выбрасывает `TypeError`, независимо от того, что делают ловушки:

```js
const { proxy: p, revoke } = Proxy.revocable({}, {});
p.foo; // работает как обычно, ничего не выброшено

revoke();

try {
  p.foo; // тот же самый объект proxy
} catch (e) {
  console.log(e.constructor.name); // TypeError — доступ навсегда заблокирован
}
```

Практическое применение — передать объект во внешний, не полностью доверенный код (например, стороннюю библиотеку или плагин) с возможностью полностью отрезать этот код от доступа к объекту позже, одним вызовом `revoke()`, не отслеживая все места, куда объект был передан.

### Типичные применения Proxy

Помимо логирования из примера выше, распространённые практические сценарии: валидация при записи (ловушка `set`, бросающая исключение при недопустимом значении вместо тихого игнорирования), виртуальные/вычисляемые свойства (ловушка `get`, вычисляющая значение на лету вместо хранения), объекты с значением по умолчанию для любого не заданного явно свойства (ловушка `get`, возвращающая дефолт вместо `undefined`), и реализация паттерна «неизменяемое представление» поверх изменяемого объекта (ловушки `set`/`defineProperty`/`deleteProperty`, всегда возвращающие `false`).

## 28.3 Module Namespace Objects — беглое напоминание

[28.3 Module Namespace Objects](https://262.ecma-international.org/#sec-module-namespace-objects) в этой главе — не новая тема, а формальная точка, где спецификация фиксирует ссылку на уже разобранный в главе 16 объект `import * as ns`. Он упоминается здесь, потому что это тоже **экзотический объект** с переопределёнными внутренними методами — тот же общий механизм, что делает возможным `Proxy`, просто зашитый в язык напрямую для одной конкретной цели, а не выставленный программисту как настраиваемый инструмент.

## Итог

> [!summary] Что взять с собой
> - `Reflect` — плоский, вызываемый как обычная функция доступ к внутренним методам объекта из главы 10 (`[[Get]]`, `[[Set]]`, `[[Delete]]`...)
> - Функции `Reflect` можно передавать как значения (в `map`, сохранять в переменные) — в отличие от синтаксических конструкций вроде `delete obj.x`
> - `Reflect.set`/`Reflect.defineProperty` и другие сообщают об успехе/неудаче через возвращаемое булево значение, а не через исключение — удобно внутри ловушек Proxy
> - `Reflect.construct(Ctor, args, newTarget)` позволяет вызвать конструктор с произвольным `new.target`, определяющим, чей `.prototype` получит созданный объект — недостижимо через обычный `new`
> - `Proxy` перехватывает внутренние методы объекта через ловушки (`get`, `set`, `has`, `deleteProperty`, `ownKeys`...); невызванная ловушка автоматически делегируется настоящему поведению цели
> - Типичная ловушка вызывает соответствующую функцию `Reflect` для цели, чтобы сохранить стандартное поведение везде, кроме нужного изменения
> - Спецификация принудительно проверяет **инварианты**: ловушка не может солгать о значении/наличии неконфигурируемого свойства цели — нарушение даёт `TypeError`, даже если сама ловушка ничего не бросала
> - `Proxy.revocable` создаёт прокси вместе с функцией `revoke`, после вызова которой любая операция с прокси навсегда становится `TypeError` — удобно для передачи объекта недоверенному коду с возможностью отозвать доступ позже
