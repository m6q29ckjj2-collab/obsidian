# Глава 24 · Коллекции по ключу (Map, Set, WeakMap, WeakSet)

> [!info] Навигация
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта раздела → [[00 Карта]]
> Официальный текст: [24 Keyed Collections](https://262.ecma-international.org/#sec-keyed-collections)

До появления `Map` и `Set` в языке единственным «словарём» был обычный объект — с рядом структурных ограничений, которые часто были неудобны: ключами могли быть только строки и символы, порядок перечисления подчинялся сложным правилам (глава 10), а размер приходилось считать вручную через `Object.keys(obj).length`. `Map` и `Set` устраняют эти ограничения явным образом. `WeakMap` и `WeakSet` — их специализированные варианты, созданные не для удобства, а для одной конкретной задачи: не мешать сборщику мусора.

---

## 24.1 Map — словарь с произвольными ключами

### Равенство ключей — SameValueZero, не `===`

Ключевой вопрос для любой структуры вида «словарь» — как именно определяется, что два ключа «одинаковые». `Map` использует не `===` (Strict Equality) и не `Object.is` (SameValue), а третий алгоритм равенства из главы 7 — **SameValueZero**: он ведёт себя как `===`, кроме одного отличия — `NaN` считается равным самому себе:

```js
const m = new Map();
m.set(NaN, 'значение для NaN');
console.log(m.get(NaN)); // 'значение для NaN' — NaN находит сам себя как ключ

m.set(0, 'a');
m.set(-0, 'b');
console.log(m.size);     // 1 — +0 и -0 SameValueZero считает одним и тем же ключом
console.log(m.get(0));   // 'b' — второй set() перезаписал значение по тому же ключу
```

Это прямое практическое следствие того, что обычный объект в принципе не мог бы использовать `NaN` как рабочий ключ (все ключи объекта — строки или символы, `NaN` превратился бы в строку `'NaN'`, что работало бы, но случайно, а не по замыслу). `Map` же честно поддерживает `NaN` как полноценный, уникальный, самонаходимый ключ — то же поведение, что и у `Set.prototype.has`/`Array.prototype.includes`, разобранных в предыдущих главах: все они используют один и тот же алгоритм SameValueZero, а не строгое равенство.

### Ключом может быть что угодно — включая объекты и функции

В обычном объекте любой нестроковый и несимвольный ключ **приводится к строке** при обращении (`obj[{}]` фактически становится `obj['[object Object]']`). У `Map` ключом может быть **любое значение любого типа** без приведения — включая сами объекты, массивы, функции:

```js
const m = new Map();
const objKey = {};
m.set(objKey, 'значение, привязанное именно к этому объекту');

console.log(m.get(objKey));  // работает — это именно тот же самый объект-ключ
console.log(m.get({}));      // undefined — другой объект с той же (пустой) структурой — другой ключ
```

Сравнение ключей-объектов происходит **по ссылке**, а не по структуре — два разных объекта с одинаковым содержимым будут разными ключами. Это делает `Map` подходящим инструментом для задач вроде «привязать метаданные к конкретному DOM-элементу» или «закешировать результат по объекту-параметру», где обычный объект такого сделать не может в принципе — ему пришлось бы серилизовать объект-ключ в строку, теряя идентичность.

### Порядок перечисления — строго порядок вставки

В отличие от обычного объекта, где порядок собственных ключей подчиняется правилу «сначала числовые ключи по возрастанию, потом строковые в порядке добавления, потом символьные» (разбирали в главе 10 — [OrdinaryOwnPropertyKeys](https://262.ecma-international.org/#sec-ordinaryownpropertykeys)), у `Map` порядок итерации **всегда** совпадает с порядком, в котором ключи были добавлены — без исключений для «похожих на числа» ключей:

```js
const m = new Map();
m.set('z', 1);
m.set('a', 2);
m.set('m', 3);
console.log([...m.keys()]); // ['z', 'a', 'm'] — точно порядок вставки, без пересортировки

const obj = {};
obj['z'] = 1; obj[1] = 'x'; obj['a'] = 2;
console.log(Object.keys(obj)); // ['1', 'z', 'a'] — числовой ключ '1' выпрыгнул вперёд
```

Если порядок перечисления важен для логики программы, `Map` — структурно более предсказуемый выбор, чем обычный объект, у которого этот порядок выглядит как побочный эффект внутреннего устройства, а не как явная гарантия.

### `size` — геттер-свойство, а не метод

[24.1.3.12 get Map.prototype.size](https://262.ecma-international.org/#sec-get-map.prototype.size) — это именно **геттер**, определённый через `Object.defineProperty` с функцией доступа, а не обычное свойство-число и не метод. Обращаться нужно как к свойству (`m.size`), а не вызывать как функцию (`m.size()`, что было бы ошибкой — `size` не функция):

```js
const desc = Object.getOwnPropertyDescriptor(Map.prototype, 'size');
console.log(typeof desc.get); // 'function' — есть функция-геттер
console.log(desc.value);      // undefined — обычного значения нет, оно вычисляется при каждом обращении
```

Это тот же паттерн аксессорных свойств, что уже разбирался в главе 10 применительно к `__proto__` — свойство выглядит как обычное данные, но фактически вычисляется функцией при каждом чтении.

### Сигнатура `forEach` унаследована от `Array`, даже там, где это избыточно

[24.1.3.5 Map.prototype.forEach](https://262.ecma-international.org/#sec-map.prototype.foreach) вызывает колбэк с тремя аргументами: `(value, key, map)` — умышленно тот же порядок, что у `Array.prototype.forEach` (`(value, index, array)`), чтобы код, привычный к массивам, переносился на `Map` без сюрпризов в порядке параметров.

```js
new Map([['k', 'v']]).forEach((value, key, map) => {
  console.log(value, key); // 'v' 'k' — значение идёт первым аргументом, как и у массивов
});
```

## 24.2 Set — коллекция уникальных значений

`Set` использует ту же логику равенства (SameValueZero) и тот же порядок вставки, что и `Map` — фактически это `Map`, где ключ и значение всегда совпадают. Это видно даже в сигнатуре [24.2.4.7 Set.prototype.forEach](https://262.ecma-international.org/#sec-set.prototype.foreach): колбэк получает `(value, value, set)` — значение передаётся **дважды**, потому что оно одновременно и «ключ», и «значение»:

```js
new Set(['x']).forEach((value, key, set) => {
  console.log(value === key); // true — намеренное сохранение единого API с Map.prototype.forEach
});
```

### Новые методы теоретико-множественных операций (недавнее дополнение)

Долгое время `Set` не предоставлял встроенных способов вычислить объединение, пересечение или разность двух множеств — приходилось писать это вручную через `filter`/spread. Относительно недавно спецификация добавила прямые методы для стандартных операций теории множеств: [`union`](https://262.ecma-international.org/#sec-set.prototype.union), [`intersection`](https://262.ecma-international.org/#sec-set.prototype.intersection), [`difference`](https://262.ecma-international.org/#sec-set.prototype.difference), [`symmetricDifference`](https://262.ecma-international.org/#sec-set.prototype.symmetricdifference), а также предикаты [`isSubsetOf`](https://262.ecma-international.org/#sec-set.prototype.issubsetof), [`isSupersetOf`](https://262.ecma-international.org/#sec-set.prototype.issupersetof), [`isDisjointFrom`](https://262.ecma-international.org/#sec-set.prototype.isdisjointfrom):

```js
const a = new Set([1, 2, 3]);
const b = new Set([2, 3, 4]);

console.log([...a.union(b)]);              // [1, 2, 3, 4]
console.log([...a.intersection(b)]);       // [2, 3]
console.log([...a.difference(b)]);         // [1] — есть в a, но нет в b
console.log([...a.symmetricDifference(b)].sort()); // [1, 4] — есть только в одном из двух

console.log(new Set([1, 2]).isSubsetOf(a)); // true
console.log(a.isDisjointFrom(new Set([9, 10]))); // true — нет общих элементов
```

Каждый из этих методов принимает не только настоящий `Set`, а любой объект, соответствующий минимальному «протоколу похожести на множество» ([24.2.1.1 Set Records](https://262.ecma-international.org/#sec-set-records) — наличие `size`, `has` и `keys`), что снова является примером открытого протокола вместо жёсткой проверки конкретного класса — той же идеи, что уже встречалась с итерируемостью и well-known symbols.

## 24.3–24.4 WeakMap и WeakSet — намеренно урезанный API

`WeakMap` и `WeakSet` выглядят как облегчённые версии `Map`/`Set`, но их назначение принципиально другое: они существуют, чтобы **не мешать сборщику мусора** удалять объекты, на которые ничто, кроме этой коллекции, больше не ссылается. Обычная `Map` держит **сильную** ссылку на свои ключи — пока запись в `Map` жива, ключ-объект никогда не будет собран сборщиком мусора, даже если на него больше нигде в программе не осталось ссылок. Это может приводить к утечкам памяти, если `Map` используется как долгоживущий кеш, привязанный к объектам с коротким временем жизни. `WeakMap` держит **слабую** ссылку: если на объект-ключ больше нет никаких других сильных ссылок в программе, движок вправе собрать этот объект и автоматически удалить соответствующую запись из `WeakMap`, не дожидаясь явного `delete`.

Из этого прямо следует набор жёстких структурных ограничений API, которые на первый взгляд выглядят как «недоделанный `Map`», но на самом деле обязательны для самой концепции слабых ссылок:

```js
const wm = new WeakMap();

try {
  wm.set(1, 'x'); // числовой примитив как ключ
} catch (e) {
  console.log(e.constructor.name); // TypeError
}
// числа, строки, булевы значения никогда не удаляются сборщиком мусора —
// «слабость» ссылки для них попросту бессмысленна

const key = {};
wm.set(key, 'ok'); // с объектом-ключом всё работает как у обычной Map

// неожиданная деталь: обычный (не зарегистрированный) символ тоже подходит как ключ
const uniqueSym = Symbol('локальный');
wm.set(uniqueSym, 'тоже работает'); // OK — у такого символа нет других постоянных ссылок на него

const registeredSym = Symbol.for('глобальный-ключ');
try {
  wm.set(registeredSym, 'x'); // символ из глобального реестра Symbol.for
} catch (e) {
  console.log(e.constructor.name); // TypeError
}
// зарегистрированный символ, наоборот, НЕ подходит: он живёт в глобальном реестре
// вечно и в принципе не может быть собран сборщиком мусора — слабая ссылка на него
// была бы противоречием в терминах

console.log('size' in wm);          // false — свойства size не существует
console.log(typeof wm[Symbol.iterator]); // 'undefined' — WeakMap не итерируем
```

Почему нет `size`, перебора (`forEach`, `keys`, `entries`, `Symbol.iterator`) и метода `clear`? Потому что момент, когда сборщик мусора реально освобождает объект, **не специфицирован и непредсказуем** — он может произойти в любой момент между тем, как последняя внешняя ссылка на ключ исчезла, и произвольным более поздним временем, когда до объекта дойдёт очередь сборщика. Если бы у `WeakMap` было наблюдаемое количество записей или возможность их перечислить, это количество могло бы измениться «само по себе» между двумя последовательными обращениями к программе без единой явной операции `set`/`delete` — то есть работа сборщика мусора стала бы наблюдаемой снаружи, а спецификация явно избегает делать сборку мусора частью наблюдаемого поведения языка. Отсюда — намеренно «урезанный» API: только `get`/`set`/`has`/`delete` для `WeakMap` и `add`/`has`/`delete` для `WeakSet`, ничего, что позволило бы заглянуть внутрь или посчитать содержимое.

Типичный практический случай использования `WeakMap` — привязка приватных или вычисляемых данных к объекту без риска утечки памяти и без изменения самого объекта: например, кеш результатов дорогой операции, ключом для которого служит объект-параметр, который может быть удалён пользователем структуры данных в любой момент — запись в кеше исчезнет вместе с ним автоматически, вместо того чтобы вечно занимать память.

## Итог

> [!summary] Что взять с собой
> - `Map`/`Set` сравнивают ключи через **SameValueZero**: `NaN` находит сам себя, `+0` и `-0` — один и тот же ключ (тот же алгоритм равенства, что и у `Array.prototype.includes`)
> - Ключом `Map` может быть любое значение, включая объекты и функции — сравнение объектов-ключей идёт по ссылке, а не по структуре; обычный объект такого не умеет (ключи всегда приводятся к строке)
> - Порядок итерации `Map`/`Set` — строго порядок вставки, без «особого случая» для числовых ключей, который есть у обычных объектов
> - `size` — геттер-свойство, а не метод: `m.size`, не `m.size()`
> - `Map.prototype.forEach` вызывает колбэк как `(value, key, map)` — тот же порядок аргументов, что у `Array.prototype.forEach`, ради переносимого API
> - `Set.prototype.forEach` передаёт значение дважды — `(value, value, set)`, потому что в множестве значение и есть «ключ»
> - Новые методы `Set` — `union`, `intersection`, `difference`, `symmetricDifference`, `isSubsetOf`, `isSupersetOf`, `isDisjointFrom` — реализуют стандартные теоретико-множественные операции без ручного кода
> - `WeakMap`/`WeakSet` держат **слабые** ссылки на объекты-ключи — не мешают сборщику мусора удалить объект, если на него больше нет других ссылок
> - Ключом `WeakMap`/`WeakSet` может быть объект или обычный (не зарегистрированный через `Symbol.for`) символ — остальные примитивы не принимаются, им нечего «слабо ссылаться»; зарегистрированный символ тоже не подходит, потому что живёт в глобальном реестре вечно
> - У `WeakMap`/`WeakSet` намеренно нет `size`, перебора и `clear()` — потому что момент сборки мусора не специфицирован, и наблюдаемый счётчик записей сделал бы работу сборщика мусора видимой снаружи, что спецификация принципиально не допускает
