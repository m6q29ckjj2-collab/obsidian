# Глава 10 · Обычные и экзотические объекты — отчёт

> [!info] Раздел спецификации
> [10 Ordinary and Exotic Objects Behaviours](https://262.ecma-international.org/#sec-ordinary-and-exotic-objects-behaviours)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Глава 6 объявила общий принцип: объект — это, по существу, набор из одиннадцати внутренних методов, а не просто "коллекция пар ключ-значение". Эта глава — прямое, детальное продолжение того объявления: здесь описано **как именно** каждый из этих методов реализован по умолчанию для самого обычного объекта, и — что практически даже важнее — что именно переопределяют массивы, функции, строки, объект `arguments`, прокси и другие "особые" объекты языка, чтобы вести себя не так, как обычный объект. Понимание этой главы превращает добрую половину "странностей" JavaScript (почему массивы ведут себя не как обычные объекты, почему `bind` нельзя переопределить повторным `bind`, почему прокси не может соврать про замороженный объект) из списка отдельных, никак не связанных фактов в следствия одного общего механизма.

## 10.1 Внутренние методы обычного объекта

[10.1 Ordinary Object Internal Methods and Internal Slots](https://262.ecma-international.org/#sec-ordinary-object-internal-methods-and-internal-slots) даёт эталонную, "поведение по умолчанию" реализацию всех одиннадцати внутренних методов, о которых глава 6 говорила пока только в общих чертах. Именно эта таблица определяет, что вообще значит слово "обычный" (ordinary) применительно к объекту: объект называется обычным тогда и только тогда, когда **каждый** из этих одиннадцати методов реализован ровно так, как здесь описано, без единого отклонения.

| Метод | Раздел | Что делает |
|---|---|---|
| `[[GetPrototypeOf]]` | [10.1.1.1](https://262.ecma-international.org/#sec-ordinarygetprototypeof) | вернуть значение внутреннего слота прототипа |
| `[[SetPrototypeOf]]` | [10.1.2.1](https://262.ecma-international.org/#sec-ordinarysetprototypeof) | сменить прототип, при этом явно запретить создание цикла в цепочке прототипов |
| `[[IsExtensible]]` | [10.1.3.1](https://262.ecma-international.org/#sec-ordinaryisextensible) | проверить внутренний флаг расширяемости объекта |
| `[[PreventExtensions]]` | [10.1.4.1](https://262.ecma-international.org/#sec-ordinarypreventextensions) | необратимо сбросить флаг расширяемости в `false` |
| `[[GetOwnProperty]]` | [10.1.5.1](https://262.ecma-international.org/#sec-ordinarygetownproperty) | вернуть полный дескриптор собственного (не унаследованного) свойства |
| `[[DefineOwnProperty]]` | [10.1.6.1](https://262.ecma-international.org/#sec-ordinarydefineownproperty) | создать новое или изменить существующее собственное свойство |
| `[[HasProperty]]` | [10.1.7.1](https://262.ecma-international.org/#sec-ordinaryhasproperty) | проверить наличие свойства, включая обход всей цепочки прототипов |
| `[[Get]]` | [10.1.8.1](https://262.ecma-international.org/#sec-ordinaryget) | прочитать итоговое значение свойства |
| `[[Set]]` | [10.1.9.1](https://262.ecma-international.org/#sec-ordinaryset) | записать значение свойства |
| `[[Delete]]` | [10.1.10.1](https://262.ecma-international.org/#sec-ordinarydelete) | удалить собственное свойство |
| `[[OwnPropertyKeys]]` | [10.1.11.1](https://262.ecma-international.org/#sec-ordinaryownpropertykeys) | перечислить собственные ключи в строго определённом порядке |

### `[[DefineOwnProperty]]` против `[[Set]]` — единственный формальный источник целого класса «непонятных» багов

Разница между [10.1.6.1 OrdinaryDefineOwnProperty](https://262.ecma-international.org/#sec-ordinarydefineownproperty) и [10.1.9.1 OrdinarySet](https://262.ecma-international.org/#sec-ordinaryset) — вероятно, самая практически важная деталь всей главы, объясняющая добрую половину вопросов про объекты, которые регулярно ставят в тупик даже опытных разработчиков на технических собеседованиях.

Ключевое различие: `[[Set]]` — это операция **записи через обычное присваивание** (`obj.x = 1`). Она проходит по цепочке прототипов в поисках свойства с этим именем и, если находит **аксессор** (сеттер) где-то по пути наверх, честно его вызывает, полностью уважая унаследованное поведение. `[[DefineOwnProperty]]`, напротив, — операция **прямого определения свойства** (используется, например, `Object.defineProperty`). Она работает исключительно с собственным свойством самого объекта, вообще не заглядывает в цепочку прототипов и полностью игнорирует любые унаследованные аксессоры, которые могли бы там оказаться:

```js
let calls = 0;
const base = { set value(v) { calls++; } };
const child = Object.create(base);

child.value = 1;                                    // [[Set]] — находит сеттер у base, вызывает его
Object.defineProperty(child, 'value', { value: 2 }); // [[DefineOwnProperty]] — сеттер игнорируется

console.log(calls, child.value, Object.hasOwn(child, 'value'));
// 1 2 true
```

Сеттер сработал только один раз — при обычном присваивании через `[[Set]]`. Второй вызов, через `Object.defineProperty`, полностью проигнорировал существование сеттера у `base` и напрямую создал **собственное** свойство с данными прямо на `child`, затерев доступ к унаследованному аксессору (`Object.hasOwn(child, 'value')` теперь `true` — свойство стало собственным).

Именно из этого же различия прямо вытекает менее очевидная, но регулярно встречающаяся на практике асимметрия: `Object.assign(target, source)` внутри себя использует именно `[[Set]]` для копирования каждого свойства — а значит, честно вызывает сеттеры у `target`, если они там есть. А раскрытие объекта в новый литерал (`{ ...source }`) внутри опирается на операцию `CopyDataProperties` (разбирается в главе 7), которая устроена принципиально иначе и сеттеры целевого объекта не трогает вовсе — потому что раскрытие всегда создаёт совершенно новый, пустой объект, у которого просто физически не может быть заранее существующих сеттеров.

Внутри `[[DefineOwnProperty]]` работает вспомогательная операция [ValidateAndApplyPropertyDescriptor](https://262.ecma-international.org/#sec-validateandapplypropertydescriptor) ([10.1.6.3](https://262.ecma-international.org/#sec-validateandapplypropertydescriptor)) — именно она отвечает за все проверки допустимости изменения дескриптора свойства (например, запрет изменить значение неконфигурируемого свойства). Эта же самая операция, что немаловажно, используется и при проверке инвариантов у Proxy — подробнее разбирается в разделе про прокси ниже в этой главе.

### `OrdinaryOwnPropertyKeys` — гарантированный, а не случайный порядок

[10.1.11.1 OrdinaryOwnPropertyKeys](https://262.ecma-international.org/#sec-ordinaryownpropertykeys) закрепляет порядок перечисления собственных ключей объекта, который многие ошибочно считают неопределённым или зависящим от реализации, — на самом деле это строгая, обязательная для всех движков последовательность из трёх групп: сначала целочисленные индексы по возрастанию их числового значения, затем остальные строковые ключи в точном порядке добавления, затем ключи-символы тоже в порядке добавления:

```js
const sym = Symbol('s');
console.log(Reflect.ownKeys({ b: 1, 2: 2, a: 3, 1: 4, [sym]: 5, '01': 6 }).map(String));
// ['1', '2', 'b', 'a', '01', 'Symbol(s)']
```

Обратите внимание на `'01'` — этот ключ лишь выглядит как число, но каноническая целочисленная форма не допускает незначащих ведущих нулей, поэтому `'01'` попадает не в первую группу вместе с `'1'`/`'2'`, а во вторую, вместе с обычными строками, сохраняя своё положение по порядку добавления.

### `OrdinaryObjectCreate` — формальная основа `Object.create`

[10.1.12 OrdinaryObjectCreate](https://262.ecma-international.org/#sec-ordinaryobjectcreate) — операция, лежащая непосредственно в основе `Object.create()`: создать совершенно новый объект с заданным прототипом и без единого дополнительного свойства сверх того, что явно указано. Особый, часто используемый на практике случай — `Object.create(null)`, создающий объект без прототипа вообще:

```js
const dict = Object.create(null);
dict.key = 1;
console.log(typeof dict.toString); // undefined — у объекта нет Object.prototype в цепочке
```

Такой объект лишён любых унаследованных методов `Object.prototype`, включая сам `toString`, `hasOwnProperty`, `valueOf` — и именно поэтому он часто рекомендуется в качестве "чистого словаря" для хранения данных с непредсказуемыми ключами (в том числе потенциально пришедшими от пользователя), где присутствие унаследованных методов на прототипе могло бы конфликтовать с реальными данными (например, если ключ данных случайно совпадёт с именем `hasOwnProperty`).

## 10.2 Функциональные объекты ECMAScript

[10.2 ECMAScript Function Objects](https://262.ecma-international.org/#sec-ecmascript-function-objects) описывает функции, определённые непосредственно кодом на JavaScript (в противоположность встроенным функциям движка, разбираемым в следующем разделе). У таких функций переопределён внутренний метод `[[Call]]` (вызов) и, если функция может использоваться как конструктор, ещё и `[[Construct]]`.

Здесь же вводится один из самых практически значимых внутренних слотов языка — `[[ThisMode]]`. Ключевая деталь, которую легко упустить: этот слот определяется **в момент создания** функции, на основании синтаксического контекста, где функция была объявлена — а вовсе не в момент её вызова, как можно было бы интуитивно предположить. Он принимает одно из трёх значений: `lexical` (для стрелочных функций — своего значения `this` нет вовсе, всегда используется внешнее), `strict` (функция всегда рассматривает `this` в строгом режиме — без оборачивания примитивов и без подстановки глобального объекта вместо `undefined`), `global` (обычное, "снисходительное" поведение — примитивы оборачиваются, `undefined`/`null` заменяются глобальным объектом).

Этим же самым слотом, зафиксированным раз и навсегда при создании функции, объясняется конкретный, регулярно проверяемый на практике факт: метод класса, "оторванный" от своего объекта и вызванный без получателя, не превращает `this` в глобальный объект — потому что тело класса **всегда** синтаксически строгое (без какой-либо директивы `'use strict'`, это встроенное правило языка для любых классов), а значит, `[[ThisMode]]` метода класса равен `strict` вне зависимости от того, как метод в итоге будет вызван:

```js
class Counter {
  #n = 0;
  inc() { this.#n++; }
}
const m = new Counter().inc;
try { m(); } catch (e) { console.log(e.constructor.name); } // TypeError, а не тихая порча globalThis
```

Если бы `[[ThisMode]]` определялся в момент вызова (а не при создании функции), поведение метода класса зависело бы от контекста конкретного вызова, что сделало бы код классов существенно менее предсказуемым. А поскольку слот жёстко зафиксирован при создании, поведение `inc` абсолютно одинаково независимо от того, как именно её потом вызывают — метод класса навсегда остаётся строгим.

Здесь же, в этом разделе, формально описано менее очевидное правило конструирования — что происходит, если тело функции-конструктора явно возвращает какое-то значение через `return`:

```js
function RetObj() { this.a = 1; return { b: 2 }; }
function RetPrim() { this.a = 1; return 42; }
console.log(JSON.stringify(new RetObj()), JSON.stringify(new RetPrim()));
// {"b":2} {"a":1}
```

Если функция, вызванная через `new`, явно возвращает **объект**, конструирование целиком отдаёт наружу именно этот возвращённый объект вместо только что автоматически созданного экземпляра — свойство `a`, записанное на `this`, оказывается попросту потеряно, потому что этот `this`-объект никуда не попадает. А если возвращается **примитив** (как `42` во втором примере), он полностью игнорируется, и конструирование как ни в чём не бывало отдаёт наружу автоматически созданный `this` со всеми свойствами, записанными в него по ходу выполнения тела функции.

## 10.3 Встроенные функциональные объекты

[10.3 Built-in Function Objects](https://262.ecma-international.org/#sec-built-in-function-objects) — функции, которые реализованы не кодом на JavaScript, а самим движком, обычно на более низкоуровневом языке реализации (например, C++ в случае V8): `Array.prototype.map`, `Object.keys`, `Math.max` и любые другие встроенные методы. Формально это отдельный, самостоятельный вид объекта со своим набором внутренних слотов, но снаружи, из обычного кода, он совершенно неотличим от функции, написанной на JavaScript: `typeof` в обоих случаях даёт одинаковую строку `'function'`, и вызывать такую функцию можно совершенно одинаковым образом. Разница проявляется разве что при попытке получить исходный текст функции — `Function.prototype.toString()` на встроенной функции возвращает специальную заглушку `[native code]` вместо реального текста (этот факт подробно разбирается в главе 20).

## 10.4 Встроенные экзотические объекты

[10.4 Built-in Exotic Object Internal Methods and Slots](https://262.ecma-international.org/#sec-built-in-exotic-object-internal-methods-and-slots) — перечень всех встроенных объектов языка, у которых хотя бы один из одиннадцати внутренних методов переопределён относительно поведения обычного объекта из [10.1](https://262.ecma-international.org/#sec-ordinary-object-internal-methods-and-internal-slots).

| Вид | Раздел | Что переопределено |
|---|---|---|
| Bound Function | [10.4.1](https://262.ecma-international.org/#sec-bound-function-exotic-objects) | `[[Call]]` автоматически подставляет заранее связанного получателя |
| Array | [10.4.2](https://262.ecma-international.org/#sec-array-exotic-objects) | `[[DefineOwnProperty]]` держит свойство `length` в постоянной согласованности с индексами |
| String | [10.4.3](https://262.ecma-international.org/#sec-string-exotic-objects) | числовые индексы ведут себя как настоящие собственные свойства объекта-обёртки строки |
| Arguments | [10.4.4](https://262.ecma-international.org/#sec-arguments-exotic-objects) | в нестрогом режиме индексы связаны "вживую" с одноимёнными параметрами функции |
| TypedArray | [10.4.5](https://262.ecma-international.org/#sec-typedarray-exotic-objects) | числовые индексы напрямую читают/пишут байты underlying-буфера |
| Module Namespace | [10.4.6](https://262.ecma-international.org/#sec-module-namespace-exotic-objects) | `[[Get]]` читает "живое" (постоянно актуальное) связывание экспортируемого модулем значения |
| Immutable Prototype | [10.4.7](https://262.ecma-international.org/#sec-immutable-prototype-exotic-objects) | `[[SetPrototypeOf]]` безусловно отказывает в смене прототипа |

### Array — самый известный на практике пример экзотического поведения

```js
const arr = [1, 2, 3];
Object.defineProperty(arr, 'length', { value: 1 });
console.log(arr); // [1] — лишние элементы удалены переопределённым [[DefineOwnProperty]]
```

Прямая запись меньшего значения в `length` **удаляет** лишние элементы массива — обычный объект так себя вести не может в принципе, потому что у него `length` — просто ещё одно свойство без какой-либо особой связи с остальными ключами. У массива же переопределённый `[[DefineOwnProperty]]` явно поддерживает инвариант "значение `length` всегда на единицу больше наибольшего числового индекса среди существующих элементов", и обрезка массива при уменьшении `length` — прямое, механическое следствие поддержания этого инварианта.

### Bound Function — почему повторный `bind` не может переопределить получателя

```js
function f() { return this.tag; }
const once = f.bind({ tag: 'a' });
console.log(once.bind({ tag: 'b' })()); // 'a'
```

Результат `'a'`, а не `'b'`, регулярно удивляет тех, кто ожидает, что второй `bind` должен "перезаписать" первый. Формальное объяснение — прямо в устройстве Bound Function Exotic Object: связанная функция хранит **целевую функцию** и **связанного получателя** в собственных, внутренних, недоступных снаружи слотах (`[[BoundTargetFunction]]` и `[[BoundThis]]`). Вызов `once.bind({tag: 'b'})` не изменяет уже существующую связанную функцию `once` — он создаёт **новую**, ещё одну связанную функцию, целью которой становится `once` (уже связанная с `{tag: 'a'}`), а не исходная `f`. При реальном вызове этой новой функции управление в конечном счёте доходит до внутреннего слота `once`, и именно его связанный получатель побеждает — второе связывание оказывается формально "снаружи" и никогда не успевает применить свою подмену `this`, потому что первая, внутренняя связка уже зафиксировала получателя раньше.

### Immutable Prototype — исключение, доступное лишь избранным встроенным объектам

```js
console.log(Object.getPrototypeOf(Object.prototype)); // null
try { Object.setPrototypeOf(Object.prototype, {}); } catch (e) { console.log(e.constructor.name); }
// TypeError
```

`Object.prototype` — один из немногих встроенных объектов, чей внутренний метод `[[SetPrototypeOf]]` переопределён так, что **безусловно** отказывает в любой попытке смены прототипа, вне зависимости от переданного значения. Смысл этого исключения — защитить самый корень всей прототипной цепочки языка: если бы прототип `Object.prototype` можно было поменять, это потенциально сломало бы работу абсолютно любого объекта в программе, потому что почти все объекты в конечном счёте наследуют именно от него. `globalThis` в браузерном окружении — ещё один пример объекта с таким же переопределённым поведением, по той же самой причине защиты фундаментальной инфраструктуры среды выполнения от случайной или злонамеренной порчи.

## 10.5 Внутренние методы прокси

[10.5 Proxy Object Internal Methods and Internal Slots](https://262.ecma-international.org/#sec-proxy-object-internal-methods-and-internal-slots) описывает, вероятно, самый концептуально насыщенный вид экзотического объекта: `Proxy` — объект, у которого **все без исключения** одиннадцать внутренних методов переопределены так, что делегируют работу пользовательским функциям-ловушкам (подробный практический разбор применения `Proxy` — в главе 28). Но здесь принципиально важно понимать: делегирование ловушкам — не безусловное; каждая ловушка **обязана** соблюдать набор формально прописанных инвариантов, привязанных к реальному состоянию целевого объекта (`target`), и попытка их нарушить приводит к тому, что сам движок перехватывает нарушение и выбрасывает исключение, независимо от того, что именно вернула ловушка:

```js
const target = Object.freeze({ x: 1 });
const p = new Proxy(target, { get: () => 'подмена' });
try { p.x; } catch (e) { console.log(e.constructor.name); }
// TypeError
```

Ловушка `get` здесь пытается всегда возвращать строку `'подмена'`, независимо от реального значения свойства — но поскольку `target` заморожен, а значит, свойство `x` неконфигурируемо и недоступно для записи, спецификация требует, чтобы ловушка `get` в таком случае возвращала **строго то же самое** значение, что хранится в `target`. Смысл этого требования — принципиальный, а не формальный: без такой проверки любой `Proxy` мог бы полностью притвориться, что замороженный объект на самом деле не заморожен, и все гарантии, которые даёт `Object.freeze` (глава 7), рассыпались бы при первом же оборачивании объекта в прокси — сама концепция "неизменяемости" стала бы бессмысленной в присутствии прокси.

Три инварианта, которые на практике встречаются чаще всего при реальной разработке кастомных прокси-обёрток:

```js
// нельзя скрыть неконфигурируемое свойство через ловушку has
const t1 = {}; Object.defineProperty(t1, 'f', { value: 1, configurable: false });
try { 'f' in new Proxy(t1, { has: () => false }); } catch (e) { console.log(1, e.constructor.name); }

// нельзя вернуть из ownKeys дублирующиеся ключи
try { Object.keys(new Proxy({}, { ownKeys: () => ['a', 'a'] })); } catch (e) { console.log(2, e.constructor.name); }

// нельзя объявить нерасширяемый целевой объект расширяемым через ловушку isExtensible
const t2 = Object.preventExtensions({});
try { Object.isExtensible(new Proxy(t2, { isExtensible: () => true })); } catch (e) { console.log(3, e.constructor.name); }

// 1 TypeError
// 2 TypeError
// 3 TypeError
```

Общая логика всех подобных инвариантов одна и та же: если целевой объект даёт какую-то *формальную гарантию* (свойство существует и неконфигурируемо; объект нерасширяем), прокси-обёртка вокруг этого объекта не имеет права скрыть или отменить эту гарантию через свои ловушки — она может лишь честно её отразить или, в отдельных случаях, добавить дополнительные ограничения сверху, но никогда не ослабить то, что уже гарантировано самим целевым объектом.

## Итог

> [!summary] Что взять с собой
> - Одиннадцать внутренних методов обычного объекта реализованы разделом 10.1 как поведение по умолчанию; переопределение хотя бы одного делает объект экзотическим
> - `[[Set]]` идёт по цепочке прототипов и вызывает унаследованные сеттеры; `[[DefineOwnProperty]]` работает только с собственным свойством и сеттеры игнорирует — отсюда разница между `Object.assign` (вызывает сеттеры) и раскрытием в литерал (не вызывает)
> - Порядок собственных ключей объекта гарантирован: целочисленные индексы по возрастанию, затем строки, затем символы, всё в порядке добавления (кроме первой группы)
> - `[[ThisMode]]` функции фиксируется при её создании, а не при вызове; тело класса всегда синтаксически строгое, поэтому оторванный метод класса не портит `globalThis`, а бросает `TypeError`
> - Если конструктор явно возвращает объект — конструирование отдаёт именно его вместо автоматически созданного `this`; возвращённый примитив полностью игнорируется
> - Встроенные функции движка снаружи неотличимы от функций на JavaScript через `typeof`, но `toString()` выдаёт заглушку `[native code]`
> - Массив, строка, объект `arguments`, связанная функция, типизированный массив, пространство имён модуля, `Object.prototype` — каждый экзотичен по-своему, с конкретным переопределённым методом
> - Повторный `bind` не перезаписывает получателя: связанная функция хранит целевую функцию и получателя во внутренних слотах, и первое связывание побеждает
> - Внутренние методы `Proxy` делегированы ловушкам не безусловно — инварианты, привязанные к реальному состоянию целевого объекта (замороженность, нерасширяемость, неконфигурируемые свойства), ловушка нарушить не может
