# Глава 19 · Глобальный объект — отчёт

> [!info] Раздел спецификации
> [19 The Global Object](https://262.ecma-international.org/#sec-global-object)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Глобальный объект — это буквально всё, что доступно в коде без какого-либо явного квалификатора вроде `Math.` или `Array.`: значения `NaN`/`undefined`, функции `parseInt`/`encodeURI`, конструкторы `Object`/`Array`/`Promise`. Любопытная деталь, о которой редко задумываются: у самого глобального объекта формально **нет собственного имени** в тексте стандарта — он не назван как какая-то одна конкретная, именованная сущность, а полностью описан через перечень свойств, которые обязаны быть доступны из кода верхнего уровня скрипта. `globalThis` (о нём ниже) — это способ *сослаться* на этот объект, но не его "настоящее" имя в каком-либо особом смысле.

---

## 19.1 Значимые свойства

[19.1 Value Properties](https://262.ecma-international.org/#sec-value-properties-of-the-global-object) описывает три особых значения, доступных глобально: `NaN`, `Infinity`, `undefined`. У всех трёх — одинаковый, максимально строгий набор атрибутов: они неперечисляемы, неизменяемы (`writable: false`) и неконфигурируемы (`configurable: false`) одновременно:

```js
console.log(Object.getOwnPropertyDescriptor(globalThis, 'undefined'));
// { value: undefined, writable: false, enumerable: false, configurable: false }
```

Это максимальная степень защиты, какую вообще может иметь свойство объекта в языке. Стоит явно отметить историческую тонкость: в очень старых, нестрогих окружениях синтаксически было возможно написать что-то вроде `NaN = 5` без немедленной ошибки — но такое присваивание попросту не имело **никакого эффекта**, потому что `writable: false` тихо блокирует запись в нестрогом режиме (аналогично разбиравшемуся в главе 6/7 поведению для любого неизменяемого свойства). В строгом режиме та же попытка сразу же выбрасывает `TypeError`. В любом случае, переопределить фактическое значение `NaN`, `Infinity` или `undefined` невозможно ни при каких условиях — это гарантия, зафиксированная непосредственно атрибутами самих свойств глобального объекта, а не соглашением или доброй волей разработчиков движка.

[19.1.1 globalThis](https://262.ecma-international.org/#sec-globalthis) — относительно недавнее, но принципиально важное дополнение к языку: единственная **стандартизированная**, одинаково работающая ссылка на глобальный объект вне зависимости от среды выполнения. До появления `globalThis` в каждой среде существовал свой, несовместимый с остальными способ добраться до глобального объекта — `window` в браузере, `self` в веб-воркере, `global` в Node.js — и код, которому требовалось быть переносимым между этими средами, был вынужден писать неуклюжие проверки наличия каждого из этих имён по очереди. `globalThis` устраняет эту проблему одним универсальным именем, работающим одинаково во всех средах, где вообще реализован современный стандарт ECMAScript.

## 19.2 Функциональные свойства

### `eval` — прямой и косвенный вызов различаются синтаксически

[19.2.1 eval](https://262.ecma-international.org/#sec-eval-x) уже разбирался ранее, в главе 14, через призму того, какую область видимости видит выполняемый внутри `eval` код. Здесь стоит добавить формально важную деталь: различие между **прямым** и **косвенным** вызовом `eval` определяется чисто **синтаксически**, по тому, как выглядит сам вызов в исходном тексте кода, а не по тому, какое конкретно значение хранится в переменной с именем `eval` в момент вызова. Буквальный, дословный вызов идентификатора `eval(...)` считается прямым; **любая** другая форма — присвоение `eval` в переменную и вызов через неё, вызов через `(0, eval)(...)`, вызов через `obj.eval(...)` — считается косвенным:

```js
function test() {
  const local = 'локальная';
  eval('console.log(local)'); // прямой вызов — видит локальную область видимости функции test
  const indirectEval = eval;
  try { indirectEval('console.log(local)'); }
  catch (e) { console.log(e.constructor.name); } // ReferenceError — косвенный вызов работает только в глобальной области
}
test();
```

Прямой вызов `eval(...)` выполняет переданный код в текущей, локальной области видимости — код внутри видит `local`, как если бы он был буквально написан на месте вызова. Косвенный вызов, даже если единственное отличие — присвоение `eval` в промежуточную переменную перед вызовом, выполняет переданный код исключительно в **глобальной** области видимости, полностью изолированно от локального контекста, откуда он был вызван — отсюда `ReferenceError`, потому что `local` попросту не существует в глобальной области. Это формальное, синтаксическое различие, зафиксированное прямо в грамматике вызова, а не что-то, зависящее от значения переменной `eval` во время выполнения.

### `parseInt` и `parseFloat` — свободный, нестрогий разбор

[19.2.4 parseFloat](https://262.ecma-international.org/#sec-parsefloat-string) и [19.2.5 parseInt](https://262.ecma-international.org/#sec-parseint-string-radix) уже упоминались в главе 7 как прямая противоположность строгому поведению `Number()`: в отличие от `Number`, требующего, чтобы **вся** строка целиком была валидным числом, `parseInt`/`parseFloat` разбирают число с начала строки и просто останавливаются на первом символе, который уже не может быть частью числа, игнорируя весь "хвост" строки. Здесь стоит отдельно отметить конкретную деталь про автоматическое определение системы счисления: если основание счисления явно не передано вторым аргументом, а сама строка начинается с префикса `0x` или `0X`, `parseInt` автоматически распознаёт шестнадцатеричную запись:

```js
console.log(parseInt('0x1F'), parseInt('1F', 16), parseInt('08'));
// 31 31 8
```

Важно явно подчеркнуть: это **единственный** случай автоматического определения основания системы счисления, оставшийся в современной спецификации. В очень старых версиях языка `parseInt` мог по своему усмотрению трактовать строку с ведущим нулём (например, `'08'`) как восьмеричное число — эта неоднозначная, исторически проблемная автоопределяемость была явно убрана из современного текста стандарта именно из-за постоянной путаницы, которую она вызывала (строка `'08'` в восьмеричной системе вообще не является валидным числом, потому что цифры `8` и `9` не существуют в восьмеричной записи, и разные движки в разное время трактовали такой случай по-разному) — поэтому `parseInt('08')` сегодня однозначно и предсказуемо даёт `8` в десятичной системе, без всякой связанной с восьмеричностью двусмысленности.

### `isNaN` и `isFinite` — глобальные версии всегда сначала приводят тип

[19.2.2 isFinite](https://262.ecma-international.org/#sec-isfinite-number) и [19.2.3 isNaN](https://262.ecma-international.org/#sec-isnan-number) уже подробно разбирались в главе 7 в сравнении с одноимёнными статическими методами `Number.isNaN`/`Number.isFinite`. Стоит ещё раз явно напомнить ключевое различие, потому что оно регулярно становится источником багов: **глобальные** версии этих функций сначала приводят переданный аргумент к числу через `ToNumber` (глава 7), и только потом проверяют результат — из-за чего, например, `isNaN('привет')` даёт `true` (строка не приводится к числу, приведение даёт `NaN`, и функция честно об этом сообщает). Версии же из `Number` (`Number.isNaN`, `Number.isFinite`) вообще не выполняют никакого приведения типа — они сразу возвращают `false` для любого значения, изначально не являющегося числом, каким бы оно ни было.

### URI-функции — четыре степени "агрессивности" кодирования

[19.2.6 URI Handling Functions](https://262.ecma-international.org/#sec-uri-syntax-and-semantics) описывает четыре встроенные функции (`encodeURI`, `decodeURI`, `encodeURIComponent`, `decodeURIComponent`), различающиеся тем, насколько широкий набор символов они кодируют — и разница между ними прямо связана с тем, для какой конкретно части URI каждая предназначена. `encodeURI` исходит из предположения, что переданный аргумент — это уже **целый**, полностью сформированный URI, и поэтому сознательно не трогает символы, зарезервированные для структуры самого URI (`/`, `?`, `#`, `:` и подобные) — иначе она сломала бы структуру адреса, который и без того уже правильно оформлен. `encodeURIComponent`, напротив, кодирует буквально всё, кроме букв, цифр и небольшого набора безопасных знаков препинания, потому что предполагает, что на входе — только **отдельный компонент** URI (например, значение одного query-параметра), которому не положено содержать структурных символов вообще:

```js
const url = 'https://example.com/search?q=привет мир';
console.log(encodeURI(url));
// https://example.com/search?q=%D0%BF%D1%80%D0%B8%D0%B2%D0%B5%D1%82%20%D0%BC%D0%B8%D1%80

console.log(encodeURIComponent('a/b?c'));
// a%2Fb%3Fc — здесь / и ? тоже закодированы, потому что это отдельный компонент, а не целый URI
```

`encodeURI` оставил `https://`, `/search`, `?` и `=` нетронутыми (это структурные символы полноценного URI), закодировав только кириллический текст и пробел. `encodeURIComponent` над строкой `'a/b?c'`, напротив, закодировал даже символы `/` и `?` — потому что для отдельного компонента (скажем, значения, которое затем нужно подставить как единый query-параметр) эти символы не должны интерпретироваться как часть структуры адреса, а как обычный, буквальный текст.

Стоит также напомнить факт, уже упоминавшийся в других главах применительно к строкам: обе кодирующие функции явно бросают исключение при попытке обработать строку с некорректной, "битой" последовательностью суррогатных пар (глава 6, 22) — потому что корректная UTF-16-последовательность обязательна для однозначного превращения строки в последовательность байт при кодировании URI.

## 19.3–19.4 Конструкторы и прочие свойства

[19.3 Constructor Properties](https://262.ecma-international.org/#sec-constructor-properties-of-the-global-object) — по существу, просто перечень имён всех встроенных конструкторов языка: `Object`, `Array`, `Function`, `Boolean`, `Symbol`, `Error` и вся его иерархия подклассов (глава 20), `Number`, `BigInt`, `Date` (глава 21), `String`, `RegExp` (глава 22), `Map`, `Set`, `WeakMap`, `WeakSet` (глава 24), `ArrayBuffer` и типизированные массивы, `DataView` (глава 25), `Promise` (глава 27), `Proxy` (глава 28) и другие — подробный разбор каждого из них уже дан или ещё будет дан в соответствующих главах этого проекта, здесь же они просто формально объявлены как обязательные свойства глобального объекта.

[19.4 Other Properties](https://262.ecma-international.org/#sec-other-properties-of-the-global-object) добавляет к этому перечню объекты, у которых **нет** собственного конструктора — их нельзя вызвать через `new`, это готовые объекты-неймспейсы со статическими методами: `Math`, `JSON`, `Reflect`, `Atomics` (все четыре уже подробно разбирались в предыдущих главах этого проекта как раз именно в этом качестве — объекты-контейнеры функций, а не фабрики экземпляров).

Здесь стоит явно зафиксировать факт, легко упускаемый из виду и способный по-настоящему удивить при первом столкновении: в отличие от максимально защищённых `NaN`, `Infinity`, `undefined` из раздела 19.1, **не все** свойства из 19.3–19.4 настолько же строго защищены. Большинство конструкторов и объектов из этих двух разделов вполне конфигурируемы — их можно переопределить обычным присваиванием или даже полностью удалить оператором `delete`:

```js
console.log(Object.getOwnPropertyDescriptor(globalThis, 'Array').configurable); // true
delete globalThis.Array;
console.log(typeof Array); // 'undefined' — да, действительно можно снести подчистую
```

На первый взгляд это может показаться потенциально опасной "дырой" в языке — но на практике это осознанное, взвешенное архитектурное решение: оно позволяет продвинутым сценариям вроде тестовых сред (например, замена `Date` на детерминированную реализацию для стабильных, не зависящих от реального времени тестов), полифиллов (замена устаревшей или отсутствующей реализации на актуальную) и специальных изолированных песочниц явно контролировать доступный набор глобальных возможностей, вплоть до полного удаления опасных или нежелательных конструкторов из области видимости выполняемого в такой песочнице кода. Именно эта конфигурируемость и делает подобные продвинутые техники в принципе возможными — если бы `Array`, как и `NaN`, был неконфигурируемым, ни один из этих сценариев не мог бы существовать.

## Итог

> [!summary] Что взять с собой
> - У глобального объекта формально нет собственного имени в тексте стандарта — он полностью описан через перечень обязательных свойств
> - `NaN`, `Infinity`, `undefined` — максимально защищённые свойства: неперечисляемы, неизменяемы, неконфигурируемы одновременно; переопределить их невозможно ни при каких условиях
> - `globalThis` — единственная стандартизированная, одинаково работающая во всех средах ссылка на глобальный объект, устранившая необходимость в несовместимых `window`/`self`/`global`
> - Прямой и косвенный вызов `eval` различаются чисто синтаксически (буквальный `eval(...)` против любой другой формы), а не значением переменной `eval` в момент вызова; косвенный вызов всегда работает только в глобальной области видимости
> - Автоматическое определение системы счисления в `parseInt` сохранилось только для шестнадцатеричного префикса `0x`/`0X` — устаревшая, неоднозначная автоопределяемость восьмеричной системы явно убрана из современной спецификации
> - Глобальные `isNaN`/`isFinite` сначала приводят аргумент к числу через `ToNumber`; одноимённые методы `Number` этого не делают и сразу отвергают всё, что изначально не число
> - `encodeURI` предполагает целый URI и не трогает структурные символы (`/`, `?`, `#`); `encodeURIComponent` предполагает отдельный компонент и кодирует их тоже
> - Большинство конструкторов и объектов-неймспейсов (`Array`, `Math`, `Promise` и другие) конфигурируемы и могут быть переопределены или полностью удалены — в отличие от максимально защищённых `NaN`/`Infinity`/`undefined`; это осознанное решение, делающее возможными полифиллы, тестовые окружения и песочницы
