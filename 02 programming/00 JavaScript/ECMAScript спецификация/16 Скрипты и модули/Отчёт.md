# Глава 16 · Скрипты и модули — отчёт

> [!info] Раздел спецификации
> [16 ECMAScript Language: Scripts and Modules](https://262.ecma-international.org/#sec-ecmascript-language-scripts-and-modules)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Модуль — не просто «файл со строгим режимом по умолчанию». Это отдельная структура записи с собственным жизненным циклом: разбор, связывание, выполнение — три раздельные фазы, и именно порядок фаз объясняет и живые связывания, и поведение циклических зависимостей.

---

## 16.1 Скрипты

[16.1 Scripts](https://262.ecma-international.org/#sec-scripts). Верхнеуровневый код скрипта инстанцируется операцией [GlobalDeclarationInstantiation](https://262.ecma-international.org/#sec-globaldeclarationinstantiation) — 16.1.7, уже разбиравшейся в главе 9 через призму Global Environment Record.

Здесь стоит подчеркнуть деталь, которую легко упустить: эта операция проверяет возможность создать **все** глобальные биндинги, прежде чем создать хотя бы один. Если хоть одно имя конфликтует с неконфигурируемым свойством глобального объекта, инстанцирование целиком проваливается до выполнения первой строки.

## 16.2 Модули

### Три фазы

[16.2 Modules](https://262.ecma-international.org/#sec-modules), [16.2.1 Module Semantics](https://262.ecma-international.org/#sec-module-semantics) описывают три раздельных этапа обработки модуля:

1. **Разбор** — модуль превращается в Module Record, собираются списки импортов и экспортов, но код ещё не выполняется
2. **Связывание** (Link, [16.2.1.6.1.2](https://262.ecma-international.org/#sec-moduledeclarationinstantiation)) — создаются записи окружения для всех модулей графа зависимостей, импортированные имена привязываются к ячейкам экспортирующих модулей
3. **Выполнение** (Evaluate, [16.2.1.6.1.3](https://262.ecma-international.org/#sec-moduleevaluation)) — тела модулей выполняются в порядке зависимостей

Разделение фаз объясняет, почему `import` работает независимо от того, где в файле он написан: связывание завершается **до** выполнения любого кода модуля.

### Живые связывания

Импортированное имя — не копия значения, а индирект-биндинг на ту же ячейку памяти, что и в экспортирующем модуле. Это прямое следствие фазы связывания: обе стороны ссылаются на одну запись окружения.

```js
// counter.mjs
export let count = 0;
export const inc = () => count++;

// main.mjs
import { count, inc } from './counter.mjs';
console.log(count); // 0
inc();
console.log(count); // 1 — обновилось без повторного импорта
```

Попытка присвоить импортированному имени напрямую бросает: связывание доступно только на чтение со стороны импортёра.

### Циклические зависимости

Поскольку связывание отделено от выполнения, цикл зависимостей не ломает граф — оба модуля успешно связываются. Проблема, если она есть, проявляется только при обращении к ещё не инициализированному значению во время выполнения.

```js
// a.mjs
import { b } from './b.mjs';
export const a = 'A';
console.log('a видит b:', b);

// b.mjs
import { a } from './a.mjs';
export const b = 'B';
console.log('b видит a:', a); // ReferenceError — a ещё не инициализирован на этом шаге
```

Модуль, выполняемый первым в порядке зависимостей, застаёт партнёра по циклу с биндингами в TDZ. Это резко отличается от поведения циклов в CommonJS, где на этом месте была бы тихая `undefined` — ошибка здесь предпочтительнее тишины.

### Экспорты и Module Namespace

[16.2.3 Exports](https://262.ecma-international.org/#sec-exports) описывает грамматику `export`, а [ResolveExport](https://262.ecma-international.org/#sec-resolveexport) (16.2.1.7.2.2) — алгоритм разрешения повторных экспортов, включая обнаружение неоднозначности при `export * from` из двух модулей с одинаковым именем.

Объект, получаемый через `import * as ns`, — экзотический [Module Namespace Object](https://262.ecma-international.org/#sec-module-namespace-exotic-objects) (10.4.6): его `[[Get]]` читает напрямую из связанной ячейки, а не из обычного собственного свойства.

```js
import * as ns from './counter.mjs';
console.log(Object.isExtensible(ns), Object.isSealed(ns));      // false true
console.log(Object.getOwnPropertyDescriptor(ns, 'count').writable); // true — отражает изменяемость let-биндинга
try { ns.count = 99; } catch (e) { console.log(e.constructor.name); } // TypeError — запись всё равно падает
```

Здесь неочевидная деталь: дескриптор говорит `writable: true` — он честно отражает, что исходная переменная объявлена через `let`. Но запись всё равно бросает исключение, потому что запрет реализован через переопределённый внутренний метод записи, а не через атрибут доступа. Из-за этого `Object.isFrozen(ns)` формально возвращает `false`: проверка смотрит на атрибуты дескрипторов, а не на фактическое поведение при записи.

### Асинхронные модули

Верхнеуровневый `await` встроен в фазу выполнения модуля: [InnerModuleEvaluation](https://262.ecma-international.org/#sec-innermoduleevaluation) отслеживает, какие модули содержат асинхронное ожидание, и упорядочивает выполнение зависимостей соответственно, не блокируя граф целиком.

```js
// data.mjs
export const value = await fetch('/api').then(r => r.json()).catch(() => 'заглушка');
// импортёр data.mjs дождётся выполнения этой строки прежде, чем получит доступ к value
```

## Итог

> [!success] Что забирать
> - GlobalDeclarationInstantiation проверяет возможность создать все глобальные биндинги, прежде чем создать хотя бы один
> - Обработка модуля — три раздельные фазы: разбор, связывание, выполнение
> - Импортированное имя — индирект-биндинг на ячейку экспортирующего модуля, а не копия значения
> - Присваивание импортированному имени запрещено — связывание доступно только на чтение
> - Связывание отделено от выполнения, поэтому цикл зависимостей не ломает граф сам по себе
> - Модуль, выполняемый первым в цикле, видит партнёра с биндингами в TDZ — явная ошибка вместо тихой undefined из CommonJS
> - Пространство имён модуля — экзотический объект, чей Get читает напрямую из связанной ячейки
> - Верхнеуровневый await упорядочивает выполнение графа зависимостей, не блокируя его целиком
