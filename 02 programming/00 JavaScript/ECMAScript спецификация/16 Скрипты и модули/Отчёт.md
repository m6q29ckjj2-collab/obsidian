# Глава 16 · Скрипты и модули — отчёт

> [!info] Раздел спецификации
> [16 ECMAScript Language: Scripts and Modules](https://262.ecma-international.org/#sec-ecmascript-language-scripts-and-modules)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Легко думать про ES-модуль просто как про "обычный файл со строгим режимом по умолчанию" — но с точки зрения спецификации это принципиально более сложная структура: у модуля есть собственный формальный жизненный цикл из трёх раздельных фаз (разбор, связывание, выполнение), и именно порядок и разделение этих фаз объясняет и "живые" связывания между модулями, и поведение циклических зависимостей, и почему `import` вообще не заботит, в каком месте файла он написан.

---

## 16.1 Скрипты

[16.1 Scripts](https://262.ecma-international.org/#sec-scripts) описывает обычный, "классический" верхнеуровневый код — не модуль, а то, что традиционно подключалось через `<script>` без `type="module"`. Такой код инстанцируется операцией [GlobalDeclarationInstantiation](https://262.ecma-international.org/#sec-globaldeclarationinstantiation) (16.1.7), уже подробно разбиравшейся в главе 9 через призму гибридной природы Global Environment Record.

Здесь стоит подчеркнуть одну легко упускаемую, но практически важную деталь этой операции: `GlobalDeclarationInstantiation` явно проверяет **возможность** создать абсолютно все глобальные связывания скрипта (все переменные и функции верхнего уровня), прежде чем реально создать хотя бы одно из них. Если хотя бы одно имя из объявляемых в скрипте конфликтует с уже существующим **неконфигурируемым** свойством глобального объекта, вся процедура инстанцирования проваливается целиком, и не выполняется вообще ни одна строка кода скрипта — даже те объявления, что формально не конфликтовали бы сами по себе. Это ещё один конкретный пример из уже знакомой категории — статическая (в широком смысле, "до реального выполнения") проверка, гарантирующая, что либо весь скрипт корректно стартует, либо не стартует вообще, без частично инициализированного, "подвисшего" состояния.

## 16.2 Модули

### Три фазы обработки — формальный источник всей "магии" модулей

[16.2 Modules](https://262.ecma-international.org/#sec-modules) и [16.2.1 Module Semantics](https://262.ecma-international.org/#sec-module-semantics) описывают три строго раздельных, последовательных этапа обработки любого модуля:

1. **Разбор (Parse)** — исходный текст модуля превращается в служебную структуру Module Record, на этом же шаге собираются полные списки того, что модуль импортирует и что экспортирует. Код модуля при этом **ещё не выполняется** ни на йоту.
2. **Связывание (Link)** ([16.2.1.6.1.2 ModuleDeclarationInstantiation](https://262.ecma-international.org/#sec-moduledeclarationinstantiation)) — для всех модулей во всём графе зависимостей создаются записи окружения, и, что особенно важно, имена, импортированные одним модулем, формально привязываются напрямую к тем же самым ячейкам памяти, что использует экспортирующий модуль.
3. **Выполнение (Evaluate)** ([16.2.1.6.1.3 ModuleEvaluation](https://262.ecma-international.org/#sec-moduleevaluation)) — только теперь, когда весь граф зависимостей уже полностью связан, тела модулей реально выполняются, причём в порядке, определяемом зависимостями (сначала выполняются модули, от которых зависят остальные).

Строгое разделение этих трёх фаз — прямое и полное объяснение того, почему `import`-декларация в ES-модулях работает совершенно независимо от того, в каком именно месте файла она физически написана (в отличие, например, от `require()` в CommonJS, который является обычным вызовом функции и выполняется строго в порядке кода): связывание всех имён между модулями **полностью** завершается ещё до того, как начнёт выполняться хоть одна строка кода хоть одного модуля — а значит, к моменту, когда любой код модуля вообще начинает исполняться, все связи между модулями графа зависимостей уже гарантированно установлены.

### Живые связывания — импортированное имя не копия, а разделяемая ячейка памяти

Одна из самых концептуально важных, но часто интуитивно неверно понимаемых деталей: импортированное через `import` имя — это **не** копия значения на момент импорта (как это часто интуитивно ожидается, особенно теми, кто пришёл из CommonJS, где `require()` действительно возвращает копию ссылки на экспортированный объект). Это прямой **индирект-биндинг** — связывание, физически указывающее на ту же самую ячейку окружения, что использует и сам экспортирующий модуль. Это прямое, механическое следствие того, что происходит именно на фазе связывания, описанной выше: обе стороны — импортирующий и экспортирующий модуль — буквально ссылаются на одну и ту же запись окружения, а не обмениваются копиями значений.

```js
// counter.mjs
export let count = 0;
export const inc = () => count++;

// main.mjs
import { count, inc } from './counter.mjs';
console.log(count); // 0
inc();
console.log(count); // 1 — обновилось само по себе, без какого-либо повторного импорта
```

Значение `count`, видимое в `main.mjs`, реально изменилось после вызова `inc()` — хотя в `main.mjs` не было ни одной строки, которая бы что-то "обновляла" вручную. Это прямое, наблюдаемое следствие того, что `count` в обоих файлах — буквально одна и та же ячейка памяти, а не две независимые переменные с изначально совпадавшим значением.

При этом стоит явно зафиксировать асимметрию: связывание доступно **только на чтение** со стороны импортирующего модуля — попытка присвоить что-то напрямую импортированному имени приводит к ошибке ещё до выполнения:

```js
import { count } from './counter.mjs';
try { count = 5; } catch (e) { console.log(e.constructor.name); } // TypeError
```

Изменять значение может только сам экспортирующий модуль (через свою собственную, "родную" переменную `count`); импортирующие модули могут только читать актуальное состояние этой разделяемой ячейки.

### Циклические зависимости — ошибка вместо тихого `undefined`

Поскольку фаза связывания (Link) полностью отделена от фазы выполнения (Evaluate), циклическая зависимость между модулями (модуль А импортирует что-то из модуля Б, который сам импортирует что-то из модуля А) **не ломает** сам граф зависимостей на этапе связывания — оба модуля вполне успешно связываются между собой, потому что связывание работает лишь с *именами* и *ячейками*, а не с реальными *значениями*. Проблема, если она вообще возникает, проявляется только позже — на этапе реального выполнения, если один из модулей в цикле попытается обратиться к значению партнёра ещё до того, как тот успел его вычислить:

```js
// a.mjs
import { b } from './b.mjs';
export const a = 'A';
console.log('a видит b:', b);

// b.mjs
import { a } from './a.mjs';
export const b = 'B';
console.log('b видит a:', a); // ReferenceError — a ещё не инициализирован на этом шаге выполнения
```

Порядок выполнения здесь таков: запуск начинается с `a.mjs`, но первая же строка — `import { b } from './b.mjs'` — требует, чтобы модуль `b.mjs` был выполнен раньше (граф зависимостей это гарантирует), поэтому управление сначала переходит в `b.mjs`. Там первая строка `import { a } from './a.mjs'` уже не запускает `a.mjs` заново (он уже находится в процессе выполнения, повторный запуск не происходит), а просто связывает имя `a` с соответствующей ячейкой — которая на данный момент ещё не инициализирована (потому что выполнение `a.mjs` буквально "застряло" на первой строке, ожидая завершения `b.mjs`). Поэтому `console.log('b видит a:', a)` в `b.mjs` бросает `ReferenceError` — обращение к связыванию, всё ещё находящемуся в TDZ, ровно та же логика, что уже подробно разбиралась применительно к `let`/`const` в главах 6, 9, 14.

Стоит явно подчеркнуть выбор дизайна: это резко отличается от поведения аналогичной ситуации в CommonJS (старой, `require`-based модульной системе Node.js), где на этом месте была бы тихая, тихо распространяющаяся `undefined` — партнёр по циклу просто получил бы недоинициализированный объект без единой ошибки, что часто превращалось в трудноуловимый источник багов. Разработчики стандарта ES-модулей сознательно выбрали явную ошибку вместо тихого распространения `undefined` — ошибка, пусть и неприятная в моменте, гораздо быстрее приводит к обнаружению и исправлению настоящей проблемы циклической зависимости, чем тихая порча данных где-то дальше по цепочке использования.

### Экспорты и Module Namespace Object — экзотика, читающая напрямую из связанной ячейки

[16.2.3 Exports](https://262.ecma-international.org/#sec-exports) описывает формальную грамматику ключевого слова `export` во всех его формах. Отдельного внимания заслуживает операция [ResolveExport](https://262.ecma-international.org/#sec-resolveexport) (16.2.1.7.2.2) — алгоритм разрешения повторных экспортов (`export * from './other.mjs'`), включающий явное обнаружение неоднозначности: если два разных повторно-экспортируемых модуля случайно экспортируют одно и то же имя, попытка получить доступ к такому неоднозначному имени формально даёт `undefined` вместо конкретного значения (спецификация явно требует не угадывать, какой из двух одноимённых экспортов "правильный").

Объект, который получается из конструкции `import * as ns from '...'`, — не обычный объект со скопированными значениями, а специальный **экзотический** [Module Namespace Object](https://262.ecma-international.org/#sec-module-namespace-exotic-objects) (10.4.6, уже упоминался в главе 10): его внутренний метод `[[Get]]` переопределён так, что читает значение **напрямую** из связанной ячейки окружения экспортирующего модуля при каждом обращении, а не из обычного, статически сохранённого собственного свойства:

```js
import * as ns from './counter.mjs';
console.log(Object.isExtensible(ns), Object.isSealed(ns));         // false true
console.log(Object.getOwnPropertyDescriptor(ns, 'count').writable); // true
try { ns.count = 99; } catch (e) { console.log(e.constructor.name); } // TypeError
console.log(Object.isFrozen(ns));                                   // false
```

Здесь скрыта тонкая, но по-настоящему интересная деталь, ради которой стоит отдельно потренироваться: дескриптор свойства `count` у объекта пространства имён честно сообщает `writable: true` — потому что он **честно отражает** факт, что исходная переменная `count` в экспортирующем модуле объявлена изменяемым `let`, а не `const`. Но реальная попытка **записи** `ns.count = 99` всё равно бросает `TypeError` — потому что сам запрет на запись реализован не через атрибут дескриптора `writable`, а через отдельный, специально переопределённый внутренний метод `[[Set]]` этого экзотического объекта, который безусловно отклоняет любую попытку внешней записи, независимо от того, что говорит дескриптор. Именно из-за этого расхождения между "что говорит дескриптор" и "что реально происходит при записи" встроенная проверка `Object.isFrozen(ns)` формально возвращает `false` — она смотрит исключительно на атрибуты дескрипторов свойств (согласно алгоритму `TestIntegrityLevel` из главы 7), а не на фактическое поведение объекта при попытке записи, и с точки зрения одних только дескрипторов объект пространства имён модуля вовсе не выглядит замороженным, хотя по факту любая запись в него гарантированно провалится.

### Асинхронные модули — верхнеуровневый `await` без блокировки всего графа

Относительно новая возможность языка — использование `await` прямо на верхнем уровне модуля, вне какой-либо `async`-функции — формально встроена непосредственно в фазу **выполнения** модуля (фаза 3 из описанных выше): операция [InnerModuleEvaluation](https://262.ecma-international.org/#sec-innermoduleevaluation) отслеживает, какие именно модули во всём графе зависимостей содержат такое асинхронное ожидание, и соответствующим образом упорядочивает выполнение всего графа, **не блокируя** его целиком — модули, не зависящие от ещё не завершившегося асинхронного модуля, продолжают выполняться своим чередом, не дожидаясь его завершения без необходимости:

```js
// data.mjs
export const value = await fetch('/api').then(r => r.json()).catch(() => 'заглушка');
// любой импортёр data.mjs автоматически дождётся выполнения этой строки,
// прежде чем получит доступ к value — это встроено в саму фазу выполнения модуля
```

Любой другой модуль, импортирующий `value` из `data.mjs`, автоматически и без какого-либо специального синтаксиса со своей стороны дожидается полного завершения асинхронной инициализации `data.mjs`, прежде чем получить реальный доступ к готовому значению `value` — это целиком встроенная часть формального порядка фазы выполнения модульного графа, а не что-то, что нужно организовывать вручную через дополнительные промисы или колбэки.

## Итог

> [!summary] Что взять с собой
> - `GlobalDeclarationInstantiation` проверяет возможность создать все глобальные связывания скрипта, прежде чем создать хотя бы одно — либо весь скрипт стартует корректно, либо не стартует вовсе
> - Обработка модуля — три строго раздельные фазы: разбор (только сбор структуры), связывание (создание общих ячеек между модулями), выполнение (реальный запуск кода) — разделение объясняет, почему `import` не зависит от места в файле
> - Импортированное имя — прямой индирект-биндинг на ту же ячейку памяти, что и в экспортирующем модуле, а не копия значения на момент импорта
> - Присваивание импортированному имени напрямую запрещено — связывание доступно только на чтение со стороны импортёра
> - Связывание отделено от выполнения, поэтому циклическая зависимость сама по себе не ломает граф модулей — оба модуля успешно связываются
> - Модуль, выполняемый первым в цикле, при попытке обратиться к ещё не готовому значению партнёра получает явную ошибку (TDZ), а не тихий `undefined`, как было бы в CommonJS
> - Пространство имён модуля (`import * as ns`) — экзотический объект, чей `[[Get]]` читает напрямую из связанной ячейки при каждом обращении
> - У пространства имён модуля дескриптор свойства честно отражает изменяемость исходного `let`-биндинга (`writable: true`), но запись всё равно блокируется отдельным переопределённым `[[Set]]` — из-за этого расхождения `Object.isFrozen()` формально даёт `false`
> - Верхнеуровневый `await` в модуле встроен в фазу выполнения графа зависимостей и не блокирует модули, от него не зависящие
