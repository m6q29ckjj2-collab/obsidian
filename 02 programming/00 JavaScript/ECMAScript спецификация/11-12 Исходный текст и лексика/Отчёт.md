## 11 Исходный текст

[11.1 Source Text](https://262.ecma-international.org/#sec-source-text) фиксирует то, что легко посчитать деталью реализации: исходный код ECMAScript — это последовательность кодовых точек Unicode, а не байтов. Кодировка обязана быть интерпретирована в code point **до** начала лексического разбора.

[11.2 Types of Source Code](https://262.ecma-international.org/#sec-types-of-source-code) вводит различие, которое определяет строгость режима по умолчанию:

| Тип кода | Строгий режим по умолчанию |
|---|---|
| Script | нет, нужна директива `'use strict'` |
| Module | да, всегда |
| Function code | наследуется от места объявления |

```js
// в обычном скрипте присваивание необъявленной переменной создаёт глобальную
function check() { try { x = 1; return 'создал глобальную'; } catch (e) { return e.constructor.name; } }
console.log(check()); // 'создал глобальную' — sloppy mode

// в модуле директива 'use strict' не нужна вовсе — строгость включена всегда
// та же функция внутри модуля даёт ReferenceError на том же присваивании
```

## 12.1–12.5 Формат исходного текста

[12.1 Unicode Format-Control Characters](https://262.ecma-international.org/#sec-unicode-format-control-characters) разрешает невидимые управляющие символы внутри исходного текста — они допустимы даже посреди идентификатора, если относятся к определённым категориям, и полностью прозрачны для значения программы.

[12.2 White Space](https://262.ecma-international.org/#sec-white-space) и [12.3 Line Terminators](https://262.ecma-international.org/#sec-line-terminators) — разные категории, и различие не косметическое: терминатор строки участвует в автоматической расстановке точек с запятой, а обычный пробел — нет.

```js
console.log(1 +
  2); // 3 — перенос строки внутри выражения не завершает инструкцию
```

[12.5 Hashbang Comments](https://262.ecma-international.org/#sec-hashbang) — синтаксис `#!/usr/bin/env node` в первой строке файла. Формально это не комментарий в обычном смысле, а отдельная продукция грамматики, разрешённая только в самом начале.

## 12.6–12.8 Токены

[12.6 Tokens](https://262.ecma-international.org/#sec-tokens) определяет пять категорий: имя, зарезервированное слово, знак пунктуации, литерал шаблона, обычный литерал.

[12.7.2 Keywords and Reserved Words](https://262.ecma-international.org/#sec-keywords-and-reserved-words) делит зарезервированные слова на группы разной строгости. Часть слов зарезервирована всегда, часть — только в строгом режиме, часть — только в определённом синтаксическом контексте.

```js
// yield — не зарезервировано глобально
var yield = 1; console.log(yield); // 1, работает в sloppy mode вне генератора

function* g() {
  // var yield = 1; // SyntaxError — внутри генератора yield зарезервирован
}
```

```js
'use strict';
// var interface = 1; // SyntaxError — зарезервировано только в строгом режиме
```

## 12.9 Литералы

### Числовые литералы

[12.9.3](https://262.ecma-international.org/#sec-literals-numeric-literals) описывает грамматику записи числа в коде — и это **другая грамматика**, чем разбор числа из строки, о котором шла речь в главе 7. Здесь разрешены разделители-подчёркивания, там — нет.

```js
console.log(1_000_000, 0b1010, 0o17, 0x1F, 1e3, .5, 5.);
// 1000000 10 15 31 1000 0.5 5
```

[12.9.3.3 NumericValue](https://262.ecma-international.org/#sec-numericvalue) — операция, вычисляющая значение литерала из его текстового представления. Числовой литерал с суффиксом `n` даёт значение произвольной точности, без суффикса — обычное число.

### Строковые литералы

[12.9.4](https://262.ecma-international.org/#sec-literals-string-literals) описывает escape-последовательности. `\u{...}` появился позже `\uXXXX` именно потому, что старая форма кодирует ровно одну 16-битную единицу и не может задать символ вне базовой плоскости одним блоком.

```js
console.log('A', '\u{1F600}'.length, '\x41', '\101');
// A 2 A A — восьмеричная форма запрещена в строгом режиме
```

### Литералы шаблонов

[12.9.6](https://262.ecma-international.org/#sec-template-literal-lexical-components) вводит две параллельные семантики для одного и того же исходного текста: **TV** (Template Value, [12.9.6.1](https://262.ecma-international.org/#sec-static-semantics-tv)) — обработанное значение, и **TRV** (Template Raw Value, [12.9.6.2](https://262.ecma-international.org/#sec-static-semantics-trv)) — исходный текст без интерпретации escape-последовательностей.

```js
const tag = (strings) => [strings[0], strings.raw[0]];
console.log(tag`a\nb`);
// [ 'a\nb' (с настоящим переносом строки), 'a\\nb' (буквально слэш-эн) ]
```

На этой паре построен `String.raw` — для путей Windows и регулярных выражений, где обратный слэш значим.

## 12.10 Автоматическая расстановка точек с запятой

[12.10 Automatic Semicolon Insertion](https://262.ecma-international.org/#sec-automatic-semicolon-insertion) — механизм, который вставляет точку с запятой, если без неё дальнейший разбор невозможен. Три правила из [12.10.1](https://262.ecma-international.org/#sec-rules-of-automatic-semicolon-insertion):

1. Следующий токен не подходит грамматически, и между ним и предыдущим есть терминатор строки — вставить точку перед ним
2. Достигнут конец программы, а разбор незавершён — вставить точку в конце
3. Особые продукции (`return`, `break`, `continue`, постфиксные `++`/`--`) содержат явный запрет переноса строки — при его нарушении точка вставляется сразу после ключевого слова

```js
function f() {
  return
    { value: 1 };
}
console.log(f()); // undefined — правило 3, перенос запрещён после return
```

```js
const a = 1
const b = [2, 3]
console.log(a, b)
// работает: строки начинаются с ключевого слова, объединения не происходит
```

> [!warning] Единственное реальное правило безопасности
> Проблема возникает не из-за отсутствия точки с запятой вообще, а когда следующая строка **начинается** с `(`, `[`, `` ` ``, `+`, `-` или `/` — тогда парсер способен продолжить предыдущее выражение, и ASI не срабатывает.
> ```js
> const x = 1
> ;[1, 2, 3].forEach(console.log) // ведущая точка с запятой — стандартная защита
> ```

## Итог

> [!success] Что забирать
> - Тип исходного кода определяет строгость режима по умолчанию: модуль строгий всегда, скрипт — только с директивой
> - Терминатор строки и обычный пробел — разные категории, первый участвует в ASI, второй нет
> - Зарезервированные слова делятся по строгости контекста: часть работает как обычный идентификатор вне строгого режима или вне определённой конструкции
> - Грамматика числовых литералов в коде и грамматика разбора числа из строки — разные; разделители-подчёркивания работают только в первой
> - `\u{...}` появился ради символов вне базовой плоскости, старая форма кодирует ровно одну единицу
> - У шаблонного литерала два параллельных значения — обработанное и сырое; на этом построен `String.raw`
> - ASI работает по трём правилам, и практическая опасность — не отсутствие точки с запятой вообще, а начало следующей строки со скобки или оператора
