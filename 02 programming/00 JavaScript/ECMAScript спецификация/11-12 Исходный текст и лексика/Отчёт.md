# Главы 11–12 · Исходный текст и лексическая грамматика — отчёт

> [!info] Раздел спецификации
> [11 Source Code](https://262.ecma-international.org/#sec-ecmascript-language-source-code) · [12 Lexical Grammar](https://262.ecma-international.org/#sec-ecmascript-language-lexical-grammar)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Две небольшие главы объединены в один файл по практической причине: одиннадцатая состоит всего из двух коротких подразделов, и без контекста двенадцатой она сама по себе не даёт цельной картины. Вместе они описывают самый нижний, "досинтаксический" уровень обработки кода — уровень **токенов**: то, что происходит ещё до того, как движок начинает разбирать структуру выражений и инструкций (главы 13–14). Это тот самый этап, где текст программы впервые превращается из потока символов в поток осмысленных "слов" языка.

## 11 Исходный текст

[11.1 Source Text](https://262.ecma-international.org/#sec-source-text) фиксирует факт, который легко по ошибке принять за незначащую техническую подробность: исходный код ECMAScript формально определён как последовательность **кодовых точек Unicode**, а не байтов. Это важное разграничение уровней абстракции: файл на диске физически хранится как последовательность байтов в какой-то конкретной кодировке (обычно UTF-8), но прежде чем движок вообще начнёт лексический разбор по правилам этой главы, кодировка обязана быть полностью интерпретирована и превращена в последовательность кодовых точек — сам процесс лексического анализа работает уже на этом более высоком, независимом от конкретной байтовой кодировки уровне представления текста.

[11.2 Types of Source Code](https://262.ecma-international.org/#sec-types-of-source-code) вводит различие, напрямую определяющее, действует ли строгий режим по умолчанию для конкретного фрагмента кода:

| Тип кода | Строгий режим по умолчанию |
|---|---|
| Script (обычный скрипт, файл, подключённый через `<script>` без `type="module"`) | нет, требуется явная директива `'use strict'` |
| Module (код ES-модуля, `import`/`export`) | да, всегда, без исключений и без явной директивы |
| Function code (тело функции) | наследует режим строгости от места своего синтаксического объявления |

```js
// в обычном скрипте (нестрогий режим) присваивание необъявленной переменной
// молча создаёт новую глобальную переменную вместо ошибки
function check() { try { x = 1; return 'создал глобальную'; } catch (e) { return e.constructor.name; } }
console.log(check()); // 'создал глобальную'
```

```js
// та же самая функция, помещённая в код модуля, ведёт себя иначе:
// модуль строгий всегда, никакая директива 'use strict' для этого не нужна
function check() { try { x = 1; return 'создал глобальную'; } catch (e) { return e.constructor.name; } }
console.log(check()); // 'ReferenceError'
```

Практический вывод из этого различия — то, что регулярно удивляет разработчиков, впервые переходящих с обычных скриптов на модули: код, годами прекрасно работавший в старом стиле подключения через `<script>`, может начать выбрасывать ошибки на давно забытых, случайных опечатках (вроде необъявленной переменной) сразу же после перевода того же файла в формат ES-модуля — просто потому, что модуль автоматически, без единого изменения в тексте самого кода, включает строгий режим.

## 12.1–12.5 Формат исходного текста

[12.1 Unicode Format-Control Characters](https://262.ecma-international.org/#sec-unicode-format-control-characters) — раздел про специальную категорию невидимых, непечатаемых управляющих символов Юникода, которым явно разрешено присутствовать внутри исходного текста программы, причём даже **посреди** идентификатора (имени переменной, функции). Такие символы (относящиеся к определённым категориям Unicode, например символ нулевой ширины для соединения) полностью прозрачны для значения программы — они игнорируются при вычислении смысла кода, но формально допустимы в тексте. Это, в частности, источник редкого, но реального класса проблем с "невидимым" вредоносным кодом — два визуально идентичных идентификатора могут оказаться разными переменными из-за скрытого управляющего символа внутри одного из них, незаметного при обычном просмотре кода.

[12.2 White Space](https://262.ecma-international.org/#sec-white-space) и [12.3 Line Terminators](https://262.ecma-international.org/#sec-line-terminators) на первый взгляд кажутся синонимами (и то, и другое — "невидимые промежутки" в тексте кода), но спецификация явно разводит их по двум разным грамматическим категориям, и разница здесь не косметическая, а функциональная: терминатор строки (перевод строки и несколько родственных ему Unicode-символов) активно **участвует** в механизме автоматической расстановки точек с запятой (разбирается ниже в этой же главе), тогда как обычный пробел или табуляция в этом механизме не участвуют вовсе:

```js
console.log(1 +
  2); // 3 — перенос строки прямо посреди незавершённого выражения не обрывает его
```

Здесь перенос строки после `+` не приводит к вставке точки с запятой, потому что грамматическое правило для оператора `+` явно ожидает продолжения после себя — правила ASI (подробно разбираются ниже) срабатывают только тогда, когда без вставки точки с запятой дальнейший разбор становится грамматически невозможным, а не при любом переносе строки.

[12.5 Hashbang Comments](https://262.ecma-international.org/#sec-hashbang) — специальный синтаксис вида `#!/usr/bin/env node` в самой первой строке файла, знакомый всем, кто писал исполняемые скрипты для Unix-подобных систем. Формально это **не** обычный комментарий в общем смысле (не то же самое, что `//` или `/* */`) — это отдельная, самостоятельная грамматическая продукция, специально разрешённая исключительно в самом начале файла и нигде больше. Именно поэтому такая строка не работает, если попытаться поместить её где-то посередине файла — грамматика такого не допускает.

## 12.6–12.8 Токены — базовые «слова» языка

[12.6 Tokens](https://262.ecma-international.org/#sec-tokens) определяет пять категорий токенов, на которые лексический анализатор разбивает поток символов исходного текста: имя (идентификатор), зарезервированное слово, знак пунктуации, литерал шаблона, обычный литерал (число, строка, регулярное выражение и подобные). Всё, что дальше происходит при синтаксическом разборе выражений и инструкций (главы 13–14), работает уже поверх этого потока токенов, а не поверх сырого текста символов.

[12.7.2 Keywords and Reserved Words](https://262.ecma-international.org/#sec-keywords-and-reserved-words) описывает деление зарезервированных слов на группы разной степени строгости — и эта деталь объясняет практическое, часто неожиданное поведение отдельных идентификаторов, которые то работают как обычные переменные, то внезапно вызывают синтаксическую ошибку в зависимости от контекста. Часть слов зарезервирована **всегда**, безусловно (`if`, `for`, `class`); часть — **только в строгом режиме** (`interface`, `implements`, `package` и другие, зарезервированные "про запас" для потенциальных будущих версий языка); а часть — **только в определённом синтаксическом контексте**:

```js
// yield не зарезервировано глобально, вне генератора и вне строгого режима
var yield = 1; console.log(yield); // 1

function* g() {
  // var yield = 1; // SyntaxError — внутри тела генератора yield зарезервировано
}
```

```js
'use strict';
// var interface = 1; // SyntaxError — зарезервировано только в строгом режиме
```

Слово `yield` — показательный пример третьей категории: оно ведёт себя как совершенно обычный, ничем не примечательный идентификатор в обычной, не-генераторной функции нестрогого режима, но становится строго зарезервированным словом внутри тела генератора (потому что там оно означает конструкцию `yield`-выражения) — то же самое грамматическое правило разбирается формально в терминах параметра продукции `[Yield]` (глава 5).

## 12.9 Литералы

### Числовые литералы — своя, отдельная грамматика

[12.9.3 Numeric Literals](https://262.ecma-international.org/#sec-literals-numeric-literals) описывает грамматику записи числа непосредственно **в тексте кода** — и здесь стоит явно напомнить ключевую мысль главы 5: это **другая** грамматика, чем та, что используется при разборе числа из строки (например, функцией `Number()`), о которой шла речь в главе 7. В частности, здесь, в грамматике числовых литералов кода, явно разрешены разделители-подчёркивания для визуальной группировки разрядов, тогда как грамматика разбора числовых строк про них ничего не знает:

```js
console.log(1_000_000, 0b1010, 0o17, 0x1F, 1e3, .5, 5.);
// 1000000 10 15 31 1000 0.5 5
```

Здесь одной строкой продемонстрированы сразу шесть разных допустимых форм: разделители-подчёркивания, двоичная запись (`0b`), восьмеричная (`0o`), шестнадцатеричная (`0x`), экспоненциальная запись (`1e3`), а также литералы с опущенной целой (`.5`) или дробной (`5.`) частью — все они дают одно и то же понятие "число", просто записанное по-разному.

[12.9.3.3 NumericValue](https://262.ecma-international.org/#sec-numericvalue) — синтаксически управляемая операция (тот же приём, что подробно разбирается в главе 8), вычисляющая настоящее значение числового литерала из его текстового представления. Литерал с суффиксом `n` (например, `10n`) даёт значение типа `BigInt`, произвольной точности; без суффикса — обычное значение типа `Number` с фиксированной 64-битной точностью.

### Строковые литералы — эволюция escape-последовательностей

[12.9.4 String Literals](https://262.ecma-international.org/#sec-literals-string-literals) описывает набор escape-последовательностей, доступных внутри строковых литералов. Стоит отдельно остановиться на форме `\u{...}` (в фигурных скобках) — она появилась в языке позже классической формы `\uXXXX` не ради синтаксического разнообразия, а по конкретной технической необходимости: старая форма `\uXXXX` жёстко кодирует ровно **одну** 16-битную кодовую единицу UTF-16 и физически не способна задать одним блоком символ, лежащий за пределами базовой многоязыковой плоскости Unicode (например, большинство эмодзи, требующих суррогатной пары двух кодовых единиц — подробно разбирается в главе 22). Новая форма `\u{...}` принимает произвольное число шестнадцатеричных цифр и сама автоматически разворачивается в нужную суррогатную пару, если код символа этого требует:

```js
console.log('A', '\u{1F600}'.length, '\x41', '\101');
// A 2 A A
```

`'\u{1F600}'.length` равно `2`, а не `1` — потому что даже записанный современной, "человекочитаемой" формой в фигурных скобках, символ эмодзи внутри строки всё равно физически хранится как пара из двух 16-битных единиц (глава 6 уже отмечала: строка ECMAScript — это последовательность именно таких единиц, а не "символов" в бытовом понимании). `\x41` — устаревшая, но всё ещё поддерживаемая двухзначная шестнадцатеричная форма, а `\101` — восьмеричная форма (даёт тот же символ `'A'`), которая **явно запрещена** в строгом режиме как унаследованный от очень старых версий языка легаси-механизм (подробно разбирается в главе 17 применительно к Annex B).

### Литералы шаблонов — два параллельных значения одного и того же текста

[12.9.6 Template Literal Lexical Components](https://262.ecma-international.org/#sec-template-literal-lexical-components) вводит концептуально важную идею: у одного и того же исходного текста внутри шаблонного литерала формально существует сразу **два** параллельных, самостоятельных значения — **TV** (Template Value, [12.9.6.1](https://262.ecma-international.org/#sec-static-semantics-tv)), обработанное значение с уже интерпретированными escape-последовательностями, и **TRV** (Template Raw Value, [12.9.6.2](https://262.ecma-international.org/#sec-static-semantics-trv)) — буквальный исходный текст, ровно как он написан в файле, без какой-либо интерпретации escape-последовательностей вообще:

```js
const tag = (strings) => [strings[0], strings.raw[0]];
console.log(tag`a\nb`);
// [ 'a\nb' (с настоящим переносом строки внутри), 'a\\nb' (буквальные символы \ и n) ]
```

Первый элемент результата — обработанное значение (TV), где `\n` уже стал настоящим символом переноса строки. Второй — сырое значение (TRV), где `\n` остался буквальным текстом из двух символов: обратный слэш и буква `n`, без всякой интерпретации. Именно на этой паре параллельных значений построен встроенный метод `String.raw` — он специально работает с сырыми значениями, что особенно полезно при работе с путями Windows (где обратный слэш — обычный разделитель директорий, а не начало escape-последовательности) или при написании текста регулярных выражений внутри шаблонного литерала, где обратный слэш тоже несёт собственное, отличное от строковых escape-последовательностей значение.

## 12.10 Автоматическая расстановка точек с запятой

[12.10 Automatic Semicolon Insertion](https://262.ecma-international.org/#sec-automatic-semicolon-insertion) (ASI) — механизм, который многие воспринимают как расплывчатую "магию", но который на деле работает по трём строго определённым правилам из [12.10.1](https://262.ecma-international.org/#sec-rules-of-automatic-semicolon-insertion):

1. Следующий токен грамматически не подходит для продолжения текущей продукции, и между ним и предыдущим токеном в исходном тексте есть хотя бы один терминатор строки — точка с запятой вставляется прямо перед этим неподходящим токеном
2. Достигнут конец всей программы, а текущий разбор ещё не завершён (не хватает точки с запятой для валидного окончания) — точка вставляется в самом конце
3. Отдельные, явно перечисленные грамматические продукции (`return`, `break`, `continue`, постфиксные `++`/`--`, а также стрелочные функции и несколько других случаев) содержат явный запрет на перенос строки в конкретном месте — если этот запрет нарушен, точка с запятой немедленно вставляется сразу после соответствующего ключевого слова или токена, обрывая продолжение конструкции

Третье правило — источник самой известной ловушки ASI:

```js
function f() {
  return
    { value: 1 };
}
console.log(f()); // undefined
```

Грамматическое правило `ReturnStatement` содержит явный запрет переноса строки сразу после ключевого слова `return` (детально разбирается уже в главе 5) — поэтому здесь срабатывает именно третье, самое "агрессивное" правило ASI: точка с запятой вставляется сразу после `return`, ещё до того, как встретился объектный литерал на следующей строке, и функция фактически выполняет `return;`, полностью игнорируя то, что написано ниже.

При этом важно понимать: подавляющее большинство обычного кода без точек с запятой в конце строк работает совершенно нормально, и первое правило ASI прекрасно с этим справляется:

```js
const a = 1
const b = [2, 3]
console.log(a, b)
// работает без единой явной точки с запятой: каждая строка начинается
// с ключевого слова или идентификатора, объединения соседних строк не происходит
```

> [!warning] Единственная реальная практическая опасность ASI
> Проблема на практике возникает не из-за общего "отсутствия точек с запятой" как таковой — это почти всегда безопасно. Настоящая опасность — когда следующая строка **начинается** с одного из символов `(`, `[`, `` ` ``, `+`, `-` или `/`: все они грамматически способны *продолжить* предыдущее выражение вместо начала нового, и в таком случае первое правило ASI не срабатывает, потому что дальнейший разбор формально всё ещё возможен без вставки точки с запятой — просто результат окажется совсем не тем, что имел в виду автор кода.
> ```js
> const x = 1
> ;[1, 2, 3].forEach(console.log) // ведущая точка с запятой — стандартная защита от такого слияния
> ```
> Без ведущей точки с запятой перед `[1, 2, 3]` строки выше слились бы в одно выражение `const x = 1[1, 2, 3].forEach(console.log)`, что дало бы либо ошибку, либо совсем не то поведение, которое ожидалось. Ведущая точка с запятой перед строкой, начинающейся с `(` или `[`, — распространённый защитный стиль написания кода именно из-за этой конкретной опасности.

## Итог

> [!summary] Что взять с собой
> - Исходный текст ECMAScript формально определён как последовательность кодовых точек Unicode, а не байтов — кодировка интерпретируется раньше, чем начинается лексический разбор
> - Тип исходного кода определяет строгость режима по умолчанию: модуль строгий всегда без исключений, скрипт — только с явной директивой `'use strict'`, тело функции наследует режим места объявления
> - Терминатор строки и обычный пробел — разные грамматические категории: только первый участвует в автоматической расстановке точек с запятой
> - Зарезервированные слова делятся по строгости контекста: часть зарезервирована всегда, часть — только в строгом режиме, часть — только внутри конкретной конструкции (`yield` внутри генератора)
> - Грамматика числовых литералов кода и грамматика разбора числовых строк — разные; разделители-подчёркивания работают только в первой
> - `\u{...}` появился специально ради символов вне базовой плоскости Unicode — старая форма `\uXXXX` кодирует ровно одну 16-битную единицу и физически не может задать такой символ одним блоком
