# Глава 20 · Базовые объекты — отчёт

> [!info] Раздел спецификации
> [20 Fundamental Objects](https://262.ecma-international.org/#sec-fundamental-objects)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Эта глава описывает пять встроенных объектов: [Object](https://262.ecma-international.org/#sec-object-objects), [Function](https://262.ecma-international.org/#sec-function-objects), [Boolean](https://262.ecma-international.org/#sec-boolean-objects), [Symbol](https://262.ecma-international.org/#sec-symbol-objects), [Error](https://262.ecma-international.org/#sec-error-objects). Это не «ещё одна библиотека» — это те самые конструкторы, которые стоят за каждым `{}`, каждой функцией, каждым `try/catch` в вашем коде.

Разбираю не все методы подряд — большинство совпадает с тем, чем вы и так пользуетесь каждый день (`Object.keys`, `Object.assign`, `Function.prototype.call` и подобные), и объяснять их смысла нет. Вместо этого — то, что либо путают, либо не замечают, но что реально влияет на поведение кода.

---

## 20.1 Object

### Object.groupBy — новый метод, о котором стоит знать

[Object.groupBy](https://262.ecma-international.org/#sec-object.groupby) появился относительно недавно и решает задачу, которую раньше решали вручную через `reduce`: разбить массив на группы по какому-то критерию.

```js
const numbers = [1, 2, 3, 4, 5, 6];
const grouped = Object.groupBy(numbers, n => n % 2 === 0 ? 'чётные' : 'нечётные');
console.log(grouped);
// [Object: null prototype] { нечётные: [1, 3, 5], чётные: [2, 4, 6] }
```

Обратите внимание на надпись `[Object: null prototype]` в выводе — это не случайность и не мусор в консоли. Результат `Object.groupBy` создаётся **без прототипа**, то есть у него нет `Object.prototype` в цепочке наследования. Практическое следствие: у такого объекта нет унаследованных методов вроде `toString`, `hasOwnProperty` и так далее — если группа данных случайно называется `toString`, это не столкнётся ни с чем и не сломает поведение.

```js
console.log(Object.getPrototypeOf(grouped)); // null
console.log(typeof grouped.hasOwnProperty);  // 'undefined' — метода просто нет
console.log(Object.hasOwn(grouped, 'чётные')); // true — а вот так проверять нужно
```

Это ровно та же идея, что мы уже видели с `Object.create(null)`: если объект используется как «словарь» — набор ключей, которыми управляет ваш код, а не как обычная сущность языка — отсутствие унаследованных методов защищает от коллизий имён.

### Object.fromEntries — работает не только с массивами

[Object.fromEntries](https://262.ecma-international.org/#sec-object.fromentries) многие используют только в паре с `Object.entries` (собрать объект → массив пар → снова объект после фильтрации). Но метод принимает **любой перебираемый источник пар**, не только массив — включая `Map` и даже генератор.

```js
// с Map — распространённый случай
const map = new Map([['a', 1], ['b', 2]]);
console.log(Object.fromEntries(map)); // { a: 1, b: 2 }

// с генератором — то, что обычно упускают
function* pairs() {
  yield ['x', 10];
  yield ['y', 20];
}
console.log(Object.fromEntries(pairs())); // { x: 10, y: 20 }
```

Практическая польза: если у вас есть ленивый источник данных (например, чтение построчно из файла, где каждая строка даёт пару ключ-значение), можно не собирать промежуточный массив вообще, а сразу передать генератор.

### Object.hasOwn против hasOwnProperty — почему новый метод лучше старого

`obj.hasOwnProperty('key')` — старый способ проверить, что свойство принадлежит именно этому объекту, а не унаследовано от прототипа. Проблема в том, что это **метод**, унаследованный от `Object.prototype`, и у объекта без прототипа его попросту нет.

```js
const dict = Object.create(null);
dict.key = 1;

// console.log(dict.hasOwnProperty('key')); // TypeError: dict.hasOwnProperty is not a function

console.log(Object.hasOwn(dict, 'key')); // true — работает всегда
```

[Object.hasOwn](https://262.ecma-international.org/#sec-object.hasown) — статическая функция, а не метод объекта, поэтому её работоспособность не зависит от того, что за объект вы проверяете. Если пишете новый код — используйте её вместо `hasOwnProperty`.

### Object.is — третий вид равенства, и он не то же самое, что includes

Мы уже разбирали в главе 7, что в языке есть три разных алгоритма сравнения значений. [Object.is](https://262.ecma-international.org/#sec-object.is) реализует средний по строгости — **SameValue**. Он отличается и от строгого равенства `===`, и от того сравнения, которое используют коллекции вроде `Set` и `Map`.

```js
console.log(Object.is(NaN, NaN));   // true  — а вот NaN === NaN даёт false
console.log(Object.is(0, -0));      // false — а вот 0 === -0 даёт true
console.log(Object.is(5, 5));       // true  — для обычных значений всё как ожидается
```

Здесь легко запутаться, потому что `[NaN].includes(NaN)` тоже даёт `true`, и кажется, что это то же самое сравнение. На деле `includes` использует **SameValueZero** — третий вариант, отличающийся от `Object.is` именно в вопросе про `-0` (SameValueZero считает `0` и `-0` одинаковыми, `Object.is` — разными). На практике `Object.is` нужен редко, но если вы пишете библиотеку, которая должна отличать `0` от `-0` (например, для точной сериализации чисел), это единственный штатный способ это сделать.

### __proto__ — это не «встроенная особенность объекта», а обычный аксессор

Вот деталь, которая объясняет неожиданное поведение объектов без прототипа. Многие думают, что `obj.__proto__` — это какая-то встроенная магия, доступная у любого объекта JavaScript. На самом деле это [геттер и сеттер](https://262.ecma-international.org/#sec-object.prototype.__proto__), определённые на `Object.prototype`. То есть `__proto__` — это **обычное унаследованное свойство**, которое ведёт себя как метод: если в цепочке прототипов объекта нет `Object.prototype`, свойства `__proto__` у него попросту не существует.

```js
const dict = Object.create(null);

console.log(dict.__proto__); // undefined — но это НЕ значит, что прототип у объекта null!
                              // это значит, что у объекта нет самого свойства __proto__

console.log(Object.getPrototypeOf(dict)); // null — а вот это действительно надёжный способ узнать прототип
```

Это частая ловушка при отладке: если код читает `obj.__proto__`, чтобы проверить прототип объекта, а объект создан через `Object.create(null)`, результат окажется `undefined` — не потому что прототип действительно неопределённый, а потому что метода чтения прототипа у объекта попросту нет. Правильный, надёжный способ — всегда `Object.getPrototypeOf(obj)`.

### Object.prototype.toString — самый надёжный способ узнать тип значения

Мы уже касались этого в главе 18 при разборе `Symbol.toStringTag`. Стоит закрепить практическое применение: `Object.prototype.toString.call(значение)` — единственный способ надёжно определить встроенный тип значения, который работает даже через границу realm (напомню из главы 9: если значение пришло из другого окна браузера или изолированного контекста, `instanceof` может соврать, потому что там другой набор встроенных прототипов).

```js
console.log(Object.prototype.toString.call([]));           // '[object Array]'
console.log(Object.prototype.toString.call(null));          // '[object Null]'
console.log(Object.prototype.toString.call(undefined));     // '[object Undefined]'
console.log(Object.prototype.toString.call(async () => {})); // '[object AsyncFunction]'
console.log(Object.prototype.toString.call(42));             // '[object Number]'
```

Заметьте: `null` и `undefined` — единственные значения, для которых этот метод работает без ошибки, несмотря на то, что обычно у них нет свойств вообще. Это особый случай, зашитый прямо в алгоритм.

## 20.2 Function

### Function.prototype.toString — исходный код, а не всегда

`fn.toString()` — то, чем часто пользуются для отладки или для метапрограммирования (например, библиотеки для сериализации функций смотрят на их текст). [Function.prototype.toString](https://262.ecma-international.org/#sec-function.prototype.tostring) обязан вернуть **точный исходный текст функции**, если он доступен движку. Но для встроенных функций исходного кода нет — вместо него возвращается специальная заглушка.

```js
function real() { return 1; }
console.log(real.toString());
// 'function real() { return 1; }' — дословный текст, как в файле

console.log(Math.max.toString());
// 'function max() { [native code] }' — заглушка, реального кода нет

console.log((() => {}).toString());
// '() => {}' — стрелка тоже возвращает свою исходную запись
```

Практическое следствие: если вы пишете код, который пытается «распарсить» функцию по её строковому представлению (например, вытащить список параметров через регулярное выражение), это сработает для функций, написанных на JS, но сломается для встроенных методов — там текста просто нет.

### Function Constructor — скрытая ловушка с областью видимости

`new Function('a', 'b', 'return a + b')` создаёт функцию из строк во время выполнения — редко используемый, но существующий способ. Важная деталь: тело такой функции выполняется **в глобальной области видимости**, а не в области того места, где вы написали `new Function(...)`. Это то же самое ограничение, что у косвенного `eval` из главы 19.

```js
function outer() {
  const secret = 'локальная';
  const fn = new Function('return typeof secret');
  return fn();
}
console.log(outer()); // 'undefined' — fn не видит secret, хотя написана прямо внутри outer
```

Если вам когда-нибудь понадобится динамически создать функцию из строки (это редко оправдано, но бывает — например, в шаблонизаторах), помните: доступа к замыканию вокруг места создания у неё не будет.

## 20.3 Boolean

Boolean — самый скромный объект главы: конструктор, `toString`, `valueOf`. Единственное, что стоит держать в голове, уже разбиралось в главе 6, но повторю кратко: `new Boolean(false)` создаёт **объект**, а не примитив, и объект в булевом контексте всегда истинен — независимо от того, какое значение обёрнуто внутри.

```js
const wrapped = new Boolean(false);
if (wrapped) {
  console.log('это выполнится'); // да, выполнится!
}
console.log(wrapped == false); // true — но при явном сравнении приведение сработает
```

Вывод простой: никогда не создавайте булевы значения через `new Boolean(...)` — только через литералы `true`/`false` или функцию-преобразователь `Boolean(x)` без `new`.

## 20.4 Symbol

### Глобальный реестр символов — способ получить «один и тот же» символ в разных местах

Обычно каждый вызов `Symbol()` создаёт уникальное значение, даже с одинаковым описанием:

```js
console.log(Symbol('id') === Symbol('id')); // false — всегда разные
```

Но иногда нужен обратный эффект — символ, который будет одним и тем же, если два разных куска кода (возможно, из разных файлов или даже разных библиотек) попросят его по одному и тому же ключу. Для этого есть [Symbol.for](https://262.ecma-international.org/#sec-symbol.for) — он берёт символ из глобального реестра, создавая его при первом обращении и переиспользуя при последующих.

```js
const a = Symbol.for('shared-key');
const b = Symbol.for('shared-key');
console.log(a === b); // true — один и тот же символ

console.log(Symbol.keyFor(a));           // 'shared-key' — узнать ключ обратно
console.log(Symbol.keyFor(Symbol('x'))); // undefined — обычный символ не в реестре
```

Ключевой факт, который делает эту функцию особенной: реестр **общий даже между разными realm** (напомню из главы 9 — это изолированные окружения вроде разных вкладок браузера или воркеров). Если у вас есть библиотека, загруженная в двух разных iframe одной страницы, и обеим копиям нужен общий символ-маркер (например, чтобы отличить «свой» объект от чужого), `Symbol.for` — единственный штатный способ этого добиться. Обычный `Symbol()`, созданный в одном realm, никогда не будет строго равен символу из другого realm.

## 20.5 Error

### Иерархия встроенных типов ошибок

Каждый раз, когда движок сам обнаруживает проблему во время выполнения, он бросает ошибку одного из шести стандартных типов, перечисленных в [20.5.5 Native Error Types](https://262.ecma-international.org/#sec-native-error-types-used-in-this-standard):

| Тип | Когда бросается движком |
|---|---|
| `TypeError` | операция применена к значению неподходящего типа |
| `RangeError` | числовое значение выходит за допустимый диапазон |
| `ReferenceError` | обращение к несуществующему или неинициализированному биндингу |
| `SyntaxError` | код не проходит разбор |
| `URIError` | ошибка в функциях кодирования/декодирования URI |
| `EvalError` | исторический тип, современные движки его практически не бросают |

Все они наследуются от общего `Error`, поэтому `catch (e)` без уточнения типа перехватит любую из них:

```js
console.log(new TypeError('x') instanceof Error); // true
console.log(new RangeError('x') instanceof Error); // true
```

Если вам нужно различать типы ошибок в обработчике, проверяйте `e instanceof TypeError` (или конкретный класс), а не полагайтесь на текст сообщения — он не стандартизирован и может отличаться между движками.

### AggregateError — ошибка, которая оборачивает сразу несколько ошибок

Обычная ошибка описывает одну проблему. [AggregateError](https://262.ecma-international.org/#sec-aggregate-error-constructor) — единственный встроенный тип, который **специально существует для нескольких причин сразу**. Он появился вместе с `Promise.any`: если все переданные промисы отклонились, нужен способ сообщить о всех отказах одновременно, а не только о первом.

```js
try {
  await Promise.any([
    Promise.reject(new Error('сервер А недоступен')),
    Promise.reject(new Error('сервер Б недоступен')),
  ]);
} catch (e) {
  console.log(e instanceof AggregateError); // true
  console.log(e.errors.length);              // 2
  console.log(e.errors[0].message);          // 'сервер А недоступен'
}
```

Если вы сами пишете код, который выполняет несколько независимых операций и хочет сообщить обо всех неудачах разом (а не остановиться на первой), `new AggregateError([...ошибки], 'сообщение')` — готовый инструмент для этого, не нужно изобретать свой формат.

### cause — как правильно сохранять исходную причину ошибки

Опция `cause` в конструкторе `Error` появилась сравнительно недавно и решает частую боль: когда вы ловите одну ошибку и хотите выбросить свою, более понятную, но не хотите потерять исходную техническую информацию.

```js
async function loadConfig() {
  try {
    return JSON.parse(await readFile('config.json'));
  } catch (e) {
    // не просто «что-то пошло не так», а понятное сообщение с сохранённой причиной
    throw new Error('Не удалось загрузить конфигурацию', { cause: e });
  }
}

try {
  await loadConfig();
} catch (e) {
  console.log(e.message);          // 'Не удалось загрузить конфигурацию'
  console.log(e.cause.constructor.name); // например, 'SyntaxError' — исходная причина сохранена
}
```

Важно понимать: `cause` — это не отдельный тип ошибки, а просто ещё одно свойство на экземпляре `Error`, описанное в [20.5.4 Properties of Error Instances](https://262.ecma-international.org/#sec-properties-of-error-instances). До появления этой опции разработчики либо теряли исходную ошибку, либо вручную прикручивали к своему объекту произвольное свойство вроде `originalError` — теперь для этого есть стандартный способ.

### stack — то, чем вы пользуетесь каждый день, но чего нет в стандарте

Последний важный факт: свойство `error.stack`, которое выводит трассировку стека вызовов, **нигде не описано** в тексте ECMA-262. Это соглашение, которое сложилось на практике и которое реализуют все движки, но каждый — по-своему: разный формат строк, разное количество кадров по умолчанию, разное поведение с асинхронным кодом. Если вы пишете код, который парсит `error.stack` регулярными выражениями, чтобы вытащить из него информацию — учитывайте, что это не гарантированное поведение языка, а деталь конкретного движка.

> [!success] Что забирать
> - `Object.groupBy` создаёт результат без прототипа — у него нет унаследованных методов вроде `toString`, что защищает от коллизий имён

> - `Object.hasOwn` — статическая функция, работающая даже с объектами без прототипа, в отличие от метода `hasOwnProperty`
> - `Object.is` реализует третий вид равенства (SameValue), отличный и от `===`, и от того, что используют `Set`/`Map`
> - `__proto__` — обычный унаследованный аксессор, а не встроенная магия; у объекта без прототипа его нет, и `obj.__proto__` тогда даст `undefined`, а не реальный прототип

> - `Object.prototype.toString.call(x)` — самый надёжный способ определить встроенный тип значения, работает через границу realm
> - `Function.prototype.toString` возвращает исходный текст функции, если он есть, и заглушку `[native code]` для встроенных функций
> - Функция, созданная через `new Function(...)`, выполняется в глобальной области и не видит окружающее замыкание
> - `new Boolean(false)` — объект, всегда истинный в условиях; никогда не создавайте булевы значения через `new`

> - `cause` в конструкторе `Error` — стандартный способ сохранить исходную ошибку при перевыбрасывании
> - `error.stack` не описано стандартом вовсе — это конвенция каждого движка
