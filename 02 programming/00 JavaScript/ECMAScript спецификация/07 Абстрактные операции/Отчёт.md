# Глава 7 · Абстрактные операции — отчёт

> [!info] Раздел спецификации
> [7 Abstract Operations](https://262.ecma-international.org/#sec-abstract-operations)
> Карточки → [[Карточки]] · квиз → [[Квиз]] · карта → [[00 Карта]]

Это, вероятно, самая цитируемая глава всего документа — почти каждый алгоритм из последующих глав в какой-то момент ссылается сюда. Она содержит "словарь" базовых операций, из которых, как из кирпичиков, собрано буквально всё остальное поведение языка: как значение одного типа превращается в значение другого, как проверяется равенство двух значений, как читаются и записываются свойства объектов, как перебираются итерируемые последовательности. Глава разбита на четыре смысловые части: преобразования типов, сравнения и проверки, операции над объектами, операции над итераторами.

## 7.1 Преобразования типов

[7.1 Type Conversion](https://262.ecma-international.org/#sec-type-conversion) — раздел, который стоит прочитать в первую очередь, потому что он сразу исправляет распространённое, но неверное ментальное представление о том, как в JavaScript работает приведение типов. В спецификации **нет** ни одной операции, которая "меняет тип существующего значения" — такой операции не существует в принципе, потому что значения языковых типов в JavaScript неизменяемы сами по себе (переменная может *хранить* разные значения в разные моменты времени, но конкретное значение, скажем, число `5`, никогда не "превращается" во что-то другое). Каждая операция преобразования берёт исходное значение и порождает **совершенно новое** значение другого типа, никак не затрагивая исходное. Мысленная модель "переменная превратилась в строку" технически неверна: правильнее говорить "была вычислена новая строка на основе значения переменной, а сама переменная как хранила прежнее значение, так и хранит его дальше" — это тонкое, но важное для понимания различие, особенно когда речь заходит о примитивах, которые (в отличие от объектов) вообще не могут быть изменены никаким способом.

### ToPrimitive — единая точка входа для превращения объекта в примитив

[7.1.1 ToPrimitive](https://262.ecma-international.org/#sec-toprimitive) — едва ли не самая важная операция преобразования во всей главе, потому что через неё в конечном счёте проходит буквально любая ситуация, где объект должен участвовать в контексте, ожидающем примитивное значение (сложение, шаблонная строка, сравнение и так далее). Операция принимает значение и необязательный "хинт" — подсказку о预pochtitel'nom результате: строковый, числовой, или "по умолчанию" (когда контекст сам не уточняет предпочтение).

Порядок действий такой: если переданное значение и без того не объект — вернуть как есть, без изменений; если у объекта есть собственный метод преобразования к примитиву (`Symbol.toPrimitive`) — вызвать именно его и полностью довериться результату; если такого метода нет — обратиться к [7.1.1.1 OrdinaryToPrimitive](https://262.ecma-international.org/#sec-ordinarytoprimitive), которая пробует по очереди два стандартных метода объекта, причём **порядок** этой пробы зависит от хинта:

| Хинт | Порядок методов |
|---|---|
| строковый | сначала `toString`, затем `valueOf` |
| числовой и "по умолчанию" | сначала `valueOf`, затем `toString` |

```js
const dual = {
  [Symbol.toPrimitive](hint) {
    return hint === 'number' ? 42 : hint === 'string' ? 'строка' : 'умолчание';
  }
};
console.log(+dual, `${dual}`, dual + '');
// 42 строка умолчание
```

Здесь наглядно видно все три возможных хинта разом: унарный `+` явно требует числа (хинт `'number'`), шаблонная строка явно требует текста (хинт `'string'`), а бинарный `+` не может заранее знать, что хочет получить программист (число или текст), поэтому запрашивает "умолчание" (хинт `'default'`).

Хинт "по умолчанию" — не самый частый случай: спецификация запрашивает его ровно в двух ситуациях: бинарное сложение (`+`) и нестрогое равенство (`==`) с объектом на одной из сторон. Все остальные операторы и контексты (вычитание, сравнение `<`/`>`, явный вызов `Number()`) запрашивают числовой хинт напрямую, минуя "умолчание". Единственный встроенный тип во всём языке, который трактует хинт "по умолчанию" не как числовой (обычное поведение `OrdinaryToPrimitive`), а как **строковый**, — это `Date` (подробно разбирается в главе 21, где объясняется и историческая причина этого исключения):

```js
const d = new Date(0);
console.log(typeof (d + 1), typeof (d - 1)); // string number
```

`d + 1` использует хинт "по умолчанию", и для `Date` это означает строковое поведение — отсюда результат `typeof` равен `'string'` (конкатенация строкового представления даты с текстом `'1'`). А `d - 1` явно требует числового хинта (вычитание не бывает "по умолчанию"), и здесь `Date` ведёт себя как любой другой объект, возвращая число миллисекунд.

Наконец, стоит явно проговорить крайний случай: если у объекта в принципе нет ни `Symbol.toPrimitive`, ни рабочего `valueOf`/`toString` (например, объект создан через `Object.create(null)` и потому вообще не наследует стандартные методы `Object.prototype`), преобразование в примитив становится **невозможным**, и операция явно выбрасывает исключение, а не тихо возвращает что-то вроде `'[object Object]'`:

```js
const hostile = Object.create(null);
try { `${hostile}`; } catch (e) { console.log(e.constructor.name); } // TypeError
```

### Остальные преобразования — практический справочник

За пределами `ToPrimitive` в главе описан ещё длинный ряд более узких, специализированных преобразований — от значения к логическому типу, к числу конкретной разрядности, к строке, к валидному ключу объекта:

| Операция | Раздел | Заметка |
|---|---|---|
| ToBoolean | [7.1.2](https://262.ecma-international.org/#sec-toboolean) | не вызывает ToPrimitive вообще: **любой** объект истинен, без исключений |
| ToNumeric | [7.1.3](https://262.ecma-international.org/#sec-tonumeric) | выбирает, приводить ли к обычному числу или к произвольной точности |
| ToNumber | [7.1.4](https://262.ecma-international.org/#sec-tonumber) | на символе и значении произвольной точности выбрасывает исключение |
| ToIntegerOrInfinity | [7.1.5](https://262.ecma-international.org/#sec-tointegerorinfinity) | усекает дробную часть к нулю, а не округляет |
| ToInt32 / ToUint32 | [7.1.6](https://262.ecma-international.org/#sec-toint32) / [7.1.7](https://262.ecma-international.org/#sec-touint32) | используются побитовыми операторами |
| ToString | [7.1.17](https://262.ecma-international.org/#sec-tostring) | на символе выбрасывает исключение — умышленно, чтобы не путать символ со строкой |
| ToObject | [7.1.18](https://262.ecma-international.org/#sec-toobject) | на `null`/`undefined` выбрасывает исключение — их нельзя обернуть в объект |
| ToPropertyKey | [7.1.19](https://262.ecma-international.org/#sec-topropertykey) | превращает произвольное значение в валидный ключ свойства объекта |
| ToLength | [7.1.20](https://262.ecma-international.org/#sec-tolength) | вычисляет длину массивоподобных объектов |
| ToIndex | [7.1.22](https://262.ecma-international.org/#sec-toindex) | проверяет индексы буферов и типизированных массивов |

Стоит явно разобрать несколько наиболее практически значимых примеров из этой таблицы:

```js
console.log(Number(''), Number('   '), Number('12px'), Number('0x1F'));
// 0 0 NaN 31
```

`Number('')` и `Number('   ')` дают `0` (пустая строка и строка из одних пробелов трактуются как ноль по явному правилу грамматики числовых строк из главы 5), а `Number('12px')` даёт `NaN` — потому что преобразование строки в число требует, чтобы **вся** строка целиком была валидным числом, без единого постороннего символа; частичный разбор (как это делает, например, `parseInt`) здесь не допускается.

```js
console.log(2 ** 32 | 0, -1 >>> 0, 1.9 | 0, -1.9 | 0);
// 0 4294967295 1 -1
```

Побитовые операторы работают только с 32-битными целыми числами — значение сначала усекается до целого (дробная часть отбрасывается **к нулю**, а не округляется: `1.9 | 0` даёт `1`, а не `2`), а затем "укладывается" в 32-битный диапазон переполнением по модулю, что и объясняет результат `2 ** 32 | 0` равный `0`, а `-1 >>> 0` (беззнаковый сдвиг) — очень большому положительному числу вместо отрицательного.

```js
const o = {}; o[1] = 'a'; o['1'] = 'b'; o[{}] = 'c';
console.log(Object.keys(o), o[1]);
// ['1', '[object Object]'] 'b'
```

Обращение к свойству объекта по индексу вида `o[1]` формально проходит через `ToPropertyKey`, который приводит **любое** нестроковое и несимвольное значение к строке — числовой индекс `1` и строковый ключ `'1'` оказываются буквально одним и тем же ключом объекта, поэтому второе присваивание перезаписывает первое, а не создаёт новое свойство.

```js
console.log(Array.prototype.slice.call({ length: -5 }).length);
// 0
```

`ToLength` — специализированная операция, которая не просто конвертирует значение в число, а дополнительно **ограничивает** результат диапазоном от `0` до `Number.MAX_SAFE_INTEGER`: отрицательная длина `-5` "обрубается" до `0`, что и объясняет пустой результат `slice` над массивоподобным объектом с отрицательной длиной.

Наконец, важный факт про `ToBoolean`, часто вызывающий удивление у тех, кто ожидает, что "пустой объект" или "пустой массив" должны считаться ложными: приведение к логическому типу **вообще не заглядывает внутрь объекта** — оно вообще не вызывает `ToPrimitive`. Абсолютно любой объект, вне зависимости от содержимого, всегда истинен. Ложных значений во всём языке ровно восемь, и все они — примитивы:

```js
console.log([false, 0, -0, 0n, '', null, undefined, NaN].filter(v => !v).length); // 8
console.log(Boolean([]), Boolean({}), Boolean(new Boolean(false)));               // true true true
```

Последний пример особенно показателен: даже объект-обёртка `new Boolean(false)`, буквально *содержащий* значение `false` внутри себя, сам по себе истинен как объект — потому что `ToBoolean` проверяет только "является ли значение объектом", а не заглядывает в его содержимое.

## 7.2 Сравнения и проверки

[7.2 Testing and Comparison Operations](https://262.ecma-international.org/#sec-testing-and-comparison-operations) описывает предикаты (операции, отвечающие "да"/"нет" на конкретный вопрос о значении) и алгоритмы сравнения значений между собой.

Среди предикатов-проверок: [IsCallable](https://262.ecma-international.org/#sec-iscallable) (можно ли вызвать значение как функцию), [IsConstructor](https://262.ecma-international.org/#sec-isconstructor) (можно ли вызвать через `new`), [IsArray](https://262.ecma-international.org/#sec-isarray), [IsPropertyKey](https://262.ecma-international.org/#sec-ispropertykey), [IsIntegralNumber](https://262.ecma-international.org/#sec-isintegralnumber) и [RequireObjectCoercible](https://262.ecma-international.org/#sec-requireobjectcoercible). Последняя из них заслуживает отдельного внимания, потому что напрямую объясняет конкретное, регулярно встречающееся на практике поведение: почему методы `String.prototype` (да и большинства других встроенных прототипов) готовы принять в качестве `this` практически что угодно, кроме ровно двух значений:

```js
console.log(String.prototype.toUpperCase.call(123)); // '123'
try { String.prototype.trim.call(null); } catch (e) { console.log(e.constructor.name); } // TypeError
```

`RequireObjectCoercible` — простая проверка "не является ли значение `null` или `undefined`" (единственными двумя значениями во всём языке, которые нельзя обернуть в объект через `ToObject`). Число `123`, вызванное как `this` метода строки, спокойно проходит эту проверку и затем неявно оборачивается во временный объект-обёртку (та же механика, что разбирается в главе 22 применительно к строковым примитивам), а `null` — нет, поэтому падает с `TypeError` ещё до того, как метод вообще успел что-либо сделать.

### Три разных алгоритма равенства — и когда какой применяется

Один из самых практически значимых фактов всей главы: в JavaScript не один, а **три** формально независимых алгоритма проверки "равенства" значений, и они дают разные ответы на пограничных случаях `NaN` и знакового нуля:

| Операция | Раздел | Где применяется | NaN ≡ NaN | 0 ≡ −0 |
|---|---|---|:---:|:---:|
| [IsStrictlyEqual](https://262.ecma-international.org/#sec-isstrictlyequal) | 7.2.15 | оператор `===`, поиск по индексу (`indexOf`), выбор ветки `switch` | нет | да |
| [SameValue](https://262.ecma-international.org/#sec-samevalue) | 7.2.11 | `Object.is`, определение атрибутов свойства | да | нет |
| [SameValueZero](https://262.ecma-international.org/#sec-samevaluezero) | 7.2.12 | ключи `Map`/`Set`, `includes` | да | да |

```js
console.log(NaN === NaN, Object.is(NaN, NaN), [NaN].includes(NaN), [NaN].indexOf(NaN));
// false true true -1

console.log(Object.is(0, -0), [0].includes(-0), 0 === -0);
// false true true
```

Наличие сразу трёх алгоритмов — не избыточность и не историческая случайность, а осознанный компромисс под разные практические задачи: `===` должен вести себя предсказуемо для обычных сравнений в условиях (`if (x === NaN)` не должно неожиданно срабатывать для любого нечисла — и оно закономерно никогда не срабатывает, потому что `NaN` не равен даже сам себе по строгому равенству); коллекции вроде `Map`/`Set`, наоборот, обязаны уметь находить `NaN` как валидный, уникальный, самонаходимый ключ (иначе `NaN` вообще нельзя было бы использовать как ключ таких коллекций, что было бы существенно менее полезным поведением) — отсюда `SameValueZero`, где `NaN` равен себе. Подробный разбор всех трёх алгоритмов и их практических следствий для коллекций — в главе 24.

### Нестрогое равенство и оператор сравнения — два разных алгоритма, отсюда парадокс

[IsLooselyEqual](https://262.ecma-international.org/#sec-islooselyequal) (алгоритм оператора `==`) и [IsLessThan](https://262.ecma-international.org/#sec-islessthan) (алгоритм операторов `<`, `>`, `<=`, `>=`) — при всей внешней похожести (оба сравнивают значения разных типов, оба неявно что-то приводят) формально это **два совершенно разных** алгоритма с разным набором правил. Именно из этого структурного факта растёт знаменитый, регулярно вызывающий недоумение парадокс:

```js
console.log(null == 0, null >= 0, null > 0, null == undefined);
// false true false true
```

На первый взгляд кажется противоречивым: если `null >= 0` истинно, разве не должно быть истинным и `null == 0`? Разгадка — в том, что в алгоритме `IsLooselyEqual` для `null` **вообще нет шага** "привести к числу и сравнить" — вместо этого `null` подчиняется отдельному, специально прописанному правилу: он считается нестрого равным только `undefined` и самому себе, и ничему больше. А вот в алгоритме `IsLessThan` (используемом операторами сравнения) приведение к числу происходит **обязательно** для обеих сторон, и здесь `null` превращается в `0` через `ToNumber` — отсюда `null >= 0` истинно, ведь по сути сравнивается `0 >= 0`.

В том же разделе спецификации проявляется и другой известный факт — нестрогое равенство **не транзитивно**, потому что при совпадении типов операндов сравнения приведения не происходит вовсе, и алгоритм ведёт себя иначе, чем при разнотипных операндах:

```js
console.log('' == 0, '0' == 0, '' == '0'); // true true false
```

`'' == 0` и `'0' == 0` истинны, потому что здесь разные типы (строка и число), и строка приводится к числу перед сравнением (пустая строка → `0`, `'0'` → `0`). А `'' == '0'` — сравнение двух строк одного типа, и здесь по правилам алгоритма приведения не происходит вовсе, строки сравниваются напрямую как текст, а `''` и `'0'` — очевидно разные строки.

Наконец, `IsLessThan` формально может дать **неопределённый** результат (не `true` и не `false`, а специальное значение "undefined" внутри алгоритма), если хотя бы один операнд оказывается `NaN` — и любое сравнение с неопределённым результатом в конечном счёте трактуется как `false`, что объясняет, почему **все четыре** оператора сравнения одновременно ложны для `NaN`, включая `<=`/`>=`, которые интуитивно могли бы показаться "более снисходительными":

```js
console.log(NaN < 1, NaN > 1, NaN <= 1, NaN >= 1); // false false false false
```

## 7.3 Операции над объектами

[7.3 Operations on Objects](https://262.ecma-international.org/#sec-operations-on-objects) — набор более высокоуровневых операций-обёрток над внутренними методами объекта (сами внутренние методы подробно разбираются в главе 10): [Get](https://262.ecma-international.org/#sec-get-o-p), [GetV](https://262.ecma-international.org/#sec-getv), [Set](https://262.ecma-international.org/#sec-set-o-p-v-throw), [GetMethod](https://262.ecma-international.org/#sec-getmethod), [HasProperty](https://262.ecma-international.org/#sec-hasproperty), [Call](https://262.ecma-international.org/#sec-call), [Construct](https://262.ecma-international.org/#sec-construct) и другие. Эти обёртки берут на себя типовую "обвязку" — проверку типов аргументов, обработку крайних случаев — вокруг более примитивных внутренних методов, чтобы остальным алгоритмам спецификации не приходилось каждый раз повторять одну и ту же проверочную логику вручную.

Среди операций этого раздела стоит подробно разобрать три, потому что каждая из них — формальная основа конкретной, широко используемой конструкции языка.

**[SetIntegrityLevel](https://262.ecma-international.org/#sec-setintegritylevel)** — операция, лежащая в основе методов запечатывания и заморозки объекта. Три уровня защиты от изменений — `preventExtensions`, `seal`, `freeze` — на самом деле различаются не какой-то принципиально разной механикой, а просто разным набором прав, которые они запрещают, по нарастающей строгости:

```js
const p = Object.preventExtensions({ a: 1 }); delete p.a;   // удаление существующего свойства разрешено
const s = Object.seal({ a: 1 }); s.a = 99;                  // изменение значения разрешено
const f = Object.freeze({ a: 1, nested: { b: 2 } });
f.nested.b = 99;                                            // заморозка касается только верхнего уровня

console.log(Object.hasOwn(p, 'a'), s.a, f.nested.b);        // false 99 99
```

`preventExtensions` запрещает только добавление *новых* свойств — существующие можно свободно удалять и менять. `seal` дополнительно запрещает удаление свойств, но изменение значения всё ещё разрешено. И только `freeze` запрещает изменение значений тоже — но, что важно и часто становится источником путаницы, заморозка **поверхностная** (shallow): она защищает только свойства самого объекта, но не проникает во вложенные объекты — `f.nested` остаётся полностью изменяемым, потому что `freeze` затрагивает атрибуты `f`, а не рекурсивно всё дерево вложенных объектов.

**[CopyDataProperties](https://262.ecma-international.org/#sec-copydataproperties)** — формальная основа для остаточного элемента объектной деструктуризации (`const { a, ...rest } = obj`) и раскрытия объекта в новый литерал (`{ ...obj }`). Ключевая деталь, которую легко упустить: копируются только **собственные перечисляемые** свойства (унаследованные через прототип пропускаются), а если среди копируемых свойств есть аксессор (геттер), он при копировании **вызывается**, и в копию попадает уже вычисленное обычное значение, а не сам геттер:

```js
let calls = 0;
const src = { a: 1, get b() { calls++; return 2; } };
const { ...copy } = src;
console.log(calls, copy.b, Object.getOwnPropertyDescriptor(copy, 'b').get);
// 1 2 undefined
```

Геттер `b` был вызван ровно один раз в процессе копирования (`calls === 1`), а в самой копии `copy.b` — уже обычное свойство со значением `2`, у него нет собственного геттера (`get` в дескрипторе — `undefined`). Раскрытие в объектный литерал — это именно копирование значений на момент раскрытия, а не перенос "живой" вычисляемой логики.

**[EnumerableOwnProperties](https://262.ecma-international.org/#sec-enumerableownproperties)** — единая, общая операция, за которой стоят сразу три знакомых метода: `Object.keys`, `Object.values`, `Object.entries` — все они формально описаны как один и тот же алгоритм с параметром, определяющим, что именно вернуть (ключи, значения или пары).

## 7.4 Операции над итераторами

[7.4 Operations on Iterator Objects](https://262.ecma-international.org/#sec-operations-on-iterator-objects) вводит служебную структуру [Iterator Record](https://262.ecma-international.org/#sec-iterator-records) — набор из самого объекта-итератора, его метода перехода к следующему значению и флага, отмечающего, что итерация уже завершена. Формальный протокол итерации (интерфейсы Iterable/Iterator) подробно разбирается в главе 27 — здесь же описан набор служебных операций, реализующих механику самого перебора: [GetIterator](https://262.ecma-international.org/#sec-getiterator) (получить итератор из итерируемого объекта), [IteratorNext](https://262.ecma-international.org/#sec-iteratornext) (перейти к следующему значению), [IteratorStep](https://262.ecma-international.org/#sec-iteratorstep) (проверить, не закончилась ли последовательность), [IteratorClose](https://262.ecma-international.org/#sec-iteratorclose) (корректно завершить перебор), [IteratorToList](https://262.ecma-international.org/#sec-iteratortolist) (собрать все оставшиеся значения в список).

Самая недооценённая из этих операций — закрытие итератора, [IteratorClose](https://262.ecma-international.org/#sec-iteratorclose). Она автоматически вызывается движком в любой ситуации, где перебор прерывается **раньше**, чем последовательность закончилась естественным образом — при `break`, при исключении внутри тела цикла, или при неполной деструктуризации, забирающей меньше элементов, чем реально есть в источнике. Именно эта операция делает перебор безопасным для ресурсов, которые может держать итератор:

```js
function* resource() {
  try { yield 'первый'; yield 'второй'; }
  finally { console.log('освобождено'); }
}

for (const v of resource()) { console.log(v); break; }
// первый
// освобождено

const [only] = resource();
// освобождено — при деструктуризации короче последовательности тоже
```

В обоих случаях генератор не был доведён до конца, но блок `finally` внутри него всё равно гарантированно выполнился — потому что `IteratorClose` вызвала метод `.return()` итератора, а у генератора этот метод автоматически реализован так, что проходит через все незавершённые `finally`-блоки его тела (детальный разбор этого механизма — в главе 27).

Тот же самый механизм — требование, что источник для деструктуризации обязан быть настоящим итерируемым объектом, а не просто "похожим на список" — объясняет ещё один регулярно встречающийся источник путаницы: деструктуризация массива работает с абсолютно любым итерируемым значением (включая `Set`, `Map`, генераторы, строки), но **падает с ошибкой** на объекте, который лишь выглядит как массив (имеет числовые ключи и `length`), но формально не реализует протокол итерации:

```js
const [a] = new Set(['x']);                    // работает — Set итерируем
try { const [b] = { 0: 'x', length: 1 }; }      // не перебирается
catch (e) { console.log(e.constructor.name); }  // TypeError
```

Массивоподобный объект (array-like) и итерируемый объект (iterable) — формально разные, не пересекающиеся сами по себе понятия: у первого просто есть числовые свойства и `length`, а у второго — метод `[Symbol.iterator]`. Многие встроенные механизмы языка (например, `Array.from`, разбирается в главе 23) специально написаны так, чтобы принимать оба вида, но деструктуризация массива — намеренное исключение, работающее строго только с настоящими итерируемыми объектами.

## Итог

> [!summary] Что взять с собой
> - Операции преобразования типов не изменяют исходное значение — они порождают новое значение другого типа; мысленная модель "переменная превратилась" технически неточна
> - `ToPrimitive` — единая точка входа для превращения объекта в примитив; порядок опробования `valueOf`/`toString` зависит от хинта (строковый, числовой, по умолчанию)
> - Хинт "по умолчанию" запрашивают только бинарный `+` и нестрогое `==`; единственный встроенный тип, трактующий его как строковый (а не числовой) — `Date`
> - `ToBoolean` не заглядывает внутрь объекта — любой объект истинен, даже `new Boolean(false)`; ложных значений во всём языке ровно восемь, и все они примитивы
> - Преобразование строки в число строгое: требуется, чтобы вся строка целиком была валидным числом, частичный разбор не допускается
> - Алгоритмов равенства формально три (`===`, `Object.is`, SameValueZero), и они расходятся ровно на двух пограничных случаях — `NaN` и знаковом нуле
> - `==` и операторы сравнения (`<`, `>=`...) — разные алгоритмы: у `null` нет шага приведения к числу в равенстве, но есть в сравнении — отсюда парадокс `null == 0` (false) при `null >= 0` (true)
> - Нестрогое равенство не транзитивно, потому что приведение типов происходит только между значениями *разных* типов
> - `SetIntegrityLevel` объясняет три нарастающих уровня защиты объекта (`preventExtensions` → `seal` → `freeze`); заморозка всегда поверхностная
> - `CopyDataProperties` — формальная основа `{...obj}` и остаточного элемента деструктуризации: копируются только собственные перечисляемые свойства, геттеры при копировании вызываются один раз
> - `IteratorClose` делает перебор безопасным для ресурсов при досрочном выходе (`break`, исключение, неполная деструктуризация) — вызывает `.return()` итератора, что для генераторов означает выполнение `finally`-блоков
> - Массивоподобный объект и итерируемый объект — разные понятия; деструктуризация массива работает только со вторым
