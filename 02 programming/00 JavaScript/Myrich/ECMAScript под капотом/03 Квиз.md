## Блок 1. Контекст исполнения и стек

### 1. Что выведет код и в каком порядке

```js
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));

queueMicrotask(() => console.log('E'));

console.log('F');
```

> [!success]- Ответ
> `A F C E D B`
>
> Синхронный код даёт `A` и `F`. Затем очередь микрозадач: `C` был поставлен первым, `E` вторым. Второй `.then` регистрируется **только после** выполнения первого, поэтому `D` попадает в очередь позже `E`. Макрозадача `setTimeout` выполняется последней, когда микрозадачи исчерпаны.

### 2. Описан ли предел глубины стека вызовов в ECMA-262

> [!success]- Ответ
> Нет. Спецификация не задаёт ограничения — `RangeError: Maximum call stack size exceeded` полностью на совести реализации. Поэтому предел различается между движками и зависит от размера фрейма: функция с большим числом аргументов и локальных переменных упирается в лимит раньше.

### 3. Почему этот код работает в Safari, но падает в Chrome

```js
'use strict';
const sum = (n, acc = 0) => n === 0 ? acc : sum(n - 1, acc + n);
sum(1e6);
```

> [!success]- Ответ
> Это **proper tail call** — вызов в хвостовой позиции. Спецификация требует переиспользовать фрейм стека (операция `PrepareForTailCall`), но из мейнстримных движков это реализовал только JavaScriptCore.
>
> В V8 и SpiderMonkey оптимизации нет, миллион фреймов даёт `RangeError`. Полагаться на PTC в кроссбраузерном коде нельзя.

### 4. Перечислите компоненты execution context

> [!success]- Ответ
> code evaluation state, Function, Realm, ScriptOrModule, LexicalEnvironment, VariableEnvironment, PrivateEnvironment.
>
> Разделение Lexical и Variable Environment — это и есть механизм, разводящий `let`/`const` (первое) и `var` (второе).

### 5. Что означают `?` и `!` в тексте спецификации

> [!success]- Ответ
> `? expr` — `ReturnIfAbrupt`: если операция завершилась abrupt completion (обычно `throw`), пробросить его наружу немедленно.
>
> `! expr` — утверждение, что abrupt completion здесь невозможен. Срабатывание такого исключения означало бы ошибку в движке или в самой спецификации.

## Блок 2. Инстанцирование и окружения

### 6. Объясните разницу в типах ошибок

```js
a(); // ?
b(); // ?
c(); // ?

function a() {}
var b = function () {};
let c = function () {};
```

> [!success]- Ответ
> `a()` — работает. Функциональные декларации инициализируются готовым объектом на стадии инстанцирования.
>
> `b()` — `TypeError: b is not a function`. Биндинг создан и содержит `undefined`.
>
> `c()` — `ReferenceError: Cannot access 'c' before initialization`. Биндинг создан, но не инициализирован (TDZ).
>
> Разные типы ошибок — прямой диагностический признак стадии, на которой находится биндинг.

### 7. Почему второй `typeof` бросает исключение

```js
console.log(typeof neverDeclared); // 'undefined'
console.log(typeof inTDZ);         // ?
let inTDZ = 1;
```

> [!success]- Ответ
> `ReferenceError`. Это **единственная** ситуация в языке, где `typeof` выбрасывает исключение.
>
> Для необъявленного имени `typeof` безопасно возвращает `'undefined'`, но переменная в TDZ объявлена — просто не инициализирована, и любой доступ к ней запрещён. Старый приём «проверю существование через typeof» с приходом `let` перестал быть надёжным.

### 8. Что выведет код в двух режимах

```js
{ function f() {} }
console.log(typeof f);
```

> [!success]- Ответ
> В strict mode — `'undefined'`: область видимости строго блочная.
>
> В sloppy mode — `'function'`: работает **Annex B.3.3**, легализующий историческое браузерное поведение. Имя протекает в функциональную область.
>
> Annex B формально нормативно-опционален для не-браузерных сред, но в браузерах реализован повсеместно.

### 9. Почему результаты различаются

```js
const a = [], b = [];
for (var i = 0; i < 3; i++) a.push(() => i);
for (let j = 0; j < 3; j++) b.push(() => j);
console.log(a.map(f => f()));
console.log(b.map(f => f()));
```

> [!success]- Ответ
> `[3, 3, 3]` и `[0, 1, 2]`.
>
> Дело не в особой природе `let`, а в операции `CreatePerIterationEnvironment`: для лексических объявлений спецификация предписывает создавать **новую запись окружения на каждой итерации** и копировать в неё текущие значения. У `var` окружение одно на всю функцию, и все три замыкания разделяют одну запись.

### 10. Останутся ли 50 МБ в памяти после возврата из функции

```js
function make() {
  const huge = new Uint8Array(50 * 1024 * 1024);
  const small = 42;

  const usesHuge = () => huge.length;
  const usesSmall = () => small;

  return usesSmall;
}
const f = make();
```

> [!success]- Ответ
> Да, останутся, пока жива `f`.
>
> V8 кладёт в Context только захваченные переменные, но **Context один на область видимости**. Функция `usesHuge` затягивает `huge` в общий контекст, а `usesSmall` этот же контекст разделяет — значит удерживает всё его содержимое.
>
> Лечится изоляцией: вычислить нужное в IIFE, чтобы крупный объект не пережил свою область. Диагностируется в heap snapshot по `system / Context` в цепочке Retainers.

## Блок 3. Связывание this

### 11. Что выведет код и почему

```js
'use strict';
function f() { return this; }
console.log(typeof f.call('текст'));
console.log(typeof f.call(null));
```

> [!success]- Ответ
> `'string'` и `'object'` (для `null` — именно `typeof null === 'object'`, само значение `null`).
>
> В strict mode `OrdinaryCallBindThis` передаёт `thisArgument` как есть. В sloppy было бы `'object'` для строки (через `ToObject`) и `globalThis` вместо `null`.

### 12. Почему падает вызов

```js
class Counter {
  #value = 0;
  increment() { this.#value++; }
}
const c = new Counter();
const detached = c.increment;
detached();
```

> [!success]- Ответ
> `TypeError`. Тела классов **всегда строгие**, поэтому оторванный метод получает `this === undefined`, а не `globalThis`.
>
> Обращение к приватному полю через `undefined` невозможно. В нестрогом коде вне класса ошибка была бы отложенной и куда менее очевидной.

### 13. Почему первая строка конструктора падает

```js
class Base {}
class Derived extends Base {
  constructor() {
    console.log(this);
    super();
  }
}
new Derived();
```

> [!success]- Ответ
> `ReferenceError: Must call super constructor before accessing 'this'`.
>
> В производном классе слот `[[ThisBindingStatus]]` равен `uninitialized`. Заполняет его операция `BindThisValue`, вызываемая из `super()`. Механизм ровно тот же, что у TDZ для `let`.

### 14. В чём разница и какова цена

```js
class Button {
  label = 'ok';
  asMethod() { return this.label; }
  asArrow = () => this.label;
}
```

> [!success]- Ответ
> `asMethod` живёт в **прототипе**, `this` берётся из вызова — теряется при отрыве (`const m = btn.asMethod; m()` даёт `TypeError`).
>
> `asArrow` — поле экземпляра: новый функциональный объект создаётся **для каждого инстанса** при конструировании и лексически захватывает `this`. Отрыв переживает.
>
> Цена — память и отсутствие переиспользования через прототип. Для компонентов, создаваемых тысячами, предпочтительнее метод.

## Блок 4. Object

### 15. Что вернёт вызов и почему именно в таком порядке

```js
const sym = Symbol('s');
const obj = { b: 1, 2: 2, a: 3, 1: 4, [sym]: 5, '01': 6 };
console.log(Reflect.ownKeys(obj));
```

> [!success]- Ответ
> `['1', '2', 'b', 'a', '01', Symbol(s)]`
>
> Операция `OrdinaryOwnPropertyKeys` задаёт порядок жёстко: целочисленные индексы по возрастанию → остальные строки в порядке добавления → символы в порядке добавления.
>
> Ключ `'01'` не является каноническим индексом, поскольку не совпадает с `ToString(ToNumber('01'))`, и потому идёт в строковую группу. Утверждение «порядок свойств не гарантирован» — устаревший миф.

### 16. Что не так с этим свойством

```js
const o = {};
Object.defineProperty(o, 'id', { value: 1 });

console.log(Object.keys(o));
console.log(JSON.stringify(o));
console.log({ ...o });
o.id = 99;
console.log(o.id);
```

> [!success]- Ответ
> `[]`, `'{}'`, `{}`, `1`.
>
> `defineProperty` без явных флагов создаёт свойство со **всеми атрибутами `false`** — в отличие от обычного присваивания, где все `true`. Свойство невидимо для `Object.keys`, не сериализуется, не переживает spread, а запись молча игнорируется в sloppy mode (в strict — `TypeError`).

### 17. Почему Proxy не может подменить значение

```js
const target = Object.freeze({ x: 1 });
const p = new Proxy(target, { get: () => 'подмена' });
console.log(p.x);
```

> [!success]- Ответ
> `TypeError`. Результат ловушки проверяется операцией `ValidateAndApplyPropertyDescriptor`: для non-configurable non-writable свойства ловушка обязана вернуть исходное значение.
>
> Без этого инварианта рухнули бы гарантии `Object.freeze`, на которые опираются системы изоляции вроде SES.

### 18. Что делает объект «экзотическим», приведите примеры

> [!success]- Ответ
> Переопределение хотя бы одного внутреннего метода вместо поведения по умолчанию.
>
> Примеры: массивы (особое `[[DefineOwnProperty]]`, поддерживающее `length`), `arguments` в sloppy mode (связь с параметрами), Proxy (все методы делегируются ловушкам), namespace-объекты модулей, объекты-обёртки String (индексы как собственные свойства).

## Блок 5. Преобразования типов

### 19. Почему результаты различаются

```js
const d = new Date();
console.log(typeof (d + 1));
console.log(typeof (d - 1));
```

> [!success]- Ответ
> `'string'` и `'number'`.
>
> `Date` — **единственный** встроенный тип, у которого `Symbol.toPrimitive` трактует хинт `default` как `string`. Оператор `+` работает с хинтом `default` → получает строку → конкатенация. Оператор `-` использует хинт `number` → миллисекунды.

### 20. Разберите по шагам

```js
console.log([] == ![]);
```

> [!success]- Ответ
> `true`.
>
> 1. `![]` → `ToBoolean([])` даёт `true` (любой объект истинен) → результат `false`
> 2. Сравнение `[] == false` → булев операнд идёт через `ToNumber` → `0`
> 3. `[] == 0` → объект через `ToPrimitive` (хинт default) → `valueOf` возвращает сам массив, не примитив → `toString()` → `''`
> 4. `'' == 0` → строка через `ToNumber` → `0`
> 5. `0 == 0` → `true`

### 21. Объясните каждый результат

```js
console.log(null == undefined); // ?
console.log(null == 0);         // ?
console.log(null >= 0);         // ?
```

> [!success]- Ответ
> `true`, `false`, `true`.
>
> Равенство `null` и `undefined` прописано в `IsLooselyEqual` **отдельным шагом**. Приведения `null` к числу в алгоритме равенства нет вовсе, поэтому `null == 0` ложно.
>
> А вот операторы сравнения работают по другому алгоритму — `IsLessThan` с обязательным `ToNumeric`, где `ToNumber(null)` даёт `0`. Отсюда парадокс: `null >= 0` истинно, но `null == 0` ложно.

### 22. Почему одно падает, а другое нет

```js
console.log(1n + '1');
console.log(1n + 1);
```

> [!success]- Ответ
> `'11'` и `TypeError: Cannot mix BigInt and other types`.
>
> `ApplyStringOrNumericBinaryOperator` сначала приводит оба операнда к примитивам. Если хотя бы один — строка, выполняется конкатенация, и ограничение на смешивание не действует. Арифметический путь требует, чтобы **оба** операнда были одной числовой природы.
>
> При этом сравнение смешивать можно: `1n < 2` и `1n == 1` истинны, а `1n === 1` ложно.

### 23. Что особенного в `document.all`

> [!success]- Ответ
> Единственный объект с внутренним слотом `[[IsHTMLDDA]]`, закреплённым в стандарте ради веб-совместимости:
>
> - `document.all == null` → `true`, хотя это объект
> - `typeof document.all` → `'undefined'`
> - в булевом контексте ведёт себя как ложное значение
>
> Это официально описанная аномалия, а не баг браузера.

## Блок 6. String

### 24. Почему строка разрушается

```js
const s = 'a𝒳b';
console.log(s.length);
console.log(s.split('').reverse().join(''));
console.log([...s].reverse().join(''));
```

> [!success]- Ответ
> `4`, битая строка, `'b𝒳a'`.
>
> `𝒳` (U+1D4B3) лежит вне BMP и кодируется **суррогатной парой** из двух code unit. `split('')` режет по code unit и разъединяет пару — получаются два непарных суррогата. Спред идёт по code point и пару сохраняет.
>
> Тот же баг возникает при обрезке текста по `length` — классическая проблема с эмодзи в превью.

### 25. Сколько «символов» в этой строке

```js
const family = '👨‍👩‍👧';
console.log(family.length);
console.log([...family].length);
console.log([...new Intl.Segmenter('ru', { granularity: 'grapheme' }).segment(family)].length);
```

> [!success]- Ответ
> `8`, `5`, `1`.
>
> Три уровня измерения: code unit (`length`), code point (спред), графемный кластер (`Intl.Segmenter`). Эмодзи собрано из трёх символов, склеенных двумя ZWJ (U+200D), каждый символ — суррогатная пара.
>
> Пользователь считает третью величину, код по умолчанию использует первую.

### 26. Что выведет код

```js
const lone = '\uD800';
console.log(lone.length);
console.log(lone.isWellFormed());
console.log(JSON.stringify(lone));
try { encodeURIComponent(lone); } catch (e) { console.log(e.name); }
```

> [!success]- Ответ
> `1`, `false`, `'"\\ud800"'`, `'URIError'`.
>
> Строка в ECMAScript — последовательность 16-битных единиц, **не обязательно валидный UTF-16**. Непарный суррогат допустим внутри языка, но ломается на границе с внешним миром: `encodeURIComponent` не может закодировать его в UTF-8.
>
> `JSON.stringify` с ES2019 экранирует такие суррогаты (well-formed JSON.stringify) вместо выдачи битого вывода. Проверка — `isWellFormed()`, починка — `toWellFormed()`.

## Блок 7. NaN

### 27. Сколько битовых представлений у NaN и сколько значений NaN в языке

> [!success]- Ответ
> Представлений — `2 × (2⁵² − 1) = 9 007 199 254 740 990`, около девяти квадриллионов. NaN кодируется как «все биты экспоненты единичные, мантисса ненулевая», остаются свободными 52 бита мантиссы и бит знака.
>
> Значение в языке — **ровно одно**. Спецификация утверждает, что тип Number содержит единственный NaN, и явно разрешает движку подставлять любое представление при записи в буфер.
>
> Свободные биты используются под **NaN-boxing** — упаковку указателей и тегов типов (JavaScriptCore, SpiderMonkey).

### 28. Объясните каждую строку

```js
console.log(NaN === NaN);
console.log(Object.is(NaN, NaN));
console.log([NaN].includes(NaN));
console.log([NaN].indexOf(NaN));
console.log(new Set([NaN, NaN]).size);
console.log(Object.is(0, -0));
console.log([0].includes(-0));
```

> [!success]- Ответ
> `false`, `true`, `true`, `-1`, `1`, `false`, `true`.
>
> В языке три алгоритма сравнения, расходящиеся ровно на NaN и знаковом нуле:
>
> | Алгоритм | Где | NaN ≡ NaN | 0 ≡ −0 |
> |---|---|:---:|:---:|
> | IsStrictlyEqual | `===`, `indexOf` | нет | да |
> | SameValue | `Object.is` | да | нет |
> | SameValueZero | `includes`, Set, Map | да | да |
>
> `SameValueZero` выбран для коллекций сознательно: он позволяет находить `NaN` и не плодит дубли из-за `-0`.

## Блок 8. Деструктуризация

### 29. Что выведет код

```js
function* gen() {
  try { yield 1; yield 2; yield 3; }
  finally { console.log('закрыт'); }
}
const [first] = gen();
console.log(first);
```

> [!success]- Ответ
> `'закрыт'`, затем `1`.
>
> Деструктуризация массива идёт **через протокол итератора**, а не по индексам: `GetIterator` → `IteratorStep` нужное число раз → `IteratorClose` при досрочном выходе. Именно `IteratorClose` вызывает `return()` генератора и запускает `finally` — до вывода `first`.
>
> Объектная деструктуризация итератор не использует, поэтому применима к любому объекту, включая неитерируемый.

### 30. Найдите все ошибки в предположениях

```js
const data = { user: null, count: 0, name: '' };

const { user = { id: 1 } } = data;   // ожидание: { id: 1 }
const { count = 10 } = data;         // ожидание: 10
const { name = 'аноним' } = data;    // ожидание: 'аноним'
const { missing = 'дефолт' } = data; // ожидание: 'дефолт'
```

> [!success]- Ответ
> Верно только последнее. Реальные значения: `null`, `0`, `''`, `'дефолт'`.
>
> Дефолт в деструктуризации срабатывает **исключительно на `undefined`** — проверка идёт не на falsy и не на `null`. Для данных из API, где «нет значения» приходит как `null`, дефолты бесполезны.
>
> Рабочий вариант:
>
> ```js
> const user = data.user ?? { id: 1 };
> ```
>
> Оператор `??` реагирует и на `null`, и на `undefined`, но не трогает `0` и `''`.
