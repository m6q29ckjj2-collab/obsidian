> [!question] У какой записи окружения проверка наличия связывания даёт ложь?
> a) Function со статусом `initialized`
> b) Global
> c) Module
> d) Declarative
>> [!success]- Answer
>> d) Declarative
>> Истину дают только Function кроме лексического статуса, а также Global и Module. Из этой таблицы напрямую следует поведение стрелок

> [!question] Какого слота НЕТ у записи окружения функции?
> a) значение получателя
> b) цель конструирования
> c) прототип
> d) сам функциональный объект
>> [!success]- Answer
>> c) прототип
>> Это слот объекта, а не записи окружения. У записи есть ещё статус связывания, чья проверка и даёт ошибку про родительский конструктор

> [!question] Когда определяется режим связывания функции?
> a) при каждом вызове
> b) при создании функции
> c) при первом обращении к получателю
> d) при явном связывании
>> [!success]- Answer
>> b) при создании функции
>> Поэтому режим задаётся местом объявления, а не местом вызова. Значения: лексический, строгий и глобальный

> [!question] Что делает операция связывания в глобальном режиме?
> a) передаёт аргумент как есть
> b) всегда подставляет глобальный объект
> c) заменяет пустые значения глобальным объектом, остальное оборачивает
> d) выбрасывает исключение при примитиве
>> [!success]- Answer
>> c) заменяет пустые значения глобальным объектом, остальное оборачивает
>> Причём подставляется глобальный объект того набора интринсиков, которому принадлежит функция

> [!question] Из какого поля структуры ссылки берётся значение получателя?
> a) имя свойства
> b) база
> c) значение
> d) флаг строгости
>> [!success]- Answer
>> b) база
>> Это единое объяснение всех потерь получателя: любая операция, извлекающая из ссылки значение, стирает базу

> [!question] Что выведет код?
> ```js
> function RetObj() { this.a = 1; return { b: 2 }; }
> function RetPrim() { this.a = 1; return 42; }
> console.log(JSON.stringify(new RetObj()), JSON.stringify(new RetPrim()));
> ```
> a) `{"b":2} 42`
> b) `{"b":2} {"a":1}`
> c) `{"a":1} {"a":1}`
> d) `{"a":1} 42`
>> [!success]- Answer
>> b) `{"b":2} {"a":1}`
>> Конструирование возвращает объект тела, только если это действительно объект. Примитив отбрасывается в пользу созданного экземпляра

> [!question] Что выведет код?
> ```js
> let seen;
> function Detect() { seen = new.target; }
> Detect();
> const a = seen;
> new Detect();
> console.log(a, seen === Detect);
> ```
> a) `undefined true`
> b) `Detect true`
> c) `undefined false`
> d) выбросит `SyntaxError`
>> [!success]- Answer
>> a) `undefined true`
>> При обычном вызове слот пуст. Наблюдать его нужно через побочный эффект: строку из тела вернуть не получится, её отбросит конструирование

> [!question] Что выведет код?
> ```js
> class Base { constructor() { console.log(new.target.name); } }
> class Sub extends Base {}
> new Sub();
> ```
> a) `Base`
> b) `Sub`
> c) `undefined`
> d) выбросит `TypeError`
>> [!success]- Answer
>> b) `Sub`
>> При наследовании цель конструирования равна подклассу. На этом строится определение того, что именно создаётся

> [!question] Является ли цель конструирования в стрелочной функции лексической?
>> [!success]- Answer
>> True
>> Она читается из той же записи окружения, что и получатель, поэтому наследуется от внешней функции

> [!question] Кто создаёт объект при конструировании производного класса?
> a) производный конструктор до вызова родительского
> b) базовый конструктор
> c) оператор создания до входа в конструктор
> d) прототип производного класса
>> [!success]- Answer
>> b) базовый конструктор
>> Вызов родительского привязывает созданный объект к текущей записи окружения

> [!question] Связывание получателя в производном конструкторе выполняет операция `___`
>> [!success]- Answer
>> BindThisValue
>> Повторный вызов родительского конструктора бросает, потому что связывание уже инициализировано

> [!question] Что выведет код?
> ```js
> class Base { constructor() { this.base = 1; } }
> class Derived extends Base {
>   field = 'значение';
>   constructor() { super(); console.log(this.field, this.base); }
> }
> new Derived();
> ```
> a) `значение 1`
> b) `undefined 1`
> c) `значение undefined`
> d) выбросит `ReferenceError`
>> [!success]- Answer
>> a) `значение 1`
>> Поля экземпляра инициализируются сразу после вызова родительского конструктора, то есть в момент связывания получателя

> [!question] Что выведет код?
> ```js
> class Config { static reg = new Map(); static add(k) { this.reg.set(k, 1); return this; } }
> class Sub extends Config {}
> Sub.add('x');
> console.log(Config.reg.has('x'), Sub.add('y') === Sub);
> ```
> a) `false true`
> b) `true true`
> c) `true false`
> d) выбросит `TypeError`
>> [!success]- Answer
>> b) `true true`
>> В статическом методе получатель — тот класс, через который был вызов. Но статическое поле найдено по цепочке конструкторов и указывает на общий объект

> [!question] Как избежать общего статического состояния между базовым классом и подклассом?
> a) использовать приватное статическое поле
> b) переобъявить поле в подклассе или создавать его в статическом блоке
> c) заморозить базовый класс
> d) никак
>> [!success]- Answer
>> b) переобъявить поле в подклассе или создавать его в статическом блоке
>> Иначе поле остаётся единственным объектом, найденным по прототипной цепочке конструкторов

> [!question] Что выведет код?

> 'use strict';
> function f() { return this; }
> console.log(typeof f.call(42), f.call(null), f());
> ```
> a) `number null undefined`
> b) `object null undefined`
> c) `number` и два глобальных объекта
> d) выбросит `TypeError`
>> [!success]- Answer
>> a) `number null undefined`
>> В строгом режиме аргумент передаётся как есть, а его отсутствие даёт неопределённое значение

> [!question] Что выведет код?
> ```js
> const base = { get self() { return this; } };
> const derived = Object.create(base);
> console.log(Reflect.get(base, 'self', derived) === derived, Reflect.get(base, 'self') === base);
> ```
> a) `true true`
> b) `false true`
> c) `true false`
> d) `false false`
>> [!success]- Answer
>> a) `true true`
>> Третий аргумент задаёт получателя для наследованного геттера. Без него им становится сам объект, у которого свойство найдено

> [!question] Что выведет код?
> ```js
> function f() { return this.tag; }
> const bound = f.bind({ tag: 'a' });
> console.log(bound.name, bound.length, bound());
> ```
> a) `bound f 0 a`
> b) `f 0 a`
> c) `bound f 1 a`
> d) выбросит `TypeError`
>> [!success]- Answer
>> a) `bound f 0 a`
>> Связанная функция получает имя с префиксом и число оставшихся параметров. Здесь их ноль, поскольку исходная функция параметров не объявляет

> [!question] Что важнее — конструирование или связывание?
> a) связывание
> b) конструирование
> c) зависит от режима
> d) выбросится исключение
>> [!success]- Answer
>> b) конструирование
>> Внутренний метод конструирования игнорирует связанное значение, что согласуется с порядком определения получателя

> [!question] Что выведет код в нестрогом файле?
> ```js
> function maker() { return function () { return this; }; }
> const made = maker();
> console.log(typeof made.call(42));
> ```
> a) `number`
> b) `object`
> c) `undefined`
> d) выбросит `TypeError`
>> [!success]- Answer
>> b) `object`
>> Режим связывания определяется при создании функции, а созданa она в нестрогом коде. Поэтому примитив оборачивается, несмотря на то что вызов сделан откуда угодно

> [!question] Какая операция ищет ближайшую запись окружения со связыванием получателя?
>> [!success]- Answer
>> GetThisEnvironment
>> Она поднимается по цепочке внешних окружений, пока проверка наличия связывания не даст истину

> a) вернётся неопределённое значение
> b) выбросится ошибка ссылки
> c) вернётся глобальный объект
> d) выбросится ошибка типа
>> [!success]- Answer
>> b) выбросится ошибка ссылки

> [!question] Три шага операции вызова обычной функции по порядку
> a) связать получателя, создать контекст, выполнить тело
> b) создать контекст и положить на стек, связать получателя, выполнить тело
> c) выполнить тело, связать получателя, снять контекст
> d) создать контекст, выполнить тело, связать получателя
>> [!success]- Answer
>> b) создать контекст и положить на стек, связать получателя, выполнить тело
>> Между вторым и третьим шагом выполняется инстанцирование деклараций, поэтому значения по умолчанию у параметров уже видят получателя

> [!question] Что выведет код?
> ```js
> const o = {
>   name: 'внешний',
>   nested: { name: 'вложенный', get() { return this.name; } }
> };
> console.log(o.nested.get());
> ```
> a) `внешний`
> b) `вложенный`
> c) `undefined`
> d) выбросит `TypeError`
>> [!success]- Answer
>> b) `вложенный`
>> Базой вызова является ближайший объект слева от точки, а не корень цепочки обращения

> [!question] Стрелочная функция имеет собственный слот получателя
>> [!success]- Answer
>> False
>> У неё статус связывания лексический, поэтому проверка наличия даёт ложь и поиск продолжается вверх по цепочке окружений
