## 1. Слова «hoisting» в стандарте нет

Метафора «объявления всплывают наверх» описывает наблюдаемый эффект, но не механизм. Ничто никуда не перемещается — ни при разборе, ни при выполнении.

Реально происходит следующее: перед выполнением первой инструкции движок выполняет **операцию инстанцирования**, которая проходит по телу и создаёт биндинги в записи окружения. Когда код начинает выполняться, имена уже существуют.

Операций четыре, по одной на вид кода:

| Операция | Когда выполняется |
|---|---|
| `GlobalDeclarationInstantiation` | перед выполнением скрипта |
| `FunctionDeclarationInstantiation` | при каждом вызове функции |
| `BlockDeclarationInstantiation` | при входе в блок |
| `EvalDeclarationInstantiation` | при вызове `eval` |

## 2. Два списка объявлений

Всё строится на разделении объявлений на две категории. Спецификация собирает их синтаксическими функциями:

- **`VarScopedDeclarations`** — `var` и функциональные декларации. Привязываются к **VariableEnvironment**
- **`LexicallyScopedDeclarations`** — `let`, `const`, `class`. Привязываются к **LexicalEnvironment**

Именно это разделение объясняет всё остальное: почему `var` не ограничен блоком, почему `let` в блоке не виден снаружи, почему функциональная декларация вызывается до объявления.

## 3. `FunctionDeclarationInstantiation` по шагам

Упрощённая, но не искажающая последовательность:

1. Собрать список параметров, проверить на дубликаты
2. Определить, есть ли значения по умолчанию и rest — от этого зависит, нужно ли **отдельное окружение параметров**
3. Создать биндинги параметров и инициализировать их переданными аргументами
4. Создать объект `arguments`, если он нужен
5. Создать биндинги для `VarScopedDeclarations` и инициализировать их `undefined`
6. Создать биндинги для **функциональных деклараций** и сразу инициализировать их **готовыми функциональными объектами**
7. Создать биндинги для `LexicallyScopedDeclarations`, оставив их **неинициализированными**
8. Начать выполнение тела

Ключевой момент — шаги 5, 6 и 7 дают три разных начальных состояния.

```js
function demo() {
  console.log(typeof fn);   // 'function' — шаг 6, объект уже создан
  console.log(typeof v);    // 'undefined' — шаг 5, биндинг есть, значение undefined
  try { console.log(l); }   // шаг 7 — биндинг есть, но не инициализирован
  catch (e) { console.log(e.constructor.name); } // 'ReferenceError'

  function fn() {}
  var v = 1;
  let l = 2;
}
demo();
```

### Три типа ошибок как диагностика

```js
notDeclared();  // ReferenceError: notDeclared is not defined — биндинга нет вовсе
varFn();        // TypeError: varFn is not a function — биндинг есть, значение undefined
letFn();        // ReferenceError: Cannot access 'letFn' before initialization

var varFn = function () {};
let letFn = function () {};
```

Три разных сообщения — три разных состояния биндинга. По тексту ошибки можно точно сказать, что произошло.

## 4. Отдельное окружение параметров

Тонкость, которую почти не описывают в учебниках. Если у функции есть хотя бы одно значение по умолчанию, rest-параметр или деструктуризация, спецификация создаёт **два окружения**: одно для списка параметров, другое (дочернее) для тела.

```js
const value = 'внешнее';

function withDefault(a = value) {
  const value = 'внутреннее';
  return a;
}
console.log(withDefault()); // 'внешнее' — дефолт вычислен в окружении параметров
```

```js
function simple(a) {
  const value = 'внутреннее';
  return a;
}
// здесь окружение одно — дефолтов нет
```

Практическое следствие — параметры видят друг друга, но только слева направо:

```js
function ok(a = 1, b = a + 1) { return [a, b]; }
console.log(ok()); // [1, 2]

function broken(a = b, b = 2) { return [a, b]; }
broken(); // ReferenceError — b ещё не инициализирован
```

## 5. Объект `arguments`

```js
function sloppy(a) {
  console.log(arguments[0]); // 1
  a = 99;
  console.log(arguments[0]); // 99 — связь двусторонняя
}
sloppy(1);

function strict(a) {
  'use strict';
  a = 99;
  console.log(arguments[0]); // 1 — связи нет
}
strict(1);
```

В нестрогом режиме создаётся **mapped arguments** — экзотический объект, у которого индексы связаны с биндингами параметров через специальные аксессоры. В строгом режиме — **unmapped**, обычный снимок значений.

```js
// связь пропадает и в sloppy, если есть дефолты, rest или деструктуризация
function withDefault(a = 0) {
  a = 99;
  console.log(arguments[0]); // 1 — unmapped, несмотря на sloppy
}
withDefault(1);
```

```js
// arguments не создаётся, если имя занято
function shadowed(arguments) { return arguments; }
console.log(shadowed('своё')); // 'своё'

// у стрелочных функций своего arguments нет
const arrow = () => arguments; // берётся из внешней функции
```

## 6. `BlockDeclarationInstantiation`

При входе в блок с лексическими объявлениями создаётся новая Declarative Environment Record.

```js
{
  console.log(typeof blockFn); // 'function' — декларации инициализируются и здесь
  // console.log(blockLet);    // ReferenceError
  function blockFn() {}
  let blockLet = 1;
  var blockVar = 2;            // уходит в VariableEnvironment функции
}
console.log(typeof blockVar);  // 'number' — протёк наружу
console.log(typeof blockLet);  // ReferenceError
```

Обратите внимание: функциональная декларация внутри блока инициализируется **в этом блоке**, а не в начале функции. Именно поэтому `typeof blockFn` до объявления даёт `'function'` внутри блока, но снаружи блока имя недоступно в строгом режиме.

### Annex B.3.3 — функции в блоках в нестрогом режиме

```js
'use strict';
{ function f() {} }
console.log(typeof f); // 'undefined' — строго блочная область
```

```js
// без strict mode
{ function f() {} }
console.log(typeof f); // 'function' — имя протекло
```

В нестрогом режиме дополнительно создаётся `var`-биндинг с тем же именем в функциональной области, и в момент **выполнения** декларации в него копируется значение.

```js
console.log(typeof g); // 'undefined' — биндинг уже создан, но копирование не произошло
{ function g() {} }
console.log(typeof g); // 'function' — теперь скопировано
```

Это единственный случай, когда значение появляется в середине выполнения, а не при инстанцировании. Ещё одна причина писать в строгом режиме.

## 7. `GlobalDeclarationInstantiation`

Глобальное окружение — гибрид, и инстанцирование учитывает это.

```js
var globalVar = 1;
let globalLet = 2;
function globalFn() {}
class GlobalClass {}

console.log(globalThis.globalVar);   // 1        — CreateGlobalVarBinding
console.log(globalThis.globalFn);    // функция  — CreateGlobalFunctionBinding
console.log(globalThis.globalLet);   // undefined — Declarative часть
console.log(globalThis.GlobalClass); // undefined
```

```js
// var и функции не удаляются
console.log(delete globalThis.globalVar); // false — [[Configurable]]: false

// проверка конфликтов происходит до выполнения
// var x = 1; let x = 2;   // SyntaxError на этапе разбора
```

Отдельная тонкость: `GlobalDeclarationInstantiation` проверяет, можно ли создать свойство, **до** создания любого из них. Если хоть одно имя конфликтует с неконфигурируемым свойством глобального объекта, не создаётся ни одно.

## 8. `EvalDeclarationInstantiation`

```js
// прямой eval видит и меняет локальную область (в sloppy)
function direct() {
  eval('var injected = 1;');
  console.log(injected); // 1
}
direct();

// в strict mode eval получает собственную область
function strictEval() {
  'use strict';
  eval('var injected = 1;');
  // console.log(injected); // ReferenceError
}
```

```js
// косвенный вызов работает в глобальной области независимо от режима
const indirect = eval;
indirect('var global1 = 1;');
console.log(globalThis.global1); // 1
```

Различие прямого и косвенного вызова определяется синтаксически: прямой — это буквально `eval(...)`, всё остальное косвенный. Лексические объявления внутри `eval` **никогда** не протекают наружу, даже в нестрогом режиме.

## 9. Классы

```js
// class не инициализируется заранее — TDZ, как у let
// new Foo();   // ReferenceError: Cannot access 'Foo' before initialization
class Foo {}

// но выражение класса вычисляется на месте
const Bar = class {};
```

```js
// тело класса выполняется в момент объявления
class WithStatic {
  static computed = (console.log('вычислено при объявлении'), 1);
}
```

Классы поднимаются так же, как `let`: биндинг создаётся при инстанцировании, но остаётся неинициализированным до выполнения объявления. Никакого особого поведения у них нет.

## 10. Итог

> [!success] Что забирать
> - Термина «hoisting» в стандарте нет — есть **четыре операции инстанцирования** по видам кода
> - Всё строится на разделении `VarScopedDeclarations` и `LexicallyScopedDeclarations`
> - Инстанцирование даёт **три разных начальных состояния**: готовый объект для функций, `undefined` для `var`, неинициализированное для `let`/`const`/`class`
> - Три типа ошибок диагностичны: `ReferenceError: not defined`, `TypeError: not a function`, `ReferenceError: before initialization`
> - При наличии дефолтов, rest или деструктуризации создаётся **отдельное окружение параметров**
> - `arguments` в sloppy mode связан с параметрами двусторонне; в strict и при наличии дефолтов — нет
> - У стрелочных функций своего `arguments` не существует
> - Функциональная декларация в блоке инициализируется **в этом блоке**
> - Annex B.3.3 копирует значение в `var`-биндинг **в момент выполнения** — единственный случай отложенной инициализации
> - `GlobalDeclarationInstantiation` проверяет все конфликты до создания хотя бы одного биндинга
> - Прямой `eval` в sloppy добавляет `var` в вызывающую область; лексические объявления не протекают никогда
> - Классы поднимаются точно как `let` — особого поведения у них нет
