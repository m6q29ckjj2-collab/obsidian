### 1. Как в спецификации называется то, что зовут hoisting, и что реально происходит

> [!success]- Ответ
> Термина в стандарте нет. Есть **четыре операции инстанцирования**, по одной на вид кода:
>
> - `GlobalDeclarationInstantiation` — перед выполнением скрипта
> - `FunctionDeclarationInstantiation` — при каждом вызове функции
> - `BlockDeclarationInstantiation` — при входе в блок
> - `EvalDeclarationInstantiation` — при вызове `eval`
>
> Ничто никуда не перемещается. Операция проходит по телу и создаёт биндинги в записи окружения **до** выполнения первой инструкции. Когда код начинает работать, имена уже существуют — отсюда и наблюдаемый эффект «всплытия».

### 2. Что выведет код

```js
function demo() {
  console.log(typeof fn);
  console.log(typeof v);
  try { console.log(l); } catch (e) { console.log(e.constructor.name); }
  function fn() {}
  var v = 1;
  let l = 2;
}
demo();
```

> [!success]- Ответ
> `'function'`, `'undefined'`, `'ReferenceError'`.
>
> Инстанцирование даёт **три разных начальных состояния**:
> - функциональные декларации инициализируются готовым объектом
> - `var` инициализируется значением `undefined`
> - `let`, `const` и `class` остаются неинициализированными
>
> Это ровно те шаги 5, 6 и 7 алгоритма `FunctionDeclarationInstantiation`.

### 3. Объясните, что означает каждая из трёх ошибок

```js
notDeclared();
varFn();
letFn();

var varFn = function () {};
let letFn = function () {};
```

> [!success]- Ответ
> `ReferenceError: notDeclared is not defined` — биндинга **нет вовсе**, имя не найдено ни в одной записи цепочки.
>
> `TypeError: varFn is not a function` — биндинг **есть** и содержит `undefined`; вызвать `undefined` нельзя.
>
> `ReferenceError: Cannot access 'letFn' before initialization` — биндинг **есть**, но находится в неинициализированном состоянии.
>
> Три разных сообщения соответствуют трём разным состояниям. По тексту ошибки можно точно восстановить, что произошло, — это практичный диагностический приём.

### 4. Что выведет код и какой механизм за это отвечает

```js
const value = 'внешнее';

function withDefault(a = value) {
  const value = 'внутреннее';
  return a;
}
console.log(withDefault());
```

> [!success]- Ответ
> `'внешнее'`.
>
> Если у функции есть хотя бы одно значение по умолчанию, rest-параметр или деструктуризация, спецификация создаёт **два окружения**: одно для списка параметров, второе (дочернее) для тела.
>
> Дефолт вычисляется в окружении параметров, где `value` разрешается по цепочке `[[OuterEnv]]` во внешнюю область. Объявление в теле функции живёт в другом окружении и повлиять на дефолт не может.

### 5. Почему второй вызов падает

```js
function ok(a = 1, b = a + 1) { return [a, b]; }
function broken(a = b, b = 2) { return [a, b]; }
```

> [!success]- Ответ
> `ok()` возвращает `[1, 2]`, `broken()` бросает `ReferenceError: Cannot access 'b' before initialization`.
>
> Параметры инициализируются строго **слева направо** в одном окружении. Каждый следующий видит уже инициализированные предыдущие, а обращение «вперёд» упирается в TDZ — тот же механизм, что у `let`.

### 6. Объясните разницу

```js
function sloppy(a) { a = 99; console.log(arguments[0]); }
function strict(a) { 'use strict'; a = 99; console.log(arguments[0]); }
sloppy(1);
strict(1);
```

> [!success]- Ответ
> `99` и `1`.
>
> В нестрогом режиме создаётся **mapped arguments** — экзотический объект, у которого индексы связаны с биндингами параметров через специальные аксессоры. Изменение параметра видно через `arguments` и наоборот.
>
> В строгом режиме создаётся **unmapped arguments** — обычный снимок переданных значений без всякой связи.

### 7. Почему здесь связи нет, хотя режим нестрогий

```js
function withDefault(a = 0) {
  a = 99;
  console.log(arguments[0]);
}
withDefault(1);
```

> [!success]- Ответ
> `1` — связи нет.
>
> Наличие значений по умолчанию, rest-параметра или деструктуризации делает `arguments` **unmapped независимо от режима**.
>
> Причина в том, что при сложном списке параметров однозначное соответствие «индекс ↔ биндинг» перестаёт существовать: непонятно, что должен отражать `arguments[0]`, если параметр получил значение из дефолта, а не из аргумента.
>
> Отдельно стоит помнить: у стрелочных функций собственного `arguments` нет вообще — имя разрешается во внешней функции.

### 8. Что выведет код

```js
{
  console.log(typeof blockFn);
  function blockFn() {}
  var blockVar = 2;
  let blockLet = 1;
}
console.log(typeof blockVar);
console.log(typeof blockLet);
```

> [!success]- Ответ
> `'function'`, `'number'`, затем `ReferenceError`.
>
> Функциональная декларация внутри блока инициализируется **в этом блоке** через `BlockDeclarationInstantiation` — поэтому она доступна до строки объявления, но внутри блока.
>
> `var` уходит в VariableEnvironment функции и блоком не ограничивается — отсюда `'number'` снаружи.
>
> `let` живёт в записи окружения блока, которая после выхода недоступна.

### 9. Объясните, почему значение появляется в середине выполнения

```js
console.log(typeof g);
{ function g() {} }
console.log(typeof g);
```

> [!success]- Ответ
> `'undefined'`, затем `'function'` (в нестрогом режиме).
>
> Работает **Annex B.3.3**. Помимо блочного биндинга дополнительно создаётся `var`-биндинг с тем же именем в функциональной области — он инициализируется `undefined` при инстанцировании. А копирование значения в него происходит в момент **выполнения** декларации.
>
> Это единственный случай во всём языке, когда значение биндинга появляется в середине выполнения, а не при инстанцировании. В строгом режиме поведение отсутствует: имя просто не видно вне блока.

### 10. Что выведет код

```js
var globalVar = 1;
let globalLet = 2;
function globalFn() {}

console.log(globalThis.globalVar, globalThis.globalFn, globalThis.globalLet);
console.log(delete globalThis.globalVar);
```

> [!success]- Ответ
> `1`, функция, `undefined`; затем `false`.
>
> `GlobalDeclarationInstantiation` работает с гибридным окружением: `var` и функциональные декларации создаются операциями `CreateGlobalVarBinding` и `CreateGlobalFunctionBinding` в объектной части, то есть становятся свойствами `globalThis`. Лексические объявления идут в декларативную часть.
>
> `delete` возвращает `false`, потому что эти свойства создаются с `[[Configurable]]: false`.
>
> Отдельная тонкость: операция проверяет возможность создать **все** биндинги до создания хотя бы одного. При конфликте не создаётся ни одного.

### 11. Разберите поведение `eval`

```js
function direct() { eval('var injected = 1;'); console.log(injected); }
function strictEval() { 'use strict'; eval('var injected = 1;'); console.log(injected); }
const indirect = eval;
indirect('var leaked = 1;');
```

> [!success]- Ответ
> `direct()` выведет `1`. `strictEval()` бросит `ReferenceError`. После косвенного вызова `globalThis.leaked` равно `1`.
>
> Прямой `eval` в нестрогом режиме добавляет `var`-биндинг в **вызывающую** область. В строгом режиме `eval` получает собственную область, и объявления наружу не протекают.
>
> Косвенный вызов — любой, кроме буквального `eval(...)` — всегда работает в глобальной области, независимо от режима вызывающего кода. Различие определяется **синтаксически**.
>
> Лексические объявления (`let`, `const`, `class`) из `eval` не протекают **никогда**.

### 12. Есть ли у классов особое поведение при поднятии

```js
new Foo();
class Foo {}
```

> [!success]- Ответ
> `ReferenceError: Cannot access 'Foo' before initialization`.
>
> Никакого особого поведения у классов нет: они поднимаются ровно как `let`. Биндинг создаётся операцией инстанцирования, но остаётся неинициализированным до выполнения объявления.
>
> Распространённое «классы не поднимаются» — та же неточность, что и «`let` не поднимается». Если бы биндинг не создавался, обращение ушло бы вверх по цепочке окружений и дало бы `is not defined` вместо `before initialization`.
