> [!question] Сколько операций инстанцирования деклараций описано в спецификации?
> a) одна общая
> b) две — для функций и для блоков
> c) четыре — по видам кода
> d) по одной на каждый вид объявления
>> [!success]- Answer
>> c) четыре — по видам кода
>> Для скрипта, для функции, для блока и для eval. Ничто никуда не перемещается: биндинги просто создаются до выполнения первой инструкции

> [!question] Что выведет код?
> ```js
> function demo() {
>   console.log(typeof fn, typeof v);
>   function fn() {}
>   var v = 1;
> }
> demo();
> ```
> a) `'function' 'undefined'`
> b) `'undefined' 'undefined'`
> c) `'function' 'number'`
> d) выбросит `ReferenceError`
>> [!success]- Answer
>> a) `'function' 'undefined'`
>> Функциональная декларация инициализируется готовым объектом, var — значением undefined. Это разные шаги одной операции инстанцирования

> [!question] О чём говорит ошибка «Cannot access X before initialization»?
> a) биндинга не существует
> b) биндинг создан, но не инициализирован
> c) значение равно undefined
> d) переменная объявлена дважды
>> [!success]- Answer
>> b) биндинг создан, но не инициализирован
>> Три типа ошибок диагностичны: «is not defined» — биндинга нет, «is not a function» — есть и содержит undefined, «before initialization» — есть и в TDZ

> [!question] В строгом режиме объект `arguments` связан с параметрами двусторонне
>> [!success]- Answer
>> False
>> В строгом создаётся unmapped arguments — обычный снимок значений. Связь через аксессоры существует только в нестрогом режиме

> [!question] Когда `arguments` становится unmapped даже в нестрогом режиме?
> a) при более чем трёх параметрах
> b) при наличии дефолтов, rest или деструктуризации
> c) при вызове через `call`
> d) никогда
>> [!success]- Answer
>> b) при наличии дефолтов, rest или деструктуризации
>> При сложном списке параметров однозначное соответствие «индекс — биндинг» перестаёт существовать: непонятно, что должен отражать arguments нулевой, если параметр получил значение из дефолта

> [!question] Биндинги при вызове функции создаёт операция `___`
>> [!success]- Answer
>> FunctionDeclarationInstantiation
>> Она же создаёт объект arguments и решает, нужно ли отдельное окружение для списка параметров

> [!question] При наличии значений по умолчанию спецификация создаёт отдельное окружение для списка параметров
>> [!success]- Answer
>> True
>> Тело функции получает дочернее окружение. Поэтому объявление в теле не влияет на дефолт — он вычислен в родительском

> [!question] Что необычного в правиле Annex B.3.3 по сравнению с остальным инстанцированием?
> a) оно работает только в модулях
> b) значение появляется в момент выполнения, а не заранее
> c) оно создаёт два биндинга одного имени в одной записи
> d) оно отключает строгий режим
>> [!success]- Answer
>> b) значение появляется в момент выполнения, а не заранее
>> Дополнительный var-биндинг создаётся при инстанцировании со значением undefined, а копирование происходит при выполнении декларации в блоке

> [!question] Чем прямой вызов `eval` отличается от косвенного?
> a) прямой быстрее
> b) прямой в нестрогом режиме добавляет `var` в вызывающую область
> c) косвенный не может объявлять переменные
> d) различия нет
>> [!success]- Answer
>> b) прямой в нестрогом режиме добавляет `var` в вызывающую область
>> Косвенный — любой, кроме буквального вызова — всегда работает в глобальной области. Различие определяется синтаксически

> [!question] Лексические объявления из `eval` протекают в вызывающую область в нестрогом режиме
>> [!success]- Answer
>> False
>> Никогда, ни в каком режиме. Протекать может только var, и только при прямом вызове в нестрогом коде

> [!question] Как поднимается объявление `class`?
> a) как функциональная декларация — с готовым значением
> b) как `var` — со значением undefined
> c) как `let` — остаётся неинициализированным
> d) не поднимается вовсе
>> [!success]- Answer
>> c) как `let` — остаётся неинициализированным
>> Никакого особого поведения у классов нет. Обращение до объявления даёт ReferenceError, а не «is not defined»

> [!question] Два списка, на которые спецификация делит объявления, называются `___`
>> [!success]- Answer
>> VarScopedDeclarations, LexicallyScopedDeclarations
>> Первый привязывается к VariableEnvironment, второй к LexicalEnvironment. Из этого разделения растёт всё остальное поведение

> [!question] Когда обнаружится конфликт между `var x` и `let x` в одной области?
> a) при первом обращении к переменной
> b) при выполнении второго объявления
> c) на этапе разбора
> d) не обнаружится
>> [!success]- Answer
>> c) на этапе разбора
>> Операция инстанцирования сверяет списки объявленных имён до выполнения. Дополнительно она проверяет возможность создать все глобальные биндинги до создания хотя бы одного

> [!question] У стрелочных функций есть собственный объект `arguments`
>> [!success]- Answer
>> False
>> Имя разрешается во внешней функции по цепочке окружений — так же, как this и new.target
