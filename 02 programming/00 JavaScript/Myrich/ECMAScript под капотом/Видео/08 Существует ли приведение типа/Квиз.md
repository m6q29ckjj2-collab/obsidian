### 1. Ответьте на вопрос из названия и обоснуйте

> [!success]- Ответ
> Нет. В ECMA-262 нет операции, меняющей тип **существующего** значения.
>
> Есть абстрактные операции — `ToPrimitive`, `ToNumber`, `ToString`, `ToBoolean`, `ToObject` и другие, — которые по одному значению порождают **новое** значение другого типа.
>
> Различие не терминологическое: модель «переменная превратилась в строку» даёт неверные предсказания. Переменная продолжает хранить прежнее значение, а результат операции — отдельная сущность, которую куда-то передали.

### 2. Какие хинты запросит каждая строка

```js
const probe = { [Symbol.toPrimitive]: h => (console.log(h), 1) };
+probe;  probe < 2;  `${probe}`;  probe + 1;  probe == 1;  ({})[probe];
```

> [!success]- Ответ
> `number`, `number`, `string`, `default`, `default`, `string`.
>
> Хинт `'default'` запрашивают **ровно два места**: бинарный `+` и нестрогое равенство. Всё остальное просит `'number'` или `'string'` явно.
>
> Последний случай — `ToPropertyKey`, который приводит ключ через `ToString`.

### 3. Почему результаты различаются

```js
const d = new Date();
console.log(typeof (d + 1));
console.log(typeof (d - 1));
```

> [!success]- Ответ
> `'string'` и `'number'`.
>
> `Date.prototype[Symbol.toPrimitive]` реализован так, что хинт `'default'` обрабатывается как `'string'`. Оператор `+` запрашивает `'default'` и получает текстовое представление даты — дальше идёт конкатенация.
>
> Оператор `-` запрашивает `'number'` и получает миллисекунды. `Date` — **единственный** встроенный тип с таким поведением, оно закреплено ради исторической совместимости.

### 4. Что вернёт каждый вызов

```js
console.log(Number(''), Number('   '), Number('\n 12 '));
console.log(Number('12px'), parseInt('12px'));
console.log(Number('0x1F'), Number('+ 1'));
```

> [!success]- Ответ
> `0 0 12`, затем `NaN 12`, затем `31 NaN`.
>
> Пустая строка и строка из одних пробелов дают ноль. Пробелы по краям отбрасываются, но пробел **внутри** записи числа недопустим — отсюда `NaN` для `'+ 1'`.
>
> Ключевое различие: `Number` требует, чтобы **вся** строка соответствовала грамматике `StringNumericLiteral`. `parseInt` читает столько, сколько может, и останавливается.

### 5. Перечислите все ложные значения и объясните два примера

```js
console.log(Boolean([]), Boolean(new Boolean(false)), Boolean('0'));
```

> [!success]- Ответ
> Ложных значений ровно восемь: `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined`, `NaN`.
>
> Все три вызова возвращают `true`.
>
> `ToBoolean` **не вызывает** `ToPrimitive` — любой объект истинен, не глядя на содержимое. Поэтому истинны и пустой массив, и объект-обёртка над `false`. Строка `'0'` истинна, потому что она непустая: числовое значение здесь ни при чём.
>
> Единственное исключение из правила «объект истинен» — `document.all`.

### 6. Опишите алгоритм оператора `+` и объясните результаты

```js
console.log([] + [], [] + {}, [1, 2] + [3], 1 + null, '' + null);
```

> [!success]- Ответ
> `''`, `'[object Object]'`, `'1,23'`, `1`, `'null'`.
>
> Алгоритм `ApplyStringOrNumericBinaryOperator`:
> 1. `ToPrimitive` **обоих** операндов без хинта
> 2. Если хотя бы один результат — строка, то `ToString` обоих и конкатенация
> 3. Иначе `ToNumeric` обоих и сложение
>
> Критично, что оба приводятся к примитивам **до** выбора ветки. Массивы через `join` дают `''`, `'1,2'` и `'3'`. `ToNumber(null)` равен `0`, отсюда `1 + null === 1`, а в строковой ветке `null` даёт `'null'`.

### 7. Почему в консоли `{} + []` даёт `0`, а в `console.log({} + [])` — строку

> [!success]- Ответ
> Разница не в преобразованиях, а в **парсинге**.
>
> В позиции инструкции `{}` читается как пустой **блок кода**, а не как объектный литерал. Остаётся выражение `+[]` — унарный плюс, то есть `ToNumber(ToPrimitive([]))` = `ToNumber('')` = `0`.
>
> Внутри `console.log(...)` или после `const x =` мы находимся в позиции выражения, где `{}` однозначно объектный литерал, и работает бинарный `+` с конкатенацией.
>
> Классическая подмена: вопрос о преобразованиях типов на деле оказывается вопросом о грамматике.

### 8. Разберите по шагам

```js
console.log([] == ![]);
```

> [!success]- Ответ
> `true`.
>
> 1. `![]` вычисляется первым: `ToBoolean([])` даёт `true`, отрицание — `false`
> 2. Сравнение `[] == false`. Булев операнд проходит `ToNumber` → `0`
> 3. `[] == 0`. Объект проходит `ToPrimitive` с хинтом default: `valueOf` возвращает сам массив (не примитив), поэтому вызывается `toString` → `''`
> 4. `'' == 0`. Строка проходит `ToNumber` → `0`
> 5. `0 == 0` → `true`

### 9. Объясните, почему `==` не транзитивен

```js
console.log('' == 0, '0' == 0, '' == '0');
```

> [!success]- Ответ
> `true`, `true`, `false`.
>
> В первых двух случаях типы разные, поэтому строка проходит `ToNumber`: `''` и `'0'` обе дают `0`.
>
> В третьем типы **совпадают**, и алгоритм сразу уходит на `IsStrictlyEqual` — никакого приведения не происходит, строки сравниваются посимвольно и различаются.
>
> Отсюда нарушение транзитивности: `a == c` и `b == c`, но `a != b`. Это структурное свойство алгоритма, а не частный случай.

### 10. Почему возникает этот парадокс

```js
console.log(null == 0);
console.log(null >= 0);
console.log(null > 0);
```

> [!success]- Ответ
> `false`, `true`, `false`.
>
> Равенство и сравнение используют **разные алгоритмы**.
>
> В `IsLooselyEqual` есть отдельный шаг для пары `null`/`undefined`, а шага «привести `null` к числу» нет вовсе — поэтому `null == 0` ложно.
>
> В `IsLessThan` оба операнда обязательно проходят `ToNumeric`, где `ToNumber(null)` даёт `0`. Отсюда `null > 0` ложно (0 не больше 0), а `null >= 0` истинно.

### 11. Почему нельзя заменить `a <= b` на `!(a > b)`

> [!success]- Ответ
> Из-за `NaN`. Все четыре сравнения с ним ложны:
>
> ```js
> NaN < 1;  // false
> NaN > 1;  // false
> NaN <= 1; // false
> NaN >= 1; // false
> ```
>
> Значит `NaN <= 1` даёт `false`, а `!(NaN > 1)` даёт `true` — результаты противоположны.
>
> В спецификации это реализовано так: `IsLessThan` может вернуть `undefined`, если хотя бы один операнд `NaN`, и операторы трактуют `undefined` как `false` независимо от направления сравнения.

### 12. Объясните поведение ключей и побитовых операторов

```js
const obj = {};
obj[1] = 'a'; obj['1'] = 'b'; obj[{}] = 'c';
console.log(Object.keys(obj), obj['[object Object]']);
console.log(2 ** 32 | 0, -1 >>> 0, 1.9 | 0);
```

> [!success]- Ответ
> `['1', '[object Object]']` и `'c'`; затем `0`, `4294967295`, `1`.
>
> `ToPropertyKey` приводит любой не-символьный ключ через `ToString`, поэтому `1` и `'1'` — один и тот же ключ, а любой обычный объект превращается в `'[object Object]'`. Отсюда классический баг: объекты в роли ключей перезаписывают друг друга.
>
> Побитовые операторы применяют `ToInt32`: дробная часть усекается к нулю, а значения за пределами 32 бит переполняются. Оператор `>>>` использует `ToUint32`, поэтому `-1` превращается в максимальное беззнаковое 32-битное число.
