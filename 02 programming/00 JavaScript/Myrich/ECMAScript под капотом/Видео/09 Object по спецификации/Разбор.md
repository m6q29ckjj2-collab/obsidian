### 1. Через что спецификация определяет объект и что делает объект экзотическим

> [!success]- Ответ
> Через набор **внутренних методов**, а не через структуру «ключ-значение». Обязательных одиннадцать: от `[[GetPrototypeOf]]` и `[[IsExtensible]]` до `[[Get]]`, `[[Set]]` и `[[OwnPropertyKeys]]`. У вызываемых объектов добавляется `[[Call]]`, у конструкторов — `[[Construct]]`.
>
> **Ordinary** — все методы реализованы поведением по умолчанию. **Exotic** — хотя бы один переопределён.
>
> Экзотические в языке: массивы (особое `[[DefineOwnProperty]]` ради связи `length` с индексами), `arguments` в sloppy mode, Proxy, обёртки `String`, namespace-объекты модулей.

### 2. Сравните два объекта и объясните каждую строку вывода

```js
const a = {}; a.x = 1;
const b = {}; Object.defineProperty(b, 'x', { value: 1 });

console.log(Object.keys(a), Object.keys(b));
console.log(JSON.stringify(a), JSON.stringify(b));
console.log({ ...b });
console.log(delete b.x);
```

> [!success]- Ответ
> `['x'] []`, `'{"x":1}' '{}'`, `{}`, `false`.
>
> При обычном присваивании все атрибуты получают значение `true`. При `defineProperty` без явных флагов — **все `false`**.
>
> Свойство `b.x` существует и читается, но невидимо для перечисления, не сериализуется, не копируется спредом и не удаляется.
>
> Важная оговорка про последнюю строку: значение `false` вы получите только в **обычном скрипте**. В строгом режиме и `b.x = 99`, и `delete b.x` бросают `TypeError`. Поскольку модули ESM и тела классов строгие по определению, в современной кодовой базе это будут именно исключения.
>
> Это регулярный источник багов: свойство «есть», но ведёт себя как отсутствующее.

### 3. Почему сеттер вызвался один раз, а не два

```js
const base = { set value(v) { console.log('сеттер:', v); } };
const child = Object.create(base);

child.value = 1;
Object.defineProperty(child, 'value', { value: 2 });
console.log(child.value);
```

> [!success]- Ответ
> Выведется `сеттер: 1`, затем `2`.
>
> `child.value = 1` — это `[[Set]]`, который идёт по цепочке прототипов, находит аксессор и вызывает его.
>
> `Object.defineProperty` — это `[[DefineOwnProperty]]`, работающий **только с собственным** свойством объекта. Он игнорирует наследованные аксессоры и создаёт обычное data property, затеняющее сеттер.
>
> Практическое следствие: `Object.assign` использует присваивание и вызывает сеттеры, а спред `{ ...obj }` использует определение и не вызывает.

### 4. Что вернёт вызов и по какому правилу

```js
const sym = Symbol('s');
const obj = { b: 1, 2: 2, a: 3, 1: 4, [sym]: 5, '01': 6, '-1': 7 };
console.log(Reflect.ownKeys(obj));
```

> [!success]- Ответ
> `['1', '2', 'b', 'a', '01', '-1', Symbol(s)]`
>
> Операция `OrdinaryOwnPropertyKeys` задаёт порядок жёстко:
> 1. целочисленные индексы по возрастанию числового значения
> 2. остальные строковые ключи в порядке добавления
> 3. символы в порядке добавления
>
> Каноническим индексом считается строка, совпадающая с `ToString(ToNumber(строка))` и лежащая в диапазоне `0`…`2³²−2`. `'01'` и `'-1'` этому не удовлетворяют, поэтому попадают во вторую группу.

### 5. Почему порядок не совпадает с порядком вставки

```js
const scores = { 100: 'сто', 5: 'пять', 50: 'пятьдесят' };
console.log(Object.keys(scores));
```

> [!success]- Ответ
> `['5', '50', '100']`
>
> Числовые ключи — целочисленные индексы, они всегда идут первыми и **сортируются по возрастанию**, независимо от того, в каком порядке добавлялись.
>
> Это ловушка при работе с объектами, где ключами служат идентификаторы: порядок вставки теряется, и попытка «сохранить последовательность» через объект не работает. Для упорядоченных данных нужен `Map` или массив.

### 6. Заполните таблицу прав для трёх уровней целостности

> [!success]- Ответ
> | Операция | Добавление | Удаление | Изменение |
> |---|:---:|:---:|:---:|
> | `preventExtensions` | нет | **да** | **да** |
> | `seal` | нет | нет | **да** |
> | `freeze` | нет | нет | нет |
>
> Каждый следующий уровень строже предыдущего. Проверки — `Object.isExtensible`, `Object.isSealed`, `Object.isFrozen`.

### 7. Что выведет код

```js
const frozen = Object.freeze({ a: 1, nested: { b: 2 } });
frozen.a = 99;
frozen.nested.b = 99;
console.log(frozen.a, frozen.nested.b);
```

> [!success]- Ответ
> `1 99`
>
> `Object.freeze` **поверхностный**: он выставляет `writable: false` и `configurable: false` собственным свойствам верхнего уровня, но не трогает объекты, на которые они ссылаются.
>
> Ссылка `frozen.nested` действительно неизменяема — присвоить другой объект нельзя. Но сам объект по этой ссылке остаётся полноценно изменяемым.
>
> Для глубокой заморозки нужен рекурсивный обход через `Reflect.ownKeys`.

### 8. Почему падает и какой инвариант защищается

```js
const target = Object.freeze({ x: 1 });
const p = new Proxy(target, { get: () => 'подмена' });
console.log(p.x);
```

> [!success]- Ответ
> `TypeError`.
>
> Proxy делегирует внутренние методы ловушкам, но спецификация не даёт им лгать: результат проверяется операцией `ValidateAndApplyPropertyDescriptor`.
>
> Инвариант: если у цели есть свойство с `configurable: false` и `writable: false`, ловушка `get` **обязана** вернуть ровно его значение. Иначе замороженный объект перестал бы быть замороженным при оборачивании в Proxy — и рухнули бы гарантии, на которые опираются системы изоляции кода.

### 9. Назовите ещё три инварианта, которые Proxy не может нарушить

> [!success]- Ответ
> **Нельзя скрыть неконфигурируемое свойство:**
> ```js
> const t = {}; Object.defineProperty(t, 'fixed', { value: 1, configurable: false });
> 'fixed' in new Proxy(t, { has: () => false }); // TypeError
> ```
>
> **Нельзя вернуть дубликаты ключей:**
> ```js
> Object.keys(new Proxy({}, { ownKeys: () => ['a', 'a'] })); // TypeError
> ```
>
> **Нельзя объявить нерасширяемый объект расширяемым:**
> ```js
> const t2 = Object.preventExtensions({});
> Object.isExtensible(new Proxy(t2, { isExtensible: () => true })); // TypeError
> ```
>
> Общий принцип: Proxy может менять поведение, но не может сделать наблюдаемым состояние, противоречащее тому, что уже гарантировано целевым объектом.

### 10. Зачем третий аргумент и что произойдёт без него

```js
const base = { get self() { return this; } };
const derived = Object.create(base);
console.log(Reflect.get(base, 'self', derived) === derived);
```

> [!success]- Ответ
> `true`.
>
> Третий параметр `receiver` задаёт значение `this` при вызове наследованного геттера. Без него геттер получил бы `base`, и результат был бы `false`.
>
> Это критично при написании ловушек Proxy: типовая реализация
> ```js
> get(target, key, receiver) { return Reflect.get(target, key, receiver); }
> ```
> пробрасывает `receiver` дальше. Если его потерять, геттеры в прототипной цепочке начнут читать свойства не того объекта — баг, который проявляется только на наследовании.

### 11. Что выведет код

```js
const base = { _v: 0, set value(v) { this._v = v; } };
const child = Object.create(base);
child.value = 5;
console.log(child._v, Object.hasOwn(child, 'value'), Object.hasOwn(child, '_v'));
```

> [!success]- Ответ
> `5 false true`
>
> Наследованный сеттер перехватывает запись, поэтому собственное свойство `value` у `child` **не создаётся**. Внутри сеттера `this` указывает на `child`, и присваивание `this._v = v` создаёт у него собственное свойство `_v`.
>
> Если бы в прототипе лежало обычное data property, запись создала бы собственное свойство-тень, а прототип остался бы нетронутым.

### 12. Почему первая строка падает, а вторая нет

```js
const dict = Object.create(null);
dict.key = 1;
console.log(dict.hasOwnProperty('key'));
console.log(Object.hasOwn(dict, 'key'));
```

> [!success]- Ответ
> `TypeError: dict.hasOwnProperty is not a function`, затем `true`.
>
> У объекта, созданного через `Object.create(null)`, нет прототипа — а значит, нет и методов `Object.prototype`, включая `hasOwnProperty`.
>
> `Object.hasOwn` (ES2022) — статический метод, работающий с любым объектом. Он и есть современная замена: короче, безопаснее и не ломается на объектах без прототипа.
>
> Именно такие объекты — правильный выбор для словарей: в них не протекают `toString`, `constructor` и `__proto__`.
