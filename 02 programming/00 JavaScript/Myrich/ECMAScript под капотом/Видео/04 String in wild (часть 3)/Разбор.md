### 1. Три механизма получают одну и ту же строку. Что сделает каждый

```js
const lone = '\uD800';

encodeURIComponent(lone);
new TextEncoder().encode(lone);
JSON.stringify(lone);
```

> [!success]- Ответ
> `URIError: URI malformed` — исключение.
> `Uint8Array [239, 191, 189]` — **тихая подмена** на `U+FFFD`.
> `'"\\ud800"'` — экранирование, без потери информации.
>
> Три разные стратегии на одну проблему. Худшая для отладки — вторая: данные повреждаются молча, и обнаруживается это далеко от места, где возникло.
>
> Отсюда правило: проверять `isWellFormed()` на входе в систему, а не полагаться на поведение конкретного механизма.

### 2. Почему проверка не срабатывает и где ошибка в порядке операций

```js
function register(username) {
  if (blacklist.includes(username)) throw new Error('занято');
  db.save(username.normalize('NFKC'));
}
```

> [!success]- Ответ
> Нормализация выполняется **после** проверки. Пользователь передаёт строку, которая не совпадает с чёрным списком в исходной форме, но после `NFKC` превращается в запрещённое значение — и попадает в базу.
>
> Правильный порядок: нормализовать на входе, затем валидировать и сохранять уже нормализованное.
>
> ```js
> function register(username) {
>   const normalized = username.normalize('NFKC');
>   if (blacklist.includes(normalized)) throw new Error('занято');
>   db.save(normalized);
> }
> ```

### 3. Почему файл «не находится»

```js
const fromDisk = await fs.readdir('.');    // имя пришло из файловой системы macOS
const fromConfig = 'résumé.txt';
console.log(fromDisk.includes(fromConfig)); // false
```

> [!success]- Ответ
> macOS хранит имена файлов в **декомпозированной** форме, близкой к NFD: `é` записан как `e` + комбинирующий акут. Строка из конфига обычно в NFC — одним кодом.
>
> Побайтово это разные строки, визуально — одинаковые.
>
> ```js
> const eq = (a, b) => a.normalize('NFC') === b.normalize('NFC');
> ```
>
> Классический источник багов в кроссплатформенных сборщиках и линтерах.

### 4. Что выведет код и что меняет флаг

```js
const emoji = '😀';
console.log(/^.$/.test(emoji));
console.log(/^.$/u.test(emoji));
console.log(emoji.replace(/./g, 'X'));
```

> [!success]- Ответ
> `false`, `true`, `'XX'`.
>
> Без флага `u` точка соответствует одному **code unit**, а эмодзи занимает суррогатную пару — то есть два. С флагом `u` движок работает с **code point**, и символ матчится целиком.
>
> Замена без `u` проходит по каждой половине пары отдельно и даёт два `X`.

### 5. Почему `\w` не годится и чем его заменить

```js
console.log('Привет'.match(/\w+/g));
```

> [!success]- Ответ
> `null` — `\w` эквивалентен `[A-Za-z0-9_]` и кириллицу не покрывает.
>
> Замена — property escapes:
>
> ```js
> 'Привет'.match(/\p{Letter}+/gu);           // ['Привет']
> 'Привет'.match(/\p{Script=Cyrillic}+/gu);  // ['Привет']
> ```
>
> Флаг `u` для `\p{...}` обязателен — без него это просто экранированная буква `p`.

### 6. Что умеет флаг `v`, чего не умеет `u`

> [!success]- Ответ
> Два принципиальных добавления:
>
> **Операции над множествами** внутри класса символов:
> ```js
> /[\p{Letter}--[aeiou]]/v.test('a'); // false — буква минус гласные
> ```
> Доступны `--` (разность) и `&&` (пересечение).
>
> **Свойства со строковыми значениями** — те, чьи элементы являются последовательностями code point, а не одиночными символами:
> ```js
> /^\p{RGI_Emoji}$/v.test('👨‍👩‍👧'); // true — семейство как единица
> ```
>
> Для составных эмодзи это единственный корректный инструмент внутри регулярных выражений.

### 7. Что не так с этой проверкой

```js
if (input.toLocaleLowerCase() === 'admin') grantAccess();
```

> [!success]- Ответ
> `toLocaleLowerCase` без аргумента берёт локаль **из окружения**. На турецкой локали `'I'` превращается в `'ı'` (без точки), а не в `'i'`.
>
> Строка `'ADMIN'` перестанет совпадать с `'admin'`, и поведение кода начнёт зависеть от настроек машины, а не от данных.
>
> Спецификация определяет `toLowerCase` (без `Locale` в имени) как **локаль-независимый** — он всегда работает по корневым правилам Unicode. Для такой проверки нужен именно он.

### 8. Что выведет и почему регистр — плохая основа для сравнения

```js
console.log('ß'.toUpperCase());
console.log('ß'.toUpperCase().toLowerCase());
console.log('İ'.toLowerCase().length);
```

> [!success]- Ответ
> `'SS'`, `'ss'`, `2`.
>
> Регистровые преобразования **не сохраняют длину** и **не обратимы**: из `'SS'` уже не восстановить `'ß'`, а `'İ'` в нижнем регистре превращается в две единицы (`i` плюс комбинирующая точка).
>
> Поэтому «привести к одному регистру и сравнить» — ненадёжная стратегия для естественного текста. Корректный инструмент — `Intl.Collator` с нужным уровнем `sensitivity`.

### 9. Почему первая сортировка неверна и как её починить

```js
const words = ['ёлка', 'яблоко', 'арбуз', 'Ель'];
console.log([...words].sort());
```

> [!success]- Ответ
> `['Ель', 'арбуз', 'яблоко', 'ёлка']` — сортировка идёт по **числовым кодам** code unit.
>
> Заглавные буквы имеют меньшие коды и оказываются впереди, а `ё` (U+0451) стоит после `я` (U+044F) — за пределами основного алфавитного блока.
>
> ```js
> const cmp = new Intl.Collator('ru', { sensitivity: 'base' }).compare;
> [...words].sort(cmp); // ['арбуз', 'Ель', 'ёлка', 'яблоко']
> ```
>
> Важно: коллатор создаётся **один раз** и переиспользуется. `localeCompare` внутри компаратора конструирует его на каждое сравнение.

### 10. Напишите корректную обрезку текста

```js
const truncate = (s, n) => s.slice(0, n) + '…'; // что здесь не так?
```

> [!success]- Ответ
> `slice` режет по code unit и разрушает суррогатные пары и графемные кластеры: составное эмодзи разваливается на части, комбинирующий знак отрывается от базы.
>
> ```js
> function truncate(text, maxGraphemes) {
>   const seg = new Intl.Segmenter(undefined, { granularity: 'grapheme' });
>   const parts = [...seg.segment(text)];
>   if (parts.length <= maxGraphemes) return text;
>   return parts.slice(0, maxGraphemes).map(g => g.segment).join('') + '…';
> }
> ```
>
> Графемный кластер — единственная единица, совпадающая с интуитивным «символом» пользователя.

### 11. Обнаружьте подмену и объясните, почему нормализация здесь не поможет

```js
const a = 'apple';
const b = 'аpple';
console.log(a === b, a.length === b.length);
```

> [!success]- Ответ
> `false true` — длины совпадают, строки различаются. Первая буква во второй строке кириллическая `а` (U+0430).
>
> Нормализация **не решает** проблему: NFKC не сводит кириллическую `а` к латинской `a`, потому что это разные буквы разных алфавитов, а не варианты одного символа.
>
> Практичная защита — запрет смешения письменностей в одном токене:
>
> ```js
> const mixed = s => ['Latin', 'Cyrillic', 'Greek']
>   .filter(sc => new RegExp(`\\p{Script=${sc}}`, 'u').test(s)).length > 1;
> ```
>
> Дополнительно стоит проверять невидимые символы — но не запрещать `U+200D` слепо, он нужен составным эмодзи.

### 12. Почему маленькая подстрока удерживает 10 МБ

```js
const huge = 'x'.repeat(10_000_000);
const tiny = huge.slice(0, 10);
// huge больше нигде не используется
```

> [!success]- Ответ
> Движок может реализовать `slice` как **sliced string** — структуру со ссылкой на родительскую строку и смещением, без копирования байтов. Тогда `tiny` удерживает весь оригинал.
>
> Это оптимизация под частый случай, когда подстроки берут из живущей строки. Побочный эффект — неожиданное удержание памяти.
>
> Принудительная материализация:
> ```js
> const safe = (' ' + huge.slice(0, 10)).slice(1);
> ```
>
> Важная оговорка: ни sliced string, ни rope, ни интернирование спецификацией не гарантированы. Это детали реализации, знание которых объясняет профиль памяти, но опираться на них в коде нельзя.
