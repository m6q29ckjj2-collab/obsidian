## Обе проблемы растут из определения типа

Часть 1 установила: String в ECMAScript — конечная упорядоченная последовательность 16-битных беззнаковых целых. Из этого определения напрямую вытекают две беды, и обе неустранимы без слома обратной совместимости.

> [!abstract] Формулировка
> **Проблема 1.** Единица измерения строки (code unit) не совпадает ни с символом Unicode, ни с тем, что пользователь считает символом.
>
> **Проблема 2.** У одного и того же текста нет единственного представления — визуально одинаковые строки могут состоять из разных последовательностей.

Ни одна из них не является багом реализации. Это следствие исторического выбора: язык проектировался, когда Unicode помещался в 16 бит, и UCS-2 казался достаточным.

# Проблема 1. Единица измерения врёт

## 1.1 Три уровня, которые путают

| Уровень | Единица | Как получить | Что считает |
|---|---|---|---|
| Хранение | code unit | `.length`, `[i]`, `charCodeAt` | 16-битные ячейки |
| Unicode | code point | `[...str]`, `codePointAt` | символы Unicode |
| Восприятие | графемный кластер | `Intl.Segmenter` | «символы» пользователя |

```js
const text = 'a𝒳é👨‍👩‍👧';

console.log(text.length);                                    // 12
console.log([...text].length);                               //  9
console.log([...new Intl.Segmenter().segment(text)].length); //  4
```

Одна строка, три разных ответа на вопрос «сколько здесь символов». Каждый по-своему верен — вопрос в том, какой из них нужен в конкретном месте кода.

## 1.2 Суррогатные пары

Unicode содержит более миллиона позиций, а 16 бит вмещают 65 536. Символы за пределами Basic Multilingual Plane кодируются **парой** code unit из специально зарезервированного диапазона:

- старший суррогат: `U+D800`–`U+DBFF`
- младший суррогат: `U+DC00`–`U+DFFF`

```js
const math = '𝒳'; // U+1D4B3

console.log(math.length);           // 2
console.log(math.charCodeAt(0).toString(16)); // 'd835' — старший
console.log(math.charCodeAt(1).toString(16)); // 'dcb3' — младший
console.log(math.codePointAt(0).toString(16)); // '1d4b3' — собранный code point
```

Ручная сборка и разбор пары:

```js
const decode = (hi, lo) => (hi - 0xD800) * 0x400 + (lo - 0xDC00) + 0x10000;
console.log(decode(0xD835, 0xDCB3).toString(16)); // '1d4b3'

const encode = cp => {
  const v = cp - 0x10000;
  return [0xD800 + (v >> 10), 0xDC00 + (v & 0x3FF)];
};
console.log(encode(0x1D4B3).map(n => n.toString(16))); // ['d835', 'dcb3']
```

## 1.3 Что из-за этого ломается

```js
const s = 'a𝒳b';

// индексация
console.log(s[1]);        // половина пары — сама по себе бессмысленна
console.log(s.charAt(1)); // то же самое

// обращение
console.log(s.split('').reverse().join('')); // пара переставлена, строка битая
console.log([...s].reverse().join(''));      // 'b𝒳a' — корректно

// обрезка
console.log(s.slice(0, 2)); // 'a' + старший суррогат без пары

// длина для UI
console.log('👍'.length);   // 2 — счётчик символов покажет вдвое больше
```

### Методы, работающие по code point

```js
console.log(String.fromCharCode(0x1D4B3));  // мусор — число обрезано до 16 бит
console.log(String.fromCodePoint(0x1D4B3)); // '𝒳'

console.log('𝒳'.codePointAt(0)); // 119987
console.log('𝒳'.charCodeAt(0));  // 55349 — только старший суррогат

// at() работает по code unit, несмотря на «современность»
console.log('𝒳'.at(0) === '𝒳'.charAt(0)); // true
```

Итератор строки — единственный встроенный механизм, идущий по code point:

```js
for (const cp of '𝒳') console.log(cp); // один проход, целый символ
console.log(Array.from('𝒳').length);   // 1 — Array.from использует итератор
console.log('𝒳'.split('').length);     // 2 — split итератор не использует
```

## 1.4 Графемный кластер — уровень, о котором забывают даже знающие про суррогаты

Знание про суррогатные пары решает только часть проблемы. Пользователь считает не code point, а **графемные кластеры**.

```js
// комбинирующий знак
const combining = 'é'; // e + акут
console.log(combining.length, [...combining].length); // 2 2 — суррогатов нет вовсе

// модификатор тона кожи
const thumb = '👍🏽';
console.log(thumb.length, [...thumb].length); // 4 2

// ZWJ-последовательность
const family = '👨‍👩‍👧';
console.log(family.length, [...family].length); // 8 5

// флаг из двух regional indicator
const flag = '🇺🇦';
console.log(flag.length, [...flag].length); // 4 2

// селектор варианта начертания
const heart = '❤️'; // U+2764 + U+FE0F
console.log(heart.length, [...heart].length); // 2 2
```

Ни в одном из случаев спред не даёт правильного ответа — во всех нужен сегментатор:

```js
const seg = new Intl.Segmenter(undefined, { granularity: 'grapheme' });
const count = s => [...seg.segment(s)].length;

console.log(count(combining), count(thumb), count(family), count(flag), count(heart));
// 1 1 1 1 1
```

> [!warning] Zalgo-текст — прикладное следствие
> Комбинирующих знаков можно навесить сколько угодно, и один «символ» раздувается до сотен code unit:
> ```js
> const zalgo = 'а' + '́'.repeat(200);
> console.log(zalgo.length);                  // 201
> console.log(count(zalgo));                  // 1
> ```
> Ограничение поля ввода по `length` такой ввод пропустит как «один символ», а вёрстка при этом разъедется. Валидировать нужно оба числа: и code unit, и графемы.

# Проблема 2. Одного текста — много представлений

## 2.1 Суть

Unicode допускает записать один и тот же текст разными последовательностями. Спецификация ECMAScript сравнивает строки **побитово по code unit** (`IsStrictlyEqual` для строк — посимвольное сравнение единиц) и никакой нормализации не выполняет.

```js
const composed   = 'é';       // é одним кодом
const decomposed = 'é';      // e + комбинирующий акут

console.log(composed === decomposed);            // false
console.log(composed.length, decomposed.length); // 1 2

// но отображаются одинаково
console.log(composed, decomposed);               // é é
```

Для человека это одна и та же буква. Для программы — две разные строки.

## 2.2 Четыре формы нормализации

```js
// каноническая эквивалентность — строки «действительно одинаковы»
console.log(composed.normalize('NFC'));  // 'é'
console.log(composed.normalize('NFD'));  // 'é'
console.log(composed.normalize('NFC') === decomposed.normalize('NFC')); // true

// совместимая эквивалентность — «похожи, но с потерей форматирования»
console.log('ﬁ'.normalize('NFKC'));      // 'fi'
console.log('①'.normalize('NFKC'));      // '1'
console.log('²'.normalize('NFKC'));      // '2'
console.log('Ⅻ'.normalize('NFKC'));      // 'XII'

// NFC такие замены НЕ делает
console.log('ﬁ'.normalize('NFC'));       // 'ﬁ'
```

| Форма | Эквивалентность | Направление |
|---|---|---|
| NFC | каноническая | композиция |
| NFD | каноническая | декомпозиция |
| NFKC | совместимая | композиция |
| NFKD | совместимая | декомпозиция |

Каноническая эквивалентность обратима — из NFD всегда получится исходный NFC. Совместимая **необратима**: из `'fi'` уже не восстановить лигатуру.

## 2.3 Что ломается без нормализации

```js
const decomposed = 'élan';
const composed   = 'élan';

// поиск
console.log(decomposed.includes('é'));  // false
console.log(decomposed.indexOf('é'));   // -1

// уникальность
console.log(new Set([composed, decomposed]).size); // 2 — «дубликат» не схлопнулся

// ключи объектов и Map
const map = new Map([[composed, 'значение']]);
console.log(map.get(decomposed)); // undefined

// регулярные выражения
console.log(/^é/.test(decomposed)); // false

// сортировка
console.log(['é', 'é', 'f'].sort()); // порядок неинтуитивен
```

Особенно коварна ситуация с уникальностью: два пользователя регистрируют визуально одинаковые имена, база принимает оба, а дальше начинается расследование.

## 2.4 Где ставить нормализацию

```js
// ЕДИНСТВЕННОЕ правильное место — граница входа
function normalizeInput(raw) {
  return raw.normalize('NFC');
}

// дальше по системе ходит только нормализованное значение
const username = normalizeInput(request.body.username);
if (await db.exists(username)) throw new Error('занято');
await db.insert(username);
```

> [!danger] Нормализация после проверки — это дыра
> ```js
> if (blacklist.includes(name)) reject();
> db.save(name.normalize('NFKC')); // проверяли одно, сохранили другое
> ```
> Строка проходит фильтр в одной форме и попадает в хранилище в другой — запрещённой.

Практическое правило выбора формы:

- **NFC** — для хранения и передачи. Компактнее, совместимее, это форма по умолчанию в вебе
- **NFKC** — для сравнения идентификаторов: логинов, имён пакетов, доменов
- **NFD** — редко, обычно при работе с диакритикой посимвольно
- **NFKD** — почти никогда в прикладном коде

## 2.5 Снятие диакритики — практический приём

```js
const stripDiacritics = s =>
  s.normalize('NFD').replace(/\p{Mark}/gu, '');

console.log(stripDiacritics('Ёлка'));     // 'Елка'
console.log(stripDiacritics('résumé'));   // 'resume'
console.log(stripDiacritics('Straße'));   // 'Straße' — ß не диакритика
```

Работает потому, что NFD выносит комбинирующие знаки в отдельные code point, а `\p{Mark}` их находит. Приём используют для поиска «без учёта акцентов» и для генерации slug.

Обратите внимание на последний случай: `ß` — самостоятельная буква, а не `s` с диакритикой, и приём её не трогает. Для таких символов нужны локальные правила, то есть снова `Intl.Collator`.

## 2.6 Правильное сравнение

```js
const collator = new Intl.Collator('ru', { sensitivity: 'base' });

console.log(collator.compare('élan', 'élan') === 0); // true — форма не важна
console.log(collator.compare('Ёлка', 'елка') === 0);            // true — регистр и ё/е
```

`Intl.Collator` решает обе проблемы разом: он нормализует внутри себя и применяет правила языка. Для сравнения естественного текста это правильный инструмент, а `normalize` + `===` — минимально необходимый.

## 3. Итог

> [!success] Что забирать
> - Обе проблемы — прямое следствие определения типа, а не ошибки реализации
> - **Проблема 1**: три уровня измерения — code unit, code point, графемный кластер. `.length` считает первый, пользователь видит третий
> - Символы вне BMP кодируются суррогатными парами; `charCodeAt`, `[i]`, `split('')`, `slice` работают по code unit и их разрушают
> - Итератор строки — единственный встроенный механизм, идущий по code point; `Array.from` его использует, `split('')` нет
> - Даже корректная работа с code point не даёт правильного счёта: комбинирующие знаки, модификаторы тона, ZWJ-последовательности, флаги и селекторы вариантов требуют `Intl.Segmenter`
> - Ограничение ввода по `length` пропускает Zalgo-текст — проверять нужно и code unit, и графемы
> - **Проблема 2**: у текста нет единственного представления, сравнение строк побитовое, нормализации нет
> - Без нормализации ломаются поиск, уникальность, ключи Map, регулярные выражения и сортировка
> - Нормализовать нужно **на входе**, до любых проверок; NFC для хранения, NFKC для идентификаторов
> - Каноническая эквивалентность обратима, совместимая — нет
> - `Intl.Collator` решает обе проблемы разом и предпочтительнее связки `normalize` + `===`
