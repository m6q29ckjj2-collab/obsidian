### 1. Сформулируйте обе проблемы и объясните, почему они неустранимы

> [!success]- Ответ
> **Проблема 1.** Единица измерения строки — 16-битный code unit — не совпадает ни с символом Unicode, ни с тем, что пользователь воспринимает как символ.
>
> **Проблема 2.** У одного и того же текста нет единственного представления: визуально одинаковые строки могут состоять из разных последовательностей code point.
>
> Обе вытекают прямо из определения типа: «конечная упорядоченная последовательность 16-битных беззнаковых целых». Язык проектировался, когда Unicode помещался в 16 бит. Исправить определение нельзя — сломается вся обратная совместимость.

### 2. Что выведет код и почему все три числа верны

```js
const text = 'a𝒳é👨‍👩‍👧';
console.log(text.length);
console.log([...text].length);
console.log([...new Intl.Segmenter().segment(text)].length);
```

> [!success]- Ответ
> `12`, `9`, `4`.
>
> Три уровня измерения: code unit (ячейки хранения), code point (символы Unicode), графемные кластеры (воспринимаемые символы).
>
> Каждое число верно для своего вопроса. Ошибка — не в цифрах, а в использовании не того уровня: `.length` для счётчика символов в UI, спред для обрезки текста с эмодзи.

### 3. Соберите code point из суррогатной пары вручную

```js
const hi = 0xD835, lo = 0xDCB3;
```

> [!success]- Ответ
> ```js
> const decode = (hi, lo) => (hi - 0xD800) * 0x400 + (lo - 0xDC00) + 0x10000;
> decode(0xD835, 0xDCB3).toString(16); // '1d4b3'
> ```
>
> Старший суррогат несёт старшие 10 бит смещения, младший — младшие 10. Итого 20 бит, плюс база `0x10000` — как раз 16 дополнительных плоскостей Unicode.
>
> Обратное преобразование:
> ```js
> const encode = cp => {
>   const v = cp - 0x10000;
>   return [0xD800 + (v >> 10), 0xDC00 + (v & 0x3FF)];
> };
> ```

### 4. Почему первый вариант ломает строку

```js
const s = 'a𝒳b';
console.log(s.split('').reverse().join(''));
console.log([...s].reverse().join(''));
```

> [!success]- Ответ
> Первый даёт битую строку, второй — корректное `'b𝒳a'`.
>
> `split('')` режет по code unit и разъединяет суррогатную пару, а `reverse` меняет половины местами. Получаются младший суррогат перед старшим — последовательность, не являющаяся валидным UTF-16.
>
> Спред использует **итератор строки** — единственный встроенный механизм, идущий по code point.

### 5. Что вернут эти вызовы

```js
console.log(String.fromCharCode(0x1D4B3));
console.log(String.fromCodePoint(0x1D4B3));
console.log('𝒳'.charCodeAt(0));
console.log('𝒳'.codePointAt(0));
console.log('𝒳'.at(0) === '𝒳'.charAt(0));
```

> [!success]- Ответ
> Мусор (аргумент обрезан до 16 бит), `'𝒳'`, `55349`, `119987`, `true`.
>
> `fromCharCode` работает с code unit, `fromCodePoint` собирает суррогатную пару. `charCodeAt` возвращает только старший суррогат, `codePointAt` — собранный code point.
>
> Ловушка в последней строке: `at()` выглядит современным методом, но работает по **code unit**, ровно как `charAt`. Никакой поддержки code point он не добавляет.

### 6. Посчитайте code unit, code point и графемы

```js
const cases = ['é', '👍🏽', '👨‍👩‍👧', '🇺🇦', '❤️'];
```

> [!success]- Ответ
> | Строка | code unit | code point | графемы |
> |---|---:|---:|---:|
> | `'é'` (декомпозированная) | 2 | 2 | 1 |
> | `'👍🏽'` | 4 | 2 | 1 |
> | `'👨‍👩‍👧'` | 8 | 5 | 1 |
> | `'🇺🇦'` | 4 | 2 | 1 |
> | `'❤️'` | 2 | 2 | 1 |
>
> Разные механизмы дают одинаковый эффект: комбинирующий знак, модификатор тона кожи, ZWJ-последовательность, пара regional indicator, селектор варианта начертания.
>
> Главный вывод: **знания про суррогатные пары недостаточно**. Даже корректная работа по code point не даёт правильного счёта — нужен `Intl.Segmenter`.

### 7. Почему ограничение поля ввода не сработает

```js
const zalgo = 'а' + '́'.repeat(200);
if (input.length <= 50) accept(input);
```

> [!success]- Ответ
> `zalgo.length` равен `201`, поэтому по `length` такой ввод как раз **не пройдёт** — но обратная ситуация опаснее и встречается чаще: строка из 50 составных эмодзи даёт `length` порядка 400 и будет отвергнута, хотя визуально это 50 символов.
>
> И наоборот, ограничение «не более 200 code unit» пропустит один-единственный символ с двумя сотнями комбинирующих знаков, который разорвёт вёрстку.
>
> Корректная валидация проверяет **оба** числа: количество графем (для смысла) и количество code unit (для защиты от раздувания).

### 8. Почему поиск не находит подстроку

```js
const text = 'élan';   // é в декомпозированной форме
console.log(text.includes('é'));  // é в композиционной
console.log(text.indexOf('é'));
```

> [!success]- Ответ
> `false` и `-1`.
>
> Спецификация сравнивает строки **побитово по code unit** и никакой нормализации не выполняет. В тексте лежит `e` + комбинирующий акут (2 единицы), в образце — единый `U+00E9` (1 единица). Совпадения нет.
>
> Лечится приведением обеих строк к одной форме перед поиском:
> ```js
> text.normalize('NFC').includes('é'.normalize('NFC')); // true
> ```

### 9. Почему в базе оказались два пользователя с одинаковым именем

> [!success]- Ответ
> Имена были записаны в разных формах нормализации. Побитово это разные строки, поэтому проверку уникальности — что через `Set`, что через уникальный индекс — они прошли обе.
>
> ```js
> const composed = 'José', decomposed = 'José';
> new Set([composed, decomposed]).size;      // 2
> new Map([[composed, 1]]).get(decomposed);  // undefined
> ```
>
> Единственное решение — нормализовать на входе, до проверки уникальности, и хранить только нормализованное значение.

### 10. Найдите уязвимость

```js
if (blacklist.includes(name)) reject();
db.save(name.normalize('NFKC'));
```

> [!success]- Ответ
> Проверяется одна строка, сохраняется другая. Злоумышленник подбирает запись, которая не совпадает с чёрным списком в исходной форме, но после `NFKC` превращается в запрещённое значение — и оно попадает в базу.
>
> Правильный порядок — нормализовать **первым действием**:
>
> ```js
> const normalized = name.normalize('NFKC');
> if (blacklist.includes(normalized)) reject();
> db.save(normalized);
> ```
>
> Общее правило: нормализация принадлежит границе входа, а не месту записи.

### 11. Чем каноническая эквивалентность отличается от совместимой

> [!success]- Ответ
> **Каноническая** (NFC/NFD) объединяет строки, которые Unicode считает буквально одним и тем же текстом: `é` одним кодом и `e` + акут. Преобразование **обратимо**.
>
> **Совместимая** (NFKC/NFKD) дополнительно сводит формы, различающиеся оформлением: лигатура `ﬁ` → `fi`, `①` → `1`, `Ⅻ` → `XII`, `²` → `2`. Преобразование **необратимо** — форматирование теряется навсегда.
>
> Отсюда выбор: NFC для хранения и передачи, NFKC для сравнения идентификаторов, где визуальные варианты нужно считать одним значением.

### 12. Как работает этот приём и где его граница

```js
const strip = s => s.normalize('NFD').replace(/\p{Mark}/gu, '');
console.log(strip('résumé'), strip('Ёлка'), strip('Straße'));
```

> [!success]- Ответ
> `'resume'`, `'Елка'`, `'Straße'`.
>
> NFD выносит комбинирующие знаки в отдельные code point, а `\p{Mark}` их находит и удаляет. Приём используют для поиска без учёта акцентов и для генерации slug.
>
> Граница видна на третьем примере: `ß` — **самостоятельная буква**, а не `s` с диакритикой, и разложению не подлежит. То же касается `ø`, `ł`, `đ`.
>
> Для таких символов нужны локальные правила транслитерации либо `Intl.Collator` с `sensitivity: 'base'`, который решает задачу сравнения, не пытаясь переписать строку.
