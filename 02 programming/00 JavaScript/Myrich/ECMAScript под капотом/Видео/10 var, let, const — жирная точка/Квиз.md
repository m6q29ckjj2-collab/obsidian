### 1. Заполните таблицу различий по трём независимым характеристикам

> [!success]- Ответ
> | | `var` | `let` | `const` |
> |---|---|---|---|
> | Область видимости | функция | блок | блок |
> | Состояние до инициализации | `undefined` | TDZ | TDZ |
> | Переприсваивание | да | да | нет |
> | Повторное объявление | да | нет | нет |
> | Попадает в `globalThis` | да | нет | нет |
> | Своё окружение на итерацию | нет | да | да |
>
> Ни одна строка не является вопросом стиля — это разные механизмы с наблюдаемыми последствиями.

### 2. Что выведет код и почему

```js
var viaVar = 1;
let viaLet = 2;
console.log(globalThis.viaVar, globalThis.viaLet);
console.log(delete globalThis.viaVar);
```

> [!success]- Ответ
> `1 undefined`, затем `false`.
>
> Глобальное окружение — гибрид. `var` и функциональные декларации попадают в **Object Environment Record** поверх глобального объекта и становятся его свойствами. Лексические объявления идут в **Declarative Environment Record**, снаружи невидимую.
>
> `delete` возвращает `false`, потому что `CreateGlobalVarBinding` создаёт свойство с `[[Configurable]]: false`. Свойство, созданное простым присваиванием `globalThis.x = 1`, удалить можно.

### 3. Докажите, что `let` поднимается

```js
let value = 'внешнее';
{
  console.log(value);
  let value = 'внутреннее';
}
```

> [!success]- Ответ
> `ReferenceError: Cannot access 'value' before initialization` — и это само по себе доказательство.
>
> Если бы внутренний `let` не создавал биндинг заранее, обращение поднялось бы по цепочке `[[OuterEnv]]` и нашло внешнюю переменную со значением `'внешнее'`. Оно этого не делает.
>
> Значит, биндинг в блоке существует с самого начала — просто находится в неинициализированном состоянии. Формулировка «`let` не поднимается» неверна: поднимаются все три, различается **начальное значение**.

### 4. Почему первый `typeof` безопасен, а второй нет

```js
console.log(typeof neverDeclared);
console.log(typeof inTDZ);
let inTDZ = 1;
```

> [!success]- Ответ
> `'undefined'`, затем `ReferenceError`.
>
> Для необъявленного имени `typeof` определён как безопасная проверка и возвращает `'undefined'`. Для переменной в TDZ имя **объявлено**, но не инициализировано, и любой доступ к нему запрещён — включая `typeof`.
>
> Это единственная ситуация во всём языке, где `typeof` выбрасывает исключение. Старый приём «проверю существование через `typeof`» с приходом лексических объявлений перестал быть надёжным.

### 5. Что из этого сработает

```js
const obj = { a: 1 };
obj.a = 2;
obj.b = 3;
obj = {};
```

> [!success]- Ответ
> Первые две строки работают, третья бросает `TypeError: Assignment to constant variable`.
>
> `const` ограничивает **связывание**, а не значение: имя нельзя привязать к другому значению. Сам объект остаётся полноценно изменяемым.
>
> Для неизменяемости содержимого нужен `Object.freeze`, и тот действует только на верхнем уровне.

### 6. Почему одно работает, а другое нет

```js
for (const item of [1, 2, 3]) console.log(item);
for (const i = 0; i < 3; i++) console.log(i);
```

> [!success]- Ответ
> Первый цикл работает, второй бросает `TypeError: Assignment to constant variable` при первом же `i++`.
>
> В `for...of` связывание создаётся **заново на каждой итерации** — переприсваивания не происходит, поэтому `const` допустим и даже предпочтителен.
>
> В классическом `for` связывание одно на весь цикл, и выражение инкремента пытается его изменить.

### 7. На каком этапе обнаружится ошибка

```js
console.log('первая строка');
let x = 1;
let x = 2;
```

> [!success]- Ответ
> `SyntaxError: Identifier 'x' has already been declared` — и `'первая строка'` **не выведется**.
>
> Это синтаксическая ошибка, обнаруживаемая на этапе разбора, до выполнения хотя бы одной инструкции. Проверку выполняет операция инстанцирования, сверяя списки `VarDeclaredNames` и `LexicallyDeclaredNames`.
>
> Тем же способом запрещено и смешение: `var c = 1; let c = 2;` тоже даёт `SyntaxError`.

### 8. Что выведет код

```js
const byVar = [], byLet = [];
for (var i = 0; i < 3; i++) byVar.push(() => i);
for (let j = 0; j < 3; j++) byLet.push(() => j);
console.log(byVar.map(f => f()), byLet.map(f => f()));
console.log(i);
```

> [!success]- Ответ
> `[3, 3, 3] [0, 1, 2]`, затем `3`.
>
> Различие обеспечивает операция `CreatePerIterationEnvironment`: для цикла с лексическим объявлением спецификация предписывает создавать новую запись окружения перед каждой итерацией, копируя туда текущие значения.
>
> Последняя строка показывает вторую проблему `var`: переменная переживает цикл и остаётся доступной в области видимости функции. С `let` обращение к `j` дало бы `ReferenceError`.

### 9. Верно ли, что `const` работает быстрее `let`

> [!success]- Ответ
> Нет.
>
> Современные движки выводят неизменяемость биндинга из статического анализа кода независимо от использованного ключевого слова. Если переменная нигде не переприсваивается, оптимизации применяются одинаково.
>
> Разница между `let` и `const` в реальном коде не измеряется. Аргументы в пользу `const` — это читаемость и защита от случайного переприсваивания, а не производительность.

### 10. Сформулируйте практический вывод, опираясь на механику, а не на вкус

> [!success]- Ответ
> **`const` по умолчанию.** Большинство связываний действительно не переприсваиваются, а явное ограничение ловит ошибки на этапе выполнения вместо тихого повреждения состояния.
>
> **`let` там, где переприсваивание необходимо** — счётчики, аккумуляторы, переменные, заполняемые по условию.
>
> **`var` — только в legacy-коде**, где его функциональная область видимости и попадание в `globalThis` требуются осознанно.
>
> Обоснование лежит не в стиле: блочная область уменьшает время жизни связывания, TDZ превращает обращение до инициализации в явную ошибку вместо `undefined`, а отсутствие в `globalThis` устраняет целый класс коллизий.
