## 1. Execution Context — состояние выполнения

Перед выполнением любого кода движок создаёт **контекст исполнения**. Это не «область видимости» и не «стековый фрейм» в машинном смысле, а структура состояния с шестью компонентами:

| Компонент | Назначение |
|---|---|
| **code evaluation state** | точка, с которой продолжить выполнение |
| **Function** | функциональный объект или `null` для скрипта и модуля |
| **Realm** | набор интринсиков: свой `Array`, свой `Object.prototype`, глобальный объект |
| **ScriptOrModule** | исходный модуль или скрипт |
| **LexicalEnvironment** | окружение для `let`, `const`, `class` |
| **VariableEnvironment** | окружение для `var` и функциональных деклараций |
| **PrivateEnvironment** | приватные имена классов |

Разделение Lexical и Variable Environment — это и есть механизм, разводящий блочные и функциональные объявления. Подробности инстанцирования — в [[12 Hoisting по спецификации (spec 03)/Отчёт|видео 12]].

## 2. Стек контекстов

Контексты складываются в **execution context stack**. Верхний элемент называется **running execution context** — именно он выполняется в данный момент.

```js
function outer() {
  inner();          // сюда добавляется контекст inner
}
function inner() {
  console.log('внутри'); // стек: global → outer → inner → console.log
}
outer();
```

Спецификация описывает вызов операцией `PrepareForOrdinaryCall`:

1. Создать новый контекст исполнения
2. Заполнить Function, Realm и ScriptOrModule
3. Создать Function Environment Record и назначить её обоими окружениями
4. **Положить контекст на стек** — он становится running
5. Выполнить `OrdinaryCallBindThis` — связать `this`
6. Выполнить `FunctionDeclarationInstantiation` — создать биндинги
7. Вычислить тело
8. Снять контекст со стека

Обратите внимание на порядок: `this` связывается **после** помещения контекста на стек, но **до** инстанцирования деклараций.

## 3. Realm — то, о чём вспоминают только при багах

Realm — изолированный набор встроенных объектов. У каждого окна, iframe, воркера и `vm`-контекста свой realm со своими `Array`, `Object`, `Error` и глобальным объектом.

```js
// в браузере, при наличии iframe
const iframeArray = iframe.contentWindow.Array;
const arr = new iframeArray(1, 2, 3);

console.log(arr instanceof Array);   // false — другой Array.prototype
console.log(Array.isArray(arr));     // true  — проверка не по прототипу
```

```js
// в Node то же самое воспроизводится через vm
import { runInNewContext } from 'node:vm';

const foreign = runInNewContext('[1, 2, 3]');
console.log(foreign instanceof Array); // false
console.log(Array.isArray(foreign));   // true

const err = runInNewContext('new TypeError("сбой")');
console.log(err instanceof TypeError); // false — интринсики разные
console.log(err.constructor.name);     // 'TypeError'
```

Практический вывод: `instanceof` ненадёжен на границе realm. Для встроенных типов используйте `Array.isArray`, `Number.isFinite`, `Object.prototype.toString` или проверку по `Symbol.toStringTag`.

## 4. Предела стека в спецификации нет

```js
function probe(n = 0) {
  try { return probe(n + 1); } catch { return n; }
}
console.log(probe()); // порядка 10⁴, число нестабильно
```

Спецификация **не задаёт** максимальной глубины и вообще не описывает `RangeError: Maximum call stack size exceeded`. Ограничение полностью на стороне реализации.

Глубина зависит от размера фрейма, а тот — от количества параметров и локальных переменных:

```js
function light(n = 0) {
  try { return light(n + 1); } catch { return n; }
}
function heavy(n = 0, a = 1, b = 2, c = 3, d = 4, e = 5) {
  const x = 1, y = 2, z = 3;
  try { return heavy(n + 1, a, b, c, d, e); } catch { return n; }
}
console.log(light(), heavy()); // второе заметно меньше
```

> [!warning] Ловля переполнения — плохая идея
> `try/catch` вокруг рекурсии выглядит как решение, но состояние после переполнения непредсказуемо: часть работы могла быть выполнена частично. Правильный подход — не допускать неограниченной рекурсии: переписать в цикл или использовать явную структуру данных.

```js
// рекурсивный обход дерева легко упирается в предел
const walkRecursive = node => {
  visit(node);
  node.children.forEach(walkRecursive);
};

// итеративный вариант с явным стеком — глубина ограничена только памятью
const walkIterative = root => {
  const stack = [root];
  while (stack.length) {
    const node = stack.pop();
    visit(node);
    stack.push(...node.children);
  }
};
```

## 5. Хвостовые вызовы

Спецификация **требует** proper tail calls: вызов в хвостовой позиции должен переиспользовать фрейм, а не добавлять новый. За это отвечает операция `PrepareForTailCall`.

```js
'use strict';
const sum = (n, acc = 0) => n === 0 ? acc : sum(n - 1, acc + n);
sum(1e6);
// Safari: 500000500000
// Chrome, Firefox: RangeError
```

Из мейнстримных движков требование выполнил только JavaScriptCore. Причины отказа V8 — потеря информации для стек-трейсов и сложность отладки.

Хвостовая позиция — не просто «последняя строка»:

```js
'use strict';
const isTail    = n => n === 0 ? 0 : isTail(n - 1);        // хвостовая
const notTail   = n => n === 0 ? 0 : 1 + notTail(n - 1);   // нет: результат используется
const notTail2  = n => { try { return notTail2(n - 1); } catch { return 0; } }; // нет: try
```

Вызов внутри `try` хвостовым не является — обработчик обязан остаться на стеке. Кроме того, PTC работают только в строгом режиме.

## 6. Генераторы: контекст не снимается, а приостанавливается

Здесь механизм особенно наглядно объясняет поведение.

```js
function* gen() {
  console.log('старт');
  const x = yield 1;    // контекст приостанавливается
  console.log('получено', x);
  yield 2;
  console.log('конец');
}

const g = gen();
console.log('генератор создан'); // тело ещё не выполнялось
g.next();      // 'старт'
g.next('ответ'); // 'получено ответ'
```

При `yield` контекст **не снимается со стека и не уничтожается** — он сохраняется в объекте генератора вместе с полем code evaluation state. Следующий `next()` кладёт его обратно на стек и продолжает с сохранённой точки.

Именно поэтому локальные переменные генератора переживают приостановку, а `return()` и `throw()` могут возобновить контекст в другом режиме:

```js
function* withCleanup() {
  try { yield 1; yield 2; }
  finally { console.log('очистка'); }
}
const g2 = withCleanup();
g2.next();
g2.return('досрочно'); // 'очистка' — контекст возобновлён ради finally
```

Асинхронные функции устроены на том же механизме: `await` приостанавливает контекст, а возобновление ставится в очередь заданий.

## 7. Задания и очередь микрозадач

Промисы **не находятся** в стеке контекстов. Их продолжения ставятся в очередь через `HostEnqueuePromiseJob` и выполняются, когда стек полностью опустел.

```js
console.log('синхронно 1');

setTimeout(() => console.log('макрозадача'), 0);

Promise.resolve()
  .then(() => console.log('микро 1'))
  .then(() => console.log('микро 3'));

queueMicrotask(() => console.log('микро 2'));

console.log('синхронно 2');

// синхронно 1 · синхронно 2 · микро 1 · микро 2 · микро 3 · макрозадача
```

Порядок `микро 1 → микро 2 → микро 3` объясняется тем, что второй `.then` регистрируется только после выполнения первого — то есть попадает в очередь позже, чем `queueMicrotask`.

> [!note] Разделение ответственности
> Очередь микрозадач описана в ECMA-262 как Job Queue. А вот **макрозадачи** — таймеры, события, ввод-вывод — стандартом языка не описаны вовсе: это зона ответственности хоста (HTML-спецификация в браузере, libuv в Node). Отсюда и различия в поведении `setTimeout` между средами.

```js
// микрозадачи выполняются до отрисовки и могут её заблокировать
function starve() {
  Promise.resolve().then(starve); // очередь никогда не опустеет
}
// starve(); // страница перестанет отвечать
```

Очередь микрозадач опустошается **полностью** перед следующей макрозадачей. Бесконечная цепочка микрозадач блокирует всё, включая отрисовку, — в отличие от цепочки `setTimeout`.

## 8. Стек-трейсы

```js
function level1() { level2(); }
function level2() { throw new Error('сбой'); }

try { level1(); } catch (e) { console.log(e.stack); }
```

Свойство `stack` **не описано** в ECMA-262 — это де-факто стандарт, реализованный всеми движками по-своему. Существует предложение по стандартизации, но на момент написания формально его нет.

```js
// V8-специфичное API
Error.captureStackTrace?.(obj);      // исключить кадры из трейса
Error.stackTraceLimit = 50;          // по умолчанию 10
```

Асинхронные границы разрывают трейс, поэтому движки добавляют async stack traces отдельным механизмом.

## 9. Итог

> [!success] Что забирать
> - Execution context — структура из шести компонентов, а не «область видимости»
> - Разделение Lexical и Variable Environment разводит блочные и функциональные объявления
> - `this` связывается **после** помещения контекста на стек и **до** инстанцирования деклараций
> - Realm — изолированный набор интринсиков; `instanceof` через его границу не работает
> - Предел глубины стека **не описан** стандартом и зависит от размера фрейма
> - Ловить переполнение через `try/catch` нельзя — состояние непредсказуемо
> - Proper tail calls **требуются** стандартом, но реализованы только в JavaScriptCore; в `try` и в нестрогом режиме не действуют
> - При `yield` контекст **приостанавливается**, а не уничтожается — отсюда сохранение локальных переменных и работа `finally` при `return()`
> - Асинхронные функции используют тот же механизм приостановки
> - Микрозадачи описаны стандартом как Job Queue; **макрозадачи — зона хоста**, не языка
> - Очередь микрозадач опустошается полностью перед следующей макрозадачей и способна заблокировать отрисовку
> - Свойство `stack` у ошибок стандартом не описано
