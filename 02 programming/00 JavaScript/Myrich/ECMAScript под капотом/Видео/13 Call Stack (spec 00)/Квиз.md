> [!question] Сколько компонентов у контекста исполнения?
> a) 3
> b) 5
> c) 7
> d) 11
>> [!success]- Answer
>> c) 7
>> Это code evaluation state, Function, Realm, ScriptOrModule, LexicalEnvironment, VariableEnvironment и PrivateEnvironment

> [!question] Предел глубины стека вызовов задан спецификацией
>> [!success]- Answer
>> False
>> Стандарт не описывает даже саму ошибку переполнения. Ограничение целиком на стороне реализации и зависит от размера фрейма

> [!question] Какой движок реализовал proper tail calls?
> a) V8
> b) SpiderMonkey
> c) JavaScriptCore
> d) все три
>> [!success]- Answer
>> c) JavaScriptCore
>> Требование стандарта есть, но V8 и SpiderMonkey от него отказались, ссылаясь на потерю информации для стек-трейсов

> [!question] Вызов внутри блока `try` может быть хвостовым
>> [!success]- Answer
>> False
>> Обработчик исключений обязан остаться на стеке. Кроме того, оптимизация работает только в строгом режиме

> [!question] Что происходит с контекстом исполнения при `yield`?
> a) снимается со стека и уничтожается
> b) приостанавливается и сохраняется в объекте генератора
> c) копируется в новый контекст
> d) остаётся на стеке до завершения генератора
>> [!success]- Answer
>> b) приостанавливается и сохраняется в объекте генератора
>> Вместе с полем code evaluation state. Поэтому локальные переменные переживают приостановку, а return может возобновить контекст ради finally

> [!question] Продолжения промисов ставятся в очередь операцией `___`
>> [!success]- Answer
>> HostEnqueuePromiseJob
>> Название начинается с Host не случайно: постановка задания делегирована окружению, хотя сама очередь описана в стандарте

> [!question] Что из перечисленного НЕ описано в ECMA-262?
> a) очередь микрозадач
> b) семантика промисов
> c) таймеры и события
> d) момент опустошения очереди
>> [!success]- Answer
>> c) таймеры и события
>> Макрозадачи — зона ответственности хоста: HTML-спецификации в браузере и libuv в Node. Отсюда различия в поведении между средами

> [!question] В каком порядке выведутся значения?
> ```js
> console.log(1);
> setTimeout(() => console.log(5), 0);
> Promise.resolve().then(() => console.log(3)).then(() => console.log(4));
> console.log(2);
> ```
> a) `1 2 3 4 5`
> b) `1 2 5 3 4`
> c) `1 3 4 2 5`
> d) `1 2 3 5 4`
>> [!success]- Answer
>> a) `1 2 3 4 5`
>> Сначала синхронный код, затем вся очередь микрозадач до опустошения, и только потом макрозадача таймера

> [!question] Свойство `stack` у объекта ошибки описано в спецификации
>> [!success]- Answer
>> False
>> Это де-факто стандарт, реализованный движками по-своему: различаются формат строк, заголовок и число кадров. Парсить его регулярками ненадёжно

> [!question] Почему `instanceof Array` возвращает `false` для массива из другого realm?
> a) массив теряет прототип при передаче
> b) у другого realm свой `Array.prototype`
> c) `instanceof` не работает с массивами
> d) массив превращается в array-like объект
>> [!success]- Answer
>> b) у другого realm свой `Array.prototype`
>> Realm — изолированный набор интринсиков. Надёжная проверка — Array.isArray, которая смотрит на внутреннюю природу объекта

> [!question] Выполняется ли тело генератора в момент создания объекта генератора?
> a) да, до первого `yield`
> b) да, полностью
> c) нет, только при первом `next()`
> d) нет, только при вызове `return()`
>> [!success]- Answer
>> c) нет, только при первом `next()`
>> Создание объекта готовит контекст, но не запускает код. Первый next доводит выполнение до первого yield

> [!question] Бесконечная цепочка микрозадач блокирует отрисовку страницы
>> [!success]- Answer
>> True
>> Очередь опустошается полностью перед следующей макрозадачей, поэтому управление не возвращается ни в цикл событий, ни к отрисовке. Аналог на таймерах интерфейс не блокирует

> [!question] В какой момент связывается `this` относительно создания биндингов?
> a) до помещения контекста на стек
> b) после помещения на стек, но до инстанцирования деклараций
> c) после инстанцирования деклараций
> d) в момент первого обращения к `this`
>> [!success]- Answer
>> b) после помещения на стек, но до инстанцирования деклараций
>> Поэтому значения по умолчанию у параметров уже могут обращаться к this

> [!question] Что делать с глубоким рекурсивным обходом, упирающимся в предел стека?
> a) обернуть в `try/catch` и продолжить
> b) увеличить лимит настройкой движка
> c) переписать в цикл с явным стеком
> d) разбить на асинхронные шаги через `setTimeout`
>> [!success]- Answer
>> c) переписать в цикл с явным стеком
>> Тогда глубина ограничена только памятью. Ловить переполнение нельзя: состояние после него непредсказуемо, часть работы могла выполниться частично
