### 1. Перечислите компоненты контекста исполнения и объясните, зачем нужны два окружения

> [!success]- Ответ
> code evaluation state, Function, Realm, ScriptOrModule, LexicalEnvironment, VariableEnvironment, PrivateEnvironment.
>
> **LexicalEnvironment** хранит `let`, `const` и `class`; **VariableEnvironment** — `var` и функциональные декларации. Это разделение и есть механизм, из-за которого `var` не ограничен блоком, а `let` ограничен.
>
> **code evaluation state** отвечает за возможность приостановить и возобновить выполнение — без него не работали бы генераторы и асинхронные функции.

### 2. В каком порядке выполняются шаги при вызове функции

> [!success]- Ответ
> 1. Создать контекст, заполнить Function, Realm, ScriptOrModule
> 2. Создать Function Environment Record и назначить её обоими окружениями
> 3. **Положить контекст на стек** — он становится running
> 4. `OrdinaryCallBindThis` — связать `this`
> 5. `FunctionDeclarationInstantiation` — создать биндинги параметров и объявлений
> 6. Вычислить тело
> 7. Снять контекст со стека
>
> Существенно, что `this` связывается **после** помещения контекста на стек, но **до** инстанцирования деклараций — поэтому значения по умолчанию у параметров уже могут обращаться к `this`.

### 3. Что выведет код и почему

```js
import { runInNewContext } from 'node:vm';
const foreign = runInNewContext('[1, 2, 3]');
console.log(foreign instanceof Array);
console.log(Array.isArray(foreign));
```

> [!success]- Ответ
> `false`, затем `true`.
>
> `runInNewContext` создаёт новый **Realm** — изолированный набор интринсиков со своими `Array`, `Object`, `Error`. Массив оттуда наследуется от **другого** `Array.prototype`, поэтому `instanceof` его не узнаёт.
>
> `Array.isArray` проверяет внутреннюю природу объекта, а не цепочку прототипов, и работает через границу realm.
>
> В браузере то же самое воспроизводится с iframe и воркерами. Практический вывод: для встроенных типов используйте `Array.isArray`, `Number.isFinite` или `Object.prototype.toString`.

### 4. Описан ли в спецификации предел глубины стека

```js
function probe(n = 0) { try { return probe(n + 1); } catch { return n; } }
console.log(probe());
```

> [!success]- Ответ
> Нет, не описан. Стандарт вообще не упоминает `RangeError: Maximum call stack size exceeded` — ограничение целиком на стороне реализации.
>
> Число нестабильно даже в рамках одного движка: глубина зависит от размера фрейма, а тот — от количества параметров, локальных переменных и от того, какие оптимизации применил движок к конкретной функции.
>
> Из этого следует, что нельзя писать код, рассчитанный на определённую глубину рекурсии.

### 5. Почему `try/catch` вокруг рекурсии — плохое решение

> [!success]- Ответ
> Переполнение стека застаёт программу в произвольной точке: часть работы могла быть выполнена частично, инварианты структур данных нарушены, ресурсы не освобождены.
>
> Поймать исключение технически можно, но продолжать работу после него нельзя — состояние непредсказуемо.
>
> Правильный подход — не допускать неограниченной рекурсии: переписать обход в цикл с явным стеком, тогда глубина ограничена только объёмом памяти.
>
> ```js
> const walk = root => {
>   const stack = [root];
>   while (stack.length) {
>     const node = stack.pop();
>     visit(node);
>     stack.push(...node.children);
>   }
> };
> ```

### 6. Определите, какие вызовы являются хвостовыми

```js
'use strict';
const a = n => n === 0 ? 0 : a(n - 1);
const b = n => n === 0 ? 0 : 1 + b(n - 1);
const c = n => { try { return c(n - 1); } catch { return 0; } };
```

> [!success]- Ответ
> Хвостовой только **`a`**.
>
> В `b` результат вызова участвует в сложении — после возврата нужно выполнить ещё одну операцию, значит фрейм обязан сохраниться.
>
> В `c` вызов находится внутри `try`: обработчик исключений должен оставаться на стеке, поэтому хвостовым такой вызов не является.
>
> Дополнительное условие: proper tail calls действуют **только в строгом режиме**. И даже при выполнении всех условий их поддерживает лишь JavaScriptCore — V8 и SpiderMonkey отказались, ссылаясь на потерю информации для стек-трейсов.

### 7. Что произойдёт с контекстом при `yield`

```js
function* gen() {
  const local = 'сохранится';
  yield 1;
  console.log(local);
  yield 2;
}
const g = gen();
g.next();
```

> [!success]- Ответ
> Контекст **приостанавливается**, а не уничтожается: он сохраняется в объекте генератора вместе с полем code evaluation state, фиксирующим точку возобновления.
>
> Поэтому локальная переменная `local` переживает приостановку — вместе с контекстом сохраняются все его окружения. Следующий `next()` кладёт контекст обратно на стек и продолжает с сохранённой точки.
>
> Отдельно стоит помнить: тело генератора при создании объекта **не выполняется** вовсе. Первый `next()` запускает его до первого `yield`.

### 8. Что выведет код

```js
function* withCleanup() {
  try { yield 1; yield 2; }
  finally { console.log('очистка'); }
}
const g = withCleanup();
g.next();
g.return('досрочно');
```

> [!success]- Ответ
> `очистка`.
>
> Метод `return()` возобновляет приостановленный контекст в **режиме возврата**: выполнение продолжается так, как если бы в точке `yield` стоял `return`. Это запускает все блоки `finally`, после чего генератор завершается.
>
> Тот же механизм срабатывает при `break` в `for...of` и при деструктуризации короче последовательности — везде, где вызывается `IteratorClose`. Именно он делает генераторы безопасными для управления ресурсами.

### 9. Определите порядок вывода

```js
console.log('1');
setTimeout(() => console.log('6'), 0);
Promise.resolve().then(() => console.log('3')).then(() => console.log('5'));
queueMicrotask(() => console.log('4'));
console.log('2');
```

> [!success]- Ответ
> `1 · 2 · 3 · 4 · 5 · 6`
>
> Сначала синхронный код. Затем очередь микрозадач: первый `.then` был зарегистрирован раньше `queueMicrotask`, поэтому идёт первым. Второй `.then` регистрируется **только после выполнения первого** — то есть попадает в очередь уже после `queueMicrotask`.
>
> Макрозадача `setTimeout` выполняется последней, когда очередь микрозадач полностью опустела.

### 10. Что из перечисленного описано в ECMA-262, а что нет

> [!success]- Ответ
> **Описано:** очередь микрозадач как Job Queue, операция `HostEnqueuePromiseJob`, семантика промисов, момент опустошения очереди.
>
> **Не описано:** `setTimeout`, `setInterval`, события DOM, ввод-вывод — то есть все **макрозадачи**. Это зона ответственности хоста: HTML-спецификации в браузере и libuv в Node.
>
> Отсюда и различия между средами: порядок таймеров, поведение `setImmediate` в Node, отсутствие гарантии минимальной задержки. Язык описывает только то, что происходит внутри одного прохода, а расписание проходов задаёт окружение.

### 11. Почему этот код опаснее аналога с `setTimeout`

```js
function starve() { Promise.resolve().then(starve); }
```

> [!success]- Ответ
> Очередь микрозадач опустошается **полностью** перед переходом к следующей макрозадаче. Каждая микрозадача добавляет новую, поэтому очередь никогда не пустеет — управление не возвращается ни в цикл событий, ни к отрисовке.
>
> Страница перестаёт отвечать: не обрабатываются события, не выполняются таймеры, кадр не перерисовывается.
>
> Аналог на `setTimeout` вёл бы себя иначе: между итерациями браузер успевал бы обработать события и отрисовать кадр, и интерфейс остался бы отзывчивым, пусть и загруженным.

### 12. Стандартизировано ли свойство `error.stack`

> [!success]- Ответ
> Нет. В ECMA-262 свойство `stack` **не описано** — это де-факто стандарт, реализованный всеми движками, но по-своему: различаются формат строк, наличие заголовка, количество кадров.
>
> Существует предложение по стандартизации, но формально его пока нет, поэтому парсить `stack` регулярными выражениями — ненадёжная практика.
>
> В V8 есть дополнительные нестандартные средства: `Error.captureStackTrace` для исключения кадров из трейса и `Error.stackTraceLimit` (по умолчанию 10). Асинхронные границы разрывают трейс, и движки достраивают его отдельным механизмом async stack traces.
