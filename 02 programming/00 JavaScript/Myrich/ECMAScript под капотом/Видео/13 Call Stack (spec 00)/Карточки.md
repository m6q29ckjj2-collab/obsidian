## Execution Context

Перечислите компоненты контекста исполнения::code evaluation state, Function, Realm, ScriptOrModule, LexicalEnvironment, VariableEnvironment, PrivateEnvironment

Зачем разделены LexicalEnvironment и VariableEnvironment::Первое хранит `let`, `const` и `class`, второе — `var` и функциональные декларации. Это и есть механизм ==разведения блочных и функциональных== объявлений

Для чего нужен компонент code evaluation state::Хранит точку, с которой продолжить выполнение — необходим для ==генераторов== и асинхронных функций

Как называется верхний элемент стека контекстов::==running execution context==

Порядок шагов при вызове функции
?
1. Создать контекст, заполнить Function, Realm, ScriptOrModule
2. Создать Function Environment Record
3. ==Положить контекст на стек==
4. `OrdinaryCallBindThis` — связать `this`
5. `FunctionDeclarationInstantiation` — создать биндинги
6. Вычислить тело
7. Снять контекст со стека

Когда связывается `this` относительно инстанцирования::==После== помещения контекста на стек, но ==до== создания биндингов деклараций

## Realm

Что такое Realm::Изолированный набор ==интринсиков==: свой `Array`, `Object.prototype`, `Error` и глобальный объект

У чего в браузере отдельный realm::У каждого окна, iframe и воркера. В Node — у каждого `vm`-контекста

Почему `instanceof` не работает через границу realm::Прототипы разные объекты — `Array.prototype` из iframe не совпадает с локальным

Чем заменить `instanceof` для встроенных типов::`Array.isArray`, `Number.isFinite`, `Object.prototype.toString.call`, проверка `Symbol.toStringTag`

## Предел стека

Описан ли предел глубины стека в спецификации::==Нет==. Стандарт не описывает и `RangeError: Maximum call stack size exceeded`

От чего зависит максимальная глубина рекурсии::От ==размера фрейма==, то есть от количества параметров и локальных переменных, и от конкретного движка

Почему нельзя полагаться на `try/catch` вокруг рекурсии::Состояние после переполнения ==непредсказуемо== — часть работы могла выполниться частично

Как переписать глубокий рекурсивный обход::Использовать ==явный стек== в цикле — тогда глубина ограничена только памятью, а не размером стека вызовов

## Хвостовые вызовы

Требует ли спецификация proper tail calls::==Да==, через операцию `PrepareForTailCall`

Какой движок реализовал PTC::Только ==JavaScriptCore== (Safari). V8 и SpiderMonkey отказались из-за потери информации для стек-трейсов

Является ли вызов внутри `try` хвостовым::==Нет==. Обработчик обязан остаться на стеке

В каком режиме работают proper tail calls::Только в ==строгом==

Что означает «хвостовая позиция»::Результат вызова ==возвращается напрямую==, без дальнейших операций над ним. `return 1 + f(n)` хвостовым не является

## Генераторы

Что происходит с контекстом при `yield`::Он ==приостанавливается==, а не уничтожается: сохраняется в объекте генератора вместе с code evaluation state

Почему локальные переменные генератора переживают приостановку::Контекст со всеми окружениями сохранён целиком и возвращается на стек при следующем `next()`

Что делает `generator.return()`::Возобновляет контекст в режиме возврата — выполняются блоки ==`finally`==, после чего генератор завершается

Выполняется ли тело генератора при его создании::==Нет==. Первый `next()` запускает выполнение до первого `yield`

На каком механизме построены асинхронные функции::На том же ==приостановлении контекста==; возобновление ставится в очередь заданий

## Задания и очереди

Находятся ли коллбэки промисов в стеке контекстов::==Нет==. Они ставятся в очередь через `HostEnqueuePromiseJob`

Когда выполняются микрозадачи::Когда стек контекстов ==полностью опустел==

Описаны ли макрозадачи в ECMA-262::==Нет==. Таймеры, события и ввод-вывод — зона ответственности ==хоста== (HTML-спецификация, libuv)

Что выведет код
?
```js
console.log('1');
setTimeout(() => console.log('5'), 0);
Promise.resolve().then(() => console.log('3')).then(() => console.log('4'));
queueMicrotask(() => console.log('3.5'));
console.log('2');
```
`1 · 2 · 3 · 3.5 · 4 · 5` — второй `.then` регистрируется после выполнения первого, поэтому попадает в очередь позже `queueMicrotask`

Чем бесконечная цепочка микрозадач опаснее цепочки `setTimeout`::Очередь микрозадач опустошается ==полностью== перед следующей макрозадачей — отрисовка и обработка событий блокируются

## Стек-трейсы

Описано ли свойство `error.stack` в спецификации::==Нет==. Это де-факто стандарт, реализованный движками по-своему

Какое V8-специфичное API управляет трейсами::`Error.captureStackTrace` и `Error.stackTraceLimit` (по умолчанию 10 кадров)

Почему асинхронные трейсы неполны::Граница `await` или коллбэка ==разрывает== стек; движки достраивают его отдельным механизмом async stack traces
