### 1. Объясните три сущности и что вернёт последняя строка

```js
function Ctor() {}
const obj = new Ctor();
console.log(obj.prototype);
```

> [!success]- Ответ
> `undefined`.
>
> - **`[[Prototype]]`** — внутренний слот объекта, ссылка на родителя в цепочке
> - **`__proto__`** — исторический аксессор из `Object.prototype`, читающий этот слот (Annex B)
> - **`prototype`** — обычное свойство **функции**, которое станет `[[Prototype]]` объектов, созданных через `new`
>
> У экземпляра свойства `prototype` нет — оно есть у конструктора. Проверять правильнее через `Object.getPrototypeOf(obj) === Ctor.prototype`.

### 2. Почему второй вариант предпочтительнее

```js
// A
const a = { x: 1 };
Object.setPrototypeOf(a, base);

// B
const b = Object.create(base);
b.x = 1;
```

> [!success]- Ответ
> Смена прототипа **после** создания инвалидирует скрытые классы (shapes) и inline-кеши — не только для этого объекта, но и для всех мест кода, которые через него читали свойства.
>
> Движок оптимизирует в расчёте на стабильную структуру; `setPrototypeOf` этот расчёт ломает и переводит объект в медленный режим.
>
> Прототип нужно задавать при создании: `Object.create(proto)` или литерал с `__proto__`.

### 3. Через какой механизм работает `super` и почему он не эквивалентен обращению к прототипу `this`

> [!success]- Ответ
> `super` использует внутренний слот метода **`[[HomeObject]]`** — ссылку на объект, в котором метод определён. Поиск идёт от прототипа `[[HomeObject]]`.
>
> Если бы `super` брал прототип `this`, при трёхуровневой иерархии возникла бы бесконечная рекурсия: метод середины иерархии, вызванный на экземпляре низа, снова нашёл бы сам себя.
>
> Следствие: `super` доступен только в сокращённой записи метода — только ей спецификация выставляет `[[HomeObject]]`. В `{ m: function () {} }` это синтаксическая ошибка.

### 4. В каком порядке выведутся строки

```js
function* resource() {
  try { yield 1; yield 2; } finally { console.log('освобождено'); }
}
for (const v of resource()) { console.log(v); break; }
```

> [!success]- Ответ
> `1`, затем `освобождено`.
>
> При досрочном выходе из `for...of` вызывается `return()` итератора, что для генератора означает выполнение блока `finally`. Тот же механизм срабатывает при деструктуризации короче последовательности и при исключении внутри цикла.
>
> Это делает генераторы безопасными для управления ресурсами: файл или соединение закроются даже при `break`.

### 5. Что выведет код

```js
function* inner() { yield 1; return 'итог'; }
function* outer() { const r = yield* inner(); console.log(r); yield 2; }
console.log([...outer()]);
```

> [!success]- Ответ
> Сначала `'итог'`, затем `[1, 2]`.
>
> Значение `return` вложенного генератора становится **значением выражения `yield*`**, а не попадает в перебор. В итоговый массив идут только значения `yield`.
>
> `yield*` — не сахар для цикла: он пробрасывает также `next(v)`, `return()` и `throw()`, то есть передаёт управление полностью.

### 6. Определите порядок вывода

```js
async function a() { console.log('a1'); await b(); console.log('a2'); }
async function b() { console.log('b1'); }

console.log('start');
a();
Promise.resolve().then(() => console.log('micro'));
console.log('end');
```

> [!success]- Ответ
> `start · a1 · b1 · end · a2 · micro`
>
> `a()` выполняется синхронно до `await`, попутно синхронно отрабатывает `b()`. В момент `await` продолжение `a` ставится в очередь микрозадач — это происходит **до** строки с `.then`, поэтому `a2` опережает `micro`.
>
> Отдельно стоит запомнить: `await` над любым значением, даже не-промисом, откладывает продолжение. Синхронного продолжения после `await` не бывает.

### 7. Чем различаются четыре комбинатора и какой выбрать для сбора всех результатов

> [!success]- Ответ
> | Комбинатор | Поведение |
> |---|---|
> | `all` | отклоняется первой же ошибкой |
> | `allSettled` | всегда исполняется, внутри статусы каждого |
> | `race` | первый завершившийся любым образом |
> | `any` | первый успешный; если все отказали — `AggregateError` |
>
> Для сбора всех результатов нужен `allSettled`. У `all` есть неприятный побочный эффект: при двух отказах вернётся только первая ошибка, а вторая останется необработанной и вызовет `unhandledrejection`.

### 8. Что выведет код и как называется механизм

```js
// counter.js
export let count = 0;
export const inc = () => count++;

// main.js
import { count, inc } from './counter.js';
console.log(count); inc(); console.log(count);
```

> [!success]- Ответ
> `0`, затем `1`.
>
> Импорт — не копия значения, а **живое индирект-связывание** на ячейку исходного модуля. Изменение внутри модуля видно всем импортёрам.
>
> При этом само имя доступно только на чтение: `count = 5` в `main.js` даст `TypeError`. Изменять значение может только модуль-владелец.

### 9. Почему падает и чем это лучше поведения CommonJS

```js
// a.js
import { b } from './b.js';
export const a = 'A';

// b.js
import { a } from './a.js';
export const b = 'B';
console.log(a);
```

> [!success]- Ответ
> `ReferenceError: Cannot access 'a' before initialization`.
>
> Модули связываются до выполнения, поэтому цикл не падает на разрешении зависимостей — имена существуют. Но модуль, выполняемый первым, видит биндинги партнёра **неинициализированными**, то есть в TDZ.
>
> В CommonJS на этом месте получилось бы `undefined`: сбой становился тихим и всплывал далеко от причины. Явная ошибка лучше.

### 10. Являются ли символьные ключи приватными

```js
const secret = Symbol('secret');
const obj = { [secret]: 'значение', visible: 1 };
```

> [!success]- Ответ
> Нет.
>
> Символьные ключи действительно не попадают в `Object.keys`, `for...in`, `JSON.stringify` и spread-копирование перечислением строк. Но они полностью доступны:
>
> ```js
> Object.getOwnPropertySymbols(obj); // [Symbol(secret)]
> Reflect.ownKeys(obj);              // ['visible', Symbol(secret)]
> ```
>
> Символы дают **отсутствие коллизий имён**, а не приватность. Настоящая приватность — только приватные поля класса (`#field`) или замыкание.

### 11. Разберите поведение дырок

```js
const holes = [1, , 3];
console.log(1 in holes);
console.log(holes.map(x => 2));
console.log([...holes]);
console.log(holes.includes(undefined), holes.indexOf(undefined));
```

> [!success]- Ответ
> `false`, `[2, <дырка>, 2]`, `[1, undefined, 3]`, `true -1`.
>
> Дырка — это **отсутствие свойства**, а не свойство со значением `undefined`. Отсюда `1 in holes === false`.
>
> Старые методы (`map`, `forEach`, `filter`) дырки пропускают, сохраняя их в результате. Новые (`find`, `includes`, спред, `Array.from`) трактуют как `undefined`. `indexOf` использует строгое равенство и пропущенные индексы не проверяет, а `includes` — `SameValueZero` и проверяет.
>
> Практический вывод: не создавать разрежённых массивов вовсе.

### 12. Что не так с заморозкой и с проверкой типа

```js
const config = Object.freeze({ nested: { value: 1 } });
config.nested.value = 2;

const arr = getArrayFromIframe();
console.log(arr instanceof Array);
```

> [!success]- Ответ
> `config.nested.value` станет `2` — `Object.freeze` **поверхностный** и замораживает только собственные свойства верхнего уровня. Нужен рекурсивный обход.
>
> `arr instanceof Array` вернёт `false`: у другого realm (iframe, worker, `vm`) собственный набор интринсиков, и `Array.prototype` там другой объект. `instanceof` сравнивает объекты прототипов, а не «сущность типа».
>
> Надёжная проверка — `Array.isArray(arr)`, которая смотрит на внутреннюю природу объекта, а не на цепочку прототипов.
