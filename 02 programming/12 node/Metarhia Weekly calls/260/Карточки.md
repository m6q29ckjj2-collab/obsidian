# Карточки — Weekly call #260

Какова главная позиция Тимура по поводу открытости метрик в разработке?
::
Методику измерения нужно держать в тайне — как только человек понимает, что и на что именно измеряется, он начинает (сознательно или подсознательно) подделывать показатель.

Какой исторический пример с индийскими офисами Microsoft приведён как иллюстрация подделки метрик?
::
После открытия маркетплейса приложений индийские офисы выпустили тысячи мусорных однотипных приложений под метрику «количество опубликованных приложений».

Какой современный аналог старой метрики «оплата по количеству строк кода» обсуждался применительно к AI?
::
Оценка эффективности по количеству «сожжённых» AI-токенов — так же не отражает реальную сложность решённой задачи.

Какое исключение из правила «метрики нужно скрывать» допускается?
::
Временные метрики, вводимые для принятия конкретного разового решения, — их можно не скрывать и отключать сразу после того, как решение принято.

Как участники разделили метрики на два класса в итоговом компромиссе звонка?
::
Метрики для установления истины (приватные, скрытые, на основе которых реально принимаются решения) и метрики для управления/мотивации людей (открытые, воспринимаемые как warning-индикаторы).

Какие три метрики из Jira привёл в пример участник как реально работающую у него схему?
::
Возврат задачи из Review в To Do (<3 раз), возврат из Testing в To Do (<2 раз), отклонение фактического времени от эстимейта (не больше 20%).

Каким способом можно обойти метрику «количество возвратов задачи»?
::
Искусственно дробить задачи на мелкие куски, чтобы формально снижать число возвратов и укладываться в эстимейт.

Почему за последний год (бурный рост AI-разработки) старые метрики (строки кода, число ошибок) временно перестали работать?
::
Все абсолютные величины выросли на порядки одновременно (строки ×100 и т.п.), из-за чего перестали что-либо информативно показывать; при этом часть багов ушла «под воду» — AI формально покрывает код тестами, но в продакшн проникают неявные плавающие ошибки.

Какую сбалансированную метрику для эпохи AI предложили на звонке?
::
Соотношение объёма изменений кода (добавлено/удалено строк) к динамике уровня ошибок за тот же период — diff относительно объёма изменений, а не абсолютное число ошибок.

Какое требование к эффективности сотрудников (со ссылкой на опыт из GitLab) обсуждалось как нереалистичное?
::
Требование руководства «стать в 100 раз эффективнее» с помощью AI — Тимур считает реалистичным потолком скорее ×10.

Что нужно на уровне инфраструктуры компании, чтобы поднять эффективность всей команды, а не отдельного специалиста?
::
Единый общий контекст компании (база знаний) с подключёнными MCP-серверами, куда стекаются данные из Jira, Confluence, репозиториев и саммари созвонов, доступные агентам при разработке любого модуля.

Какова позиция Тимура насчёт прямой привязки зарплаты разработчика к метрикам?
::
Против — над разработчиком должен стоять непосредственный руководитель малой группы (≤10 человек), чьё субъективное мнение (не формула) определяет бонусную часть, потому что жизненные обстоятельства временно влияют на эффективность даже лучших специалистов.

Как Тимур относится к штрафованию сотрудников за бизнес-риски (например, дорогостоящий даунтайм сервиса)?
::
Резко против — если сотрудники наняты как добросовестные квалифицированные специалисты, ошибки являются рисками бизнеса, а не поводом перекладывать финансовую ответственность на людей.

Почему «зелёные квадратики» активности на GitHub названы метрикой активности, а не эффективности?
::
Джун, который «портит всё и ходит из задачи в задачу», может показывать активность выше, чем сеньор — количество коммитов не отражает качество или пользу работы.

Какие инструменты рекомендованы для безопасного тестирования UX-изменений с учётом эффекта привычки пользователей?
::
Canary Release и Blue-Green Deploy — тестировать изменение на небольшом проценте пользователей, желательно с их согласием на участие и возможностью отката.

Почему недовольство пользователей сразу после UX-изменения не всегда означает, что изменение плохое?
::
Это может быть временный эффект привычки к старому интерфейсу — метрику нужно смотреть в тренде за 2-3 месяца, а не сразу после релиза.

По какой метрике, согласно Тимуру, должен оцениваться архитектор, и почему не так, как тимлид?
::
Тем, насколько им довольна его собственная команда (а не начальство) — потому что решения архитектора не подкреплены прямой властью, он должен убедить и увлечь команду, а не продавить решение директивно.

Что происходит, если архитектор не смог убедить команду в своём архитектурном решении (пример с Kafka vs Redis)?
::
Возникает «распределённый монолит» — команда формально выполняет задачи, но не вкладывается в освоение новых инструментов и невольно производит некачественный код («диверсии»).

Почему CTO не обязан быть самым сильным программистом в команде, и что тогда для таких специалистов?
::
Если сильнейший разработчик не пишет код, роли распределены неэффективно; а rockstar-программист без rockstar-задач начинает заниматься оверинжинирингом или демотивируется — для таких людей должны быть отдельные позиции (Principal Engineer, архитектор).

Какого рода техническая эрудиция важнее для CTO/архитектора — глубина в одном языке или широта?
::
Широта — опыт на 5-6+ языках позволяет управлять командой на незнакомом лично стеке, потому что архитектурные принципы переносятся между языками.

Какие метрики качества кода собирает SonarQube и подобные quality gates перед мержем PR?
::
Цикломатическую сложность, вложенность циклов, размер файлов/методов, число методов в классе, покрытие тестами, уязвимости.

Зачем нужны warning-пороги (например, метод длиннее ~50 строк) в SonarQube, если они не блокируют коммит жёстко?
::
Чтобы «устыдить» программиста визуально («всё красное горит») — особенно актуально с учётом больших объёмов AI-сгенерированного кода.

Какую новую метрику Тимур пытается внедрить через AI-модель, и почему её нельзя измерить статическим анализом?
::
Cognitive complexity (когнитивную сложность) — плохо поддаётся статическому анализу и требует смысловой оценки; человек-ревьюер быстро привыкает к стилю коллеги и перестаёт замечать сложность, а AI-модель — нет.

Что анонсировал Тимур в конце звонка по поводу истории записанных созвонов?
::
Планирует регулярно автоматически суммаризировать записи созвонов (короткое summary с таймкодами), потому что сотни прошедших звонков образуют неструктурированную базу знаний, в которой сложно найти что-либо постфактум.
