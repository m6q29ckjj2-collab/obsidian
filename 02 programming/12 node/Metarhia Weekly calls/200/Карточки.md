# Карточки — Weekly call #200

Почему нужно обязательно коммитить `package-lock.json`, даже если правила семвера гарантируют совместимость патч-версий?
::
Даже патч-версии на практике могут ломать код — например, если пакет тянет за собой другой пакет, или если в апстриме починили баг, под который уже был сделан несовместимый с фиксом обходной путь. Только lock-файл с хэш-суммами даёт по-настоящему воспроизводимую сборку.

Когда оправдано коммитить весь `node_modules` целиком в репозиторий?
::
Только в узком случае — если нужно распространять автономный дистрибутив приложения без последующего npm install.

Как изменилась политика npm в отношении подмены уже опубликованной версии пакета (unpublish)?
::
Раньше можно было опубликовать пакет поверх существующей версии; сейчас в течение суток после публикации можно сделать unpublish, после этого — нет.

С какой версии Node.js доступен `Promise.try()`, и почему Тимур предостерёг рано полагаться на неё в широко используемых библиотеках?
::
С Node.js v23 (переходная нечётная версия, не LTS на момент звонка) — библиотекам для широкой аудитории стоит подождать LTS-версию с поддержкой.

В каком браузере поддержка `Promise.try()` появилась позже всех и почему это создаёт риск?
::
В Firefox — раскатывалась с 7 января, полностью только с 4 марта; риск в том, что пользователи Firefox реже обновляют браузер вручную, в отличие от автообновляемых Chrome/Safari.

На каком движке в итоге построен современный Microsoft Edge, несмотря на несколько собственных JS-движков компании в прошлом (JScript, ChakraCore)?
::
На Chromium — Microsoft «сдалась» и перешла на движок Google Chrome.

В каком порядке рекомендовано изучать базовые темы-преквизиты, согласно построенной на звонке структуре репозитория?
::
Basic syntax → Data types → Data structures → Lexical scope → Pure functions → Composition → Closures → Chaining → Signatures/contracts → OOP Basics → Module systems (ESM/CommonJS).

Почему Module systems (ESM/CommonJS) сознательно поставлены в конец списка преквизитов?
::
Потому что понимание модульных систем подразумевает уже понимание lexical scope, которое идёт значительно раньше в списке.

Какие темы (каррирование, рекурсия, мемоизация, монады, функторы) были явно исключены из преквизитов курсов и почему?
::
Они признаны необязательными знаниями — не требуются напрямую ни для одного из курсов Metarhia (Node.js, Patterns, Async).

Почему алгебраические типы данных не включены в преквизиты, хотя и запланирована отдельная лекция про них?
::
Это расширение кругозора, а не предпосылка ни к одному из курсов — в JS/TS таких типов нет «из коробки», их пришлось бы реализовывать через контейнерные типы.

Почему темы архитектуры сознательно не включены в преквизиты?
::
Архитектура логически идёт после паттернов, асинхронного программирования и даже после Node.js, а не до них.

Какое популярное определение closure Тимур на звонке назвал неверным/неполным?
::
«Closure — это функция, которая возвращает функцию» — вложенность функций сама по себе не создаёт замыкания, если внутренняя функция не захватывает переменную из внешней области видимости.

При каком условии функция, вложенная в другую функцию, реально создаёт работающее замыкание?
::
Только когда внутренняя функция фактически ссылается («зацепляется») на переменную из внешней области видимости — простого возврата аргумента или невовлечённой функции недостаточно.

Как оптимизирующий компилятор V8 может «убрать» синтаксически существующее замыкание?
::
Если захватываемое значение — константа, которую можно подставить напрямую (инлайнинг), V8 может заинлайнить код и убрать замыкание из фактически выполняемого скомпилированного кода, даже если формально по спецификации оно есть.

Какое формальное определение closure сформулировано в итоге обсуждения на звонке?
::
Closure = внутренний scope функции + её лексическое окружение, зацепленные за scope внешней функции, в которой она определена.

Где физически хранится структура замыкания в памяти — в стеке или в куче?
::
В куче (heap), как отдельная структура данных, к которой у пользовательского кода нет прямого доступа — только сам движок читает/пишет в неё.

Какой пример утечки памяти через замыкание разобран на звонке (HTTP-сервер)?
::
Подписка на событие с опечаткой в имени (`connect` вместо `connection`) — замыкание обработчика будет жить в памяти вечно, пока жив сам HTTP-сервер, потому что событие никогда не сработает и не освободит ссылку.

Создаёт ли функция, объявленная в глобальном контексте браузерной консоли и использующая внешнюю переменную, настоящее замыкание?
::
Нет — там нет вложенности контекстов, всё находится в одном общем глобальном scope, поэтому замыкание формально не создаётся.

Почему та же функция, объявленная внутри CommonJS-модуля Node.js, автоматически создаёт closure?
::
Система модулей Node.js оборачивает содержимое файла в скрытую функцию-обёртку (с exports, require, module и т.д.), и любая функция внутри файла, ссылающаяся на модульные переменные, оказывается зацеплена за scope этой обёртки.

Как исторически реализована передача `module.exports` в CommonJS, и почему Тимур назвал это «архаичным хаком»?
::
Через побочное присвоение global.module перед вызовом функции-обёртки файла, а не через прямой аргумент — решение почти 20-летней давности, от которого уже невозможно избавиться без слома обратной совместимости.

Чем block scope принципиально отличается от того, как его можно создать (кроме if/for)?
::
Block scope создаётся любыми `{}`, включая просто «голые» вложенные фигурные скобки без какого-либо управляющего оператора — эта возможность существует в языке уже 10+ лет.

Какая ловушка возникает из-за поведения function declaration внутри вложенных блоков?
::
Function declaration внутри блока «поднимается» (hoisting) до начала охватывающего блока, ведя себя как var, в отличие от const/let — из-за этого легко ошибиться, какая версия одноимённой функции активна в конкретной строке кода.
