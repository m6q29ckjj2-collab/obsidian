## 1. `package-lock.json`: почему обязательно коммитить

Вопрос из зала про боль с обновлением npm-зависимостей вылился в чёткую рекомендацию: **`package-lock.json` нужно обязательно коммитить**, потому что даже патч-версии (последняя цифра семвера, по идее не ломающие совместимость) на практике могут ломать код — например, если один пакет тянет за собой другой, или если в апстриме починили баг, под который в своём коде уже был сделан обходной путь (workaround), несовместимый с фиксом. `package-lock` фиксирует точные версии и хэш-суммы, поэтому по-настоящему воспроизводимую сборку даёт только он, а не сам `package.json`.

Отдельно разобран нюанс про **npm unpublish**: раньше можно было опубликовать пакет поверх уже существующей версии (подмена кода при той же версии), сейчас эта возможность ограничена — в течение суток после публикации можно сделать `unpublish`, после этого — нет; если версия отозвана, а на неё кто-то ссылался в lock-файле, npm поставит ближайшую совместимую по semver. Коммит `node_modules` целиком в репозиторий признан оправданным только в узком случае — если нужно распространять автономный дистрибутив приложения без последующего `npm install`.

## 2. `Promise.try` и почему рано на него полагаться в браузерном коде

Участник поделился находкой — `Promise.try()`, синтаксический сахар, убирающий необходимость оборачивать вызов в `new Promise((resolve) => resolve(...))`. Разбор поддержки в реальном времени (via caniuse):
- В Node.js — доступен только начиная с **v23** (переходная нечётная версия, не LTS на момент звонка) — Тимур предостерёг, что рано полагаться на неё в библиотеках, ориентированных на широкую аудиторию, пока не выйдет LTS-версия с поддержкой.
- В браузерах — Chrome с августа 2024, Safari с декабря 2024, а вот **Firefox** — только с 4 марта, раскатывалось постепенно с 7 января, то есть на момент звонка это очень свежая поддержка. Вывод: пользователи Firefox (особенно те, кто не обновляет браузер вручную/принудительно, в отличие от auto-update у Chrome/Safari) — зона риска; если нужна такая фича без полифилла — только для чисто серверного Node.js-кода, не для универсальных браузерных библиотек.

## 4. Построение репозитория «Prerequisites» — таксономия базовых концепций курсов

Основная практическая часть звонка — Тимур в прямом эфире создаёт на GitHub новый репозиторий (`Native Concepts` → переименован в раздел `Prerequisites`), продолжающий ранее опубликованный `Native Contracts`, и формирует список базовых тем, знание которых предполагается **перед** любым из его курсов (Node.js, Patterns, Async). Итоговая структура, выстроенная по порядку изучения:

1. **Basic syntax** — операторы, конструкции языка, regexp, прототипы, глобальные объекты (уточнено: часть таких «глобальных» объектов — это JS, часть — Web API/рантайм-специфика, например таймеры относятся уже не к языку, а к рантайму).
2. **Data types** — встроенные типы данных.
3. **Data structures** — включая typed arrays.
4. **Lexical scope** (он же lexical environment — по ходу обсуждения признаны практически синонимами).
5. **Pure functions** (чистые функции).
6. **Function composition / object composition**.
7. **Closures** (замыкания) — сознательно поставлены после scope, поскольку без понимания scope невозможно понять closure.
8. **Chaining** (function chaining / object chaining).
9. **Signatures and contracts**.
10. **OOP Basics** — конструктор, статические/приватные/публичные методы и поля, наследование, полиморфизм, абстрактный класс, интерфейс, инкапсуляция, рефлексия/интроспекция.
11. **Module systems** — как минимум ESM и CommonJS (сознательно вынесено в конец, потому что подразумевает уже понимание scope).
12. Отдельными ссылками, не строго по порядку: **V8 Optimizations** (ссылка на другой репозиторий) и **Basic async contracts** (ссылка на `Native Contracts`; будет отдельно пересмотрен в субботнем стриме с Денисом про полный обзор асинхронных абстракций).

### Что осознанно исключено из преквизитов
- **Каррирование, частичное применение, рекурсия, мемоизация, монады, функторы** — отмечены как необязательные знания: не требуются напрямую ни для одного из курсов Metarhia.
- **Алгебраические типы данных** — отдельно зафиксировано как тема для будущей лекции (Тимур поясняет идею на пальцах: алгебраические операции над самими типами, а не над их значениями — в JS/TS такого нет «из коробки», нужно реализовывать через контейнерные типы/боксинг), но подчёркнуто: это не преквизит ни к чему, а отдельное расширение кругозора.
- **Diamond Problem** (проблема ромбовидного наследования) — теоретическая CS-тема; в JS решаема через прототипное наследование, но нетривиально; не преквизит.
- Темы архитектуры — сознательно не включены, потому что архитектура логически идёт **после** паттернов, асинхронного программирования и даже после Node.js, а не до них.

## 5. Главная техническая тема: путаница между Scope и Closure

Самая содержательная часть звонка — развёрнутая на конкретных примерах дискуссия о том, чем **scope** отличается от **closure**, спровоцированная тем, что участники путают эти понятия (в том числе цитируя недостаточно точные определения из популярных онлайн-ресурсов, например Learn JavaScript, которые Тимур и участник явно назвали местами неточными).

### Область видимости (scope) — три вида
`Scope` бывает **global**, **block** и **function**. Block scope создаётся любыми `{}` — не только `if`/`for`, но и просто «голыми» вложенными фигурными скобками (с ~10+ лет как в языке). Показан живой пример вложенных block scope с переопределением одноимённых идентификаторов (`f`, `c`) на разных уровнях вложенности — продемонстрировано, что такая вложенность синтаксически похожа на переопределение метода при наследовании в ООП, хотя механизм совершенно другой. Отдельно показана ловушка: `function` **declaration** внутри блока «поднимается» (hoisting) до начала охватывающего блока (ведёт себя как `var`), в отличие от `const`/`let` — из-за этого при чтении кода с одинаковыми именами функций в разных вложенных блоках легко ошибиться, какая версия функции активна в конкретной строке; рекомендация — **не переиспользовать одинаковые короткие имена** (вроде `f`) в соседних блоках, чтобы не повышать когнитивную нагрузку читающего код человека.

### Closure — не просто «функция, возвращающая функцию»
Ключевой тезис, ради которого затевался весь разбор: **популярное определение «closure — это функция, которая возвращает функцию» — неверно/неполно**. Показано на конкретных контрпримерах:
- Функция, которая просто возвращает свой аргумент (`return arg`) или возвращает функцию, не читающую внешние переменные — **не создаёт работающего замыкания**, даже когда синтаксически «функция вложена в функцию».
- Замыкание возникает только тогда, когда внутренняя функция **фактически ссылается на переменную из внешней области видимости** («зацепляется» за неё) — то есть нужна не просто вложенность, а именно захват (capture) внешнего идентификатора.
- Важный нюанс уровня V8: даже когда замыкание **синтаксически** создано (внутренняя функция объявлена внутри внешней и вроде бы имеет доступ к внешней переменной), **оптимизирующий компилятор может «заинлайнить»** значение и фактически убрать замыкание из скомпилированного кода, если, например, захватываемое значение — константа, которую можно подставить напрямую. То есть один и тот же код может формально «иметь» closure по спецификации языка, но **не иметь его физически** после оптимизации JIT-компилятором.
- Формальное определение, к которому пришли в результате обсуждения (сформулировано и Тимуром, и участниками): **closure = внутренний scope функции + её лексическое окружение, зацепленные за scope внешней функции, в которой она определена**. Более «человеческое» альтернативное определение от участника: scope — это карта, где в программе доступны те или иные идентификаторы; closure — это функция + захваченное окружение, дающее доступ к этим именам спустя время (после возврата из внешней функции).

### Closure на низком уровне
На вопрос «как это устроено физически» — closure хранится **не в стеке, а в куче (heap)** как отдельная структура данных, к которой у пользовательского кода нет прямого доступа (только сам движок читает/пишет в неё) — по аналогии с тем, как объект хранит `this`, но без прямой ссылки снаружи. Обычно (в нормальном случае — без возврата функции) фрейм стека функции уничтожается сразу после `return`; но если возвращаемая функция удерживает ссылку на переменные внешней функции, GC не может собрать связанный scope — именно это удержание сборщиком мусора и есть механическая суть замыкания.

### Утечки памяти через «висящие» замыкания
Прямое практическое следствие: если функция с активным замыканием попадает в долгоживущий объект (глобальный объект, `process`, HTTP-сервер, любой `EventEmitter`) — например, подписывается на событие, которое реально никогда не произойдёт (показан пример опечатки в имени события — `connect` вместо `connection` у HTTP-сервера) — замыкание **будет жить в памяти вечно**, пока жив сам долгоживущий объект-держатель. Это одна из самых распространённых причин утечек памяти в Node.js-приложениях: разработчик не осознаёт, что подписка на несуществующее/неверно названное событие удерживает весь захваченный контекст замыкания в куче бессрочно.

### Модульная система как источник неочевидного замыкания
Отдельный практический кейс, разобранный по запросу участника: обычная функция, объявленная **в глобальном контексте браузерной консоли** (без модульной системы), формально **не создаёт closure** даже если использует внешнюю переменную — потому что там просто нет вложенности контекстов, всё в одном общем глобальном scope. А та же функция, объявленная **внутри CommonJS-модуля** (`.js`-файл, загружаемый через `require`) — **создаёт closure автоматически**, потому что сама система модулей Node.js оборачивает содержимое файла в скрытую функцию-обёртку (получающую `exports`, `require`, `module`, `__filename`, `__dirname`), и любая функция внутри этого файла, ссылающаяся на модульные переменные, автоматически оказывается «зацеплена» за scope этой скрытой обёртки. Попутно объяснена архаичная механика `module.exports` в Node.js (передача `global.module` через побочный костыль, а не напрямую аргументом — «древний хак 20-летней давности, от которого уже невозможно избавиться» без слома обратной совместимости).
