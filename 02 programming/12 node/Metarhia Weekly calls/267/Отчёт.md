## 1. Иммутабельные структуры данных: кому они нужны

Тимур перед звонком запускал в группе опрос: «какие библиотеки вы используете для иммутабельных структур?» — **57% опрошенных вообще не пользуются** иммутабельными структурами данных. Из этого разговор развернулся в принципиальный вопрос: где иммутабельность вообще нужна.

Прозвучал аргумент от слушателя: если у него есть контракт (например, объект, считанный из базы, который по внешнему протоколу можно подрезать/дополнить), то создавать новую структуру ради иммутабельности — лишняя работа; проще пройтись по существующей и отредактировать «на месте», раз дисциплина использования и так не проверяется автоматически.

Тимур сформулировал общее правило, которое стало центральной идеей звонка:

- **Системное программирование** (стримы, буферы, сетевые чанки, всё, что должно быть максимально быстрым) → **мутабельные** структуры данных, написанные руками, без абстракций. Пример: двусвязный список для чтения чанков из сети делается не как классический linked list, а как **Unrolled list** — список из нескольких *массивов* (или **circular array**), потому что по массиву дешевле двигать указатель, чем ресайзить сам массив.
- **Прикладной код / бизнес-логика** → структуры вроде `struct`, `record`, `result`, `cons`(-list) из библиотеки **metautil** — они не оптимизируются под производительность, а оптимизируются под **developer experience и надёжность**: дополнительная дисциплина работы с состоянием, предсказуемость, отсутствие мутаций «из ниоткуда».

### `struct` из metautil: как это устроено технически
`struct` не просто замораживает (`Object.freeze`) объект — он даёт **копии через наследование** (по сути prototype-chain copy-on-write): копия не хранит полный набор полей, а только диф от родителя, и её можно **материализовать** (`materialize`) — схлопнуть цепочку наследования в плоскую (`flat`) коллекцию, когда это нужно для экономии памяти.

Побочный эффект такой модели — «история» изменений остаётся доступной через цепочку прототипов, а значит на объектах `struct` можно реализовывать **undo / транзакции**, паттерн вроде **Saga** (откат к предыдущему состоянию).

### `fixed queue`
Мимоходом упомянута структура `fixed queue` (уже есть в самом Node.js, добавлен pool для переиспользования arrays) — она лежит в основе `process.nextTick`, и её дальнейшая оптимизация напрямую ускоряет асинхронность во всём Node.js.

## 2. Библиотека Effect (effect-ts) — взгляд со стороны

Тимур спросил мнение по поводу библиотеки **Effect** для TypeScript/JavaScript. Его оценка:

- **Синтаксис** (`Effect.gen` с `function*` и `yield*`) — смущает, выглядит непривычно.
- **Концепция** — хорошая: часть бизнес-логики, которая может возвращать ошибку, оборачивается в контейнер `Effect`, у которого явно специфицированы зависимости на вход и типы результата/ошибки на выход. Все `Effect` — ленивые, их можно **композировать** и запускать. Runtime-проверка контрактов схемами (а не типами, которые «исчезают» после компиляции TS) — это то, что Тимур сам продвигает («контракты, проверяемые в рантайме схемами»).
- **Файберы** — `Effect` запускается в fiber (аналог goroutine из Go, похоже на то, что популяризирует React). Тимур считает это **лишним** для JS: у языка и так есть event loop + очередь микротасков, то есть встроенный движок конкурентности, отдельный слой файберов не обязателен.
- Итог: идея правильная («хочу это, но дешевле»), но текущая реализация усложнена сверх необходимого.

## 3. Новые модули для Meta Qube

Обсуждали, какие модули нужны участникам сообщества. Из конкретики:

- **QR-код генератор** — предложение от участников.
- **Беспарольная криптографическая авторизация/аутентификация на клиенте** — на основе генерации сертификатов, по мотивам стандарта **Passkeys**, который уже поддерживают браузеры. У Тимура готовы два варианта: один поверх стандарта Passkeys, второй — самописный, делающий то же самое без него.
  - Вопрос хранения приватного/публичного ключа в браузере: **localStorage**, **OPFS** (Origin Private File System), cookies — все варианты по сути «спрятать в браузере». У Passkeys для этого есть выделенное **защищённое хранилище браузера** с шифрованием на диске. Тимур рассуждает, можно ли добиться того же для своих ключей (шифровать самим, или хранить в IndexedDB — «никто с диска (веника) не прочитает», но при компрометации самого процесса браузера защиты уже никакой нет в любом случае).
- **Модуль платежей** — самая длинная дискуссия звонка, вынесена в раздел 6.

## 4. Разбор pull request'ов

### Impress
- **PR по namespace-префиксам** — автоматическое преобразование строк вида `node:fs/promises` в camelCase-имя (`fsPromises`) при загрузке зависимостей, вместо ручного прописывания алиасов. Нашли баг: где-то в коде вместо `splice` написали `slice` — Тимур предположил, что это либо невнимательность автора, либо неудачная правка ИИ-инструментом. Открытый вопрос — нужны ли явные **алиасы** (например, кто-то привык писать `fs`, а не `fsPromises`) — решили, что нужны, но для этого нужно сперва написать тесты-таблицы с примерами преобразований.
- **Большой рефакторинг стиля кода в Impress**: конкатенации строк заменены на **template strings** (они быстрее — при склейке 3+ строк конкатенация делает промежуточные строки, а template literal — сразу одну результирующую строку); внедрено более активное использование optional chaining (`?.`); вынесение повторяющихся констант (`Application file` → отдельная переменная). Отдельно поднята задача **убрать деструктуризацию массивов из возвращаемых значений функций** по всей кодовой базе Metarhia — вместо `return [a, b]` функции должны возвращать структуру (`{a, b}`) и деструктурироваться как объект: это быстрее (**destructuring структуры быстрее, чем массива** — обсуждалось как факт производительности V8) и это принцип, которого команда придерживается как «мы же системный код».
- **Static compression review**: в `impress` уже добавлена компрессия статических файлов (конфигурируется тип компрессии), но **нет проверки заголовков клиента** (какой тип компрессии клиент поддерживает) и **нет fallback**, если клиент не поддерживает выбранный тип — клиент будет получать ошибку без понятной причины. Отмечено как открытая проблема.
- **Наследование Certificate от Static** — архитектурно некрасиво: класс, отдающий TLS-сертификаты, наследует слишком много специфичного для раздачи статики функционала. Предложение — ввести промежуточный класс/базу **Place** (или **Resource**) для «поднятия бинарных данных в память», от которого будут наследоваться и `Static`, и `Certificate`.
- **SharedArrayBuffer / VFS для статики** — один из участников уже реализовал собственную реализацию виртуальной ФС на SharedArrayBuffer (независимо от той, что позже влили в сам Node.js — нодовская версия **не переиспользует буфер между тредами**, самописная — переиспользует). Обсуждали, стоит ли добавлять это в Impress: Тимур — «за», но предупредил, что для интеграции такую вещь придётся переписывать много раз, это большая и ключевая функциональность, работать над ней нужно долго и аккуратно.
- **Байткод-шаринг модулей между тредами** — идея загружать исходники JS-модулей с диска один раз, компилировать через `vm.compileFunction` в байткод и рассылать по всем worker-тредам (а не грузить и парсить в каждом отдельно) — потенциально ускоряет старт системы. Открытый риск: неясно, как это повлияет на **оптимизации V8** (байткод от `vm.compileFunction`, скорее всего, неоптимизированный/сырой). Решили, что нужно завести **ADR (Architectural Design Record)**, чтобы знания о том, почему приняты такие решения, не терялись для будущих контрибьюторов.

### Metautil
- **Priority Queue на основе Heap** — большой PR (+751 строка), код признан «системным», плотным («простынным»), но оправданно сложным ради производительности; часть можно улучшить, требуется полноценный ревью.
- **Патч про таймеры в тестах** — проблема: между версиями Node.js (после 22 или 24) тесты стали падать, потому что нигде не было `ref()` на указатели на ресурсы, которые держат процесс живым. Предложенный fix — доп. `setTimeout`, который держит процесс. Обсуждение показало, что это **не устраивает по-хорошему**: проблема проявляется только в тестах (в реальном продакшен-коде бизнес-логика и так держит ресурс), а решение через `AbortSignal.timeout` выглядело бы «красивее», но требует runtime-патча под конкретную версию Node.js, который сам может конфликтовать с патчами пользователей. Решение отложено — задача помечена как **RnD, work in progress**.
- **Feature-request на `add()` в Unroll List** — пользователь попросил метод добавления в произвольную позицию списка. Разобрали на живую реализацию: `Unroll list` устроен как список из `UnrollNode` с `NodePool` внутри, доступ идёт через голову/хвост (`NQ`/`DQ`, `peek`), у структуры нет произвольного индексного доступа без полного обхода — а раз он нужен для `add()`, то реализация убьёт весь смысл оптимизации (Unroll list эффективен только для операций с концов). Вывод: **не реализовывать** — вместо этого пользователю посоветовать обычный `List` (двусвязный список из `ListNode`), где есть `add(index)`, пусть и не супербыстрый, но приемлемый.

## 5. Документация: как писать доки, чтобы они годились и людям, и AI

Долгий и важный для проекта разговор. Отправная точка — сравнение текущего состояния доков metautil (во многом дублируют TypeScript-тайпинги без пояснений) с документацией **Tokio (Rust)**: там у каждой функции — сигнатура, развёрнутое текстовое описание нюансов и пример кода (snippet). Участники звонка признали, что при беглом чтении такой развёрнутой доки они реально «читают только сигнатуру и snippet», а текст пролистывают («это для меня шум») — но согласились, что для менее очевидных случаев (например, обработка ошибок в Rust, где нужно явно понимать тип ошибки) развёрнутый текст всё же нужен.

Дискуссия вышла на более общую и стратегическую тему: **нужно проектировать документацию сразу для двух потребителей — разработчиков и AI-агентов**, и не хранить это как отдельные, независимо редактируемые артефакты, потому что тогда неизбежно **разъедутся** код, тайпинги, markdown-доки и AI-skills (уже 4-5 мест для правки одного и того же факта). Предложение: единый источник истины в виде **JSON-описания в духе JSON Schema с дополнительными «человекочитаемыми» полями** (metaschema и так поддерживает произвольные поля), из которого компилируются: TS-тайпинги, HTML/Markdown-доки, AI skills.

Отдельно поднята мысль про **разделение skills по назначению**:
- **usage skill** — как использовать структуру данных / модуль в обычном случае;
- **optimization skill** — отдельно, подгружается **только** когда явно просят оптимизировать производительность.

Причина разделения: если в модель «зашить» инструкцию сравнивать производительность структур данных на каждый чих, AI-агент начнёт на ровном месте генерировать бенчмарки и сравнительные таблицы вместо того, чтобы просто написать код — это дорого по токенам и по времени, и Тимур сравнил это поведение с прокрастинацией у программистов-людей («вместо того, чтобы делать продажи, пишу двусвязный список»). Для случаев, когда оптимизация всё-таки нужна, предложено держать заранее посчитанные бенчмарки/таблицы прямо в docs, чтобы AI не тратил токены на их генерацию заново.

## 6. Модуль платежей для Meta Qube — самая долгая дискуссия

Толчком послужил вопрос: зачем вообще делать универсальный модуль-агрегатор платежей, если с современными AI-инструментами подключить один платёжный провайдер (например, Stripe) — дело 5 минут?

Тимур и один из участников (сам подключавший несколько провайдеров: Stripe, PayPal, локальные украинские Rozetka Pay/QPay, турецкий провайдер) разобрали, почему в реальности всё сложнее:

- **Подключить один провайдер — легко.** Сложность начинается, когда в одном проекте нужно **несколько провайдеров одновременно** и их нужно объединить общим доменным кодом (единый интерфейс статуса платежа, обработка ошибок и т.д.).
- **Почему нельзя обойтись одним глобальным провайдером типа Stripe**: Stripe (и аналоги) недоступны/забанены для компаний из ряда стран (пример — Украина, Турция упомянуты явно). Бизнесы из этих стран либо регистрируют юрлицо в поддерживаемой юрисдикции (Эстония и т.п., чтобы платить меньше налогов и получить доступ к Stripe), либо, если бизнес привязан к физическому присутствию/складу в стране (и не может «просто уехать» юридически), вынуждены работать через **локальные системы** (Приватбанк, Монобанк и т.п.) — а те хуже задокументированы и с ними больше проблем интеграции.
- **Рекуррентные платежи — отдельный источник боли.** У самого Metarhia есть свежий (на момент звонка) инцидент: интеграция с провайдером **SendPulse** для проекта **Nextic** — примерно **80 подписчиков** не получили продление подписки, потому что провайдер **не уведомил ни пользователей, ни систему** о неудачном списании. Никто (ни люди, ни бэкенд) не узнал о проблеме вовремя. Обсуждались вероятные причины подобных проблем в целом: (а) сырой/недокументированный провайдер, куда сложно интегрироваться даже по OpenAPI-контракту; (б) система изначально спроектирована под один сценарий оплаты (разовая покупка из корзины), а рекуррентные платежи добавлены поверх как чужеродная функциональность — из-за чего расходятся модели данных и обработки статусов.
- **Итоговая идея модуля**: не «одна интеграция под каждый проект с нуля», а постоянная небольшая команда (3-4 человека) внутри Metarhia/Meta Qube, которая **знает все нюансы всех поддерживаемых платёжных систем**, поддерживает готовые, протестированные интеграции-плагины (уже упомянуты три готовых плагина), и к которой можно обращаться, а не «изобретать велосипед» в каждом новом стартапе на этом стеке.
- **План действий**, озвученный в конце: сначала **собрать требования** (участники присылают свои реальные проблемы из практики), сформировать общий пул задач → принять архитектурные и организационные решения (что входит в скоуп, что нет, какие провайдеры поддерживаются «из коробки», где точка расширения для кастомных плагинов) → написать техническое задание → отдать LLM на генерацию реализации → ревью и тестирование людьми.
