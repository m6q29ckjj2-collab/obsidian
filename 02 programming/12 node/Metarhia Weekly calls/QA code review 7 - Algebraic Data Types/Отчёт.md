# Q&A and code review #7 — Algebraic Data Types

> [!info] О звонке
> Отдельный формат от «Weekly call» — Q&A + код-ревью с более глубоким погружением в одну тему за раз. В этот раз — live coding алгебраических типов данных (ADT) на чистом JavaScript: зачем они нужны, что уже умеет язык из коробки, и что не удалось сделать красиво. Конспект по автосубтитрам.

---

## 1. Зачем вообще алгебраические типы данных в JS

Ответ на стартовый вопрос: ADT не строго необходимы ни для курса паттернов, ни для продакшена — это (а) инструмент, расширяющий понимание типов (полезно для лучшего TypeScript), и (б) упражнение на то, что почти всё в языке можно «полифилить» средствами самого языка (как когда-то Promise). Исторический контекст: в TC39 был proposal на нативные immutable **Record & Tuple**, но от него отказались — обсуждаемый на звонке код — попытка получить похожий функционал руками.

---

## 2. Отступление: ООП по Алану Кею и как оно решает race condition

Большой блок (в ответ на вопрос из зала) — объяснение первоначальной концепции ООП, задуманной Аланом Кеем (язык **Smalltalk**, 1970-е), и почему она **по конструкции исключает race condition**:

- Мир мыслится как объекты с состоянием и внешним интерфейсом. У каждого объекта — **очередь сообщений** на вход (прообраз метода — «message», не «method»); объект вычитывает сообщения по одному и обрабатывает последовательно — что автоматически исключает одновременный вызов нескольких методов одного объекта (в терминах JS — это как если бы каждый объект нативно был `EventEmitter`/`Observable`, обрабатывающим события строго по одному).
- Второй принцип — **никакой объект не видит внутреннего состояния другого напрямую**: ни к полям, ни к методам нет прямого доступа, только через сообщения (в современных терминах — только через геттеры/сеттеры, которые сам объект контролирует). Отсюда — состояние объекта невозможно испортить извне, в отличие от JS, где через точечную нотацию можно напрямую переписать внутренние поля (пример: подменить приватную коллекцию `EventEmitter`-а изнутри, если знать структуру).
- Побочная историческая ремарка от участника (со ссылкой на статью Мартина Фаулера): Smalltalk — первый язык с архитектурой **MVC**, и оттуда же по цепочке (через presentation model → view model в одном из Microsoft-фреймворков) выросли современные фронтенд state-менеджеры — решение проблемы, куда девать UI-логику, которая не относится ни к контролам, ни к доменной модели.
- Race condition вообще возникает в местах **разрыва управления** (в асинхронном JS — await/callback, в многопоточных языках — переключение потоков): между двумя логически связанными операциями (например, списать с одного банковского счёта / зачислить на другой) может вклиниться конкурирующая операция и испортить промежуточное состояние.

## 3. `Record` — иммутабельные/мутабельные структуры-контейнеры

Первая и, по оценке Тимура в конце звонка, **единственная действительно удачная** из продемонстрированных конструкций (её планируется перенести в `metautil`).

### Реализация
- `Record.immutable(...fields)` / `Record.mutable(...fields)` — статические фабрики, обе вызывают приватный `build(fields, mutable)`, который **динамически создаёт новый класс** через `class` внутри функции и возвращает его.
- Экземпляры создаются через `object create(null)` (не через `{}` — важно, чтобы **цепочка прототипов заканчивалась на `null`**, а не на `Object.prototype`: это не только чище, но и **быстрее** — поиск отсутствующего поля не тратит лишний шаг на проверку `Object.prototype`).
- В зависимости от `mutable`/`immutable`, финализация — `Object.seal` (можно менять значения полей, нельзя добавлять/удалять) или `Object.freeze` (нельзя менять вообще ничего).
- `update(instance, updates)` — точечное изменение полей (бросает исключение, если объект `frozen`); `fork(instance, updates)` — создаёт **новую** структуру-потомка (аналог `Object.assign` в чистый объект без прототипа), не трогая исходный экземпляр — на этом принципе строится **immutable-обновление**: старая ссылка продолжает указывать на предыдущую версию, новая — на изменённую. Именно так функциональный стиль работы с состоянием сочетается с этими структурами.
- Практический пример на звонке: типы `City` (immutable — название города после создания не меняется) и `User` (mutable — можно менять `nickname`, `city` и т.п.), где `User` **агрегирует** `City` по ссылке — и раз `City` иммутабельна, нет риска, что кто-то незаметно «переименует» город и тем самым сломает данные всех пользователей, ссылающихся на него.
- Обсуждённая на звонке альтернативная реализация того же через plain object literals оказалась короче и «прозрачнее» по коду — Тимур признал, что **когнитивная нагрузка растёт** при переходе на алгебраические структуры, и оправдан такой переход только там, где нужна дополнительная гарантия целостности типа (пример — тип `Money`, где обязательна валидация точности до копейки и предотвращение появления «плавающих» полукопеек, которые в реальных финансовых системах становятся источником накопительных ошибок).

### Ремарка от участника (Дмитро) про `Reflect.has`
Использование `Reflect.has()` вместо `in`/`hasOwnProperty` в реализации — Тимур подтвердил, что это чисто стилистический выбор («синтаксически красиво»), не связанный с оптимизацией, и что код в целом — черновой прототип, не оптимизированный.

### Ограничения TypeScript-типизации для Record
Отдельно показан `.d.ts`: типизация получается **малополезной**, потому что реальные поля структуры (`id`, `name`, `city`, `email` и т.п.) создаются **динамически в рантайме**, и TypeScript вынужден оперировать `unknown`/generics без содержательной информации — статическая система типов принципиально не может знать заранее форму объекта, порождённого во время выполнения.

## 4. Почему «алгебраические»

Пояснение терминологии (в ответ на вопрос участника): АДТ называются алгебраическими, потому что новый тип конструируется **алгебраическими операциями** (сложение/объединение) над существующими типами — идея от математиков, воплощённая в языках вроде **Haskell**. `User` — это, по сути, «сумма» (произведение) четырёх полей-типов, склеенных в одну структуру; в JS это неочевидно из-за синтаксиса, но в Haskell такая композиция типов видна прямо в объявлении. Отдельно уточнено: сокращение **ADT неоднозначно** — многие программисты по умолчанию читают его как «Abstract Data Type» (абстрактный тип данных), а не «Algebraic».

## 5. `Tuple` — иммутабельный фиксированной длины массив

Аналогичная `Record` машинерия, но результат — иммутабельный `Array` фиксированной длины (arity проверяется при создании, `Object.freeze` на сам массив). Пример — `Point.create(x, y)` без именования полей (в отличие от `Record`, где поля именованы) — Тимур признал, что для этого конкретного случая, возможно, `Record` был бы удобнее, но `Tuple` показан отдельно ради демонстрации техники.

---

## 6. `Sum`/`Option` (Some/None) — наименее удавшаяся часть

Попытка реализовать **sum-тип** (объединение нескольких типов в один, разветвляющийся вариант — `Option = Some | None`), где `None` сделан синглтоном (пустой объект, единственный инстанс через приватное статическое поле в конструкторе). Проблемы, признанные самим Тимуром в процессе:
- Разделение на вариант `Some`/`None` в конструкторе строится на грубой проверке `value === undefined` — из-за этого невозможно, например, различить `Some` от нативного `Number`-контейнера при расширении на третий вариант (пропадает возможность корректного ветвления).
- Классы `Some` и `None` получились **взаимно зацеплены по именам** друг на друга и на фабрику, что Тимур явно назвал плохой архитектурой («это плохая реализация, я не понимаю, как это сделать красивее»).
- Итоговая оценка: для `Record` и `Tuple` есть реальное практическое применение, а для `Sum`/`Option` «с трудом можно придумать полезное применение» в текущем виде — не доведено до продакшн-состояния.

## 7. `Result` — задача признана красивой на бумаге, но чужеродной для JS

Идея: объединить тип ошибки и тип значения в одну структуру (`{ error, data }` или `{ error, value }`), аналог Rust/Go-подхода. Показаны два способа:
1. **JS way** — обычные объекты-литералы с полями `error`/`data` (то, что уже неявно используется в callback-конвенции error-first).
2. **ADT way** (недописанный набросок) — динамическая композиция типа `Result = Error + Value` через `Sum.create(...)`.

Итоговый вывод Тимура: сама концепция `Result` хороша, но **плохо ложится на парадигму JS**, потому что в языке уже есть `Promise`, который решает ту же задачу (доставка значения-или-ошибки) другим, более естественным для JS способом — поэтому паттерн `Result` не прижился так широко в JS-экосистеме, как в Go/Rust, где нет `Promise`-подобного примитива.

## 8. Поиск существующих решений в реальном времени

В процессе звонка Тимур и участники искали существующие библиотеки:
- **Effect (effect-ts)** — упомянута участником как библиотека, реализующая `Result`/`Either` в похожем духе, но **без возможности динамически конструировать новые типы в рантайме** — у неё готовый фиксированный набор контейнеров, а не алгебра типов.
- **fp-ts** — упомянута как известная функциональная TS-библиотека с похожими идеями.
- Поиск в интернете (Google, Wikipedia, DEV Community) не дал ни одной живой готовой библиотеки, реализующей именно динамический вывод типов через алгебраические операции на чистом JS/TS — везде находили либо статью про Haskell/математику без кода, либо TypeScript union types (`type Option<T> = Some<T> | None`), которые Тимур считает недостаточными: union type — это чисто compile-time декларация, полностью **пропадающая в рантайме** и не дающая никакой пользы после компиляции, тогда как цель звонка — рантайм-структуры с реальным поведением.
- Найдена полезная параллель — встроенные утилитные типы TypeScript (`Omit`, `Pick`) названы как «зачатки» алгебраических операций над типами, которые уже есть в языке, но малоиспользуемы на практике («добавляют задротства»).
- Упомянута библиотека **Protobuf** как имеющая похожие архитектурные принципы (`oneof`/composite-типы).

### Архивный код Metarhia: `Maybe`/`Either`/enum
В процессе поиска Тимур откопал старый код из репозитория `metacom` (модуль `libFP`) — там были реализованы `Maybe`, `Either` как **монады через классы** (не через замыкания, что Тимур отметил как редкость — обычно монады в JS делают через замыкания), а также громоздкая реализация `enum`-подобного типа. Итог: эти конструкции **не прижились** и не использовались после первоначальной реализации — «значит, не особо жизнеспособная идея», прямое признание неудачного архитектурного эксперимента прошлого.

## 9. Финальный вывод и идея на будущее

- **В metautil точно перенесут `Record`** — единственная из показанных конструкций с однозначно доказанной пользой (иммутабельность + быстрый прототип на `null` + удобный `fork`/`update` API).
- `Tuple`, вероятно, не перенесут отдельно.
- Для `Sum`/`Option`/`Result` решение пока не найдено — открытый вопрос для сообщества, предложено присылать найденные библиотеки и идеи на следующие созвоны.
- Отдельная идея на будущее, показавшаяся Тимуру перспективной: библиотека типов данных для **физических величин / системы единиц измерения (СИ)** — с выводом не только значения, но и единицы измерения при операциях (пример — закон Ома: из значений с единицами на входе выводится значение с правильной единицей на выходе). Названа хорошим кандидатом для предметно-ориентированного моделирования (физика, химия).

## Итог звонка

В отличие от типичного отчёта о готовой фиче, этот звонок — редкий пример **прозрачно показанного незавершённого исследования**: часть идей (Record, Tuple) признаны удачными и пойдут в продакшн-библиотеку, часть (Sum/Option, Result, Enum) — явно признаны неудавшимися или плохо ложащимися на парадигму JavaScript, с честной рефлексией «я не знаю, как сделать это красивее» и историческим прецедентом (архивный `Maybe`/`Either` из Metarhia, который не прижился). Общий вывод о применимости ADT в JS: они добавляют когнитивную нагрузку и синтаксические «церемонии», поэтому оправданы только там, где нужна дополнительная гарантия целостности типа (финансовые величины, критичные доменные инварианты) — не как замена обычным объектам-литералам повсеместно.
