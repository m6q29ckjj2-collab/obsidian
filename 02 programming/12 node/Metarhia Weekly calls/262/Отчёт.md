# Weekly call #262 — System programming with AI, network protocols, data structures and containers

> [!info] О звонке
> Live-рефакторинг WebSocket-реализации в Metacom и структур данных в metautil при помощи AI (Cursor, модели Sonnet/Fable). Конспект по автосубтитрам + подробной AI-сгенерированной главе-содержанию под видео.

## 1. Почему ядро Metarhia не имеет production-зависимостей

Ядро (Impress, Metacom, основные библиотеки) принципиально не имеет внешних runtime-зависимостей — только dev-time (линтеры, TypeScript). Собственная реализация WebSocket-сервера в Metacom заменила единственную оставшуюся внешнюю зависимость — библиотеку `ws`. Причины: безопасность (меньше поверхность атаки через supply chain), контроль над кодом, отсутствие необходимости поддерживать совместимость со сторонним API при апдейтах.

Исключение — необязательные утилитные библиотеки типа **MetaSQL** (зависит от `pg`, Postgres-only): это осознанно **не ядро**, а надстройка, которую можно не использовать. Тимур явно отказался писать универсальный SQL-драйвер под несколько СУБД («мы же не будем поддерживать 100 разных СУБД») — вместо этого просто не тянуть эту зависимость в ядро.

Заодно из Metacom **дропнута поддержка Node.js 18/20/21** — потому что в них нет нативного WebSocket-клиента, а Metacom-архитектуре нужен и клиент, и сервер сразу. Минимальная версия — Node.js 22.

## 2. Рефакторинг WebSocket pull request (изначально от контрибьютора Георгия)

Разобран большой PR: взята ветка Георгия (конец февраля), Тимур её существенно упростил:

- **Убран дублирующийся incremental UTF-8 валидатор** — было две реализации валидации (в парсере и во фреймах), а инкрементальность не нужна, потому что данные и так приходят целыми чанками.
- **Константы перенесены in place**, а не в отдельный файл-константы: если строка используется 1 раз, выносить её в константу бессмысленно (память не экономится — строковый литерал не дублируется в памяти при многократном использовании); если константа используется только в одном модуле — она объявляется прямо в этом модуле, а не в общем файле.
- **`Set`/`Map` заменены на `Array`/plain objects** там, где коллекция маленькая и почти не меняется (например, коды закрытия соединения WebSocket) — накладные расходы на хэш-функцию не окупаются на маленьком фиксированном наборе значений; линейный поиск в цикле по ~20 элементам не медленнее хэш-таблицы. `Object.freeze` на такие константы почти не добавляет оверхеда.
- **Устранены три параллельные реализации ping/pong**-механизма (одна в самом Metacom, одна внутри WebSocket-модуля, одна — забытый недописанный код нескольких лет давности) — оставлена одна.
- **История коммитов**: мерж-коммиты в мастере запрещены правилами Metarhia (нужен rebase, не merge-commit) — обсуждалась гигиена веток и почему нельзя одновременно переименовывать файл и рефакторить его содержимое в одном коммите (GitHub может потерять историю diff при переименовании+больших правках одновременно).
- **`Result`-контейнер** (обёртка ok/fail для возврата значения-или-ошибки из функции) перенесён из Metacom в metautil — общая утилита, не специфичная для конкретного протокола.

## 3. Структуры данных в metautil: системный код тоже может их использовать

Тимур years использовал разные структуры данных (списки, буферы) в разных проектах поштучно, копируя код между репозиториями — решил наконец собрать их в metautil. Ранее считал, что «хитрые» структуры данных не подходят для системного кода metautil, но пересмотрел эту позицию: metautil можно использовать и в доменном коде тоже, а хитрые структуры (`unrolled list`, оптимизированные под лимиты V8 на размер массива — упомянуто число, близкое к 2048 элементам, после которого массив уходит в деоптимизацию) полезны именно в системном коде для потоковой обработки данных.

### Иерархия структур
- **`LinkedList`** — низкоуровневый базовый класс с полями `head`/`tail` (специально **не приватными** — этот класс никогда не «торчит наружу» пользователю, на его основе строятся другие структуры). Методы низкоуровневые, написаны через `for`-циклы (не `for...of`), мономорфный код. Есть `prepend`, `add`, `insert`, `delete`, `remove`, `rotate` (отмечено, что деление по модулю в rotate — не идеальное решение, деление медленное, нужно оптимизировать).
- **`List`** — userland-обёртка поверх `LinkedList` с богатым API: `range`, `merge`, `append/prepend`, `insert/delete`, `at/first/last/tail/init/drop/take/slice`, `swap/move/split/group by/includes/indexOf/equals/addAll/removeAll`, а также функциональные `filter/find/reduce/map/lazyMap/flatMap/average`. `rotateLeft`/`rotateRight` — два метода-обёртки над одной внутренней `rotate` ради семантики API, а не ради разной реализации.
- **`Deque`** (double-ended queue) — на основе буфера (дефолтный размер 16, автоматически ресайзится), API `prepend/append/dq/pop/add/set/first` — похож на остальные структуры.
- **`Queue`**, **`Stack`** — обёртки поверх `Array` с семантическими именами методов (`NQ`/`DQ` для очереди) — не меняют производительность, но делают код читаемым по смыслу использования структуры. Очередь построена на массиве через указатель на голову + размер, без постоянного `splice`.
- **`PersistentList`** — неизменяемая структура в духе Lisp-списков (`first`/`rest`, аналог `car`/`cdr`, но с более привычными для JS именами). Каждое добавление элемента создаёт **новый экземпляр**, ссылающийся через `next` на предыдущий — старые ссылки остаются валидны и неизменны навсегда, список может «ветвиться» (несколько версий с общим хвостом). Подходит для функционального стиля: можно передавать ссылку куда угодно с гарантией иммутабельности, и это не требует копирования всей структуры при добавлении.
- **`Struct`** (Persistent object) — тот же принцип persistent-списка, но для объектов, реализован через **цепочку прототипов** (`Object.create`): каждая модификация создаёт новый объект-потомок, у которого новые поля лежат в самом объекте, а старые — доступны через прототипную цепочку (экономия памяти ценой чтения через `[[Prototype]]`-обход). Есть `mutable`/`immutable` фабрики: `immutable`-объекты — `Object.freeze` (запрет и структуры, и значений), `mutable` — `Object.seal` (можно менять значения существующих полей, нельзя добавлять/удалять поля). `fork` — отсоединяет копию от цепочки наследования (полная копия всех текущих полей, новый независимый объект); `branch` — добавляет новые поля через `Object.defineProperty`, не трогая уже определённые в цепочке.

## 4. Live-coding эксперимент: может ли AI дать классу динамическое имя без `eval`/`Function`/патчинга `name`

Задача, которую Тимур поставил AI-агенту (Fable): класс `Entity`, создаваемый динамически внутри `Struct.build()`, всегда называется `Entity` в рантайме (`constructor.name === 'Entity'`) — а нужно, чтобы `.name` соответствовал переданному пользователем имени (`User`, `Vehicle` и т.п.), причём **нативными средствами JS**, без `eval`, `new Function` и без добавления отдельного `.name`-свойства как костыля (это было бы «брендингом», а не переименованием).

- **Первая попытка агента**: через `Object.defineProperty(cls, 'name', ...)` — Тимур это отклонил: `Function.prototype.name` конструктора **нельзя переопределить у самого класса после создания** так, чтобы это выглядело нативно — это добавляет новое свойство, а не меняет исходное поведение.
- **Правильное нативное решение**, которое сам Тимур знал заранее: обернуть создание класса в **объектный литерал с вычисляемым именем ключа**, и класс без явного имени внутри такого литерала **наследует имя от ключа объекта**, в который присвоен (`{[name]: class { ... }}[name]`) — стандартное поведение спецификации ECMAScript для присвоения имени анонимной функции/класса.
- Агент со второй попытки (после подсказки «don't use defineProperty») нашёл рабочее нативное решение самостоятельно (немного другим синтаксисом, но с тем же принципом — деструктуризацией вычисляемого ключа объекта).
- Побочное методологическое наблюдение: разные уровни «мощности» модели в Cursor (high/max/medium/low) стоит переключать по фазе задачи — сложные архитектурные решения на high/max, рутинную донастройку — на low/medium.

## 5. Баг: тесты Collector виснут на Node.js < 24 (AbortController)

При батч-рефакторинге классов `metautil` (перевод полей в приватные, типизация под V8) агент (Fable) заодно переписал внутреннюю реализацию `Collector` с `setTimeout` на **`AbortController`/`AbortSignal`** — и тесты стали **виснуть** на старых версиях Node.js.

Процесс диагностики в прямом эфире:
1. Локализовали через матрицу CI: падает на 18/20/22/23, **проходит начиная с Node.js 24**.
2. Гипотеза — баг/несовместимость именно в связке `AbortController` + `AbortSignal.timeout`/`AbortSignal.any`, а не в бизнес-логике коллектора (код «выглядит правильно», все методы и сигнатуры на месте, но подвисает).
3. Попытки поправить через AI-агента ушли в сторону (агент один раз случайно удалил лишний контроллер, дважды подписывался на `abort`-событие) — пришлось откатывать и переформулировать промпт точнее, явно указав диапазон версий для прогона (`nvm`, Node 18–26) и **явно запретить трогать логику AbortController/AbortSignal/таймаутов**, попросив только вернуть предыдущую рабочую реализацию на `setTimeout` для этого конкретного файла.
4. Итоговый практический вывод Тимура: это типичный случай, когда **у модели нет интуиции о низкоуровневых платформенных багах** — она не может «вспомнить», что в ранних версиях API `AbortController`/`AbortSignal` (появились в районе Node 14–17) была нестабильная реализация с边 edge-кейсами. Для таких багов нужен человеческий опыт и целенаправленный поиск по changelog'ам Node.js, а не общая языковая генерация — предложено (как идею на будущее) скармливать changelog'и версий модели отдельно, чтобы она искала конкретные исправленные баги.
5. Решение на звонке: откатить AbortController-версию Collector, оставить рабочую реализацию на `setTimeout`, применить ко всем остальным классам оптимизацию приватных полей **кроме** файлов с AbortController/сигналами/таймаутами — с явным запретом трогать эту логику в промпте.

## 6. Планы на технологический стек

Дорожная карта, озвученная в конце: привести `metautil` в стабильное состояние → пересадить на него `metacom` → перенести наработки по **local-first / CRDT** в **GlobalStorage** → выпустить новый `metacom` → выпустить обновлённый `GlobalStorage` поверх него.

Анонсирован формат **регулярных live-coding сессий** (возможно, 1–2 раза в неделю, не всегда по четвергам — иногда четверг будет отведён под другие темы) — код для таких сессий Тимур готовит заранее (PR-заготовки), потому что писать с нуля в прямом эфире слишком долго для формата стрима. Отдельно упомянут параллельный формат стримов прикладного кода в рамках гильдии **NextTick** (совместно с Ильёй) — то есть будет отдельно контент по системному программированию (Metarhia) и отдельно по прикладному (NextTick).

## Итог звонка

Ключевая техническая тема — построение целой линейки структур данных metautil (`LinkedList` → `List`/`Deque`/`Queue`/`Stack` → `PersistentList`/`Struct`) по общему архитектурному принципу «низкоуровневая база + семантическая userland-обёртка», и демонстрация персистентных (persistent, copy-on-write через прототипную цепочку) структур как моста между mutable и immutable мирами. Вторая важная тема — практическая граница возможностей AI-агентов в системном программировании: там, где нужно творческое языковое решение (динамическое имя класса) — агент справляется за 1-2 итерации; там, где нужен опыт диагностики низкоуровневых платформенных багов (AbortController regression) — агент буксует, и решение всё равно находит человек через матрицу версий и целенаправленный откат.
