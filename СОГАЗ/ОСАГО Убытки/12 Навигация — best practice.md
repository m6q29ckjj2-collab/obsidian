# Навигация без «загрузили → выяснили → перекинули»

Связанное: [[11 План переезда и карта переходов]], [[02 Флоу и навигация]].

## Context
Во флоу ОСАГО экран открывается, грузит данные и только потом решает, что он не нужен, и перекидывает пользователя дальше. Примеры:
- **Initial** → хаб, если черновик уже начат;
- **VehicleDamage** → AddVehicle, если нет полисов (плюс костыль `pop(2)` на возврате);
- **VehicleDamage** → AddVehicleForm, если документ ТС неполный;
- после ЕСИА вопросы на Initial показываются повторно.

Последствия: мигает лишний экран, в стеке остаётся мусор, аналитика пишет просмотры экранов, которых пользователь не видел, а логика «куда идти» размазана по `useEffect` в экранах.
Цель — выбрать проверенный подход и зафиксировать правила, по которым будем делать навигацию модуля. Шаги внедрения начнутся только после согласования. Правки UI пользователь пока откладывает.

## Сравнение подходов (по источникам)
| Подход | Плюсы | Минусы | Где уместен |
|---|---|---|---|
| A. Сначала открыть экран, потом редирект (как сейчас) | просто писать | мигания, мусор в стеке, водопад запросов, ложная аналитика | — |
| B. Сначала решить, потом перейти (pending navigation: по умолчанию в Remix, `beforeLoad` в TanStack) | нет миганий, чистый стек, решения в одном месте | пользователь ждёт на исходном экране, нужен индикатор, гонки (двойной тап, уход с экрана) | ветвление между **разными экранами** |
| C. Перейти сразу + скелетон или гейт, ветвиться внутри экрана (render-as-you-fetch) | отклик < 0.1 с, честная загрузка, работает с deeplink | экран отвечает за все свои состояния | варианты **одного экрана** (пустое состояние, нет данных) |
| D. Условные экраны в навигаторе (паттерн auth-flow в React Navigation) | недопустимые переходы невозможны | подходит для глобальных режимов; экраны размонтируются; deeplink-и через нестабильный API | вход/выход, не шаги мастера |
| E. Prefetch (RTK `usePrefetch`, `onPressIn`, при открытии хаба) | убирает ожидание в B и C | лишние запросы при неточной предсказуемости | всегда как дополнение |
| F. XState (машина состояний) | формальная модель, визуализация | новая зависимость, порог входа | если флоу продолжит расти |

## Рекомендуемый подход (гибрид B + C + E)
1. **Prefetch заранее.** Хаб при открытии и по `onPressIn` грузит данные следующего шага (полисы и т.п.) через RTK `usePrefetch` или `initiate`. Тогда решение в п.2 почти всегда мгновенное.
2. **Переход между разными экранами — «решить, потом перейти».** Через `useOsagoLossesFlow().go(event)` + `domain/flow.ts` + условия из `domain/rules.ts`. Правила:
   - лоадер на нажатом элементе, если решение занимает > ~300 мс (порог отклика 0.1 / 1 с по NN/g);
   - повторные нажатия блокируются, пока решение в процессе;
   - результат игнорируется, если пользователь ушёл с экрана;
   - ошибка → тост, пользователь остаётся на месте.
3. **Экраны сами никогда не делают редирект.** Пока нет данных — гейт или скелетон (`OsagoClaimGate`). Варианты одного экрана — внутренние состояния (например, пустое «нет полисов» с кнопкой).
4. **Один экран-распределитель на входе** (deeplink, ЕСИА, холодный старт). Только лоадер, решение и `replace`. Initial становится просто экраном вопросов. Черновик создаётся по ответу «Я пострадавший», а не при открытии.
5. **Возврат на хаб — один способ:** `popTo(Resultant)`.
6. Условные экраны (D) и XState (F) сейчас не вводим.

## Пилот (после разрешения трогать UI)
«Хаб → Ущерб ТС»:
- prefetch полисов на хабе (`Resultant` уже вызывает `useGetOsagoPoliciesQuery`);
- `go('hub','openVehicleDamage')` → VehicleDamage или AddVehicle по правилу `canPickVehicleFromPolicies` (фильтр «е-ОСАГО» + виртуальный полис из `claim.vehicleDamage`, как в `screens/OsagoLossesVehicleDamageScreen.tsx`);
- удалить редирект-эффект из VehicleDamage и `pop(2)` из `screens/OsagoLossesAddVehicleScreen.tsx`.

Файлы:
- новые: `domain/flow.ts`, хук `useOsagoLossesFlow`, `rules.ts` (+ `canPickVehicleFromPolicies`);
- изменяются: `ResultantScreen`, `VehicleDamageScreen`, `AddVehicleScreen`.

Нерешённый продуктовый вопрос: когда полисов нет, сразу вести на AddVehicle (B) или показывать пустое состояние с кнопкой (C). Нужно согласование с дизайном.

## Verification
- `tsc` и `eslint` без ошибок. Сборку и запуск делает пользователь.
- Ручная проверка:
  1. есть полисы → сразу форма;
  2. нет полисов → сразу «Добавить ТС», «назад» ведёт на хаб;
  3. есть ТС, добавленное вручную, а полисов нет → форма;
  4. офлайн → тост, остаёмся на хабе;
  5. двойной тап → один переход;
  6. в аналитике нет события `view_page_damage_auto` при уходе на AddVehicle.
