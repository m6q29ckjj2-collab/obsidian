# План переезда структуры и карта переходов

Собрано по коду: все вызовы `navigate` / `replace` / `popTo` / `pop` / `goBack` модуля и граф импортов (какой файл кем используется). Подходы, на которые опирается план: Screaming Architecture, colocation, Bulletproof React, идеи FSD (Feature-Sliced Design), группы экранов в React Navigation, `eslint-plugin-boundaries`. Источники в конце заметки.

Связанное: [[00 Обзор]], [[02 Флоу и навигация]], [[04 Модель данных]].

**Внутри каждого шага одна раскладка:** экран лежит в корне папки шага, рядом `components/`, `hooks/`, `utils/`, `validation.ts`. Если файлов меньше трёх, подпапку не заводим.

**Принципы:**
- Верхний уровень — шаги пути клиента, а не типы файлов (Screaming Architecture).
- Всё, что относится к шагу, лежит в его папке (colocation).
- Слои `api → domain → store → flow`, импорт только «вниз». Это правило импорта из FSD.
- В `flow/` только UI шагов. Переходы и бизнес-правила живут в `domain/`. FSD признал отдельный слой для многостраничных процессов (`processes`) устаревшим, потому что он превращался в свалку.
- `shared/` сразу сигнализирует, что код переиспользуется несколькими шагами.

**Что нашлось по ходу разбора графа импортов:**
- `BankRequisitesLogo.tsx` никто не импортирует. Перед удалением нужно проверить использование вне модуля.
- `getVehicleDamageDefaultValues` нужен и хабу (функция `shouldShowVehicleDamageDriver`). Это бизнес-правило, его стоит перенести в `domain/rules.ts`, иначе хаб будет импортировать код из шага.
- `shouldSkipOsagoLossesBankDetailsScreen` дублирует `rules.needsPayoutDetails`. После перевода самоосмотра на модель его можно удалить.
- `filterSecondParticipantFormInput` используют 7 файлов в разных шагах. При переносе в `shared/` хорошо бы дать ему общее имя.

## Часть 2. Карта переходов

### Как это сейчас (из кода)

| Откуда | Событие | Условие | Куда | Метод сейчас |
|---|---|---|---|---|

| | «Я пострадавший» | есть `oid` (ЕСИА) | CheckProfile | `replace` |
| | «Я пострадавший» | нет `oid` | GU | `replace` |

| | «ДТП не оформлено» | — | gosuslugi.ru/europrotocol или 112 | внешнее |

| **CheckProfile** | сохранено | — | Resultant | `replace` |
| **Resultant (хаб)** | карточки | — | Culprit / Accident / VehicleDamage / Property / Health | `navigate` |

| **Accident** | «Указать на карте» | — | AccidentMap(initialPlace) | `navigate` |

| **AddVehicleForm** | сохранено | — | VehicleDamage(+документ) | `popTo` |
| | закрыть | — | хаб | `popTo` |
| **Property / Health** | сохранено | — | хаб | `navigate` |
| | закрыть | — | хаб | `goBack` |
| **SelfInspection → Vin → Damage** | продолжить | — | следующий экран | `navigate` |
| **SelfInspectionDamage** | продолжить | нужны реквизиты | BankDetails | `navigate` |
| | | только ТС + ремонт | DocumentSign | `navigate` |
| **BankDetails** | продолжить | — | DocumentSign | `navigate` |
| **DocumentSign** | submit | ок | Success(claimId, номер) | `navigate` |
| | | ошибка | Failure | `navigate` |
| **Failure** | «Повторить» | — | DocumentSign | `goBack` |
| **Success** | «Перейти к убытку» / «На главную» | — | webview / RootTabs → Health | `navigate` |

**Что видно из карты:**
1. **Возврат на хаб сделан четырьмя способами:** `goBack`, `navigate`, `popTo`, `pop(2)`. В карте это будет один переход «вернуться на хаб».
2. **Условия переходов разбросаны по экранам.** Проверки `oid`, «выбран ли ТС», «только ТС и ремонт» и т.п. Часть уже лежит в `domain/rules.ts` (`needsSelfInspection`, `needsPayoutDetails`), остальные надо туда добавить: `hasEsiaAccount`, `isDraftStarted`.
3. **Переходы, которые можно убрать:** RouterSheet «Продолжить» навигирует сам на себя, а ServiceMap недостижим.

### Как это будет выглядеть

Один файл `domain/flow.ts` (или `flow/routes.ts`). Для каждого экрана в нём перечислены события, и у каждого события есть цель: экран, «вернуться на хаб» или «выйти из модуля». Если переход зависит от условия, оно берётся из `rules.ts` по модели заявления. Экраны вызывают `go('Resultant', 'continue')` и не знают, куда именно уходят.

По форме это та же таблица, что выше, только в коде. Поэтому при необходимости её можно перевести на XState (машины состояний можно смотреть визуально в Stately), не трогая экраны.

## Часть 3. Порядок переезда

Каждый этап — отдельный коммит или PR. Файлы переносим через `git mv`, чтобы сохранить историю. После каждого этапа запускаем `tsc` и `eslint` и проверяем приложение руками.

| # | Что | Затрагивает | Логика меняется? |
|---|---|---|---|
| 1 | **Слои:** `osagoLossesSlice/` → `api/`, `slice/` → `store/`, гео-API в `api/geocodeApi.ts`, `entry/`, `OsagoLossesStack.tsx` в корень модуля | импорты в модуле + **7 внешних файлов:** `App.tsx`, `navigationTypes.ts`, `app/store.ts`, `useLinkHandler/linkHandler.ts`, `PolicyDetails.tsx`, `BoxedRouteCell.tsx`, `DisasterScreen.tsx`, `ReportInsuranceScreen.tsx` | нет |
| 2 | **`shared/`** — общие компоненты, хуки и утилиты | импорты | нет |
| 3 | **Пилот:** `flow/3-steps/culprit/`. Смотрим, удобно ли | импорты | нет |
| 4 | Остальные шаги `flow/…` по одному коммиту | импорты | нет |
| 5 | `Stack.Group` в `OsagoLossesStack` по шагам + `README.md` модуля | стек | нет |
| 6 | **Карта переходов** `domain/flow.ts` + хук `go(...)`, перевод экранов на неё | экраны | **да**, отдельный PR с ручной проверкой всех сценариев |
| 7 | **eslint-plugin-boundaries:** `domain` не импортирует `flow`/`store`, шаг не импортирует другой шаг | `eslint.config.mjs`, новая зависимость | нет |

**Что стоит учесть:**
- Этапы 1–5 — только перенос файлов. Имена экранов, маршрутов, deeplink-и и события аналитики не меняются.
- Этап 6 — единственный, где меняется поведение (унификация возврата на хаб). Его стоит согласовать с QA.
- Этап 7 добавляет зависимость в проект, это решение за командой.
- Номера в именах папок (`1-start` … `7-result`) оставлены, чтобы порядок был виден, не открывая файлы. Если они мешают, их легко убрать на этапе 4.

**Не рекомендуется сейчас:** полный переход на FSD (затронет всё приложение), Expo Router (смена роутера), вложенные навигаторы на каждый шаг (документация React Navigation прямо советует минимизировать вложенность).
