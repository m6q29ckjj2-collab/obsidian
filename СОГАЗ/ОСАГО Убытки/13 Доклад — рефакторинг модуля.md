## 1. Коротко (30 секунд)

- Модуль «ОСАГО Убытки» разросся: экраны по 500–800 строк, бизнес-правила внутри компонентов, DTO бэка прямо в UI и Redux.
- Я переложил модуль на слои: **домен → API-слой → стор → флоу (экраны)**. Правила и типы бизнеса отделены от формата бэка и от вёрстки.
- Переходы между экранами вынесены в одну карту (`osagoLossesFlow.ts`): экраны сами больше не решают, куда идти.
- Экраны разложены по шагам клиентского пути (`0-entry … 7-result`), папка шага = всё, что нужно шагу.
- По ходу починил баги, которые нашлись при переносе и при прогоне на стенде.
- Прогнал основной путь на стенде в браузере: от входа до «Заявление отправлено».
- `tsc` — 0 ошибок, eslint — 0 ошибок.

## 2. Зачем это было нужно

| Боль | Чем мешало |
|---|---|
| Огромные экраны (`VehicleDamageScreen` 784 строки, `BankDetailsScreen` 652, `IncidentDataScreen` 639) | Нельзя прочитать за раз, любое изменение ломает соседнюю логику, ревью почти невозможно |
| Бизнес-правила внутри компонентов («нужен ли самоосмотр», «кто получатель выплаты», «каким способом подписывать») | Нельзя переиспользовать и проверить отдельно; одно правило размазано по нескольким экранам |
| DTO бэка в UI и в Redux | Любое изменение API бэка ломало экраны. Нарушали договорённость «в сторе — доменные модели» |
| Переходы зашиты в экраны | Чтобы понять путь пользователя, надо читать 28 экранов. Условные редиректы на экранах приводили к «мигающим» переходам |
| GUID типов документов в `.tsx` | UI знал внутренние идентификаторы бэка |
| Раскладка по типу файла (`components/`, `utils/`, `hooks/`, `screens/` на 149 файлов) | Чтобы поправить один шаг, надо ходить по 5 папкам |

## 3. Что сделано

### 3.1. Слои

```
OsagoLosses/
├── domain/   — модель заявления и бизнес-правила (без React, без DTO)
├── api/      — RTK Query, DTO, мапперы fromDto / toDto, GUID бэка
├── store/    — Redux: доменные модели, селекторы, useOsagoClaim
├── flow/     — экраны по шагам + карта переходов
├── shared/   — строки, общие компоненты и утилиты модуля
└── docs/     — пример модели заявления
```

Правило зависимостей: `flow → store → api → domain`, обратно нельзя. DTO живёт только в `api/`, во `flow` и `domain` его нет.

### 3.2. Домен (`domain/`)

- `model.ts` — модель заявления `OsagoClaim` (заявитель, виновник, ДТП, ущерб, выплата, подписание).
- `rules/claim.ts` — `isClaimStarted`, `needsSelfInspection`, `needsPayoutDetails`, `canPickVehicleFromPolicies`.
- `rules/payout.ts` — кто может быть получателем (`getBeneficiaryCandidates`, `resolveBeneficiary`).
- `rules/signing.ts` — способ подписания (`resolveSignatureMethod`).
- `rules/documents.ts`, `rules/vehicle.ts` — правила по документам и ТС.

Пример: раньше «нужен ли самоосмотр» считался на двух экранах по-разному. Теперь одна функция.

### 3.3. API-слой (`api/`)

- `mappers/fromDto/*` — ответ бэка → доменная модель (в т.ч. `draftToClaim`).
- `mappers/toDto/*` — доменная модель/форма → тело запроса (`to*Patch`).
- Документы передаются **слотами** (`DocumentSlot`), а GUID подставляется только в `api/`.
- Почтовый перевод отсеивается на уровне ответа (`transformResponse` у реквизитов банков).
- Выплата: `PayoutOption = { kind: 'bankAccount', account, isLocal } | { kind: 'postalTransfer' }`.

### 3.4. Стор (`store/`)

- Slice хранит доменные модели, маппинг из DTO — в `extraReducers`.
- Экраны читают через селекторы и `useOsagoClaim`.

### 3.5. Карта переходов (`flow/navigation/`)

- `osagoLossesFlow.ts` — таблица «событие → куда идти»: `push`, `replace`, `stepAboveHub`, `hub`, `back`.
- `useOsagoLossesFlow(draftId)` → `go('accidentPlaceSelected', { selection })`.
- Решение принимается **до** перехода, данные догружаются в карте, экраны редиректов не делают.
- Условия переходов — функции из `domain/rules`.

Итог: путь пользователя читается в одном файле (382 строки), а не в 28 экранах.

### 3.6. Раскладка экранов по шагам

| Папка | Шаг |
|---|---|
| `0-entry` | Внешние входы (3 файла) |
| `1-start` | Вопросы, Госуслуги, проверка данных |
| `2-hub` | Хаб заявления |
| `3-steps` | Виновник, ДТП, ущерб ТС, имущество, здоровье |
| `4-selfInspection` | Самоосмотр |
| `5-payout` | Реквизиты выплаты |
| `6-sign` | Подписание |
| `7-result` | Результат |
| `navigation` | Карта переходов |

Принцип «фрактал»: внутри шага тот же набор папок (`components`, `hooks`, `utils`), общее поднимается на уровень выше только когда его используют несколько шагов. Проверял скриптом по графу импортов.

### 3.7. Большие куски разрезаны

- Виновник: `useCulpritForm`, `useCulpritExitFlow`, `useSecondVehicleLookup`.
- Подписание: `useDocumentSign`.
- Начальные вопросы: `useInitialQuestions`.
- Данные ущерба ТС: единая цепочка `loadVehicleDamage` → `useVehicleDamageData`.
- Выплата: `bankDetailToFormData`, `5-payout/constants.ts`.

### 3.8. Вынесенное в общие места

- `ScreenFooter` — из `OsagoLosses/components` в `src/components` (его теперь использует и «Жизнь»).
- `formatBankAccountDigits`, `filterBankNameInput` — в `src/utils` (используют ОСАГО и LifeInvestment).
- Правки в смежных модулях (Health, Analysis, Chat, Connect, Disaster, Misc, Life и др.) — это обновление путей импортов, не поведения.

## 11. Вопросы, которые могут задать

**Почему файлов стало больше?** Большие экраны и «общие» файлы разрезаны; появились слои и мапперы. Читаемость и локальность изменений важнее общего числа файлов.

**Зачем отдельный слой `domain`, если приложение маленькое?** Правила («нужен ли самоосмотр», «кто получатель», «способ подписи») раньше жили в компонентах и расходились между экранами. В домене они в одном месте и без React.

**Зачем мапперы DTO ↔ модель?** Бэк меняется чаще, чем бизнес. Теперь изменение формата ответа правится в `api/mappers`, а экраны и стор не трогаются.

**Что с обратной совместимостью?** Бэкенд-контракт не менялся. Тело запросов собирается теми же `to*Patch`, только из доменной модели.

**Как убедиться, что ничего не сломано?** `tsc` и eslint чистые, основной путь пройден на стенде, непройденные ветки перечислены явно (раздел 6).

**Можно ли вливать по частям?** Разбить на MR по слоям тяжело: слои зависят друг от друга. Реалистично — один MR + регресс QA.
